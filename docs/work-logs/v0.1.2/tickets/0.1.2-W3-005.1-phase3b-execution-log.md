**檔案位置**：`.claude/hooks/dispatch-count-guard-hook.py`

**行數**：~320 行

**核心功能**：

| 功能 | 說明 |
|------|------|
| **PostToolUse 觸發** | 每次 Agent tool 呼叫時，偵測 prompt/description 中的派發關鍵字 |
| **狀態檔管理** | 使用 ppid-based JSON 狀態檔追蹤派發計數（格式見下方） |
| **計數遞增** | 每次 Agent dispatch 遞增 actual 計數 |
| **UserPromptSubmit 觸發** | 用戶下一次輸入時驗證計數是否一致 |
| **不一致警告** | 若 actual < expected，輸出警告到 stderr + 日誌 |
| **容錯設計** | 狀態檔不存在、過期、損毀時靜默跳過，無干擾 |

#### 狀態檔格式

```json
{
  "expected": 3,                          // 期望派發數量（由關鍵字決定）
  "actual": 1,                            // 實際派發數量
  "keywords": ["三人組"],                 // 偵測到的關鍵字
  "batch_started_at": "2026-03-23T...",  // 批次開始時間戳
  "PostToolUse_call_count": 1             // PostToolUse Hook 呼叫計數（供除錯）
}
```

| 關鍵字 | 期望派發數 | 說明 |

| 多視角 | 3 | 多視角評估派發 |

| 3-4x | 3 | 成本倍數標記 |

## 設計決策與為什麼

### 設計 1：雙重觸發機制（PostToolUse + UserPromptSubmit）

**為什麼**：
- PostToolUse 能即時偵測派發關鍵字，但無法驗證最終派發數量（因為 Agent dispatch 是非同步的）
- UserPromptSubmit 等到用戶下一次輸入時已有完整派發資訊，適合驗證和警告
- 分離偵測和驗證，降低單一 Hook 的複雜度

**替代方案考慮**：
- 單一 PostToolUse Hook 偵測後等待固定時間？→ 不可靠，派發速度不一
- 系統在派發完成後主動檢查？→ 需要修改 Claude Code 本身，不可行

### 設計 2：ppid-based 狀態檔隔離

**為什麼**：
- 每個 Claude Code session 有唯一的 ppid（parent process ID）
- 避免多個並發 session 互相干擾
- 簡單可靠的隔離機制

**實現方式**：
```python
ppid = os.getppid()
state_file = Path(f"/tmp/claude-dispatch-batch-{ppid}.json")
```

### 設計 3：5 分鐘狀態檔過期機制

**為什麼**：
- 防止古老的狀態檔積累在 /tmp
- 5 分鐘足夠單個 session 內完成所有派發
- 超時後 session 已結束，狀態無效

**過期檢查邏輯**：
```python
elapsed = (now - mtime).total_seconds()
if elapsed > 300:  # 5 分鐘
    state_file.unlink()
```

### 設計 4：容錯設計

| 故障場景 | 處理方式 | 理由 |
|---------|---------|------|
| 狀態檔不存在 | 靜默跳過 | 無派發關鍵字偵測到，正常狀態 |
| 狀態檔過期 | 自動清理並跳過 | 舊狀態無效，主動清潔 |
| JSON 解析失敗 | 記錄 warning，跳過 | 狀態檔損毀，fallback 到靜默模式 |
| Hook 執行錯誤 | 記錄 error，返回 EXIT_SUCCESS | 不阻擋用戶流程，問題可查日誌 |

## 相關錯誤模式

### PC-020：派發計數敘述-執行不一致

**症狀**：
- PM 敘述「派發給三人組」但實際只派 1 個 agent
- 導致預期的並行評估沒有發生

**根本原因**：
- PM 敘述與實際派發動作未同步驗證
- 缺乏自動偵測機制

**本 Hook 的防護**：
- 自動偵測派發關鍵字（「三人組」、「多視角」等）
- 計數實際 Agent dispatch 數量
- 驗證敘述與執行一致性
- 不一致時輸出警告（stderr + 日誌）
