# Phase 3a 實作策略規劃：錯誤學習雙通道記錄保護機制

**執行時間**: 2026-03-23

## 1. 實作策略設計

### 核心策略

本 Ticket 的實作屬於「文字常數 + 規則文件更新」，無需修改程式邏輯。實作分為**兩個獨立但關聯的模組級修改**：

| 修改對象 | 修改類型 | 複雜度 | 風險等級 |
|---------|---------|--------|---------|
| `ask_user_question_reminders.py` | 常數字串更新 | 低 | 低 |
| `askuserquestion-rules.md` | 規則文件新增 | 低 | 低 |

### 修改流程圖

```
Phase 3b 實作開始
    |
    v
模組 1：更新 COMMIT_HANDOFF_REMINDER 常數
  ├─ 定位常數位置（ask_user_question_reminders.py）
  ├─ 讀取現有 COMMIT_HANDOFF_REMINDER 字串
  ├─ 識別 #16 相關文字片段
  ├─ 在「選擇『記錄』」後補充雙通道說明
  ├─ 新增 WARNING 警告文字
  └─ 驗證格式完整（無破壞 Python 字串語法）
    |
    v
模組 2：更新 askuserquestion-rules.md 規則
  ├─ 定位場景列表表格
  ├─ 確認場景 #16 行已存在
  ├─ 在表格後、執行順序約束前新增獨立規則區塊
  ├─ 規則區塊標題：「### 場景 #16 雙通道記錄要求（強制）」
  ├─ 規則區塊內容：
  │  ├─ 介紹文字（1-2 句說明雙通道要求）
  │  ├─ 表格定義（通道 | 操作 | 位置 | 說明）
  │  ├─ 禁止行為說明
  │  └─ 範例說明（可選）
  └─ 驗證 Markdown 格式正確
    |
    v
驗證階段
  ├─ 執行單元測試驗證 COMMIT_HANDOFF_REMINDER 常數
  ├─ 執行文件驗證測試驗證規則文件結構
  ├─ 執行 BDD 行為鏈測試驗證完整流程
  └─ 測試全部通過
    |
    v
Phase 3b 實作完成
```

### 實作順序決策

**關鍵決定**：先修改常數（模組 1），再修改規則文件（模組 2）。

**理由**：
1. 常數修改相對簡單且容易驗證（直接字串搜尋）
2. 規則文件修改涉及 Markdown 格式，複雜度稍高
3. 先完成低風險的常數修改可提早發現問題
4. 兩個模組邏輯上是「內容 + 規則」的完整對應

## 2. 資料結構選擇

### 修改對象 1：COMMIT_HANDOFF_REMINDER 常數

**位置**：`.claude/hooks/lib/ask_user_question_reminders.py`

**資料結構類型**：多行 Python 字符串常數

**現有結構**（簡化示意，實際位置需檢視）：

```python
class AskUserQuestionReminders:
    COMMIT_HANDOFF_REMINDER = """
    [第一步 - 強制，不可跳過] AskUserQuestion #16（錯誤學習確認）：
      即使非 Ticket 工作，commit 後仍必須執行。
      → ToolSearch("select:AskUserQuestion") 載入後使用
      → 選項：無需記錄 (Recommended) / 記錄錯誤學習
      → 選擇「記錄」→ /error-pattern add → 重新確認 #16 直到選擇「無需記錄」
    """
```

**更新結構**：在「選擇『記錄』」後補充雙通道內容：

```
原文：→ 選擇「記錄」→ /error-pattern add → 重新確認 #16 直到選擇「無需記錄」

新增：→ 選擇「記錄」→ [雙通道，兩項必須同時執行]：
        (1) /error-pattern add（寫入 .claude/error-patterns/）
        (2) 更新 memory（寫入使用者 auto-memory）
      → 重新確認 #16 直到選擇「無需記錄」

      [WARNING] 雙通道要求：只寫 memory 或只執行 /error-pattern add 均不符合規範
```

### 修改對象 2：askuserquestion-rules.md 規則區塊

**位置**：`.claude/rules/core/askuserquestion-rules.md`

**資料結構類型**：Markdown 文檔段落

**新增規則區塊結構**：

```markdown
### 場景 #16 雙通道記錄要求（強制）

選擇「記錄錯誤學習」後，必須同時執行雙通道記錄：

| 通道 | 操作 | 位置 | 說明 |
|------|------|------|------|
| error-pattern | /error-pattern add | .claude/error-patterns/ | 結構化可查詢知識庫 |
| memory | 更新使用者 auto-memory | .claude/projects/.../memory/ | 跨對話個人記憶 |

禁止只寫單一通道：只寫 memory 不執行 /error-pattern add，或反之，均違反雙通道要求。
```

## 6. 權宜方案與技術債務

### 最小可行實作

本 Ticket 採用**最小可行實作策略**：
- 只修改文字和規則，不新增 Hook 邏輯
- 不涉及資料庫或複雜資料結構
- 不改動現有 Hook 函式簽名或邏輯流程

**簡化點**：
- 雙通道檢查完全依賴文字提醒，不依賴 Hook 偵測
- 規則區塊採用簡單表格格式，易於解析和修改
- 測試全部為單元測試 + 文件驗證 + BDD，無複雜的環境模擬

### 已知限制

| 限制 | 說明 | 後續處理 |
|-----|------|---------|
| 無主動偵測 | Hook 無法主動偵測「只寫 memory 未執行 /error-pattern add」的情況 | 依賴文字提醒和人工遵守，未來可考慮 Phase 4 重構時新增偵測機制 |
| 手動更新 | 兩個檔案的內容需手動保持同步 | 已記錄於規則文件，維護者應定期驗證一致性 |
| 不影響現有流程 | 此機制為被動提醒，不改變 commit-handoff-hook 的觸發邏輯 | 屬於特性設計，不視為限制 |

### 技術債務標記

**Phase 4 重構建議**：

| 項目 | 描述 | 優先級 |
|------|------|--------|
| Hook 偵測邏輯 | 考慮在 commit-handoff-hook 中添加偵測邏輯，主動檢查是否同時執行了 /error-pattern add 和 memory 更新 | P2 |
| 雙通道驗證機制 | 建立自動化驗證機制，檢查每次「記錄」操作後 error-pattern 和 memory 都有新增記錄 | P3 |
| 文件一致性檢查 | 新增 Hook 驗證 COMMIT_HANDOFF_REMINDER 和 askuserquestion-rules.md 的雙通道說明是否一致 | P3 |

## 7. 語言特定實作注意事項

### Python 考量（ask_user_question_reminders.py）

**字符串格式**：
- 使用三引號多行字符串（`"""`）格式，便於可讀性
- 注意縮排：不同方案在字符串中的縮排可能影響顯示效果
- 轉義字符：確保 `\n`、`\\` 等特殊字符正確解釋

**常數定義位置**：
- 位於 `AskUserQuestionReminders` 類別下
- 無需修改類別簽名或方法
- 無需修改匯入語句

**測試驗證**：
- 直接讀取常數值（無需初始化類別）
- 使用字符串搜尋驗證關鍵詞彙位置和順序

### Markdown 考量（askuserquestion-rules.md）

**格式規範**：
- 表格分隔符使用管道符 `|`，前後需要空格
- 標題層級應與周邊標題一致（推薦 `###`）
- 清單項目縮排 2 或 4 個空格（與既有風格一致）

**編碼和換行**：
- 檔案編碼為 UTF-8
- 行尾無多餘空格
- 使用 LF（`\n`）而非 CRLF（`\r\n`）

**解析相容性**：
- Markdown 解析器應能正確識別表格和標題
- 避免在表格內使用管道符（除非轉義）
- 避免在標題內使用特殊字符

## 8. 實作風險評估

### 風險分析

| 風險 | 可能性 | 嚴重度 | 緩解措施 |
|------|--------|--------|---------|
| Python 字符串語法錯誤 | 中 | 低 | 修改完成後執行 Python 編譯檢查（`python -m py_compile`） |
| Markdown 格式破損 | 低 | 低 | 修改完成後使用 Markdown linter 驗證 |
| 文字位置錯誤（插入到錯誤位置） | 低 | 中 | 修改前備份檔案，驗證搜尋結果準確性 |
| 測試設計與實作不符 | 低 | 低 | 測試失敗時回顧 Phase 2 設計，確認實作邏輯 |
| 兩個檔案內容不同步 | 中 | 低 | 修改後驗證兩個檔案中的雙通道說明語義一致 |

### 驗收風險

| 風險 | 說明 | 預防措施 |
|------|------|---------|
| 驗收條件遺漏 | 未完整實現 Phase 1 設計中的 4 項驗收條件 | 修改後對照驗收條件逐一檢查 |
| 向後相容性破壞 | 現有 Hook 邏輯或 commit 類型過濾被意外修改 | 測試 5 和 9 驗證邊界條件（docs/chore commit 類型） |
| 測試套件完整性 | 遺漏某個測試案例導致隱藏缺陷 | 所有 11 個測試案例必須通過（5 + 4 + 2） |
