## 2. 虛擬碼與邏輯設計

### 2.1 Registry YAML Schema 結構（虛擬碼）

```yaml
# .claude/agents/registry.yaml (虛擬碼)

定義 RegistrySchema:
  必填欄位:
    schema_version: "1.0"  // Major.Minor 格式（Semver）

  agents: {
    {agent_name_key}: {
      name: string,           // 人類可讀名稱，與 agent .md 的 name 欄位對應
      version: string,        // 能力版本 X.Y 格式
      description: string,    // 一行簡介
      model: enum,            // "haiku" | "sonnet" | "opus"

      accepts: [             // 此 agent 接受的輸入
        {
          artifact_type: string,   // 物件識別符（kebab-case）
          required: boolean,       // 是否必填
          format: string,          // markdown | yaml | code | ...
          description: string
        }
      ],

      requires: [            // 執行環境能力需求（可空）
        {
          capability: string,  // git-commit | dart-analysis | ...
          description: string
        }
      ],

      produces: [            // 此 agent 產出物
        {
          artifact_type: string,  // 識別符
          path_pattern: string,   // glob 路徑模式，用於衝突檢查
          format: string,
          description: string
        }
      ],

      preconditions: [       // 執行前條件
        {
          condition: string  // "{subject} {verb} {object}" 格式
        }
      ],

      conflict_avoidance: [  // 衝突避免規則
        {
          type: enum,  // "cannot_work_with" | "must_complete_before" | "cannot_work_after"
          agents: [string],
          reason: string,
          scope: enum  // "same_ticket" | "same_file" | "global"
        }
      ],

      tdd_phases: [string],  // ["phase1", "phase3b", ...] 此 agent 參與的階段
      file_patterns: [string]  // glob 路徑集合，與 produces[].path_pattern 聯集相同
    }
  }
}

驗證邏輯:
  1. YAML 語法檢查 (PyYAML parse)
  2. 必填欄位檢查 (schema_version, agents, 各 agent 的 9 個頂層欄位)
  3. 型別驗證:
     - version 格式: /^\d+\.\d+$/
     - artifact_type 格式: kebab-case, 無空格和大寫
     - path_pattern 合法性: fnmatch 可解析
     - tdd_phases: 在白名單 [phase0, phase1, ..., phase4c]
  4. 引用驗證:
     - conflict_avoidance[].agents[*] 必存在於當前 registry
  5. 一致性驗證:
     - file_patterns 聯集 == produces[].path_pattern 聯集
```

### 2.2 Agent 能力提取函式（虛擬碼）

```
函式 capability_extractor(agent_md_filepath) -> dict:
  """從 agent .md 檔案提取派發決策相關能力"""

  輸入: agent_md_path (如 ".claude/agents/parsley-flutter-developer.md")
  輸出: {
    name: string,
    version: string,
    model: string,
    accepts: [],
    requires: [],
    produces: [],
    preconditions: [],
    conflict_avoidance: [],
    tdd_phases: [],
    file_patterns: []
  }

  演算法:
    1. 讀取 .md 檔案，取 frontmatter (YAML 部分)
    2. 提取欄位:
       a) name = frontmatter['name']
       b) model = frontmatter['model'] // "haiku" | "sonnet" | "opus"
       c) version = "1.0" // 初始版本，與 agent .md 無直接對應，後續可從版本控制更新

    3. 從 .md 內容的「Accepts」章節提取 accepts:
       - 掃描 "## Accepts" 至下一個同層級標題
       - 解析表格 (artifact_type | required | format | description)
       - 若無表格則列表為空

    4. 從 .md 內容的「Produces」章節提取 produces:
       - 掃描 "## Produces" 章節
       - 解析 artifact_type, path_pattern, format

    5. 從 .md 內容的「Preconditions」章節提取 preconditions:
       - 掃描 "## Preconditions" 章節
       - 解析結構化條件字串: "{subject} {verb} {object}"

    6. 從 .md 內容的「Conflict Avoidance」章節提取 conflict_avoidance:
       - 掃描表格: type | agents | reason | scope
       - 轉換為 yaml 列表格式

    7. 從 .md 內容識別 tdd_phases:
       - 若在 decision-tree.md 第五層列出 → 對應 phase 加入
       - 掃描 .md 中是否有 "## TDD Phases" → 優先使用此欄位

    8. 從 .md 推斷 file_patterns:
       - 若 produces[] 已定義 → file_patterns = produces[].path_pattern 聯集
       - 若未定義 → 掃描 .md 中的 "## File Patterns" 章節
       - 預設值: 根據 agent 類型推斷
         * 代碼開發 agent (parsley/cinnamon) → ["ui/lib/**/*.dart", "ui/test/**/*_test.dart", ...]
         * 文件編寫 agent (sage/lavender) → ["docs/work-logs/*/tickets/*.md", ".claude/rules/**/*.md"]
         * Hook agent (basil) → [".claude/hooks/**/*.py"]

    9. 從 .md 的 "## Requires" 提取環境能力需求

    10. 驗證提取結果完整性:
       if accepts.empty and produces.empty:
         警告: "Agent {name} 的 accepts/produces 均為空，可能提取遺漏"

結束函式
```

### 2.3 三種衝突檢查演算法（虛擬碼）

```
函式 dispatch_validation_hook(dispatched_agents: [Agent]) -> ValidationResult:
  """檢查並行派發的 agent 是否存在衝突"""

  輸入: dispatched_agents = [Agent A, Agent B, Agent C, ...]
  輸出: {
    has_conflict: boolean,
    conflicts: [Conflict],  // Conflict = {type, agents, reason, suggestion}
    warnings: [string]
  }

  演算法:

  # 檢查 1: Agent 同時派發衝突
  函式 check_agent_conflict():
    for each pair (A, B) in dispatched_agents:
      if A.conflict_avoidance 含有 {type: "cannot_work_with", agents: [B.name]}:
        衝突 = {
          type: "agent_incompatibility",
          agents: [A.name, B.name],
          reason: 來自 registry 的 reason 欄位,
          suggestion: "改為序列派發：先執行 A，完成後再派發 B"
        }
        conflicts.append(衝突)

  # 檢查 2: TDD Phase 相序衝突
  函式 check_phase_order():
    當前 ticket 的 tdd_stage = 已閱讀的 ticket frontmatter['tdd_stage'][-1]  // 最新 phase

    for each agent in dispatched_agents:
      if agent 不能在此 phase 執行:  // 由 agent.preconditions 判定
        檢查 preconditions 中 "phase_* must_complete_before *"
        if 條件不滿足:
          衝突 = {
            type: "phase_order_violation",
            agent: agent.name,
            required_phase: precondition 中提到的前置 phase,
            current_phase: 當前 ticket phase,
            suggestion: "須先完成 Phase X，再派發此 agent"
          }
          conflicts.append(衝突)

  # 檢查 3: 檔案寫入衝突（ARCH-005 型）
  函式 check_file_write_conflict():
    all_files = 空集合

    for each agent in dispatched_agents:
      agent_files = agent.file_patterns 的檔案清單 (glob 展開)

      if all_files ∩ agent_files 非空:
        冒突檔案 = all_files ∩ agent_files
        對應衝突的兩個 agent = {A, B}

        衝突 = {
          type: "file_write_conflict",
          agents: [A.name, B.name],
          conflicted_files: 冒突檔案列表,
          reason: "ARCH-005：兩個 agent 同時寫入相同檔案",
          suggestion: "改為序列派發，確保檔案寫入次序"
        }
        conflicts.append(衝突)

      all_files.update(agent_files)

  # 最終判定
  結果 = {
    has_conflict: (conflicts 非空),
    conflicts: conflicts,
    warnings: 生成警告訊息清單
  }

  return 結果
結束函式

輸出格式 (發現衝突時):
  WARNING: [dispatch-validation-hook] Agent 同時派發衝突偵測
  ├── 衝突類型: agent_incompatibility
  ├── Agent: parsley-flutter-developer ↔ cinnamon-refactor-owl
  ├── 原因: 兩個代理人都會修改 ui/lib/domain/* 檔案，無法並行
  ├── 建議: 改為序列派發
  │   Step 1: 派發 parsley（Phase 3b）
  │   Step 2: 等待完成後，派發 cinnamon（Phase 4b）
  └── 日誌: .claude/hook-logs/dispatch-validation.log

```

### 2.4 Dispatch Recommend 評分演算法（虛擬碼）

```
函式 dispatch_recommend(ticket_id: string) -> [AgentRecommendation]:
  """根據 ticket 特徵推薦最適合的代理人"""

  輸入: ticket_id (如 "0.1.2-W1-006")
  輸出: [
    {agent_name, score, breakdown, rationale},
    {agent_name, score, breakdown, rationale},
    ...
  ]  // 按 score 降序排列

  演算法:
    1. 讀取 ticket frontmatter:
       - type (IMP/ANA/DOC/...)
       - tdd_stage (當前 phase)
       - where.files (預期修改檔案)
       - description/what (功能描述)

    2. 從 registry 篩選候選 agent:
       candidates = []
       for each agent in registry.agents:
         if agent.tdd_phases 包含 ticket.tdd_stage:
           candidates.append(agent)

    3. 為每個候選 agent 計算評分:
       score = 0
       breakdown = {}

       a) Accepts 匹配度 (最高 30 分):
          ticket_artifacts = 從 ticket 內容推斷的輸入物件
          matched = ticket_artifacts ∩ agent.accepts
          score_accepts = len(matched) / len(agent.accepts) * 30
          breakdown['accepts'] = score_accepts

       b) Preconditions 滿足度 (最高 25 分):
          滿足的前置條件數 / 全部前置條件數 * 25
          breakdown['preconditions'] = score_preconditions

       c) Phase 匹配度 (最高 20 分):
          if ticket.tdd_stage == agent.primary_phase:
            score_phase = 20
          elif ticket.tdd_stage in agent.tdd_phases:
            score_phase = 15
          else:
            score_phase = 0
          breakdown['phase'] = score_phase

       d) 衝突風險 (最低減 15 分):
          risk = 掃描 conflict_avoidance 中是否有 "cannot_work_with" 當前已派發的 agent
          if 有衝突:
            score_conflict = -15
          else:
            score_conflict = 0
          breakdown['conflict'] = score_conflict

       e) 模型效率 (最高 10 分):
          if agent.model == "haiku" 且 ticket 複雜度低:
            score_model = 10
          elif agent.model == "sonnet" 且 ticket 複雜度中等:
            score_model = 10
          elif agent.model == "opus" 且 ticket 複雜度高:
            score_model = 10
          else:
            score_model = 5
          breakdown['model'] = score_model

       總分 = sum(breakdown.values())

    4. 排序:
       candidates.sort_by(score, descending=True)

    5. 生成理由文本:
       for each agent in candidates:
         rationale = f"""
         {agent.name} (score: {agent.score}/100)
         - Accepts 匹配: {breakdown['accepts']}/30 ({matched_artifacts})
         - Preconditions 滿足: {breakdown['preconditions']}/25
         - Phase 匹配: {breakdown['phase']}/20
         - Conflict 風險: {breakdown['conflict']}
         - 模型效率: {breakdown['model']}/10
         """

    return candidates

輸出格式:
  代理人推薦 (Ticket: 0.1.2-W1-006)

  1. parsley-flutter-developer (95/100)
     - Accepts 匹配: 25/30 (phase3b-execution-report)
     - Preconditions 滿足: 25/25 (Phase 3a 已完成)
     - Phase 匹配: 20/20 (正在 Phase 3b)
     - Conflict 風險: 0 (無衝突)
     - 模型效率: 10/10 (Sonnet 適合中等複雜度)

  2. thyme-python-developer (72/100)
     - Accepts 匹配: 15/30 (僅 python-code，缺 flutter-code)
     ...

  3. system-analyst (45/100)
     ...
```

## 7. 語言特定實作注意事項

### 7.1 Python 考量（Hook + CLI）

**工具鏈**：
- YAML 解析：PyYAML (`yaml.safe_load()`)
- 路徑匹配：pathlib (`glob()` 擴展) + fnmatch
- 測試框架：pytest
- 執行方式：`uv run python` （遵循 python-execution.md）

**性能考量**：
- Registry YAML 讀取：~50ms (一次性，可 cache)
- 衝突檢查：O(n²) 演算法（n = agent 數 ≈ 30），<100ms
- 檔案 glob 展開：O(m) （m = glob 模式個數），<1s（需優化）

**最佳化建議**：
- Cache registry YAML 解析結果（避免重複讀取）
- 延遲 glob 展開：只在衝突檢查時展開（不預展開全部路徑）
- 使用 fnmatch 預篩選（快速排除明顯非衝突）

### 7.2 程式碼品質規則（Dart + Python 混合）

遵循：
- `.claude/rules/core/quality-python.md`：常數管理、訊息集中、魔法數字消除
- `.claude/rules/core/quality-common.md`：命名、函式長度、認知負擔
- `.claude/rules/core/document-format-rules.md`：無 emoji、狀態標記、Markdown 格式

**特別注意**：
- Hook 異常處理：雙通道（stderr + 日誌檔），遵循 quality-baseline.md 規則 4
- Registry schema 驗證錯誤：輸出 WARNING（不阻止操作，exit 0）
- CLI 評分演算法：必須有文件化說明（避免「魔法演算法」）
