# Phase 2 測試設計：錯誤學習雙通道記錄保護機制

## 層級定位

[Layer 3 (Hook 配置)] + [Layer 5 (規則文件)]

本功能涉及兩個層級的變更：Hook 配置常數更新（Layer 3）和規則文件更新（Layer 5）。測試應同時覆蓋兩個層級。

### 驗收條件

| 序號 | 驗收條件 | 驗證方式 | 完成標誌 |
|------|---------|--------|--------|
| 1 | COMMIT_HANDOFF_REMINDER 常數包含完整的雙通道要求文字（/error-pattern add + 更新 memory） | 讀取 ask_user_question_reminders.py，驗證字串包含兩個關鍵詞 | test_commit_handoff_reminder_contains_dual_channel_keywords 通過 |
| 2 | COMMIT_HANDOFF_REMINDER 包含 [WARNING] 警告標示，明確禁止只寫單一通道 | 驗證常數文字包含「[WARNING]」和「違反」或「不符合」等警告詞 | test_warning_label_present_and_complete 通過 |
| 3 | askuserquestion-rules.md 場景 #16 新增獨立的雙通道規則區塊，明確列出 error-pattern 和 memory 兩個通道 | 讀取 askuserquestion-rules.md，驗證場景列表後存在新規則區塊，區塊同時列出兩個通道 | test_scene16_dual_channel_section_exists 和 test_dual_channel_rules_complete 通過 |
| 4 | 既有 Hook 邏輯和 commit 類型過濾機制保持不變，向後相容性驗證通過 | 驗證 docs/chore/style 等 commit 類型仍被正確過濾，不觸發 #16 | test_commit_type_filtering_preserved 通過 |
| 5 | 雙通道規則區塊的 Markdown 格式正確，檔案可被解析器正確處理 | 驗證規則文件的 Markdown 格式有效性（標題層級、表格格式、清單縮排） | test_markdown_format_valid 通過 |

### 測試檔案規劃

## 1. 測試策略規劃

### 1.1 測試層級決策

根據 Hybrid Testing Strategy，本功能涉及兩個面向：

| 面向 | 程式碼層級 | 測試策略 | 類型 |
|------|-----------|---------|------|
| COMMIT_HANDOFF_REMINDER 常數更新 | Layer 3（Hook 配置） | 單元測試 | 文字內容驗證 |
| askuserquestion-rules.md 規則更新 | Layer 5（文件） | 整合測試 | 文件結構和內容驗證 |

**層級分類依據**：
- Layer 3（Hook 配置）：Hook 的常數和配置層，通過 unit test 驗證文字內容
- Layer 5（文件/規則）：文件層測試，驗證文件格式和內容的正確性

### 1.2 測試覆蓋範圍

**必測功能點**：
1. COMMIT_HANDOFF_REMINDER 常數包含雙通道要求文字
2. COMMIT_HANDOFF_REMINDER 包含 /error-pattern add 的明確提及
3. COMMIT_HANDOFF_REMINDER 包含「更新 memory」或「auto-memory」的明確提及
4. COMMIT_HANDOFF_REMINDER 包含 [WARNING] 警告標示
5. askuserquestion-rules.md 場景 #16 新增雙通道規則區塊
6. 雙通道規則區塊同時列出 error-pattern 和 memory 兩個通道
7. commit 類型過濾邊界：docs/chore/style 等不觸發雙通道要求（現有行為保留）
8. 既有 Hook 測試仍通過（向後相容性）

### 1.3 Mock 設計和測試資料

**Mock 需求**：

| Mock 對象 | 模擬範圍 | 用途 |
|---------|---------|------|
| commit-handoff-hook 環境 | Git commit 訊息、Hook 環境變數 | 模擬不同 commit 類型的 Hook 觸發 |
| 檔案系統 | askuserquestion-rules.md 讀取 | 驗證檔案內容和 Markdown 格式 |

**測試資料**：

| 資料項 | 內容 | 用途 |
|--------|------|------|
| commit_message_feat | `feat(0.1.2-W3-004): 雙通道記錄測試` | 觸發 #16 的 commit 訊息 |
| commit_message_docs | `docs: 文件更新` | 跳過 #16 的 commit 訊息 |
| commit_message_fix | `fix(bug-id): 修復問題` | 觸發 #16 的 commit 訊息 |
| markdown_content_rules | askuserquestion-rules.md 讀取內容 | 驗證文件結構和格式 |

## 2. 測試案例設計（Given-When-Then 格式）

### 2.1 COMMIT_HANDOFF_REMINDER 常數文字驗證

#### 場景 1：COMMIT_HANDOFF_REMINDER 包含雙通道要求

**Given（前置條件）**：
- `ask_user_question_reminders.py` 已載入
- COMMIT_HANDOFF_REMINDER 常數已定義
- Hook 環境正常初始化

**Then（前置驗證斷言）**：
- COMMIT_HANDOFF_REMINDER 為非空字串
- COMMIT_HANDOFF_REMINDER 長度 > 200 字元（包含雙通道說明）

**When（測試動作）**：
- 讀取 COMMIT_HANDOFF_REMINDER 常數值
- 掃描字串是否包含關鍵詞彙

**Then（預期結果）**：
- COMMIT_HANDOFF_REMINDER 包含 "/error-pattern add" 字串
- COMMIT_HANDOFF_REMINDER 包含 "更新 memory" 或 "auto-memory" 字串
- COMMIT_HANDOFF_REMINDER 包含 "[WARNING]" 或 "[WARNING] 雙通道" 字串
- 字串位置順序正確：先出現「選擇『記錄』」→ 再出現「雙通道」 → 最後出現「WARNING」

**測試案例識別符**：`test_commit_handoff_reminder_contains_dual_channel_keywords`

---

#### 場景 2：/error-pattern add 說明完整

**Given（前置條件）**：
- COMMIT_HANDOFF_REMINDER 常數已定義
- 字串已包含 /error-pattern add 相關文字

**Then（前置驗證斷言）**：
- 包含 /error-pattern add 子字串
- 包含「.claude/error-patterns/」路徑

**When（測試動作）**：
- 掃描 /error-pattern add 周邊文字
- 提取包含該指令的完整句子

**Then（預期結果）**：
- /error-pattern add 後方 50 字內提及「寫入」或「結構化知識庫」
- 文字表述清楚：使用「寫入 .claude/error-patterns/」或類似措辭
- 不含含糊的措辭（如「可能」「建議」）

**測試案例識別符**：`test_error_pattern_add_instruction_complete`

---

#### 場景 3：memory 更新說明完整

**Given（前置條件）**：
- COMMIT_HANDOFF_REMINDER 常數已定義
- 字串已包含 memory 相關文字

**Then（前置驗證斷言）**：
- 包含「更新 memory」或「auto-memory」子字串
- 字串長度足以容納完整說明

**When（測試動作）**：
- 掃描 memory 相關文字周邊
- 提取包含該詞的完整句子

**Then（預期結果）**：
- memory 相關文字後方 50 字內提及「寫入」、「auto-memory」或「跨對話記憶」
- 文字位置在 /error-pattern add 之後（邏輯順序）
- 不含歧義的措辭

**測試案例識別符**：`test_memory_update_instruction_complete`

---

#### 場景 4：WARNING 警告標示

**Given（前置條件）**：
- COMMIT_HANDOFF_REMINDER 常數已定義
- 字串已包含雙通道說明和指令

**Then（前置驗證斷言）**：
- 包含「[WARNING]」標示
- 警告位置在雙通道說明之後

**When（測試動作）**：
- 掃描 [WARNING] 或警告相關文字
- 驗證警告內容

**Then（預期結果）**：
- 警告文字包含「只寫」或「只執行」等否定詞
- 警告文字同時提及 error-pattern 和 memory 兩個通道
- 警告明確標示為「違反」或「不符合」
- 示例：「只寫 memory 不執行 /error-pattern add，或反之，均違反雙通道要求」

**測試案例識別符**：`test_warning_label_present_and_complete`

---

#### 場景 5：既有 commit 類型過濾邊界（負測試）

**Given（前置條件）**：
- COMMIT_HANDOFF_REMINDER 常數已定義
- Hook 邏輯中存在 SKIP_SCENE16_COMMIT_PREFIXES 常數

**Then（前置驗證斷言）**：
- SKIP_SCENE16_COMMIT_PREFIXES 包含「docs」、「chore」、「style」等
- 過濾邏輯仍然存在（未被破壞）

**When（測試動作）**：
- 逐一檢驗 docs/chore/style 等 commit 類型
- 對每個類型驗證是否應用 COMMIT_HANDOFF_SKIP16_REMINDER

**Then（預期結果）**：
- docs commit 類型不應出現 COMMIT_HANDOFF_REMINDER（出現 SKIP16_REMINDER 或無提醒）
- chore commit 類型不應出現雙通道要求文字
- style commit 類型不應出現 /error-pattern add 指令
- 向後相容性驗證通過

**測試案例識別符**：`test_commit_type_filtering_preserved`

### 2.3 行為鏈式推演（BDD 完整場景）

#### 完整行為鏈 1：PM 執行 commit 並正確遵循雙通道記錄流程

**場景描述**：PM 完成 git commit（feat 類型）後，commit-handoff-hook 觸發場景 #16，PM 選擇「記錄」並正確執行雙通道。

**行為鏈推演**：

```
開始
  |
  v
A：PM 執行 git commit（feat 類型）
  |
  +-- 驗證前置 → commit 訊息格式正確（feat({id}): ...)
  +-- 驗證前置 → Git 狀態正常（working directory clean）
  |
  v
B：commit-handoff-hook 偵測到 commit 成功
  |
  +-- 驗證中間狀態 → Hook 被正確觸發（env.GIT_COMMIT_MSG 已設定）
  +-- 驗證中間狀態 → commit 類型識別為 feat（非 docs/chore/style）
  |
  v
C：Hook 輸出 COMMIT_HANDOFF_REMINDER（包含場景 #16 選項）
  |
  +-- 驗證中間狀態 → additionalContext 包含 COMMIT_HANDOFF_REMINDER 文字
  +-- 驗證中間狀態 → 文字包含「選擇『記錄』」
  +-- 驗證中間狀態 → 文字包含「/error-pattern add」
  +-- 驗證中間狀態 → 文字包含「更新 memory」
  +-- 驗證中間狀態 → 文字包含「[WARNING] 雙通道」
  |
  v
D：PM 使用 AskUserQuestion #16 確認
  |
  +-- 驗證動作前置 → AskUserQuestion 工具已載入
  +-- 驗證動作前置 → 場景 #16 定義已包含雙通道要求
  |
  v
E：PM 選擇「記錄錯誤學習」
  |
  +-- 驗證結果 → 進入記錄流程（而非直接進入 #11）
  |
  v
F：PM 執行 /error-pattern add
  |
  +-- 驗證動作完成 → .claude/error-patterns/ 下有新檔案
  +-- 驗證動作完成 → 新檔案符合 error-pattern 格式
  |
  v
G：PM 更新 auto-memory
  |
  +-- 驗證動作完成 → .claude/projects/.../memory/ 下的檔案被修改
  +-- 驗證動作完成 → memory 檔案包含相關錯誤學習記錄
  |
  v
H：PM 重新確認 #16（「無需記錄」選項）
  |
  +-- 驗證狀態 → 雙通道都已執行（前置條件滿足）
  |
  v
完成 → 進入 #11 Handoff
```

**前置條件驗證斷言**（每一步驟前必須驗證）：

| 步驟 | 前置條件 | 驗證斷言 |
|------|---------|---------|
| A | commit 命令執行 | `git rev-parse --short HEAD` 返回值改變 |
| B | Hook 被觸發 | commit-handoff-hook.py 執行日誌出現該次 commit 記錄 |
| C | Hook 輸出提醒 | additionalContext 包含非空字串 |
| D | AskUserQuestion 可用 | ToolSearch("select:AskUserQuestion") 成功載入 |
| E | 使用者選擇「記錄」 | 進入記錄流程（不是直接 #11） |
| F | /error-pattern add 執行 | 新檔案建立且可讀取 |
| G | memory 更新 | 檔案 mtime 更新，內容包含新增記錄 |
| H | 雙通道完成 | 兩個檔案都有新增記錄 |

**四個維度的行為分支**：

1. **正常流程**（場景 1）：PM 選擇「記錄」→ 執行雙通道 → 重新確認 #16 → 進入 #11（本場景）

2. **異常流程 1**：PM 選擇「無需記錄」
   ```
   Given: commit 類型為 feat，Hook 觸發 #16
   When: PM 選擇「無需記錄」
   Then: 跳過記錄流程，直接進入 #11 Handoff
   ```

3. **異常流程 2**：PM 只執行 /error-pattern add 未更新 memory
   ```
   Given: PM 選擇「記錄」，已執行 /error-pattern add
   When: PM 未更新 memory，直接進入 #16 再次確認
   Then: [規則文字提醒] 雙通道要求未滿足，應繼續記錄
   ```

4. **邊界條件**：docs/chore commit 類型
   ```
   Given: commit 類型為 docs，Hook 偵測到
   When: Hook 應用 SKIP_SCENE16_COMMIT_PREFIXES 過濾
   Then: 不觸發 #16，不出現雙通道要求
   ```

#### 完整行為鏈 2：PM 閱讀規則文件確認雙通道要求

**場景描述**：開發者或 PM 閱讀 askuserquestion-rules.md 了解場景 #16 的雙通道要求。

**行為鏈推演**：

```
開始
  |
  v
A：開發者打開 askuserquestion-rules.md
  |
  +-- 驗證前置 → 檔案存在且可讀取
  |
  v
B：開發者定位到場景 #16
  |
  +-- 驗證中間狀態 → 找到場景列表表格中的「#16」行
  +-- 驗證中間狀態 → 該行包含「錯誤學習經驗確認」描述
  |
  v
C：開發者閱讀場景 #16 的觸發條件和規則說明
  |
  +-- 驗證中間狀態 → 場景列表下方存在新的「場景 #16 雙通道記錄要求」區塊
  +-- 驗證中間狀態 → 區塊位置邏輯正確（場景列表之後）
  |
  v
D：開發者閱讀雙通道規則區塊
  |
  +-- 驗證動作前置 → 區塊標題明確提及「雙通道」
  +-- 驗證動作前置 → 區塊包含清單或表格
  |
  v
E：開發者理解兩個通道的定義
  |
  +-- 驗證結果 → 理解 error-pattern 通道的位置和用途
  +-- 驗證結果 → 理解 memory 通道的位置和用途
  +-- 驗證結果 → 理解「必須同時執行」的強制要求
  |
  v
F：開發者查閱禁止行為說明
  |
  +-- 驗證動作完成 → 規則明確說明「只寫單一通道」屬禁止行為
  +-- 驗證動作完成 → 禁止行為描述清楚（同時提及兩個通道）
  |
  v
完成 → 開發者明確理解雙通道要求
```

**前置條件驗證斷言**（每一步驟前必須驗證）：

| 步驟 | 前置條件 | 驗證斷言 |
|------|---------|---------|
| A | 檔案存在 | `ls -l askuserquestion-rules.md` 成功 |
| B | 檔案可讀取 | 檔案編碼為 UTF-8，行數 > 0 |
| C | 場景列表存在 | grep "## 場景列表" 或 grep "#16" 成功 |
| D | 區塊已新增 | grep "場景 #16 雙通道" 成功 |
| E | 區塊內容完整 | 包含 error-pattern 和 memory 兩個詞 |
| F | 禁止行為說明 | grep "禁止" 或 grep "必須同時" 成功 |

**四個維度的行為分支**：

1. **正常流程**：開發者按順序閱讀規則 → 理解雙通道要求（本場景）

2. **異常流程 1**：規則文件格式破損
   ```
   Given: askuserquestion-rules.md 檔案存在但 Markdown 格式破損
   When: 開發者嘗試解析檔案
   Then: Markdown 解析器應仍能識別關鍵內容（容錯性）
   ```

3. **異常流程 2**：場景 #16 說明缺失
   ```
   Given: 場景列表表格存在但場景 #16 行缺失或描述不清
   When: 開發者搜尋場景 #16
   Then: [測試應驗證] 場景 #16 行必須存在且完整
   ```

4. **邊界條件**：版本升級前後的相容性
   ```
   Given: askuserquestion-rules.md 已更新（新增雙通道區塊）
   When: 舊版本代碼仍引用此檔案
   Then: 格式變更應向後相容（不破壞現有解析邏輯）
   ```

## 7. 測試設計發現和關鍵決策

### 7.1 設計發現

1. **文字常數驗證的可靠性**：
   - 由於 COMMIT_HANDOFF_REMINDER 是純文字常數，測試通過字串搜尋驗證是可行的
   - 無需複雜的 Mock 或 Hook 邏輯模擬，直接讀取常數即可

2. **規則文件和常數的相互參照**：
   - COMMIT_HANDOFF_REMINDER（常數）和 askuserquestion-rules.md（規則文件）兩個文件需要保持一致性
   - 測試應同時驗證兩個文件中的雙通道要求文字

3. **行為鏈的前置條件驗證必須完整**：
   - PM commit → Hook 觸發 → 場景 #16 選項 → 雙通道記錄，整個流程中每個環節的前置條件都必須驗證
   - 否則測試結果的可靠性會受到影響

### 7.2 關鍵決策

1. **選擇字串匹配而非 Mock**：
   - 理由：COMMIT_HANDOFF_REMINDER 是純文字常數，直接搜尋關鍵詞比 Mock 更簡單可靠
   - 好處：測試執行速度快，不依賴複雜的環境模擬

2. **分離 Hook 常數測試和規則文件測試**：
   - 理由：兩個測試層級職責不同，分離可提高測試的單一責任性
   - 好處：測試失敗時更容易定位問題（是常數還是規則文件）

3. **包含完整的行為鏈測試**：
   - 理由：虛單元測試無法驗證流程的完整性，需要端對端驗證
   - 好處：確保雙通道要求在實際使用中能被正確理解和執行
