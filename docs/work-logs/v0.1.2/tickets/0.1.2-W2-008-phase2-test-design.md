# Phase 2 測試設計：file-ownership-guard-hook

## 設計摘要

本文件設計 `file-ownership-guard-hook.py` 的完整測試套件，共 **28 個測試案例**，涵蓋：
- **無衝突場景**（4 個案例）
- **有衝突場景**（10 個案例）
- **邊界條件**（8 個案例）
- **異常處理**（6 個案例）

測試工具：`uv run pytest`（Python 3.11+）

---

## 1. 測試策略規劃

### 1.1 測試分層

| 層級 | 測試主題 | 案例數 | 職責 |
|------|---------|-------|------|
| **Unit** | 核心演算法單元 | 15 | 驗證個別函式的邏輯正確性 |
| **Integration** | 整合 Hook 生命週期 | 8 | 驗證 stdin/stdout、日誌、退出碼 |
| **Edge Case** | 邊界和異常條件 | 5 | 驗證容錯和特殊情況 |

### 1.2 核心測試目標

| 目標 | 驗證方式 |
|------|---------|
| 路徑規範化正確 | 輸入多種路徑格式，檢查規範化結果 |
| 衝突偵測準確 | 預期衝突能偵測，無衝突能通過 |
| 邊界處理妥當 | where.files 空值、跨 Wave、狀態篩選 |
| 異常不中斷 | 缺失檔案、YAML 破損、JSON 格式錯誤 |
| 輸出可操作 | 警告訊息含衝突清單、建議行動、決策幫助 |
| Hook 生命週期正確 | 觸發判斷、stdin/stdout 格式、退出碼（0） |

```python
    def _factory(
        ticket_id,
```

#### D. Ticket 檔案建立輔助

```python
@pytest.fixture
def make_ticket_file():
    """在臨時目錄建立 Ticket 檔案"""

    return _factory
```

## 9. 測試設計決策

### 9.1 為什麼使用 pytest 而非 unittest？

- **fixture 機制**：簡化 mock 和 setup/teardown
- **參數化測試**：`@pytest.mark.parametrize` 支援多案例簡潔寫法
- **更強大的 assert**：自動詳細的失敗訊息
- **生態成熟**：與 ci 和 coverage tool 整合良好

### 9.2 為什麼用臨時目錄 (tmp_path)？

- **隔離性**：每個測試都有獨立檔案系統，互不影響
- **清潔性**：測試後自動清理，無殘留
- **並行性**：多個測試可並行執行而無衝突

### 9.3 為什麼設計工廠 (factory) Fixture？

- **靈活性**：測試可動態改變參數，無需多個固定 Fixture
- **可讀性**：測試程式碼清晰表達「給定什麼參數」
- **可維護性**：參數變更只需改工廠，不涉及多個 Fixture

### 9.4 為什麼分離 `test_*.py` 檔案？

- **職責清晰**：各檔案專注一個測試維度（路徑、衝突、邊界、異常等）
- **執行靈活**：可選擇性執行某一維度的測試
- **維護性**：每個檔案邏輯獨立，修改時影響範圍小

## 10. Mock 和 Isolation 策略

### 10.1 Mock 對象清單

| Mock 對象 | 原因 | 策略 |
|----------|------|------|
| Logger | 外部依賴 | Mock logger，驗證 log level 和訊息 |
| get_project_root | 環境依賴 | Mock 返回 tmp_path |
| Ticket 檔案讀取 | I/O 操作 | 使用 tmp_path 建立真實檔案 |
| stdin/stdout | 外部介面 | Mock sys.stdin 和 sys.stdout |
| parse_ticket_frontmatter | 內部服務 | 使用真實解析器（YAML 格式標準） |

### 10.2 隔離原則

- **不 Mock Ticket 解析**：使用真實 YAML 格式，確保與實際一致
- **不 Mock 路徑規範化**：測試實際的規範化邏輯
- **Mock 檔案 I/O**：除非測試異常處理
- **Mock Logger**：驗證日誌輸出，不依賴實際日誌檔案
