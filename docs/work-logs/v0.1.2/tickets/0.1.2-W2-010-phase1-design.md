# Phase 1 功能規格設計：擴展重複偵測範圍至 completed 狀態

## 1. 功能需求分析

### 1.1 核心問題

`_detect_duplicate_tickets()` 目前僅掃描 `status == STATUS_PENDING` 的 Ticket，導致以下盲區：

- 已完成（completed）的 Ticket 在重複偵測中完全不可見
- 進行中（in_progress）的 Ticket 也被排除，同樣形成盲區
- 在不同 session 或較長時間間隔後建立 Ticket，容易重複已完成工作

### 1.2 使用者場景

場景一（主要場景）：使用者在新 session 中嘗試建立「實作 SRP 偵測機制」，但同版本 3 天前已完成相同 Ticket。目前不會觸發警告，使用者無從得知。

場景二：使用者建立的 Ticket 與進行中的某 Ticket 標題高度重疊，目前也不會警告。

場景三（邊界場景）：超過 7 天的 completed Ticket 不需要警告（屬於歷史記錄，不視為近期重複風險）。

### 1.3 成功標準

- 建立 Ticket 時，同版本 7 天內完成的重複 Ticket 輸出 WARNING
- 同版本進行中（in_progress）的重複 Ticket 輸出 WARNING（標示狀態來源）
- 超過 7 天的 completed Ticket 不掃描（效能與警告品質的平衡）
- 現有測試全部通過（B-004、B-005 測試語義需對應更新）

## 2. 功能規格設計

### 2.1 輸入定義

函式簽名不變：

```python
def _detect_duplicate_tickets(
    version: str,
    new_title: str,
    new_what: str,
    new_ticket_id: str,
) -> None:
```

無需新增參數。時間窗口使用內部常數控制，不對外暴露。

### 2.2 輸出規格

輸出格式依狀態分類，區分「活躍重複」（in_progress）和「歷史重複」（completed）：

**活躍重複警告（in_progress）**：
```
[WARNING] 發現 {count} 個可能重複的活躍 Ticket，請確認是否需要建立新 Ticket：
   - {ticket_id}: {title} [進行中]
   建議：執行 /ticket track list 查看所有現有 Ticket 後再決定
```

**歷史重複警告（completed，7 天內）**：
```
[WARNING] 發現 {count} 個可能重複的近期已完成 Ticket，請確認是否需要建立新 Ticket：
   - {ticket_id}: {title} [已完成]
   建議：執行 /ticket track list 查看所有現有 Ticket 後再決定
```

**混合情境（同時有 in_progress 和 completed）**：
```
[WARNING] 發現 {count} 個可能重複的 Ticket，請確認是否需要建立新 Ticket：
   - {ticket_id_1}: {title_1} [進行中]
   - {ticket_id_2}: {title_2} [已完成]
   建議：執行 /ticket track list 查看所有現有 Ticket 後再決定
```

標籤格式（`[進行中]`、`[已完成]`）追加在標題後，與現有 pending 警告格式保持向下相容。pending Ticket 不加標籤（維持現有行為）。

### 2.3 正常操作流程

現有流程基礎上，只修改步驟 B 的過濾邏輯：

```
步驟 A：驗證輸入（不變）
    若 title 和 what 均空 → 提前返回

步驟 B：載入同版本 Ticket（修改過濾邏輯）
    B-1：計算排除 ID（不變：自身 + 父任務）
    B-2：計算 7 天時間窗口基準時間 = now - timedelta(days=7)
    B-3：掃描清單中符合以下任一條件的 Ticket（新邏輯）：
        - status == pending（維持原有）
        - status == in_progress（新增）
        - status == completed 且 completed_at >= 7 天窗口基準時間（新增）
    B-4：若過濾後無候選 Ticket → 提前返回（邏輯不變）

步驟 C：相似度計算（不變）
    對每個候選 Ticket 計算 Jaccard 相似度
    閾值：DUPLICATE_DETECTION_THRESHOLD（0.3）
    completed 和 in_progress 不使用不同閾值（維持一致性）

步驟 D：輸出結果（修改警告格式）
    若有相似 Ticket → 輸出帶狀態標籤的 WARNING
    標籤規則：
        - pending → 不加標籤
        - in_progress → [進行中]
        - completed → [已完成]
```

### 2.4 例外處理策略

維持現有容錯設計，不變更例外處理策略：

- 外層 `try/except`：捕捉全部異常，靜默通過（重複偵測為輔助功能）
- 內層 `try/except`（單項計算）：捕捉相似度計算異常，跳過該項繼續
- `completed_at` 欄位遺失或格式異常：視為超過時間窗口，排除（保守策略）
- `completed_at` 時間解析異常：靜默排除該 Ticket，不中斷整體偵測

## 3. 邊界條件分析

| 場景 | 輸入狀態 | `completed_at` | 預期行為 |
|------|----------|----------------|----------|
| pending Ticket | pending | 無 | 維持現有：掃描 |
| in_progress Ticket | in_progress | 無 | 新增：掃描 |
| 7 天內完成 Ticket | completed | now - 3 天 | 新增：掃描 |
| 7 天前完成 Ticket | completed | now - 8 天 | 不掃描 |
| 剛好 7 天前完成（邊界） | completed | now - 7 天整 | 不掃描（`<` 而非 `<=`，使用嚴格小於） |
| completed 但無 `completed_at` | completed | None | 排除（保守策略）|
| completed 且 `completed_at` 格式錯誤 | completed | "invalid" | 排除（保守策略） |
| blocked Ticket | blocked | 無 | 不掃描（無需加入） |

### 3.1 時間窗口邊界語義

```python
# 7 天窗口定義（closed-open interval）
# window_start = now - timedelta(days=7)
# 條件：completed_at 解析後的 datetime >= window_start
# 即：最近 7 天（不含第 7 天的整數邊界）
```

### 3.2 `completed_at` 欄位格式

根據 `lifecycle.py:450` 的寫入邏輯：
```python
ticket["completed_at"] = datetime.now().isoformat(timespec="seconds")
# 產生格式範例："2026-03-21T14:30:00"（無時區資訊）
```

時間解析使用 `datetime.fromisoformat()` 即可，但需處理：
- `None`（未完成的 Ticket）
- 舊版 Ticket 可能使用其他格式
- 解析失敗：`except ValueError, TypeError` → 排除該 Ticket

### 4.4 過濾邏輯核心實作草圖

```python
from datetime import datetime, timedelta

def _is_in_detection_scope(ticket: dict) -> bool:
    """判斷 Ticket 是否在重複偵測範圍內。

    範圍規則：
    - pending → 始終包含
    - in_progress → 始終包含
    - completed → 7 天內完成者包含
    - 其他狀態 → 排除
    """
    status = ticket.get("status")

    if status == STATUS_PENDING:
        return True

    if status == STATUS_IN_PROGRESS:
        return True

    if status == STATUS_COMPLETED:
        completed_at_str = ticket.get("completed_at")
        if not completed_at_str:
            return False  # 保守策略：無時間戳排除
        try:
            completed_at = datetime.fromisoformat(str(completed_at_str))
            window_start = datetime.now() - timedelta(
                days=DUPLICATE_DETECTION_COMPLETED_WINDOW_DAYS
            )
            return completed_at >= window_start
        except (ValueError, TypeError):
            return False  # 保守策略：格式異常排除

    return False  # blocked 等其他狀態排除
```

### 4.5 輸出標籤輔助函式草圖

```python
def _get_status_label(status: str) -> str:
    """根據 Ticket 狀態返回顯示標籤。

    pending 返回空字串（不顯示標籤，維持現有行為）。
    """
    if status == STATUS_IN_PROGRESS:
        return CreateMessages.DUPLICATE_STATUS_LABEL_IN_PROGRESS
    if status == STATUS_COMPLETED:
        return CreateMessages.DUPLICATE_STATUS_LABEL_COMPLETED
    return ""  # pending 不顯示標籤
```

## 7. 行為場景（Given-When-Then）

### 場景 1：in_progress 重複 Ticket 被偵測（正常流程）

Given: 同版本存在 in_progress Ticket「實作 SRP 自動偵測機制」
When: 使用者建立「實作 SRP 偵測功能」
Then: 輸出 WARNING，含 Ticket ID、標題和 `[進行中]` 標籤

### 場景 2：7 天內完成的重複 Ticket 被偵測（正常流程）

Given: 同版本存在 completed Ticket，`completed_at` 為 3 天前，標題「實作 SRP 自動偵測機制」
When: 使用者建立「實作 SRP 偵測功能」
Then: 輸出 WARNING，含 Ticket ID、標題和 `[已完成]` 標籤

### 場景 3：超過 7 天的 completed 不觸發警告（邊界條件）

Given: 同版本存在 completed Ticket，`completed_at` 為 10 天前，標題高度相似
When: 使用者建立相似標題的 Ticket
Then: 靜默通過，無任何輸出

### 場景 4：`completed_at` 欄位缺失（異常流程）

Given: completed Ticket 無 `completed_at` 欄位（舊版格式）
When: 重複偵測函式執行
Then: 該 Ticket 被排除（保守策略），靜默處理不拋出異常

### 場景 5：mixed 警告（同時有 in_progress 和 completed）（複合場景）

Given: 同版本存在 1 個 in_progress + 1 個 7 天內 completed，兩者都與新 Ticket 相似
When: 使用者建立新 Ticket
Then: 輸出 WARNING 列出兩個，分別標示 `[進行中]` 和 `[已完成]`

### 場景 6：pending Ticket 維持現有行為（回歸驗證）

Given: 同版本存在 pending Ticket，標題相似
When: 使用者建立相似 Ticket
Then: 輸出 WARNING，Ticket 項目不含狀態標籤（向下相容）
