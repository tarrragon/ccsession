## 1. 測試策略概述

### 1.1 測試層級分布

| 層級 | 責任 | 優先級 | 測試類型 | 預期數量 |
|------|------|--------|---------|---------|
| **Schema 驗證** | 格式檢查、必填欄位、型別驗證 | 高 | Unit | 15-20 個 |
| **能力提取** | Agent entry 完整性、交叉驗證 | 高 | Unit | 10-15 個 |
| **三種衝突檢查** | Agent 衝突、Phase 相序、檔案寫入 | 高 | Unit + Integration | 25-30 個 |
| **Dispatch Recommend CLI** | 評分計算、排序、參數處理 | 中 | Unit + Integration | 15-20 個 |
| **端到端驗證** | Registry + Hook + CLI 整合 | 中 | Integration + E2E | 5-8 個 |
| **向後相容性** | 現存 ticket dry-run 符合率 | 高 | Integration | 1 個（統計驗證） |

**測試優先級順序**：
1. 三種衝突檢查（阻止性強、風險高）
2. Schema 驗證（基礎設施）
3. Dispatch recommend CLI（用戶主要功能）
4. 能力提取驗證（支撐性）

### 1.2 測試策略決策

| 決策 | 選擇 | 原因 |
|------|------|------|
| Unit vs Integration | 90% Unit + 10% Integration | Registry 是靜態資料層，Unit 為主；Hook/CLI 與 registry 整合用 Integration |
| Mock 策略 | Mock YAML、Mock Ticket 資料 | Registry 本身是資料檔，直接使用測試 fixture；Ticket 用 Mock |
| 測試框架 | pytest（Python Hook 和 CLI） + unittest（自動化驗證） | 與專案既有 Python 測試框架一致 |
| Sociable Unit Tests | 是 | Unit 測試 registry 讀取、parsing、衝突演算法；Integration 測試 Hook/CLI 與 registry 互動 |

### 2.1 Schema 驗證測試（TC_SCHEMA_001-020）

**目標**：驗證 registry.yaml 的結構、型別、格式、必填欄位

#### 必填欄位驗證
- **TC_SCHEMA_001**: schema_version 必填，格式 `{major}.{minor}` 整數
- **TC_SCHEMA_002**: agents object 必填，至少包含 1 個 agent entry
- **TC_SCHEMA_003**: 每個 agent 的 `name` 欄位必填（非空字串）
- **TC_SCHEMA_004**: 每個 agent 的 `version` 欄位必填，格式 `X.Y` 數字
- **TC_SCHEMA_005**: 每個 agent 的 `model` 欄位必填（haiku/sonnet/opus）

#### 欄位型別驗證
- **TC_SCHEMA_006**: `accepts` 型別驗證（必須是 list，可空）
- **TC_SCHEMA_007**: `accepts[].artifact_type` 為 kebab-case 字串，禁止空格和大寫
- **TC_SCHEMA_008**: `accepts[].required` 為 boolean 型別
- **TC_SCHEMA_009**: `produces` 型別驗證（必須是 list，可空）
- **TC_SCHEMA_010**: `produces[].path_pattern` 為合法 glob 模式
- **TC_SCHEMA_011**: `preconditions` 為 list，每個 condition 符合 `{subject} {verb} {object}` 格式
- **TC_SCHEMA_012**: `conflict_avoidance` 型別驗證（list，可空）
- **TC_SCHEMA_013**: `conflict_avoidance[].type` 為允許值（cannot_work_with/must_complete_before/cannot_work_after）
- **TC_SCHEMA_014**: `conflict_avoidance[].agents` 為字串清單，每個引用必須是現存 agent
- **TC_SCHEMA_015**: `tdd_phases` 為 list，每個值為合法 Phase（phase0-4c）
- **TC_SCHEMA_016**: `file_patterns` 為 list，每個為合法 glob 模式

#### 格式一致性驗證
- **TC_SCHEMA_017**: `file_patterns` 與 `produces[].path_pattern` 的聯集相等（無遺漏或重複）
- **TC_SCHEMA_018**: YAML 語法正確，可被 PyYAML 解析
- **TC_SCHEMA_019**: agent key 名稱與 `name` 欄位對應（snake_case key 對應人類可讀 name）
- **TC_SCHEMA_020**: 無多餘欄位或棄用欄位混入

### 2.2 能力提取驗證測試（TC_EXTRACT_001-015）

**目標**：驗證所有 agent 能力已正確從 .md 提取至 registry

- **TC_EXTRACT_004**: 所有派發相關 agent 均有 `accepts` 和 `conflict_avoidance`（即使為空清單）

#### 交叉驗證（Registry vs decision-tree.md）
- **TC_EXTRACT_005**: registry 中的 agent 身份（tdd_phases）與 decision-tree.md 第五層完全一致（無矛盾）
- **TC_EXTRACT_006**: registry 中的 agent 身份與 incident-response.md 派發表一致
- **TC_EXTRACT_007**: 所有 conflict_avoidance.agents 引用的 agent 必須存在於 registry（無懸掛引用）

#### 能力宣告質量
- **TC_EXTRACT_008**: 每個 agent 的 `accepts` 列出的 artifact_type 必須在已定義清單中（或被添加到清單）

### 2.3 三種衝突檢查測試（TC_CONFLICT_001-030）

#### 衝突類型一：Agent 同時派發衝突（TC_CONFLICT_001-010）

**測試前置**：Mock registry 含衝突定義

- **TC_CONFLICT_001**: 同一 agent 被派發兩次時，Hook 輸出 CONFLICT WARNING
  - Given: 派發 [parsley-flutter-developer, parsley-flutter-developer]
  - When: Hook 執行衝突檢查
  - Then: 輸出 "cannot_work_with: [parsley]" 衝突訊息

- **TC_CONFLICT_002**: 相容 agent 並行派發時無衝突
  - Given: 派發 [parsley-flutter-developer, sage-test-architect]
  - When: Hook 執行衝突檢查
  - Then: 無衝突輸出

- **TC_CONFLICT_003**: 衝突 agent 在 conflict_avoidance 中被標記時 Hook 攔截
  - Given: registry 中 agent A 的 conflict_avoidance 含 "cannot_work_with: [B]"
  - When: 派發 [A, B] 並行
  - Then: Hook 輸出 CONFLICT WARNING 含具體衝突原因

- **TC_CONFLICT_004**: 序列派發相同 agent 時無衝突（scope=same_ticket 預設）
  - Given: 同一 Ticket，先派發 parsley，後派發 parsley（不同步驟）
  - When: Hook 檢查第二次派發
  - Then: 無衝突輸出（序列執行合法）

- **TC_CONFLICT_005**: 跨 Ticket 派發相同 agent 時無衝突（scope=same_ticket）
  - Given: Ticket A 派發 parsley，同時 Ticket B 也派發 parsley
  - When: Hook 檢查
  - Then: 無衝突輸出（不同 Ticket 的資源隔離）

- **TC_CONFLICT_006**: 全域衝突（scope=global）時跨 Ticket 亦被攔截
  - Given: registry 中 agent A 定義 "cannot_work_with: [B]" scope=global
  - When: Ticket 1 派發 A，Ticket 2 派發 B（同時進行）
  - Then: Hook 輸出 CONFLICT BLOCK（全域衝突）

- **TC_CONFLICT_007**: 衝突訊息包含「建議修正」章節
  - Given: 偵測到衝突
  - When: Hook 輸出訊息
  - Then: 訊息含「建議修正」、「序列派發」或「檢查 file_patterns」等建議

- **TC_CONFLICT_008**: must_complete_before 型衝突驗證
  - Given: registry 中 A 定義 "must_complete_before: [B]"
  - When: B 未完成時派發 A
  - Then: Hook 輸出 CONFLICT BLOCK

- **TC_CONFLICT_009**: cannot_work_after 型衝突驗證
  - Given: A 定義 "cannot_work_after: [B]"
  - When: B 已執行後派發 A
  - Then: Hook 檢查 Ticket 歷史，偵測衝突

- **TC_CONFLICT_010**: 多個衝突同時存在時全部列出
  - Given: 派發 [A, B, C]，其中 A-B 有衝突，B-C 有衝突
  - When: Hook 執行
  - Then: 輸出含兩個衝突的完整清單

#### 衝突類型二：TDD Phase 相序衝突（TC_CONFLICT_011-020）

**測試前置**：Mock Ticket 的 tdd_stage，Mock agent 的 tdd_phases 和 preconditions

- **TC_CONFLICT_011**: Phase 2 代理人在 Phase 1 未完成時被攔截
  - Given: Ticket.tdd_stage=[phase1]，execution_log 無 phase1-feature-spec
  - When: 派發 sage-test-architect（phase2）
  - Then: Hook 輸出 CONFLICT BLOCK，說明「Phase 1 尚未完成」

- **TC_CONFLICT_012**: Phase 相序檢查驗證 artifact_type 存在於 execution_log
  - Given: Ticket.tdd_stage=[phase2]，execution_log 中記錄了 phase1-feature-spec
  - When: 派發 sage-test-architect
  - Then: Hook 通過驗證，無衝突

- **TC_CONFLICT_013**: Phase 3a 代理人需要 Phase 1 + 2 都完成
  - Given: execution_log 中只有 phase1-feature-spec，無 phase2-test-design
  - When: 派發 pepper-test-implementer（phase3a）
  - Then: Hook 阻止派發，列出缺少的 phase2-test-design

- **TC_CONFLICT_014**: Phase 3b 需要 Phase 3a 完成（precondition 驗證）
  - Given: execution_log 中無 phase3a-strategy-doc
  - When: 派發 parsley-flutter-developer
  - Then: Hook 輸出衝突訊息含缺少的 artifact

- **TC_CONFLICT_015**: 多個 precondition 同時驗證
  - Given: agent 的 preconditions 列出 [phase1-completed, phase2-completed, ...]
  - When: 部分 precondition 未滿足
  - Then: Hook 列出所有缺少的前置條件

- **TC_CONFLICT_016**: Phase 4 相序驗證（4a → 4b → 4c 順序）
  - Given: execution_log 中無 phase4a-analysis-report
  - When: 直接派發 cinnamon-refactor-owl（phase4b）
  - Then: Hook 阻止派發，提示需先執行 phase4a

- **TC_CONFLICT_017**: 同一 Phase 可重複派發（無序列約束）
  - Given: Ticket.tdd_stage=[phase3b]，已派發一次 parsley
  - When: 派發第二個子任務的 parsley（子任務拆分場景）
  - Then: Hook 通過（同 Phase 內可多次派發不同 agent 或同 agent 的子任務）

- **TC_CONFLICT_018**: 非 TDD Phase 派發（如 incident-responder）無 Phase 相序約束
  - Given: Ticket 任意 tdd_stage
  - When: 派發 incident-responder
  - Then: Hook 不檢查 Phase 相序約束

- **TC_CONFLICT_019**: preconditions 支援複雜條件（如 OR 邏輯，如果實現）
  - Given: agent 的 preconditions 列出 "phase2-completed OR approved-by-sa"
  - When: 滿足其中一個條件
  - Then: Hook 通過驗證

- **TC_CONFLICT_020**: preconditions 不存在時視為無約束
  - Given: agent 的 preconditions 為 []
  - When: 派發此 agent
  - Then: Hook 無 precondition 相關的衝突檢查

#### 衝突類型三：檔案寫入衝突（ARCH-005）（TC_CONFLICT_021-030）

**測試前置**：Mock agent 的 file_patterns，實作 glob 模式比對演算法

- **TC_CONFLICT_021**: 完全相同的 file_pattern 被兩個 agent 擁有時偵測衝突
  - Given: agent A: file_patterns=["ui/lib/**/*.dart"]，agent B: file_patterns=["ui/lib/**/*.dart"]
  - When: 派發 [A, B] 並行
  - Then: Hook 輸出 "檔案寫入衝突偵測（ARCH-005）"，列出重疊模式

- **TC_CONFLICT_022**: 包含關係被偵測為衝突
  - Given: agent A: ["ui/lib/**/*.dart"]，agent B: ["ui/lib/core/**/*.dart"]
  - When: 派發 [A, B]
  - Then: Hook 偵測衝突（B 的模式在 A 的範圍內）

- **TC_CONFLICT_023**: 完全不重疊的路徑無衝突
  - Given: agent A: ["ui/lib/**/*.dart"]，agent B: ["server/**/*.go"]
  - When: 派發 [A, B]
  - Then: Hook 無衝突輸出

- **TC_CONFLICT_024**: 路徑前綴不同時無衝突
  - Given: agent A: ["docs/work-logs/**"]，agent B: ["docs/references/**"]
  - When: 派發 [A, B]
  - Then: Hook 無衝突（前綴 work-logs vs references 不重疊）

- **TC_CONFLICT_025**: 檔案副檔名差異時無衝突
  - Given: agent A: ["ui/**/*.dart"]，agent B: ["ui/**/*.yaml"]
  - When: 派發 [A, B]
  - Then: Hook 無衝突（.dart vs .yaml 為不同檔案）

- **TC_CONFLICT_026**: ARCH-005 回溯測試：parsley + cinnamon 並行時偵測衝突
  - Given: parsley.file_patterns=["ui/lib/**/*.dart", "ui/test/**/*.dart"]
  -        cinnamon.file_patterns=["ui/lib/**/*.dart"]
  - When: 派發 [parsley, cinnamon]
  - Then: Hook 輸出衝突警告，建議序列派發

- **TC_CONFLICT_027**: ARCH-005 回溯測試：parsley + sage 並行時無衝突
  - Given: parsley: ["ui/lib/**/*.dart"]，sage: ["docs/work-logs/*/tickets/*-phase2-*.md"]
  - When: 派發 [parsley, sage]
  - Then: Hook 無衝突（不同路徑根）

- **TC_CONFLICT_028**: 檔案寫入衝突是 WARNING 而非 BLOCK（允許 PM 手動確認）
  - Given: 偵測到潛在檔案衝突
  - When: Hook 輸出訊息
  - Then: 輸出級別為 WARNING，派發不被阻止

- **TC_CONFLICT_029**: 核心檔案衝突（如 constants.dart、settings.json）輸出強烈警告
  - Given: 衝突涉及 constants.dart 或 settings.json
  - When: Hook 偵測
  - Then: 輸出級別升高為 STRONG WARNING，強烈建議序列派發

- **TC_CONFLICT_030**: 衝突訊息包含具體衝突的模式清單
  - Given: 偵測到多個衝突模式
  - When: Hook 輸出訊息
  - Then: 列出所有衝突的模式對（"pattern_a ∩ pattern_b"）

### 2.4 dispatch recommend CLI 測試（TC_CLI_001-025）

**測試前置**：Mock registry，Mock ticket data（type、where、tdd_stage）

#### 基本功能（TC_CLI_001-010）

- **TC_CLI_001**: 命令執行且返回候選清單
  - Given: `/ticket dispatch recommend 0.1.2-W1-006`
  - When: CLI 執行
  - Then: 返回 JSON 或表格格式的候選 agent 清單

- **TC_CLI_002**: 返回的候選按分數從高到低排序
  - Given: 候選分數為 [90, 70, 50, 0]
  - When: CLI 排序
  - Then: 輸出順序為 90, 70, 50, 0

- **TC_CLI_003**: 每個候選包含分數和推薦理由
  - Given: 候選 parsley-flutter-developer
  - When: CLI 輸出
  - Then: 包含 "分數: 90/100" 和 "推薦理由: ..."

- **TC_CLI_004**: `--top N` 參數限制返回數量
  - Given: `--top 3`
  - When: 候選 > 3 個
  - Then: 只返回前 3 個

- **TC_CLI_005**: 預設 `--top 5`（無參數時）
  - Given: 無 `--top` 參數
  - When: 候選 > 5 個
  - Then: 返回前 5 個

- **TC_CLI_006**: `--phase` 參數篩選特定 TDD Phase
  - Given: `--phase phase3b`
  - When: CLI 過濾
  - Then: 只返回 tdd_phases 包含 phase3b 的 agent

- **TC_CLI_007**: `--dry-run` 參數不執行驗證，只返回評分
  - Given: `--dry-run`
  - When: CLI 執行
  - Then: 無 Hook 執行、無副作用，只返回評分清單

- **TC_CLI_008**: Ticket 不存在時返回錯誤訊息
  - Given: `dispatch recommend 0.0.0-W0-999`（不存在）
  - When: CLI 執行
  - Then: 返回 "Ticket not found" 錯誤

- **TC_CLI_009**: registry.yaml 缺失或格式錯誤時返回錯誤
  - Given: registry.yaml 不存在
  - When: CLI 執行
  - Then: 返回 "Registry not found" 或 YAML parse error

- **TC_CLI_010**: 無任何候選時返回友好訊息
  - Given: 所有 agent 都不符合票狀態
  - When: CLI 執行
  - Then: 返回 "No matching agents found"

#### 評分計算（TC_CLI_011-020）

**測試前置**：詳細的評分公式驗證（參見 Phase 1 設計文件 5.2 節）

- **TC_CLI_011**: type_match_score 計算正確（40 × 符合比例）
  - Given: Ticket 有 phase1-feature-spec、phase2-test-design
  - When: 計算 parsley 的 type_match（需要 phase3a-strategy-doc）
  - Then: 分數 = 40 × 0 = 0（缺少 phase3a）

- **TC_CLI_012**: precondition_score 計算正確（30 × 滿足比例）
  - Given: agent 有 2 個 preconditions，其中 1 個已滿足
  - When: 計算 precondition_score
  - Then: 分數 = 30 × 0.5 = 15

- **TC_CLI_013**: phase_match_score 全分或零分（20 分或 0）
  - Given: ticket.tdd_stage=[phase3b]，agent.tdd_phases=[phase3b]
  - When: 計算 phase_match_score
  - Then: 分數 = 20

- **TC_CLI_014**: file_conflict_penalty 為 -100（致命衝突）
  - Given: agent A 的 file_patterns 與並行 agent B 有交集
  - When: 計算衝突懲罰
  - Then: 分數 -= 100，最終分數可能為負

- **TC_CLI_015**: 總分 = type_match + precondition + phase_match - conflict_penalty
  - Given: 各項分數為 40 + 30 + 20 - 0
  - When: 計算總分
  - Then: total = 90

- **TC_CLI_016**: 滿分評分（所有條件都符合）
  - Given: Ticket 已完成所有先前 Phase，agent 接受所有必要 artifact
  - When: 計算評分
  - Then: 分數接近 90（無衝突），或最多 100

- **TC_CLI_017**: 零分評分（無任何符合）
  - Given: agent 的 tdd_phases 與 ticket.tdd_stage 不符合
  - When: 計算評分
  - Then: 分數 = 0

- **TC_CLI_018**: 負分評分（衝突造成致命懲罰）
  - Given: 存在 file_conflict_penalty = -100
  - When: 計算總分
  - Then: 分數 < 0（如 90 - 100 = -10）

- **TC_CLI_019**: 評分範圍驗證（通常 0-100，可能 < 0）
  - Given: 各種評分組合
  - When: 計算所有可能的分數
  - Then: 最大 ≈ 100，最小可能 < 0

- **TC_CLI_020**: 浮點數精度（分數計算中的四捨五入）
  - Given: type_match = 40 × 0.33333...
  - When: 計算並輸出
  - Then: 四捨五入到小數點第 2 位（如 13.33）

#### 豁免碼處理（TC_CLI_021-025）

- **TC_CLI_021**: dry-run 掃描所有 Ticket 並統計符合率
  - Given: 執行全量 dry-run
  - When: 掃描 100 個 Ticket，其中 95 個符合

## 5. 測試環境與 Mock 設計

### 5.1 Mock 策略

| 物件 | Mock 方式 | 理由 |
|------|---------|------|
| registry.yaml | 使用 fixture YAML + in-memory parse | Registry 是靜態資料，直接讀取測試檔案 |

| Hook 環境 | 模擬 settings.json 和 Hook 掛載點 | 測試 Hook 註冊和觸發，不執行實際工作流 |

## 8. 補充說明

### 8.1 測試設計決策

**為什麼優先測試衝突檢查？**
- 衝突檢查是 Hook 系統的核心，涉及派發安全
- ARCH-005 回溯測試驗證已知 bug 的修復
- 三種衝突互不重疊，各自獨立驗證

**為什麼 dispatch recommend 用整合測試？**
- CLI 依賴 registry.yaml 解析、Ticket 資料、評分演算法
- Unit 測試評分公式、Integration 測試 CLI 與 registry 互動
- dry-run 是統計驗證（符合率）而非 case-by-case 測試

**為什麼需要 ARCH-005 回溯測試？**
- ARCH-005 是已知的實作問題（歷史案例）
- 回溯測試驗證新 Hook 能正確偵測已知衝突
- 防止同一問題復發
