## 1. 實作策略設計

### 1.1 整體實作思路

此機制的核心是在建立 Ticket 前，自動掃描同版本的 pending Ticket，使用相似度算法比對標題和目標描述，若發現相似則輸出 WARNING 提醒使用者。

**關鍵特性**：
- 非阻塞式設計（WARNING 不阻止建立）
- 容錯設計（內部錯誤靜默通過）
- 簡化實作（使用 Jaccard 係數，無外部依賴）

### 1.2 虛擬碼流程

```
執行 ticket create 命令
    |
    v
[Phase 2] 解析參數、驗證 ID 格式、驗證欄位
    |
    v
[Phase 3] 驗證 blockedBy 引用和循環依賴
    |
    v
[新增] 呼叫 detect_duplicate_tickets()
    |
    +── try:
    |   |
    |   +── 呼叫 list_tickets(version)
    |   |   └─ 返回同版本所有 Ticket
    |   |
    |   +── 過濾 pending 狀態的 Ticket
    |   |   └─ 過濾條件：status == "pending"
    |   |   └─ 排除條件：ticket_id == new_ticket_id（自身排除）
    |   |
    |   +── 初始化相似列表（empty）
    |   |
    |   +── 迴圈 pending 清單：
    |   |   |
    |   |   +── 合併 candidate.title + candidate.what
    |   |   |
    |   |   +── 呼叫 calculate_jaccard_similarity(
    |   |   |       (new_title + new_what),
    |   |   |       (candidate_text)
    |   |   |   )
    |   |   |
    |   |   +── 若相似度 >= THRESHOLD（0.3）：
    |   |   |       加入相似列表
    |   |   |
    |   |   +── 若相似度計算拋出例外：
    |   |           跳過此 Ticket，繼續下一個
    |   |
    |   +── 若相似列表非空：
    |       格式化警告訊息並輸出
    |       遍歷相似列表，逐個列出 Ticket ID + 標題
    |
    +── except (任何例外):
        靜默捕捉，無輸出（重複偵測是輔助功能）
    |
    v
[Phase 4] 儲存 Ticket 檔案（不受偵測結果影響）

    v

```

## 2. 資料結構選擇

### 2.1 相似度計算資料結構

**演算法選擇**：Jaccard 係數（集合交集 / 聯集）

**優點**：
- 無外部依賴（純 Python 集合操作）
- 計算複雜度 O(n)，對少量 Ticket 無效能疑慮
- 對中文友善（以字元為最小單位）
- 閾值易於調整

**實作方式**：
```
1. 將文字合併（title + " " + what）
2. 分割為詞集合（中文以字元分割，英文以空白分割）
3. 計算交集大小 / 聯集大小
4. 返回 float [0.0, 1.0]
```

### 2.2 相似 Ticket 集合結構

**儲存格式**：列表，每項包含 `(ticket_id, title)`

```
similar_tickets = [
    ("0.1.2-W3-001.2", "實作 SRP 自動偵測機制"),
    ("0.1.2-W3-002", "新增 SRP 偵測功能")
]
```

**選擇理由**：
- 順序保持發現順序（便於除錯）
- 包含 ID 和標題，足以輸出 WARNING
- 便於迴圈組裝訊息

## 5. 關鍵實作指引

### 5.1 第一階段目標：核心演算法

**目標測試**：
- U-001：完全相同文字 → 返回 1.0
- U-002：完全不同 → 返回 0.0
- U-003：部分重疊（中文） → 約 0.33
- U-004：部分重疊（英文） → 約 0.33

**實作步驟**：

1. **文字分割函式**（私有）
   - 輸入：字串
   - 輸出：詞集合
   - 邏輯：
     ```
     遍歷字元：
     - 若是中文字 → 逐個加入集合
     - 若是英文 → 累積成單詞，遇到空白/標點時加入集合
     - 標點符號 → 忽略
     ```

2. **Jaccard 計算函式** `_calculate_jaccard_similarity(text_a, text_b)`
   - 輸入：text_a, text_b（字串）
   - 輸出：float [0.0, 1.0]
   - 邏輯：
     ```
     set_a = tokenize(text_a)
     set_b = tokenize(text_b)

     if both sets empty → return 0.0 (or 1.0, 需設計決定)

     intersection = len(set_a & set_b)
     union = len(set_a | set_b)

     return intersection / union if union > 0 else 0.0
     ```

3. **邊界情境**（必須在實作時澄清設計決定）
   - 空字串 vs 空字串 → 定義為 0.0 或 1.0？
   - 大小寫差異 → 區分還是忽略？（建議不區分以提高容錯）
   - 特殊字符 → 保留還是去除？（建議去除）

4. **異常處理**
   - None 輸入 → 拋出 TypeError（由外層捕捉）
   - 非字串輸入 → 嘗試轉換或拋出 TypeError

**優先順序**：核心演算法 > 邊界細節 > 異常邊界

### 5.2 第二階段目標：重複偵測邏輯整合

**目標測試**：
- B-001：發現單個相似 Ticket → 輸出 WARNING
- B-003：無相似 Ticket → 靜默通過
- B-011：list_tickets 例外 → 靜默通過

**實作步驟**：

1. **實作 `_detect_duplicate_tickets()` 函式**
   - 簽名：`_detect_duplicate_tickets(version, new_title, new_what, new_ticket_id) -> None`
   - 不拋出例外（所有例外內部捕捉）

2. **核心邏輯順序**
   ```
   Step A: 驗證輸入
   - if not new_title and not new_what:
     靜默返回（無可比對文字）

   Step B: 載入 pending Ticket
   - pending_list = list_tickets(version)
   - 過濾：ticket.status == "pending"
   - 排除：ticket.id == new_ticket_id

   Step C: 相似度計算
   - new_combined = new_title + " " + new_what
   - similar_tickets = []
   - for ticket in pending_list:
     combined = ticket.title + " " + ticket.what
     similarity = _calculate_jaccard_similarity(new_combined, combined)
     if similarity >= DUPLICATE_DETECTION_THRESHOLD:
       similar_tickets.append((ticket.id, ticket.title))

   Step D: 輸出結果
   - if similar_tickets:
     print(format_warning(...))
   ```

3. **異常處理策略**
   ```
   try:
       [Step A-D]
   except Exception:
       # 靜默通過，記錄到日誌（可選）
       pass
   ```

4. **訊息格式化**（使用 `command_lifecycle_messages.py` 的常數）
   ```
   [WARNING] 發現 {count} 個可能重複的 pending Ticket，請確認是否需要建立新 Ticket：
      - 0.1.2-W3-001.2: 實作 SRP 自動偵測機制
      - 0.1.2-W3-002: 新增 SRP 偵測功能
      建議：執行 /ticket track list 查看所有現有 Ticket 後再決定
   ```

**優先順序**：邏輯正確 > 訊息格式 > 異常邊界案例

### 5.3 第三階段目標：整合至 execute() 和常數定義

**目標測試**：
- I-001：呼叫時機驗證（blockedBy 後、save 前）

## 6. 權宜方案與技術債務

### 6.1 最小可行實作

本實作採用最小化原則，專注於核心偵測機制的正確性：

1. **演算法簡化**
   - 使用 Jaccard 係數而非複雜的 NLP 算法
   - 文字分割採用簡單的字元/單詞分割
   - 不做語意分析或近音詞處理

2. **效能優化暫緩**
   - 不使用快取機制（每次都新鮮載入）
   - 不使用異步處理（順序執行）
   - 預期 pending tickets < 50 個，效能無問題

3. **UI 簡化**
   - 警告訊息為純文字格式
   - 不提供互動式選擇（使用者自行決定）

### 6.2 已知限制

| 限制項 | 說明 | 影響 | Phase 4 建議 |
|--------|------|------|-------------|
| 無語意分析 | 只看字面重疊，不理解含義 | 可能遺漏同義但用詞不同的重複 | Phase 4 可考慮 NLP 提升 |
| 固定閾值 | 0.3 可能不適用所有場景 | 需根據實測反饋微調 | Phase 4 動態閾值或 A/B 測試 |
| 無快取 | 每次都掃全部 pending Ticket | 大量 Ticket 時可能變慢 | Phase 4 引入快取機制 |
| 無歷史追蹤 | 不記錄被警告過的 Ticket 對 | 同一對重複可能重複提示 | Phase 4 學習機制 |

### 6.3 技術債務標記

以下為 Phase 4 重構時的候選改善點：

1. **偵測演算法升級**
   - 目標：支援模糊匹配（同義詞、近音）
   - 工作量：中等（需引入 NLP 套件或自訓練模型）
   - 優先級：低（目前 Jaccard 已足夠）

2. **效能最佳化**
   - 目標：快取 pending tickets 清單，減少磁碟讀取
   - 工作量：低（在 execute 生命週期內快取）
   - 優先級：低（目前無效能問題）

3. **閾值動態調整**
   - 目標：根據 warning/false positive 比例自動調整
   - 工作量：高（需機器學習或使用者反饋回環）
   - 優先級：低（先用 0.3 驗證有效性）

4. **智慧建議**
   - 目標：不止警告，還建議用戶確實要建立還是修改現有
   - 工作量：高（需整合 CLI 確認邏輯）
   - 優先級：低（非關鍵功能）

## 7. 語言特定實作注意事項

### 7.1 Python 考量

**字元編碼**：
- 中文字符使用 Unicode 編碼，正常透過 `for char in text` 遍歷
- 英文單詞需用正則表達式分割（`\w+`）
- 特殊字符和標點需過濾或忽略

**正則表達式**：
```python
import re
# 提取英文單詞和中文字符
pattern = r'[\w\u4e00-\u9fff]+'  # 英文單詞 + 中文
tokens = re.findall(pattern, text)
```

**集合操作**：
- Python 的 `set` 支援交集 `&` 和聯集 `|`
- 轉換為小寫可用 `.lower()` 確保大小寫不敏感

**型別檢查**：
- 使用 `isinstance(text, str)` 驗證輸入型別
- 靜態型別提示使用 `def func(a: str, b: str) -> float:`

**異常捕捉**：
- 使用 `except Exception:` 捕捉所有異常（過寬但符合設計需求）
- 可選：紀錄異常到 logger（如 `logger.debug(...)`）但不輸出給使用者

### 7.2 效能最佳實踐

**避免重複計算**：
```python
# 不建議
new_combined = new_title + " " + new_what  # 迴圈內重複
for ticket in tickets:
    similarity = calculate(new_combined, ...)  # new_combined 固定

# 建議
new_combined = new_title + " " + new_what  # 迴圈外計算一次
for ticket in tickets:
    similarity = calculate(new_combined, ...)
```

**集合轉換一次**：
```python
# 不建議
set_a = set(tokens_a)  # 迴圈內重複建立集合
set_b = set(tokens_b)

# 建議
set_a = set(tokens_a)  # 迴圈外建立
for ticket in tickets:
    set_b = set(tokenize(ticket.combined))
    similarity = len(set_a & set_b) / len(set_a | set_b)
```

### 7.3 測試相關

**Mock 設置**：
- 使用 `pytest-mock` 的 `mocker.patch()` 模擬 `list_tickets()`
- 使用 `capsys` 驗證 print 輸出

**測試資料**：
- 使用 fixture 提供重複 pending tickets 清單
- 使用參數化測試 (`@pytest.mark.parametrize`) 覆蓋多個相似度案例

### 9.3 手動驗證清單

## 12. 風險預防與緊急應變

### 12.1 可能遇到的問題與解決方案

**問題 1：相似度計算太慢**
- 症狀：50 個 pending tickets 時計算 > 100ms
- 原因：文字分割或集合操作低效
- 解決：優化文字分割邏輯或使用 set 推導式

**問題 2：中文分割不完整**
- 症狀：某些中文組合無法正確分割
- 原因：正則表達式模式不夠全面
- 解決：擴展 Unicode 範圍或使用 jieba（如可引入外部套件）

**問題 3：誤報太多（警告疲勞）**
- 症狀：許多實際無關的 Ticket 被標記為相似
- 原因：閾值 0.3 過低
- 解決：提升閾值至 0.4 或優化分割方式

**問題 4：相似 Ticket 被遺漏**
- 症狀：確實重複的 Ticket 沒被偵測到
- 原因：閾值 0.3 過高或文字分割過度
- 解決：降低閾值至 0.25 或改進演算法

### 12.2 升級條件

若遇到以下情況，應升級至 PM：

1. **設計衝突**：Phase 3b 發現相似度演算法無法滿足邊界條件
2. **技術困難**：Python 正則表達式無法有效分割特定語言組合
3. **效能瓶頸**：優化後仍無法達到 100ms 目標
4. **需求變更**：使用者反饋發現現有設計存在根本缺陷
