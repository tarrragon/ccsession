# 0.1.2-W1-005 Phase 1 功能規格設計

## 1. 功能需求分析

### 1.1 核心問題

Ticket frontmatter 缺乏版本號，導致 schema 演進時無法區分新舊 ticket。具體問題案例：

- `direction` 欄位格式從 `"to-sibling"` 演進為 `"to-sibling:target_id"` 時，舊程式碼精確匹配失敗（IMP-011 根因）
- 新增 `tdd_phase`、`creation_accepted` 等欄位時，舊 ticket 缺少欄位，消費端無法判斷應使用預設值還是視為無效

### 1.2 使用者場景

**場景 A（系統管理員執行遷移）**：
- 前置條件：專案存在大量無 `protocol_version` 欄位的舊 ticket
- 操作：執行 dry-run 驗證腳本
- 期望結果：所有舊 ticket 的遷移成功率 100%，驗證報告清楚列出成功數、格式異常數和異常原因

**場景 B（代理人載入 ticket）**：
- 前置條件：ticket 的 `protocol_version` 為 "1.0" 或缺失
- 操作：呼叫 ticket 載入函式
- 期望結果：自動完成版本遷移，消費端得到符合 v2.0 schema 的資料，無需感知遷移過程

**場景 C（新 ticket 建立）**：
- 前置條件：使用者執行 `/ticket create`
- 操作：系統建立新 ticket
- 期望結果：新 ticket frontmatter 自動包含 `protocol_version: "2.0"` 欄位

**場景 D（格式異常 ticket 載入）**：
- 前置條件：ticket 的 `protocol_version` 為非標準格式（如 "v2.0"、"2" 或空字串）
- 操作：Hook 偵測到異常格式
- 期望結果：輸出 WARNING 級別訊息，不阻止操作，記錄雙通道日誌

## 2. 功能規格設計

### 2.1 protocol_version 欄位定義

**型別**：字串（`str`）

**格式**：`"Major.Minor"`
- `Major`：非負整數，代表主版本號
- `Minor`：非負整數，代表次版本號
- 分隔符：英文句號 `.`

**初始值**：`"1.0"`（用於描述無 `protocol_version` 欄位的舊 ticket 的版本）

**當前版本**：`"2.0"`（v0.1.2 實作後的所有新 ticket 使用此版本）

**有效範例**：
```
"1.0"   - 舊版 ticket（無 protocol_version 欄位時推斷）
"2.0"   - 目前版本（v0.1.2 後新建 ticket）
"2.1"   - 未來向後相容新增時遞增 Minor
"3.0"   - 未來破壞性改變時遞增 Major
```

**無效範例（格式異常）**：
```
"v2.0"  - 含 v 前綴
"2"     - 缺少 Minor 號
"2.0.1" - 包含 Patch 號（不支援三層）
""      - 空字串
null    - null 值
```

### 2.2 版本號語義（Major.Minor）

| 版本類型 | 遞增條件 | 範例 |
|---------|---------|------|
| **Major** | 破壞性改變：欄位刪除、欄位語義重定義、必填欄位新增（不向後相容） | 1.0 → 2.0 |
| **Minor** | 向後相容新增：可選欄位新增、欄位可接受值擴充（舊值仍有效） | 2.0 → 2.1 |

**不遞增版本的情況**：
- 欄位描述文字修正
- 工作日誌內容更新（frontmatter 不變）
- 無 schema 影響的功能修復

**設計決策：為何採用 Major.Minor 而非 Major.Minor.Patch（三層）**

採用兩層版本號的理由：
1. Ticket frontmatter schema 的 Patch 層修復（如拼寫修正）對消費端沒有行為影響，無需版本追蹤
2. 三層版本增加解析複雜度，而遷移邏輯只需要區分 Major 層（決定遷移函式）和 Minor 層（決定相容性警告）
3. 簡化遷移鏈：`v1.x.y → v2.0` 優於 `v1.x.y → v1.x.(y+1) → v2.0`

### 2.3 frontmatter schema 變更

**新增欄位位置**：在 `id` 欄位之後、`title` 之前（frontmatter 第二行）

**標準新 ticket frontmatter 範例**：
```yaml
---
id: 0.1.2-W1-001
protocol_version: "2.0"
title: 範例 Ticket
type: IMP
status: pending
...
---
```

**舊 ticket（無 protocol_version）**：
```yaml
---
id: 0.1.0-W1-001
title: 舊 Ticket（無版本欄位）
type: IMP
status: completed
...
---
```

載入時推斷 `protocol_version` 為 `"1.0"` 並執行 v1→v2 遷移。

## 3. API / 介面定義

### 3.1 constants.py 新增常數

在 `.claude/skills/ticket/ticket_system/lib/constants.py` 的 `TDD_PHASES` 常數之後新增以下常數區塊：

```python
# ============================================================
# Protocol Version 版本控制常數
# ============================================================

# 當前使用的 Protocol Version
# Major = 破壞性改變，Minor = 向後相容新增
# v0.1.2 引入此版本控制機制，現有 ticket schema 定義為 v2.0
# 舊版 ticket（無 protocol_version 欄位）自動視為 v1.0 並遷移至 v2.0
PROTOCOL_VERSION_CURRENT: str = "2.0"

# 舊版 ticket 的預設版本（無 protocol_version 欄位時推斷使用）
PROTOCOL_VERSION_DEFAULT: str = "1.0"

# 所有受支援的 Protocol Version 清單（用於 Hook 驗證）
PROTOCOL_VERSIONS_SUPPORTED: list[str] = ["1.0", "2.0"]

# Protocol Version 格式驗證正則表達式
# 有效格式：Major.Minor（如 "2.0", "1.0", "2.1"）
# 不支援：含 v 前綴、三層版本、空字串
PROTOCOL_VERSION_PATTERN: str = r"^\d+\.\d+$"

# 預編譯正則表達式
PROTOCOL_VERSION_RE = re.compile(PROTOCOL_VERSION_PATTERN)
```

**常數用途說明**：

| 常數名稱 | 型別 | 用途 |
|---------|------|------|
| `PROTOCOL_VERSION_CURRENT` | `str` | 新建 ticket 使用的版本號；遷移的目標版本 |
| `PROTOCOL_VERSION_DEFAULT` | `str` | 舊 ticket 缺少欄位時的推斷版本 |
| `PROTOCOL_VERSIONS_SUPPORTED` | `list[str]` | Hook 驗證時的允許版本清單 |
| `PROTOCOL_VERSION_PATTERN` | `str` | 版本格式的正則字串（供文件引用） |
| `PROTOCOL_VERSION_RE` | `re.Pattern` | 預編譯正則（供驗證函式直接使用） |

### 3.2 migrate_ticket() 函式規格

**模組位置**：`.claude/skills/ticket/ticket_system/lib/migrations.py`（新建模組）

**函式簽名**：

```python
def migrate_ticket(ticket_data: dict) -> dict:
    """
    將 ticket 資料遷移至當前 Protocol Version。

    無副作用：輸入 dict 不被修改，回傳新的 dict。

    遷移邏輯：
      - 無 protocol_version 欄位 → 視為 v1.0，執行 v1→v2 遷移
      - protocol_version == "1.0" → 執行 v1→v2 遷移
      - protocol_version == "2.0" → 無需遷移，原樣回傳（copy）
      - 其他已知版本 → 執行對應遷移鏈
      - 格式異常版本號 → 回傳原資料（copy），附加 _migration_warning 欄位

    Args:
        ticket_data: 從 YAML frontmatter 解析的 dict，可能含或不含 protocol_version

    Returns:
        遷移後的 ticket dict（新物件），包含 protocol_version 欄位。
        遷移成功時不含額外欄位。
        格式異常時含 _migration_warning: str 欄位（以底線開頭，非 schema 欄位）。

    Raises:
        無（所有異常情況以 _migration_warning 回報，不拋出例外）
    """
```

**行為規格（所有分支）**：

| 輸入 protocol_version | 輸出 protocol_version | 行為 |
|----------------------|----------------------|------|
| 無此欄位 | `"2.0"` | 執行 `_migrate_v1_to_v2()`，所有原有欄位保留 |
| `"1.0"` | `"2.0"` | 執行 `_migrate_v1_to_v2()`，所有原有欄位保留 |
| `"2.0"` | `"2.0"` | 原樣回傳（dict 淺拷貝，不含 _migration_warning） |
| 格式異常（如 `"v2.0"`、`"2"`） | 不變 | 回傳淺拷貝，附加 `_migration_warning` 欄位 |
| 未來支援的版本（如 `"2.1"`） | 視遷移鏈 | 執行對應版本的遷移函式 |

**_migrate_v1_to_v2() 內部函式規格**：

```python
def _migrate_v1_to_v2(ticket_data: dict) -> dict:
    """
    執行 v1.0 → v2.0 的遷移。

    v1.0 → v2.0 遷移規則：
      - 保留所有原有欄位（100% 無資訊遺失）
      - 新增 protocol_version: "2.0"
      - 無其他欄位增刪或語義變更

    設計決策：v1→v2 遷移只加欄位不刪欄位，確保向後相容。

    Returns:
        新的 dict，包含所有原有欄位加上 protocol_version: "2.0"
    """
```

**v1.0 → v2.0 欄位對應表**：

| 欄位 | v1.0（舊 ticket） | v2.0（遷移後） | 說明 |
|------|-----------------|--------------|------|
| `protocol_version` | 不存在 | `"2.0"` | 新增 |
| `id` | 原值 | 原值 | 保留 |
| `title` | 原值 | 原值 | 保留 |
| `type` | 原值 | 原值 | 保留 |
| `status` | 原值 | 原值 | 保留 |
| `version` | 原值 | 原值 | 保留 |
| 所有其他欄位 | 原值 | 原值 | 保留 |

**無資訊遺失保證**：遷移後的 dict 必須滿足 `all(k in migrated for k in original)` 為 True。

### 3.3 protocol-version-check-hook 行為規格

**檔案位置**：`.claude/hooks/protocol-version-check-hook.py`（新建）

**Hook 類型**：PostToolUse

**觸發條件**：工具名稱為 `Read`，且讀取的檔案路徑符合 ticket 檔案模式（位於 `docs/work-logs/` 下的 `.md` 檔案）

**觸發時機選擇的設計決策**：

採用「載入時（PostToolUse Read）」而非「寫入時（PreToolUse Write）」觸發遷移的理由：
1. 讀取比寫入更頻繁，可確保每次使用 ticket 資料前都經過版本檢查
2. 避免在寫入時修改欄位，造成「預期寫入 A，實際寫入 A + 隱式欄位 B」的意外副作用
3. 遷移為在記憶體中進行（不實際修改檔案），降低誤修改 ticket 檔案的風險
4. 未來若需要持久化遷移，可由獨立的遷移腳本（005.4）執行，Hook 僅負責運行時轉換

**Hook 行為流程**：

```
PostToolUse (Read) 觸發
    |
    v
路徑是否為 ticket 檔案（docs/work-logs/**/*.md）？
    |
    +-- 否 → 靜默跳過（exit 0）
    |
    +-- 是 → 解析檔案的 YAML frontmatter
        |
        v
    解析成功？
        |
        +-- 否（YAML 格式錯誤）→ 輸出 WARNING（雙通道），不阻止
        |
        +-- 是 → 讀取 protocol_version 欄位
            |
            v
        欄位存在且格式有效（符合 PROTOCOL_VERSION_PATTERN）？
            |
            +-- 否（欄位不存在）→ 輸出 INFO: "偵測到 v1.0 ticket，建議執行遷移"，不阻止
            |
            +-- 否（格式異常）→ 輸出 WARNING: "protocol_version 格式無效: {value}"，不阻止
            |
            +-- 是 → 版本號在 PROTOCOL_VERSIONS_SUPPORTED 清單中？
                |
                +-- 否 → 輸出 WARNING: "不支援的版本: {version}"，不阻止
                |
                +-- 是 → 版本號等於 PROTOCOL_VERSION_CURRENT？
                    |
                    +-- 是 → 輸出 INFO: "protocol_version 已是最新版本 ({version})"（可靜默）
                    |
                    +-- 否 → 輸出 INFO: "ticket 版本 {current} 低於當前版本 {latest}，建議執行遷移"
```

**輸出級別規範**：

| 情況 | 輸出級別 | 輸出通道 | 阻止操作 |
|------|---------|---------|---------|
| 版本已是最新 | INFO（可選） | stdout | 否 |
| 版本低於當前（舊 ticket） | INFO | stdout + 日誌檔 | 否 |
| 格式異常 | WARNING | stderr + 日誌檔 | 否 |
| YAML 解析失敗 | WARNING | stderr + 日誌檔 | 否 |
| 不支援的版本 | WARNING | stderr + 日誌檔 | 否 |

**雙通道可觀測性要求**（遵循 quality-baseline.md 規則 4）：
- WARNING 級別訊息必須同時輸出至 stderr（用戶可見）和日誌檔（`~/.claude/hooks/protocol-version-check/`）
- INFO 級別訊息只需輸出至 stdout 和日誌檔
- 禁止靜默吞掉任何異常情況

## 4. 遷移規則細節

### 4.1 v1.0（無 protocol_version）→ v2.0 的欄位對應

**遷移觸發判斷**：`ticket_data.get("protocol_version", PROTOCOL_VERSION_DEFAULT) == "1.0"`

**遷移操作（唯一操作）**：

```python
result = dict(ticket_data)        # 淺拷貝，保留所有原有欄位
result["protocol_version"] = PROTOCOL_VERSION_CURRENT  # 新增 "2.0"
return result
```

**保留欄位的明確說明**：v1→v2 遷移不刪除、不重命名、不修改任何現有欄位的值。舊 ticket 若有欄位 X，遷移後仍有欄位 X 且值不變。

### 4.2 遷移過程的錯誤處理

**格式異常的定義**：`protocol_version` 欄位存在但不符合 `PROTOCOL_VERSION_PATTERN`（如 `"v2.0"`、`"2"`、`""`、整數 `2`）

**處理方式**：

```python
# 格式異常時的回傳值
result = dict(ticket_data)  # 淺拷貝，保留原有資料
result["_migration_warning"] = (
    f"protocol_version 格式異常: '{ticket_data.get('protocol_version')}'. "
    f"有效格式為 Major.Minor（如 '2.0'）。"
    f"此 ticket 未執行遷移，資料保持原狀。"
)
return result
```

**設計決策：為何不拋出例外**：
- 遷移失敗不應阻止 ticket 系統繼續運作（操作優先，修復次之）
- `_migration_warning` 欄位以底線開頭標記為非 schema 欄位，便於消費端偵測
- Hook 負責將 WARNING 輸出至使用者可見通道

**欄位缺失的定義**：`"protocol_version"` 鍵不存在於 `ticket_data` dict 中

**處理方式**：視同 v1.0，正常執行遷移。

### 4.3 向後相容保證

**保證內容**：

1. 所有 v1.0 ticket 可 100% 遷移至 v2.0，無資訊遺失
2. 遷移後的 ticket 仍可被期待 v1.0 格式的程式碼讀取（因為只新增欄位，不刪除）
3. `migrate_ticket()` 函式為純函式（pure function）：無副作用、相同輸入永遠產生相同輸出
4. 遷移不寫入磁碟（只在記憶體中進行），ticket .md 檔案不被自動修改

**測試可驗證性**：

```python
# 向後相容保證的可驗證形式
def test_no_information_loss(original: dict):
    migrated = migrate_ticket(original)
    for key, value in original.items():
        assert key in migrated
        assert migrated[key] == value
```

| 驗收條件 | 驗證方法 | 成功標準 |
|---------|---------|---------|
| 所有現存 ticket 皆已驗證 | 驗證報告的「已掃描數」等於 `find docs/work-logs -name "*.md" -path "*/tickets/*" | wc -l` | 數量一致 |
| 遷移成功率 100% | 驗證報告的「成功數」等於「已掃描數」- 「格式異常數」| 成功數 + 異常數 = 總數 |
| 格式異常有明確錯誤訊息 | 驗證報告中每個異常 ticket 有對應原因說明 | 無「未知異常」條目 |
| 無資訊遺失 | 對 10 個 ticket 抽樣確認遷移前後欄位一致 | 所有抽樣欄位不變 |
| 驗證報告格式完整 | 確認報告包含：已掃描數、成功數、格式異常數、各異常原因分類 | 四個項目均存在 |

### 5.5 dry-run 成功判定規則

**成功條件（全部滿足）**：

1. 遷移成功率 = (成功數 / 已掃描數) × 100% 達到 **100%**（格式異常 ticket 不計入成功率分母）
2. 驗證報告可正常產出（腳本執行不崩潰）
3. 格式異常 ticket 有明確分類（不接受「未知異常」）

**失敗條件（任一觸發）**：

1. 任何 ticket 遷移後欄位值被修改或遺失
2. 腳本在任一 ticket 上拋出未捕獲例外
3. 驗證報告顯示成功率低於 100%（排除格式異常後）

**格式異常 ticket 的說明**：格式異常 ticket（`protocol_version` 格式不符合 `PROTOCOL_VERSION_PATTERN`）記錄在報告的「異常分類」區塊，不計入「遷移失敗」，因為異常 ticket 的資料不被修改（保留原狀）。

## 6. 行為場景（Given-When-Then）

### 場景 1：舊 ticket 載入遷移（正常流程）

```
Given: 存在一個無 protocol_version 欄位的 ticket dict，含 12 個原有欄位
When: 呼叫 migrate_ticket(ticket_data)
Then: 回傳的 dict 包含 protocol_version = "2.0"
  And: 原有 12 個欄位的值完全不變
  And: 回傳 dict 不是輸入 dict 的同一物件
```

### 場景 2：已是最新版本（無需遷移）

```
Given: 存在一個 protocol_version = "2.0" 的 ticket dict
When: 呼叫 migrate_ticket(ticket_data)
Then: 回傳的 dict 與輸入 dict 內容完全一致
  And: 不含 _migration_warning 欄位
```

### 場景 3：格式異常版本號（異常流程）

```
Given: 存在一個 protocol_version = "v2.0" 的 ticket dict
When: 呼叫 migrate_ticket(ticket_data)
Then: 回傳的 dict 含 _migration_warning 欄位
  And: 原有欄位值不變（包含 protocol_version = "v2.0"）
  And: 不拋出任何例外
```

### 場景 4：Hook 偵測舊 ticket（INFO 提示）

```
Given: 代理人讀取位於 docs/work-logs/ 的舊 ticket 檔案（無 protocol_version 欄位）
When: PostToolUse Read Hook 觸發
Then: 終端機輸出 INFO: "偵測到 v1.0 ticket"
  And: Hook exit code 為 0（不阻止操作）
  And: 日誌檔有對應記錄
```

### 場景 5：Hook 偵測格式異常（WARNING）

```
Given: 存在一個含 protocol_version = "v2.0" 的 ticket 檔案
When: PostToolUse Read Hook 觸發後讀取此檔案
Then: stderr 輸出 WARNING: "protocol_version 格式無效: 'v2.0'"
  And: Hook exit code 為 0（不阻止操作）
  And: 日誌檔有 WARNING 記錄
```

### 場景 6：讀取非 ticket 檔案（靜默跳過）

```
Given: 代理人讀取 README.md 或 .claude/rules/ 下的規則檔案
When: PostToolUse Read Hook 觸發
Then: Hook 靜默跳過，無任何輸出
  And: Hook exit code 為 0
```

### 場景 7：dry-run 驗證全量 ticket（邊界條件）

```
Given: docs/work-logs/ 下存在 N 個 ticket，其中 M 個無 protocol_version，K 個格式異常
When: 執行 dry-run 驗證腳本
Then: 驗證報告顯示已掃描 N 個 ticket
  And: 遷移成功數 = N - K
  And: 格式異常數 = K
  And: 每個格式異常 ticket 有明確原因說明
  And: 所有 M 個舊 ticket 的原有欄位在遷移後保持不變
```

## 7. 設計決策記錄

### 決策 1：Major.Minor 而非 Major.Minor.Patch

**決策**：採用兩層版本號（`"2.0"` 而非 `"2.0.0"`）

**理由**：
- Ticket schema 的修復層（Patch）不影響消費端行為，無需版本追蹤
- 遷移邏輯只需識別 Major 層（決定是否需要遷移）和 Minor 層（決定相容性警告）
- 簡化 `PROTOCOL_VERSION_PATTERN` 和版本比較邏輯

**取捨**：若未來需要 Patch 層追蹤，可將 `"2.0"` 語義延伸為 `"2.0.0"`，並調整 `PROTOCOL_VERSION_PATTERN`。因為 Minor 層遞增不破壞相容性，此變更只需遞增 Minor（`"2.0"` → `"2.1"`），不需 Major 遞增。

### 決策 2：遷移在載入時（記憶體中）而非寫入時（磁碟持久化）

**決策**：Hook 在 PostToolUse Read 時進行版本偵測，`migrate_ticket()` 在記憶體中轉換，不自動修改磁碟上的 .md 檔案

**理由**：
1. 自動修改磁碟檔案有較高風險（一旦誤修改，需要 git 回滾）
2. 記憶體中遷移對消費端透明，不需要每個 ticket .md 檔案都有 `protocol_version` 欄位
3. 真正的持久化遷移由 005.4 dry-run 腳本主動執行，使用者有機會確認後再持久化

**取捨**：ticket .md 檔案本身不自動更新，若未來需要磁碟持久化，需另行設計寫入流程。

### 決策 3：格式異常不拋出例外

**決策**：格式異常的 `protocol_version` 以 `_migration_warning` 欄位回報，而非拋出 `ValueError`

**理由**：
- Ticket 系統的操作應優先於格式修正（不能讓格式問題阻止工作）
- `_migration_warning` 底線前綴標記為非 schema 欄位，消費端可以選擇性處理
- Hook 負責將 WARNING 輸出至使用者可見通道，不依賴例外傳播

**取捨**：消費端若沒有明確檢查 `_migration_warning`，可能無感知地使用異常資料。緩解措施：Hook 的 stderr WARNING 確保使用者可見。

### 決策 4：初始版本值為 "1.0" 而非 "0.1"

**決策**：舊 ticket 的推斷版本為 `"1.0"`，現有版本為 `"2.0"`

**理由**：
- v0.1.2 之前的 ticket 已是穩定的生產格式（雖未標記版本），定義為 v1.0 語義上合理
- 從 v1.0 升至 v2.0 表示引入了版本控制機制本身（這是一個「結構性」改變，屬於 Major 遞增）
- 使用 "0.x" 可能造成與 monorepo 版本號混淆
