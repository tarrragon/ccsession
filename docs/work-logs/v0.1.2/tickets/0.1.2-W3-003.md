## Problem Analysis

### 問題根因

PC-013 案例 2：PM 建立修復 Ticket 前未查詢既有 pending tickets，導致與 W3-001.2 重複建立。根因是「重複查詢」完全依賴人工記憶，缺乏系統化防護，且 `ticket create` 命令本身不提供任何重複警示。

### 影響範圍

- `.claude/skills/ticket/ticket_system/commands/create.py`：新增 `_detect_duplicate_tickets()` 和 `_calculate_jaccard_similarity()` 私有函式，並在 `execute()` 中整合呼叫
- `.claude/skills/ticket/ticket_system/lib/constants.py`：新增 `DUPLICATE_DETECTION_THRESHOLD` 常數
- `.claude/skills/ticket/ticket_system/lib/command_lifecycle_messages.py`：在 `CreateMessages` 中新增重複偵測 WARNING 訊息常數

### 相關 Error Pattern

- PC-013：PM 建立重複 Ticket 錯誤模式

---

## Solution

### Phase 1 設計摘要（2026-03-23）

已完成 Phase 1 功能規格設計，設計文件位於：
`docs/work-logs/v0.1.2/tickets/0.1.2-W3-003-phase1-design.md`

**核心設計決策**：

1. **整合點**：在 `execute()` 的 blockedBy 驗證後、`save_ticket()` 前執行重複偵測
2. **相似度演算法**：Jaccard 係數，以中文字符和英文單詞為 token，閾值 0.3
3. **查詢範圍**：同版本所有 pending 狀態 Ticket（排除自身 ID）
4. **輸出格式**：WARNING 提示（含 ID 和標題），不阻止建立流程
5. **容錯設計**：`list_tickets()` 例外時靜默跳過，不影響核心建立流程

**API 定義**：
- 新函式 `_detect_duplicate_tickets(version, new_title, new_what, new_ticket_id) -> None`
- 新函式 `_calculate_jaccard_similarity(text_a, text_b) -> float`
- 新常數 `DUPLICATE_DETECTION_THRESHOLD = 0.3`
- 新訊息常數（3 個）加入 `CreateMessages` 類別
