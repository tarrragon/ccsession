```
  驗證：無其他呼叫點（僅 L210 呼叫）

步驟 B：簡化 _build_decision_tree_path 邏輯（7-case → 3 分支）

  位置：create.py L158-229

  新邏輯結構：

  def _build_decision_tree_path(
      entry: Optional[str],
      decision: Optional[str],
      rationale: Optional[str],
      is_child: bool,
      ticket_type: str,
  ) -> Optional[Dict[str, str]]:
      """驗證並構建 decision_tree_path 字典。

      3 個分支：
      1. 豁免且無參數 → None
      2. 完整三參數 → 驗證後返回字典
      3. 其餘（部分或非豁免無參數）→ 輸出對應錯誤 + raise ValueError
      """

      # 步驟 1：計算豁免條件和提供參數個數
      is_exempted = is_child or ticket_type == "DOC"
      params = [entry, decision, rationale]
      provided_count = sum(1 for p in params if p is not None)

      # 分支 1：豁免且無參數
      if provided_count == 0 and is_exempted:
          return None

      # 分支 2：完整三參數
      if provided_count == 3:
          if not _validate_decision_tree_params(entry, decision, rationale):
              raise ValueError("決策樹參數驗證失敗")
          return {
              "entry_point": entry,
              "final_decision": decision,
              "rationale": rationale,
          }

      # 分支 3：其餘情況（部分參數，或非豁免無參數）
      if provided_count == 0:
          # 非豁免且無參數
          print(format_error(CreateMessages.DECISION_TREE_MISSING_ALL))
      elif is_exempted:
          # 豁免但部分參數
          print(format_error(CreateMessages.EXEMPTED_PARTIAL_PARAMS_ERROR))
      else:
          # 非豁免且部分參數
          missing_fields = []
          if entry is None:
              missing_fields.append("entry_point")
          if decision is None:
              missing_fields.append("final_decision")
          if rationale is None:
              missing_fields.append("rationale")
          print(format_error(
              CreateMessages.DECISION_TREE_MISSING_PARTIAL,
              missing_fields=", ".join(missing_fields)
          ))
      raise ValueError("決策樹參數不完整")

  變更說明：
  - 移除 early return 的 `if provided_count == 0` 的舊邏輯
  - 將 L210 的 `return _build_decision_tree_dict(...)` 改為直接返回字典
  - 將 L215 的硬編碼字串改為 CreateMessages.EXEMPTED_PARTIAL_PARAMS_ERROR

驗證方式：
  - 測試案例 TC-3.1 到 TC-3.7 覆蓋所有分支
  - 測試輸出訊息是否符合常數定義
```

**風險評估**：
- 中等風險：邏輯重構，但行為應保持一致
- 邊界條件覆蓋：
  - 分支 1：`provided_count == 0 and is_exempted == True` → 返回 None
  - 分支 2：`provided_count == 3` → 驗證後返回字典
  - 分支 3a：`provided_count == 0 and is_exempted == False` → 輸出 DECISION_TREE_MISSING_ALL
  - 分支 3b：`provided_count in [1,2] and is_exempted == True` → 輸出 EXEMPTED_PARTIAL_PARAMS_ERROR
  - 分支 3c：`provided_count in [1,2] and is_exempted == False` → 輸出 DECISION_TREE_MISSING_PARTIAL

```
在 Solution 區段追加以下內容：

## 問題 7：format_error/format_warning/format_info 評估

**決策：不合併**

理由：
1. 三個函式的實作雖然相同，但函式名稱提供了「語意文件化」功能
2. 呼叫端透過函式名稱可以知道訊息的性質（錯誤/警告/資訊）
3. 訊息類型已由常數類別（ErrorMessages 等）隱含，函式名稱提供了額外的意圖表達
4. 合併會影響 ~20+ 呼叫點（create.py 內），改動範圍過大且收益有限
5. 三個函式的實作相同，但它們服務於不同的語境：
   - messages.py 的 format_error/warning/info：全域通用訊息
   - command_lifecycle_messages.py 的 format_msg：命令層級訊息
   - 兩者語境不同，不應強行合併

若未來需要優化，可以：
- 在各函式中添加運行時驗證（確保 template 確實為對應的訊息類別常數）
- 建立內部輔助函式 `_format_message_template` 提取共同邏輯
- 但保持外部 API（format_error/warning/info）不變，維持意圖清晰
```

- 零風險：純文件記錄，無程式碼變更

### `_build_decision_tree_path` 簡化流程

```

  |

  |

  |     └─→ 返回 None
  |
  +─→ 分支 2：provided_count == 3
  |     |
  |     +─→ 驗證：_validate_decision_tree_params
```

## 八、語言特定實作注意事項

### Python 考量

**命名規範**：
- 函式改名：`_persist_and_report` → `_finalize`（改名後更簡潔，符合 PEP 8 命名風格）
- 常數命名：全大寫蛇形（`EXEMPTED_PARTIAL_PARAMS_ERROR`, `TICKET_LOCATION`, `PARENT_UPDATED`）

**類型標註**：
- `Optional[List[str]]` vs `List[str] | None`：保持現有風格 `Optional[...]`（相容舊版）
- `Dict[str, str]` 返回值類型明確標註

**Import 規範**：
- 模組頂部 import：將函式內 import 移至標準位置
- Import 順序：標準庫 (re, sys) 在前，第三方 (ticket_system) 在後

**字串格式化**：
- 使用 `format_msg()` 和 `format_error()` 封裝字串模板
- 支援佔位符參數（`{ticket_path}`, `{parent_id}`）

**異常處理**：
- 保留現有 `except Exception` 容錯設計（_detect_duplicate_tickets）
- 提高異常可見性（stderr 輸出 [DEBUG] 資訊）

**效能考量**：
- import re 移至模組頂部：避免每次呼叫 _tokenize 時重新載入
- import sys 移至模組頂部：避免每次呼叫 _detect_duplicate_tickets 時重新載入

**可能的技術挑戰**：
- 決策樹邏輯簡化後測試覆蓋：需確保 7-case 的所有分支被轉換後的 3 分支覆蓋
- 字典直接返回 vs 函式封裝：性能無差異，但可讀性更直接
