# Phase 1 功能設計：file-ownership-guard-hook

## 設計摘要

`file-ownership-guard-hook.py` 是一個派發前檔案所有權隔離檢查 Hook，用於自動偵測同 Wave 中兄弟 Ticket 的 `where.files` 衝突。此 Hook 目標是在派發代理人前提前識別檔案重疊風險，提示 PM 採取修復行動（合併任務、建立依賴、調整檔案清單），而非事後才在 git diff 驗證時發現。

**核心目標**：預防約 100 個 High 風險的檔案所有權重疊情況（來源：W1-004 分析報告，模式 2）。

---

## 1. Hook 觸發時機

### 選擇：PreToolUse（推薦） vs UserPromptSubmit

**推薦：PreToolUse** — Agent 工具使用前

**觸發條件**：
- 工具名稱：`Agent`（代理人派發指令）
- 指令包含 Ticket ID（識別同 Wave 兄弟）

**觸發頻率**：
- 派發單個 agent 執行 Ticket 時觸發 1 次
- 派發 N 個並行 agent 執行 N 個 Ticket 時觸發 N 次（每個檢查每個 agent 的目標 Ticket）

**為何選 PreToolUse**：
1. Agent 派發是檔案修改的入口點，此時攔截最早
2. 與現有 `parallel-dispatch-verification-hook.py` 的生命週期對稱（派發前防護 ↔ 完成後驗證）
3. UserPromptSubmit 過於寬泛，會在非派發場景誤觸（如用戶提問、查詢等）

**輸出模式**：Warning（exit 0）— 不阻塊派發流程，但輸出可操作的警告訊息供 PM 判斷

## 2. 檔案所有權衝突偵測算法

### 2.1 核心演算法流程

```
Hook 啟動
    |
    v
[Step 1] 提取目標 Ticket ID
    → 從 Agent 工具輸入中正則提取 Ticket ID
    → 例如：`Agent(..., ticket_id="0.1.2-W2-003")`
    |
    v
[Step 2] 讀取同 Wave 中所有「活躍」Ticket
    → 讀取所有 `docs/work-logs/v{version}/tickets/` 下符合版本 + Wave 的檔案
    → 篩選狀態為 pending 或 in_progress 的 Ticket
    → 排除目標 Ticket 本身
    |
    v
[Step 3] 提取每個 Ticket 的 where.files
    → 從 Ticket YAML frontmatter 讀取 `where.files` 欄位
    → 規範化每個路徑（移除 `./`、統一斜線、轉小寫）
    → 跳過 where.files 為空的 Ticket（無法檢查）
    |
    v
[Step 4] 偵測寫入衝突（Write-Write）
    → 對象：目標 Ticket 的 where.files ∩ 其他活躍 Ticket 的 where.files
    → 規則：目錄路徑前綴匹配
         （例如 `lib/` 和 `lib/ticket_system/` 視為衝突）
    |
    v
[Step 5] 輸出結果
    → 無衝突：靜默通過（return 0）
    → 有衝突：WARNING 訊息 → stdout + Hook 日誌
```

### 2.2 路徑比對規則

**目錄前綴匹配**（遵循 `parallel-dispatch-verification-hook.py` 的邏輯）：

| 路徑 A | 路徑 B | 判定 | 說明 |
|--------|--------|------|------|
| `lib/ticket_system/create.py` | `lib/ticket_system/create.py` | 衝突 | 完全相同 |
| `lib/` | `lib/ticket_system/create.py` | 衝突 | A 是 B 的父目錄 |
| `lib/ticket_system/` | `lib/ticket_system/create.py` | 衝突 | A 是 B 的父目錄 |
| `lib/ticket_system/` | `lib/ticket_system/other.py` | 衝突 | 同一目錄 |
| `.claude/hooks/` | `.claude/skills/` | 無衝突 | 完全獨立 |
| `.claude/rules/` | `.claude/rules/core/` | 衝突 | A 是 B 的父目錄 |

**規範化規則**（確保跨 Ticket 一致性）：
1. 統一使用正斜線 `/`（轉換反斜線 `\`）
2. 移除多重斜線 `//`
3. 移除前綴 `./`
4. 移除尾斜線 `/`
5. 轉為小寫

### 2.3 邊界條件處理

#### 2.3.1 where.files 為空的 Ticket

**行為**：跳過，不報錯

**理由**：
- 早期 Ticket 可能未填寫 where.files
- Hook 應寬鬆容錯，不因缺失欄位阻塞派發
- 缺失 where.files 的問題應由 `ticket-creation-validation-hook` 在建立時捕獲（驗證強制）

**實作**：
```python
if not where_files:
    logger.debug(f"Ticket {ticket_id} 無 where.files，跳過")
    continue
```

#### 2.3.2 目錄路徑 vs 具體檔案路徑

**規則**：都視為「寫入範圍」，前綴匹配即判定衝突

**範例**：
- 若 Ticket A 聲稱修改 `lib/`，Ticket B 聲稱修改 `lib/create.py`
  → 衝突（A 的範圍包含 B）

**合理性**：
- 目錄路徑代表該目錄內所有檔案都可能被修改
- 具體檔案路徑則明確了修改範圍
- 交集時應採用「寬鬆合併」：只要有前綴包含關係，就視為衝突

#### 2.3.3 父子 Ticket 間的檔案重疊

**預期行為**：允許（不報錯）

**識別方式**：
- 從 Ticket 的 `parent_id` 欄位判斷是否為子任務
- 若 A 是 B 的父，且 A、B 的 where.files 有重疊 → 允許

**實作邏輯**：
```python
# 獲取目標 Ticket 的 parent_id
target_parent = frontmatter.get("parent_id")

# 在衝突檢查中加入例外：
if target_parent and other_ticket_id == target_parent:
    continue  # 父子重疊，允許，跳過此 Ticket
if other_parent and other_ticket_id == target_id:
    continue  # 目標 Ticket 是 other 的父，允許
```

#### 2.3.4 跨 Wave 或不同版本的 Ticket

**行為**：不檢查（只檢查同 Wave）

**理由**：
- 不同 Wave 的 Ticket 不會同時派發
- 不同版本的 Ticket 屬於不同發布週期

**實作**：
```python
# 提取目標 Ticket 的版本和 Wave
target_version = extract_version_from_id(target_ticket_id)
target_wave = extract_wave_from_id(target_ticket_id)

# 篩選同 Wave 的 Ticket
for other_ticket_file in all_tickets:
    other_version, other_wave = extract_version_wave(other_ticket_file)
    if other_version != target_version or other_wave != target_wave:
        continue  # 不同版本或不同 Wave，跳過
```

#### 2.3.5 其他狀態的 Ticket（completed、blocked 等）

**行為**：不檢查

**理由**：
- `completed` Ticket 已結束，不會再被修改
- `blocked` Ticket 被阻塞，不會執行

**篩選條件**：
```python
status = frontmatter.get("status")
if status not in ["pending", "in_progress"]:
    continue  # 僅檢查活躍 Ticket
```

## 3. 偵測演算法核心函式

### 3.1 主要輸出函式簽名

```python
def find_file_ownership_conflicts(
    target_ticket_id: str,
    project_root: Path,
    logger: logging.Logger
) -> list[ConflictInfo]:
    """
    偵測目標 Ticket 與同 Wave 其他活躍 Ticket 的檔案所有權衝突

    Returns:
        list[ConflictInfo]: 衝突清單（含衝突 Ticket ID、衝突檔案、建議行動）
    """
    pass

class ConflictInfo:
    """衝突資訊"""
    target_ticket_id: str          # 派發目標（例 0.1.2-W2-003）
    conflicting_ticket_id: str     # 衝突對象（例 0.1.2-W2-001.1）
    conflicting_files: list[str]   # 重疊的檔案清單
    is_parent_child: bool          # 是否為父子關係（允許重疊）
    conflict_type: str             # 衝突類型：'brother'|'unrelated'|'parent'|'none'
```

### 3.2 主函式邏輯

```python
def main() -> int:
    logger = setup_hook_logging("file-ownership-guard-hook")

    try:
        # 1. 讀取 stdin JSON
        input_data = read_json_from_stdin(logger)

        # 2. 驗證觸發條件（Agent 工具 + 含 Ticket ID）
        if not is_valid_trigger(input_data):
            return 0  # 非目標觸發，靜默退出

        # 3. 提取目標 Ticket ID
        target_ticket_id = extract_ticket_id(input_data)
        if not target_ticket_id:
            logger.warning("無法從派發指令中提取 Ticket ID")
            return 0

        # 4. 執行衝突檢查
        project_root = get_project_root()
        conflicts = find_file_ownership_conflicts(
            target_ticket_id, project_root, logger
        )

        # 5. 篩選可操作的衝突（排除預期重疊如父子）
        actionable_conflicts = [c for c in conflicts if not c.is_parent_child]

        # 6. 輸出結果
        if actionable_conflicts:
            warning_msg = format_conflict_warning(
                target_ticket_id, actionable_conflicts
            )
            logger.warning(warning_msg)

            # 輸出到 additionalContext
            output = {
                "hookSpecificOutput": {
                    "hookEventName": "PreToolUse",
                    "additionalContext": warning_msg
                }
            }
        else:
            # 靜默通過
            output = DEFAULT_OUTPUT

        print(json.dumps(output))
        return 0

    except Exception as e:
        logger.critical(f"Hook 執行失敗: {e}", exc_info=True)
        sys.stderr.write(f"[Hook Error] {HOOK_NAME}: {e}\n")
        return 0  # 異常時仍回傳 0，不阻塊派發
```

## 4. 輸出格式與訊息設計

### 4.1 警告訊息結構

```
============================================================
[檔案所有權衝突警告]
============================================================

Ticket 0.1.2-W2-003 派發前偵測到以下檔案所有權衝突：

衝突分析（2 個衝突）：

衝突 1：同 Wave 兄弟 Ticket
  - 派發目標：0.1.2-W2-003
  - 衝突對象：0.1.2-W2-001.1
  - 衝突檔案（2 個）：
    - .claude/skills/ticket/ticket_system/lib/ticket_builder.py
    - .claude/skills/ticket/ticket_system/commands/create.py
  - 衝突類型：兄弟 Ticket（同父：0.1.2-W2-001）

衝突 2：同 Wave 無關 Ticket
  - 派發目標：0.1.2-W2-003
  - 衝突對象：0.1.2-W2-002
  - 衝突檔案（1 個）：
    - .claude/hooks/handoff-auto-resume-stop-hook.py
  - 衝突類型：無關 Ticket（不同父）

建議行動：

[檢查清單] 確認並解決衝突：

1. 衝突 1 — 兄弟 Ticket （0.1.2-W2-001.1）：

   判定：0.1.2-W2-001 是包含三個子任務的協調 Ticket，由 system-analyst
        評估並拆分為 1.1 和 1.2。0.1.2-W2-003 是獨立功能。

   選項 A（推薦）：調整 0.1.2-W2-003 的 where.files，移除與 1.1 重疊的檔案
                （若修改是獨立的）
   選項 B（次選）：建立 blockedBy 依賴：0.1.2-W2-003 blockedBy 0.1.2-W2-001.1
                （若 W2-003 需等 W2-001 完成）
   選項 C：合併任務（若兩個修改有邏輯聯繫）

2. 衝突 2 — 無關 Ticket （0.1.2-W2-002）：

   判定：0.1.2-W2-002 和 0.1.2-W2-003 均修改 hook 但無父子或兄弟關係。

   選項 A（推薦）：調整 where.files，明確界定各自修改範圍
   選項 B：建立 blockedBy：0.1.2-W2-003 blockedBy 0.1.2-W2-002
   選項 C：序列派發，先派 0.1.2-W2-002，完成後再派 0.1.2-W2-003

決策建議：
  - 優先檢查 Ticket 內容，判斷修改是否真的有依賴
  - 若修改獨立 → 調整 where.files 避免衝突
  - 若修改有依賴 → 建立 blockedBy 或序列派發
  - 如確認無誤，忽略此警告並繼續派發

============================================================
```

### 4.2 訊息內容設計原則

| 原則 | 實現方式 |
|------|---------|
| 可操作 | 列出具體衝突（Ticket ID + 檔案），給出 3 個以上選項 |
| 上下文清晰 | 區分衝突類型（兄弟/無關/父子），解釋衝突原因 |
| 風險評估 | 標示衝突類型和嚴重度（必須解決 vs 建議檢查） |
| 決策指引 | 為每個衝突提供推薦行動順序 |
| 簡潔 | 總長度 < 2000 字元，使用表格和清單提高可讀性 |

## 5. 異常與容錯

### 5.1 例外情況處理

| 例外情況 | 行為 | 日誌等級 |
|---------|------|--------|
| 無法提取 Ticket ID | 日誌 debug，靜默退出 | DEBUG |
| where.files 為空 | 跳過此 Ticket，繼續檢查 | DEBUG |
| Ticket 檔案不存在 | 跳過此 Ticket，記錄警告 | WARNING |
| YAML 解析失敗 | 跳過此 Ticket，記錄錯誤 | ERROR |
| 同 Wave 無其他活躍 Ticket | 靜默通過 | DEBUG |
| Git 命令執行失敗 | 不執行 git 操作，僅使用 YAML 分析 | WARNING |

### 5.2 錯誤恢復策略

**原則**：失敗寧可漏報，不可誤報

- Hook 異常時立即 logger.critical + stderr 雙通道輸出
- 若無法完整分析，回傳 exit 0 並記錄部分結果
- 不以單一檔案讀取失敗中斷整個檢查

## 6. Hook 退出碼語意

| 退出碼 | 意義 | 何時返回 |
|-------|------|---------|
| 0 | 正常 | 所有情況（有無衝突都返回 0，只改變輸出） |
| 2 | 阻塊錯誤 | 不使用（此 Hook 不阻塊派發） |

**設計理由**：
- `exit 0` 讓派發繼續進行，但提供警告訊息供 PM 決策
- 不採用 `exit 2` 阻塊，因為：
  1. 檔案所有權衝突不是 fatal error（可透過序列派發解決）
  2. PM 可能有正當理由忽視警告（例如已建立 blockedBy）
  3. Hook 應提示而非決策（決策權在 PM）

## 7. 與現有 Hook 系統的整合

### 7.1 與 parallel-dispatch-verification-hook 的關係

| 特徵 | file-ownership-guard-hook | parallel-dispatch-verification-hook |
|------|---------------------------|-----------------------------------|
| 觸發時機 | **派發前**（PreToolUse Agent） | **派發後**（PostToolUse Bash — ticket complete） |
| 檢查對象 | 同 Wave 所有活躍 Ticket 的 where.files | 單一 Ticket 的 where.files vs git diff |
| 偵測目的 | 預防衝突（設計階段） | 驗證完整性（實現階段） |
| 輸出 | 衝突警告 + 行動建議 | 缺失檔案警告 |
| 退出碼 | 0（Warning） | 0（Warning） |

**協作流程**：
```
PM 派發 Agent
    ↓
file-ownership-guard-hook 檢查同 Wave 衝突
    ↓
Agent 執行實作
    ↓
ticket track complete
    ↓
parallel-dispatch-verification-hook 驗證完整性
```

### 7.2 Hook 日誌結構

**日誌路徑**：`.claude/hook-logs/file-ownership-guard-hook/`

**日誌內容**：
- 檢查時間戳
- 目標 Ticket ID + 版本 + Wave
- 檢查結果摘要（X 個衝突已偵測）
- 詳細衝突清單（可供事後分析）

## 附錄 A：測試場景清單

### A.1 無衝突場景
- 單獨派發 Ticket（無同 Wave 兄弟）
- 同 Wave 多個 Ticket，where.files 完全不重疊

### A.2 有衝突場景
- 兄弟 Ticket 重疊（同父，如 W2-001.1 vs W2-001.2）
- 無關 Ticket 重疊（不同父，如 W2-001.1 vs W2-003）
- 目錄前綴重疊（`lib/` vs `lib/create.py`）
- 多個衝突疊加（A 與 B 衝突，A 與 C 也衝突）

### A.3 邊界場景
- where.files 為空的 Ticket
- 不同版本的 Ticket（應被篩選）
- 不同 Wave 的 Ticket（應被篩選）
- completed/blocked 狀態 Ticket（應被篩選）

### A.4 異常場景
- Ticket 檔案不存在
- YAML frontmatter 格式破損
- 無法提取 Ticket ID
- stdin JSON 格式非預期
