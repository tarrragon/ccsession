## 二、逐項問題分析與修改方案

### 問題 1：`_persist_and_report` 改名為 `_finalize`，且 blockedBy 驗證邏輯前移至獨立步驟

#### 現況分析

**位置**: `create.py` L546-L617，函式 `_persist_and_report`

目前函式名稱 `_persist_and_report` 語意不準確：
1. 函式實際上除了「持久化+報告」外，還包含 `_validate_blocked_by_references` 和 `_detect_duplicate_tickets` 兩個驗證步驟
2. 函式文件字串明確標注「Step 3: 驗證 blockedBy + 重複偵測 + 持久化 + 輸出」，可見語意已超出名稱描述
3. `execute()` 在呼叫時以「Step 3」標注，但 blockedBy 驗證在概念上屬於前置驗證，不應混入持久化步驟

**問題根因**: 函式職責不單一（SRP 違反），命名無法反映全部行為。

#### 修改方案

**方案**：改名為 `_finalize`，並在函式文件字串中說明「Step 3: 最終驗證 + 持久化 + 輸出」。

blockedBy 驗證邏輯已存在於獨立函式 `_validate_blocked_by_references`，**不需要移出** `_finalize` 成為更上層的獨立步驟（認知負擔增加無收益）。驗收條件「前移至獨立步驟」的含義是：在 `_finalize` 內部，將 blockedBy 驗證作為第一步 guard clause，這已經是現有的實作方式（L568 `if not _validate_blocked_by_references...`）。因此只需改名即可滿足驗收條件。

**具體變更**:

```python
# 修改前
def _persist_and_report(
    args, config, version, ticket_id, tdd_result
) -> int:
    """Step 3: 驗證 blockedBy + 重複偵測 + 持久化 + 輸出."""

# 修改後
def _finalize(
    args, config, version, ticket_id, tdd_result
) -> int:
    """Step 3: 最終驗證 + 持久化 + 輸出.

    子步驟：
    1. 驗證 blockedBy 存在性（前置驗證）
    2. 重複偵測（警告）
    3. 持久化（建立 Ticket 物件並儲存）
    4. 輸出建立訊息
    """
```

#### 影響範圍（呼叫端）

搜尋 `_persist_and_report` 的所有呼叫：

- `create.py` L643：`return _persist_and_report(args, config, version, ticket_id, tdd_result)`
  - 須同步改為 `return _finalize(args, config, version, ticket_id, tdd_result)`

無其他模組呼叫此私有函式（`_` 前綴確認為模組私有）。

**API 介面變更**: 函式簽名不變，僅名稱改變。

### 問題 3：`_build_decision_tree_path` 7-case 簡化為 3 分支

#### 現況分析

**位置**: `create.py` L158-L229，函式 `_build_decision_tree_path`

文件字串列出 7 個 case：
1. 豁免 + 無參數 → None
2. 豁免 + 完整參數 → 返回字典
3. 豁免 + 部分參數 → raise ValueError
4. 非豁免 + 無參數 → raise ValueError
5. 非豁免 + 完整參數 → 返回字典
6. 非豁免 + 部分參數 → raise ValueError
7. （隱含）完整參數驗證失敗 → raise ValueError

**觀察**: Case 2 和 5（「有完整參數 → 返回字典」）行為完全相同；Case 3、4、6（「部分參數 → raise」）行為邏輯一致但有不同錯誤訊息。

7 cases 的本質可以合併為 3 個分支：
1. `provided_count == 0 and is_exempted` → return None
2. `provided_count == 3` → 驗證後返回字典
3. 其餘（部分參數，或非豁免無參數）→ 輸出錯誤 + raise ValueError

#### 修改方案

**新的 3 分支設計**：

```python
def _build_decision_tree_path(entry, decision, rationale, is_child, ticket_type):
    """驗證並構建 decision_tree_path 字典。

    3 個分支：
    1. 豁免且無參數 → None
    2. 完整三參數 → 驗證後返回字典
    3. 其餘（部分或非豁免無參數）→ 輸出對應錯誤 + raise ValueError
    """
    is_exempted = is_child or ticket_type == "DOC"
    params = [entry, decision, rationale]
    provided_count = sum(1 for p in params if p is not None)

    # 分支 1：豁免且無參數
    if provided_count == 0 and is_exempted:
        return None

    # 分支 2：完整三參數
    if provided_count == 3:
        if not _validate_decision_tree_params(entry, decision, rationale):
            raise ValueError("決策樹參數驗證失敗")
        return {
            "entry_point": entry,
            "final_decision": decision,
            "rationale": rationale,
        }

    # 分支 3：其餘情況（部分參數，或非豁免無參數）
    if provided_count == 0:
        # 非豁免且無參數
        print(format_error(CreateMessages.DECISION_TREE_MISSING_ALL))
    elif is_exempted:
        # 豁免但部分參數
        print(format_error(CreateMessages.EXEMPTED_PARTIAL_PARAMS_ERROR))
    else:
        # 非豁免且部分參數
        missing_fields = []
        if entry is None:
            missing_fields.append("entry_point")
        if decision is None:
            missing_fields.append("final_decision")
        if rationale is None:
            missing_fields.append("rationale")
        print(format_error(
            CreateMessages.DECISION_TREE_MISSING_PARTIAL,
            missing_fields=", ".join(missing_fields)
        ))
    raise ValueError("決策樹參數不完整")
```

**注意**：分支 3 中「豁免但部分參數」的錯誤訊息需要新增常數 `CreateMessages.EXEMPTED_PARTIAL_PARAMS_ERROR`（見問題 4）。

**影響範圍**:
- `_build_decision_tree_path` 本身重構
- 問題 2（刪除 `_build_decision_tree_dict`）整合至此
- 新增 Messages 常數（問題 4 處理）

**API 介面變更**: 函式簽名不變，行為一致，內部邏輯簡化。

### 問題 5：`config.get("blocked_by")` 預設值修正

#### 現況分析

**位置**: `create.py` L565

```python
blocked_by = config.get("blocked_by", [])
```

在 `_parse_cli_args_to_config`（L537）中，當無 blocked_by 參數時：

```python
"blocked_by": blocked_by if blocked_by else None,
```

因此 `config["blocked_by"]` 的值可能為 `None`（無依賴時）或 `["some-id"]`（有依賴時）。

`config.get("blocked_by", [])` 在 key 存在且值為 `None` 時，**不使用預設值**，直接回傳 `None`。

接著：

```python
if not _validate_blocked_by_references(version, ticket_id, blocked_by):
```

`_validate_blocked_by_references` 內的 guard clause（L80）：

```python
if not blocked_by:
    return True
```

`not None` 為 `True`，因此實際上傳入 `None` 是安全的（會直接 return True）。

但問題在於**語意誤導**：預設值 `[]` 暗示「無資料時用空列表」，而實際行為是 `None`（因 key 存在）。

**問題根因**：預設值 `[]` 在 key 存在但值為 `None` 時無效，且暗示了錯誤的語意。

#### 修改方案

修正為不設預設值，直接取用 config 中的值（可能為 `None` 或 list）：

```python
# 修改前
blocked_by = config.get("blocked_by", [])

# 修改後
blocked_by = config.get("blocked_by")
```

`_validate_blocked_by_references` 的函式簽名已接受 `Optional[List[str]]`，傳入 `None` 或空列表均正確處理。

**影響範圍**: 僅 `_finalize`（原 `_persist_and_report`）內一行。

**型別一致性確認**：`_validate_blocked_by_references` 簽名為 `blocked_by: Optional[List[str]]`，接受 `None`。

### 問題 6：函式內 import 移至模組頂部

#### 現況分析

**位置 A**：`_tokenize` 函式（L232-L251）

```python
def _tokenize(text: str) -> set:
    import re  # 函式內 import
    pattern = r'[\u4e00-\u9fff]|\w+'
    tokens = re.findall(pattern, text)
    return set(tokens)
```

**位置 B**：`_detect_duplicate_tickets` 函式（L299-L415）

```python
def _detect_duplicate_tickets(...):
    import sys  # 函式內 import
    from ticket_system.lib.constants import (  # 函式內 import
        STATUS_PENDING,
        DUPLICATE_DETECTION_THRESHOLD,
    )
```

函式內 import 違反 PEP 8 規範（標準 import 應置於模組頂部），增加每次呼叫的認知負擔，且對效能有微小影響（Python 會快取模組，但每次仍需執行 import 語句）。

**注意**：`import sys` 也出現在 `_detect_duplicate_tickets` 內的 except 區塊（L382）：`sys.stderr.write(...)`，這個 `sys` 引用是在函式內 import 之後才能使用的。

#### 修改方案

將三個 import 移至模組頂部（現有 import 區塊末尾）：

```python
# 在 create.py 頂部 import 區塊新增
import re
import sys
from ticket_system.lib.constants import (
    COGNITIVE_LOAD_FILE_THRESHOLD,  # 原已存在
    STATUS_PENDING,                  # 新增
    DUPLICATE_DETECTION_THRESHOLD,  # 新增
)
```

同時移除 `_tokenize` 內的 `import re` 和 `_detect_duplicate_tickets` 內的 `import sys` 及 `from ticket_system.lib.constants import ...`。

**注意**：`COGNITIVE_LOAD_FILE_THRESHOLD` 已在 L42 作為頂部 import，需要將新常數合併到同一個 `from ticket_system.lib.constants import` 語句。

**影響範圍**:
- 模組頂部 import 區塊：新增 `import re`、`import sys`、constants import 補充
- `_tokenize` L246：移除 `import re`
- `_detect_duplicate_tickets` L322-L326：移除 `import sys` 和 `from ticket_system.lib.constants import ...`

### 問題 7：`format_error/format_warning/format_info` 評估是否合併

#### 現況分析

**位置**: `messages.py` L212-L279

三個函式定義：

```python
def format_error(template: str, **kwargs) -> str:
    return template.format(**kwargs)

def format_warning(template: str, **kwargs) -> str:
    return template.format(**kwargs)

def format_info(template: str, **kwargs) -> str:
    return template.format(**kwargs)
```

三個函式的**實作完全相同**，唯一差別是函式名稱。各自對應一類訊息常數（ErrorMessages / WarningMessages / InfoMessages），但這三個常數類別的訊息已在字串本身包含前綴（如 `[Error]`、`[Warning]`、`[OK]`），函式本身不添加前綴。

**評估：是否合併？**

**合併的理由**：
- 三個函式實作完全相同，符合 DRY 原則的合併候選
- 合併為 `format_msg` 可簡化介面（`command_lifecycle_messages.py` 已有 `format_msg`）

**不合併的理由**：
- 三個函式名稱提供了**語意文件化**的功能：呼叫端透過函式名稱可以知道訊息的性質（錯誤/警告/資訊）
- `messages.py` 中的 `format_error/warning/info` 和 `command_lifecycle_messages.py` 的 `format_msg` 是兩個不同模組的函式，功能一致但語境不同
- 合併會要求所有現有呼叫端修改（影響範圍大，create.py 內約有 20+ 處呼叫）
- 訊息類型本身已由常數類別（ErrorMessages 等）隱含，函式名稱提供了額外的意圖表達

**建議結論：不合併**

理由：語意文件化價值大於 DRY 考量。三個函式的實作雖然相同，但名稱提供了程式碼可讀性。若未來需要，可以在各函式中添加格式驗證（如驗證 template 確實為對應的訊息類別常數）。

此決策須記錄在 Execution Log 中（見驗收條件 7）。

## 六、行為場景（Given-When-Then）

### 場景 1：`_finalize` 改名 — 正常流程

Given: `execute()` 呼叫 create 命令，Step 1/2 成功
When: `execute()` 執行 Step 3
Then: 呼叫 `_finalize`（非舊名稱），Ticket 成功建立

### 場景 2：`_build_decision_tree_path` 3 分支 — 豁免且無參數

Given: `is_child=True`，無 decision tree 參數
When: `_build_decision_tree_path` 被呼叫
Then: 回傳 `None`，不 raise ValueError（分支 1）

### 場景 3：`_build_decision_tree_path` 3 分支 — 完整三參數

Given: `is_child=False`，三個 decision tree 參數均提供
When: `_build_decision_tree_path` 被呼叫
Then: 回傳含 `entry_point`/`final_decision`/`rationale` 的字典（分支 2）

### 場景 4：`_build_decision_tree_path` 3 分支 — 非豁免無參數
