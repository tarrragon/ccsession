# Phase 1 功能規格設計：TDD Phase Input/Output Contract 驗證機制

**[Layer 1] Contract Schema**：`.claude/tdd/contracts.yaml`
**[Layer 2] Validator Hook**：`.claude/hooks/phase-contract-validator-hook.py`
**[Layer 3] TDD Skill 整合**：`.claude/skills/tdd/commands/phase_complete.py`

## 1. 功能描述

### 1.1 問題背景

目前 TDD Phase 1-4 的產出物格式規範散落在以下六個位置：

| 來源 | 描述內容 |
|------|---------|
| `.claude/rules/flows/tdd-flow.md` | Phase 代理人表和轉換條件 |
| `.claude/agents/lavender-interface-designer.md` | Phase 1 產出物命名規範（-phase1-design.md） |
| `.claude/agents/sage-test-architect.md` | Phase 2 產出物命名規範（-phase2-test-design.md） |
| `.claude/agents/pepper-test-implementer.md` | Phase 3a 產出物命名規範（-phase3a-strategy.md） |
| `.claude/agents/parsley-flutter-developer.md` | Phase 3b 產出物命名規範（-phase3b-execution-report.md） |
| `.claude/rules/core/ticket-id-conventions.md` | 所有 Phase 後綴命名規範 |

這種散落狀態導致 IMP-011 類問題：消費端（下一個 Phase 的代理人）無法確認生產端（當前 Phase 代理人）的精確格式規範。典型案例：

```
Phase 3a 產出 direction 欄位
  ↓（消費方假設格式）
Phase 3b 讀取 direction 欄位
  ↓
假設：direction = "to-sibling"（簡單字串）
實際：direction = "to-sibling:0.31.1-W3-002"（包含 target_id 後綴）
  ↓
精確匹配失敗，修復無效
```

### 1.2 解決方案概述

建立 **TDD Phase Contract 系統**，將散落的規範集中為機器可驗證的 YAML 定義，並在 Phase 轉移時自動執行驗證。

系統由三個元件組成：

| 元件 | 位置 | 職責 |
|------|------|------|
| Contract Schema | `.claude/tdd/contracts.yaml` | 集中定義每個 Phase 的生產者、消費者、產出物規格和驗證規則 |
| 驗證 Hook | `.claude/hooks/phase-contract-validator-hook.py` | 在 Phase 完成時執行四層驗證，阻止不合規的 Phase 轉移 |
| TDD 整合 | `.claude/skills/tdd/commands/phase_complete.py` | 整合 contract 驗證到 `/tdd next` 命令，驗證結果寫入 Ticket execution log |

### 1.3 使用者場景

**場景 1：Phase 1 正常完成**
1. lavender-interface-designer 完成 `{ticket-id}-phase1-design.md`
2. 執行 `/tdd next`（或 `ticket track complete`）
3. Hook 自動驗證：檔案存在、frontmatter 格式、acceptance_criteria 條數
4. 驗證通過 → 允許轉移至 Phase 2
5. 驗證結果寫入 Ticket execution log

**場景 2：Phase 1 缺少必要 Section**
1. lavender-interface-designer 完成設計文件，但缺少「驗收條件」Section
2. 執行 `/tdd next`
3. Hook 第三層（結構驗證）失敗：「必要 Section '驗收條件' 缺失」
4. 返回 ERROR，阻止 Phase 轉移
5. 代理人補充 Section 後重新執行

**場景 3：Phase 3a 產出 direction 欄位（IMP-011 回溯）**
1. pepper-test-implementer 完成策略文件，direction 欄位格式為 `"to-sibling:target_id"`
2. Hook 驗證 direction 欄位格式符合 contract 定義（`to-{type}[:target_id]`）
3. 驗證通過，Phase 3b 代理人讀取策略文件時可依 contract 確認完整格式
4. 消費端使用前綴匹配而非精確匹配，正確處理所有格式變體

**場景 4：現有 Phase 輸出向後相容（100+ 現存輸出）**
1. 現存設計文件缺少 frontmatter 中的 acceptance_criteria 欄位
2. Hook 第二層（格式驗證）：輸出 WARNING 而非 ERROR
3. Phase 轉移正常進行（不阻止）
4. 警告記錄到 Ticket log，提示未來補充

```yaml
    missing_required_section: "error"   # 阻止 Phase 轉移
```

### 2.2 四層驗證定義

```
Layer 1：存在性驗證（Existence Check）
  檢查：必要產出物檔案是否存在
  失敗行為：ERROR — 阻止 Phase 轉移
  範例：{ticket-id}-phase1-design.md 不存在

Layer 2：格式驗證（Format Check）
  檢查：frontmatter 格式是否正確（YAML 解析不出錯）
  失敗行為：新文件 → ERROR；legacy 文件 → WARNING
  範例：frontmatter 中 YAML 語法錯誤

Layer 3：結構驗證（Structure Check）
  檢查：必要 Section 是否存在（以 ## Section 名稱 匹配）
  失敗行為：新文件 → ERROR；legacy 文件 → WARNING
  範例：Phase 1 文件缺少「驗收條件」Section

Layer 4：內容驗證（Content Check）
  檢查：Section 內容是否符合規範（長度、格式、特定欄位）
  失敗行為：始終為 WARNING（不阻止，僅提示）
  範例：驗收條件少於 3 條；direction 欄位格式不符合規範
```

**重要設計決策**：Layer 4 始終為 WARNING 的理由詳見第 4 節。

### 2.3 驗證失敗行為定義

| 驗證層級 | 新文件（post-contract） | Legacy 文件（pre-contract） |
|---------|----------------------|---------------------------|
| Layer 1 存在性 | ERROR（阻止轉移） | ERROR（阻止轉移） |
| Layer 2 格式 | ERROR（阻止轉移） | WARNING（提示） |
| Layer 3 結構 | ERROR（阻止轉移） | WARNING（提示） |
| Layer 4 內容 | WARNING（提示） | INFO（記錄） |

**Legacy 文件判定標準**：
- 文件最後修改時間早於 `contracts.yaml` 建立時間，或
- 文件 frontmatter 中缺少 `phase` 欄位

### 2.4 Hook 介面定義

```python
# .claude/hooks/phase-contract-validator-hook.py

class ValidationResult:
    """驗證結果容器"""
    errors: list[str]      # Layer 1-3 失敗（阻止轉移）
    warnings: list[str]    # Layer 4 失敗或 legacy 降級（提示）
    infos: list[str]       # 資訊性提示（不影響流程）

    @property
    def can_proceed(self) -> bool:
        """是否允許 Phase 轉移"""
        return len(self.errors) == 0

class PhaseContractValidator:
    """Phase Contract 驗證器"""

    def validate(
        self,
        ticket_id: str,
        phase: str,          # "1" | "2" | "3a" | "3b"
        ticket_dir: str      # docs/work-logs/v{version}/tickets/
    ) -> ValidationResult:
        """
        執行四層驗證。

        Args:
            ticket_id: Ticket ID（如 0.1.2-W1-002）
            phase: Phase 代號
            ticket_dir: Ticket 文件所在目錄

        Returns:
            ValidationResult，errors 非空時阻止 Phase 轉移
        """

    def _check_existence(
        self,
        ticket_id: str,
        artifact_spec: dict,
        ticket_dir: str
    ) -> list[str]:
        """Layer 1：存在性驗證"""

    def _check_format(
        self,
        file_path: str,
        artifact_spec: dict,
        is_legacy: bool
    ) -> tuple[list[str], list[str]]:
        """Layer 2：格式驗證，返回 (errors, warnings)"""

    def _check_structure(
        self,
        file_path: str,
        artifact_spec: dict,
        is_legacy: bool
    ) -> tuple[list[str], list[str]]:
        """Layer 3：結構驗證，返回 (errors, warnings)"""

    def _check_content(
        self,
        file_path: str,
        artifact_spec: dict
    ) -> list[str]:
        """Layer 4：內容驗證，返回 warnings（無 errors）"""

    def _is_legacy_artifact(
        self,
        file_path: str,
        contracts_creation_date: str
    ) -> bool:
        """判斷是否為 legacy 文件"""
```

```python
# .claude/skills/tdd/commands/phase_complete.py

def complete_phase(
    ticket_id: str,
    phase: str,
    ticket_dir: str,
    contracts_path: str = ".claude/tdd/contracts.yaml"
) -> bool:
    """
    標記 Phase 完成並執行 contract 驗證。

    執行流程：
    1. 載入 contracts.yaml
    2. 執行 PhaseContractValidator.validate()
    3. 輸出驗證結果（errors 以 [ERROR] 前綴，warnings 以 [WARNING] 前綴）

    6. 若僅有 warnings，顯示提示並繼續（返回 True）

    Returns:
        True 表示可以繼續，False 表示必須修正後重試
    """
```

## 4. 關鍵設計決策

### 4.1 YAML vs JSON：選用 YAML

**決定**：Contract 定義使用 YAML 格式。

**理由**：
- 支援注釋（`#`），可在 schema 中解釋設計意圖
- 多行字串（`|`）適合定義 examples 和 patterns
- 與現有 `.claude/` 目錄下的配置檔格式一致（hooks 配置、agent 定義均用 YAML）
- Python 的 `pyyaml` / `ruamel.yaml` 完整支援

**代價**：YAML 縮排敏感，錯誤難以調試。緩解措施：在 phase_complete.py 中捕獲 YAMLParseError 並輸出友好提示。

### 4.2 Layer 4 始終為 WARNING（不阻止轉移）

**決定**：Layer 4 內容驗證失敗只輸出 WARNING，不阻止 Phase 轉移。

**理由**：
- 內容品質（驗收條件數量、direction 格式等）存在合理例外情況
- 現行已有 acceptance-gate-hook 負責最終驗收，Phase 轉移時的 Layer 4 是「早期提示」而非「硬性強制」
- 以免過度嚴格導致代理人頻繁被阻止（降低流程效率）
- IMP-011 類的格式問題由 Layer 3 field_formats 以 ERROR 處理，不依賴 Layer 4

**例外**：若未來發現 Layer 4 被繞過的案例，可在 contracts.yaml 中為特定規則設定 `overridable: false`，升級為 ERROR。

### 4.3 向後相容策略：以建立日期為界

**決定**：以 `contracts.yaml` 的建立日期作為 legacy / non-legacy 的分界。

**理由**：
- 100+ 現存 Phase 輸出文件不可能全部補充 frontmatter 和 Section
- 基於建立日期的判斷是客觀且可實作的標準
- 新建立的 Phase 文件（post-contract）應遵守完整規範

**替代方案**（已排除）：以文件是否包含 `phase` frontmatter 欄位為界。排除原因：需要修改所有現存文件才能明確標記，成本過高。

**實作細節**：
- `is_legacy_artifact()` 函式比較 `os.path.getmtime(file_path)` 與 `contracts.yaml` 的 `mtime`
- 若比較失敗（無法取得 mtime），預設視為 legacy（安全降級）

### 4.4 path_pattern 解析策略

**決定**：path_pattern 中的 `{ticket-id}` 佔位符以 prefix 匹配而非完整字串匹配。

**理由**：這是 IMP-011 的核心教訓——使用前綴匹配而非精確匹配，以正確處理帶後綴的格式變體。

**實作**：
```python
def resolve_artifact_path(ticket_id: str, path_pattern: str, ticket_dir: str) -> str | None:
    """解析 path_pattern，找到實際檔案路徑"""
    prefix = path_pattern.replace("{ticket-id}", ticket_id)
    # 移除 .md 後綴，以前綴匹配目錄中的檔案
    base = prefix.replace(".md", "")
    candidates = [f for f in os.listdir(ticket_dir) if f.startswith(base)]
    if candidates:
        return os.path.join(ticket_dir, candidates[0])
    # 嘗試 alternate_patterns
    for alt in artifact_spec.get("alternate_patterns", []):
        alt_prefix = alt.replace("{ticket-id}", ticket_id).replace(".md", "")
        candidates = [f for f in os.listdir(ticket_dir) if f.startswith(alt_prefix)]
        if candidates:
            return os.path.join(ticket_dir, candidates[0])
    return None
```

```
Given: 新建立的 Phase 1 設計文件（post-contract date）
       且文件缺少「驗收條件」Section

And:   執行者必須補充 Section 後重新執行
```

### 場景 2：Phase 1 舊文件缺少 Section（Warning 不阻止）

```
Given: 建立於 contracts.yaml 之前的 Phase 1 設計文件（legacy）
       且文件缺少「驗收條件」Section
When:  執行 /tdd next
Then:  Layer 3 結構驗證回傳 WARNING（降級，非 ERROR）
And:   ValidationResult.can_proceed == True
And:   Phase 轉移繼續進行
And:   輸出 "[WARNING] Legacy artifact: '驗收條件' section missing (not enforced for legacy files)"
```

### 場景 3：IMP-011 direction 欄位格式驗證

```
Given: Phase 3a 策略文件包含 direction 欄位，值為 "to-sibling:0.31.1-W3-002"

Then:  Layer 4 內容驗證：direction 值符合 pattern "^to-(sibling|parent|child|context-refresh)(?::\\S+)?$"

And:   Phase 3b 代理人讀取策略文件時，可依 contracts.yaml 確認 direction 允許帶 :target_id 後綴
```

### 場景 4：direction 舊格式（無後綴）同樣通過


## 6. 已知限制和風險

### 6.1 已知限制

| 限制 | 說明 | 緩解措施 |
|------|------|---------|
| Section 匹配使用字串比較 | `## 驗收條件` 與 `## 驗收標準` 視為不同 Section | contracts.yaml 中列出允許的 alternate section names |
| path_pattern 僅支援 Ticket 目錄 | 不支援跨目錄的 artifact | 目前 Phase 輸出均在 Ticket 目錄，此限制可接受 |
| 無法驗證 Dart 程式碼內容 | Phase 3b 的 source-code 格式驗證只能檢查 `dart analyze` 結果是否記錄於 execution report | 依賴 parsley 執行報告的誠實性 |
| legacy 判定依賴 mtime | 檔案 mtime 可能因 git checkout 等操作被修改 | 提供 `--force-legacy` 旗標允許手動覆蓋 |

### 6.2 風險評估

| 風險 | 機率 | 影響 | 緩解措施 |
|------|------|------|---------|
| contracts.yaml 格式錯誤導致 Hook 崩潰 | 中 | 高（阻止所有 Phase 轉移） | Hook 在解析失敗時 fallback 為「跳過驗證並輸出 WARNING」，不阻止轉移 |
| legacy 判定錯誤（新文件被誤判為 legacy） | 低 | 低（只影響是否強制執行） | 提供 `--strict` 旗標強制使用非 legacy 規則 |
| contracts.yaml 與代理人定義不同步 | 中 | 中（誤報或漏報） | 在 CLAUDE.md 或 agent 定義中加入對 contracts.yaml 的引用，提醒更新 |
| Python 版本相容性 | 低 | 中（Hook 無法執行） | 指定 Python 3.11+，與現有 Hook 系統一致 |

### 6.3 超出範圍

以下項目明確**不在本功能範圍內**：

- 自動修復不符合 contract 的現存文件
- Phase 4（Phase 4a/4b/4c）的 contract 定義（Phase 4 產出較多樣化，需額外分析）
- contracts.yaml 的 UI 管理介面
- contract 版本控制和升版機制
