**Ticket**: 0.1.2-W1-006 實作 Agent Capability Registry 機制
**設計者**: lavender-interface-designer
**設計日期**: 2026-03-23
**版本**: 1.0.0

## 1. 功能需求分析

### 1.1 核心問題

目前專案的 agent 能力資訊完全散落在自然語言 `.md` 檔案中，無法程式化查詢。PM 派發決策依賴：

- `.claude/rules/core/decision-tree.md` 第五層 TDD 代理人對應表
- `.claude/rules/flows/incident-response.md` 錯誤派發對應表
- `.claude/rules/guides/query-vs-research.md` 查詢 vs 研究派發表
- 各 agent `.md` 的自然語言觸發條件描述（共 29 個 agent）

**具體問題**：
1. PM 派發時必須記住多個不同文件中的對應規則
2. 無法以程式化方式驗證派發決策正確性
3. Agent 能力衝突（如 ARCH-005：兩個並行 agent 同時寫入同一檔案）無法自動偵測
4. 新增 agent 時無標準化的能力宣告格式

### 1.2 使用者場景

**場景 A（正常派發）**：PM 需要派發 Phase 3b 代理人，Registry 提供能力匹配推薦，Hook 驗證選擇合理。

**場景 B（衝突偵測）**：PM 並行派發兩個 agent，Hook 在派發前偵測到 `file_patterns` 交集，輸出 WARNING 並建議改為序列派發。

**場景 C（Phase 相序驗證）**：PM 嘗試在 Phase 1 完成前派發 Phase 2 代理人，Hook 偵測前置條件未滿足，輸出阻止訊息。

**場景 D（推薦查詢）**：PM 執行 `/ticket dispatch recommend 0.1.2-W1-006`，CLI 返回評分排序的候選 agent 清單。

### 1.3 系統邊界

**Registry 負責**：能力宣告的結構化儲存、能力查詢介面、派發驗證的資料層

**Registry 不負責**：
- 決策邏輯（保留在 decision-tree.md）
- 流程路由（保留在 decision-tree.md）
- 行為判斷（保留在各 .md 的觸發條件描述）

## 2. Registry Schema 設計

### 2.1 完整 YAML Schema 定義

```yaml
# .claude/agents/registry.yaml
# Schema Version: 1.0.0
# 用途：Agent 能力宣告的機器可讀 Source of Truth
# 更新原則：每次新增或修改 agent 時同步更新

schema_version: "1.0"  # Major.Minor 格式（Semver 決策 2）

agents:
  {agent-name}:                    # key = agent .md 的 name 欄位（必填）
    name: string                   # 人類可讀名稱（必填）
    version: string                # 能力宣告版本，Major.Minor 格式（必填）
    description: string            # 一行簡介（可選，輔助人類閱讀）
    model: string                  # claude model（必填，如 haiku/sonnet）
    color: string                  # 識別顏色（可選）

    accepts:                       # 此 agent 接受的輸入物件（必填，可空清單）
      - artifact_type: string      # 物件類型識別符（必填）
        required: boolean          # 是否為必要前置輸入（必填）
        format: string             # 預期格式（可選，如 markdown/yaml）
        description: string        # 說明（可選）

    requires:                      # 執行環境能力需求（可選）
      - capability: string         # 能力識別符（如 dart-analysis、git-commit）
        description: string        # 說明（可選）

    produces:                      # 此 agent 產出的物件（必填，可空清單）
      - artifact_type: string      # 物件類型識別符（必填）
        path_pattern: string       # glob 路徑模式（必填，用於衝突檢查）
        format: string             # 輸出格式（可選）
        description: string        # 說明（可選）

    preconditions:                 # 執行前必須滿足的條件（必填，可空清單）
      - condition: string          # 條件描述（結構化字串，見 2.4 節）

    conflict_avoidance:            # 衝突避免規則（必填，可空清單）
      - type: string               # 衝突類型：cannot_work_with | must_complete_before | cannot_work_after
        agents: [string]           # 相關 agent 名稱列表（必填）
        reason: string             # 原因說明（必填）
        scope: string              # 衝突範圍：same_ticket | same_file | global（可選，預設 same_ticket）

    tdd_phases: [string]           # 此 agent 參與的 TDD Phase（必填，可空清單）
                                   # 合法值：phase0 | phase1 | phase2 | phase3a | phase3b | phase4a | phase4b | phase4c
    file_patterns: [string]        # 此 agent 可能寫入的 glob 路徑模式（必填，用於 ARCH-005 衝突檢查）
```

### 2.2 欄位語義詳解

#### `accepts` 欄位

定義 agent 執行前需要哪些輸入物件（前置 Phase 的產出）。

| 子欄位 | 語義 | 格式 | 必填 | 驗證規則 |
|--------|------|------|------|---------|
| `artifact_type` | 物件類型識別符 | kebab-case 字串 | 是 | 不可含空格，只允許小寫字母、數字、連字號 |
| `required` | 是否必要 | boolean | 是 | true = 缺少此輸入則 Hook 阻止派發 |
| `format` | 預期格式 | 自由字串 | 否 | 供人類參考，不驗證 |
| `description` | 說明 | 自由字串 | 否 | 人類可讀說明 |

**已定義的 artifact_type 清單**（實作時可擴充）：

| artifact_type | 說明 | 由誰產出 |
|---------------|------|---------|
| `phase1-feature-spec` | Phase 1 功能規格文件 | lavender-interface-designer |
| `phase2-test-design` | Phase 2 測試設計文件 | sage-test-architect |
| `phase3a-strategy-doc` | Phase 3a 策略文件 | pepper-test-implementer |
| `phase3b-execution-report` | Phase 3b 執行報告 | parsley-flutter-developer |
| `phase4a-analysis-report` | Phase 4a 多視角分析報告 | parallel-evaluation |
| `architecture-review-report` | SA 架構審查報告 | saffron-system-analyst |
| `incident-analysis-report` | 事件分析報告 | incident-responder |
| `new-feature-requirement` | 新功能需求 | PM / user |
| `architecture-change-proposal` | 架構變更提案 | PM / user |
| `error-report` | 錯誤回報 | user / Hook |

#### `produces` 欄位

定義 agent 執行後產出什麼物件，以及寫入哪些路徑。

| 子欄位 | 語義 | 格式 | 必填 | 驗證規則 |
|--------|------|------|------|---------|
| `artifact_type` | 物件類型識別符 | kebab-case | 是 | 同 accepts.artifact_type 規則 |
| `path_pattern` | 產出路徑的 glob 模式 | glob pattern | 是 | 用於衝突檢查（ARCH-005） |
| `format` | 輸出格式 | 自由字串 | 否 | 供人類參考 |
| `description` | 說明 | 自由字串 | 否 | 人類可讀說明 |

#### `preconditions` 欄位

定義 agent 執行前的必要前置條件，Hook 在派發時驗證。

**結構化條件語法**（`condition` 字串格式）：

```
{subject} {verb} {object}
```

支援的動詞：
- `completed` - 某個 Phase 或 Ticket 已完成
- `approved` - 某個審查已通過
- `exists` - 某個資源存在

範例：
```yaml
preconditions:
  - condition: "phase2-test-design completed"
  - condition: "phase3a-strategy completed"
  - condition: "acceptance-auditor approved"
```

#### `conflict_avoidance` 欄位

定義不相容的代理人或派發順序約束。

| `type` 值 | 語義 | 使用場景 |
|----------|------|---------|
| `cannot_work_with` | 不可同時在同一 scope 中工作 | 避免並行寫入衝突、語義衝突 |
| `must_complete_before` | 必須在指定 agent 之前完成 | TDD Phase 相序約束 |
| `cannot_work_after` | 必須在指定 agent 之前執行 | 前置審查約束 |

**scope 定義**：

| scope 值 | 語義 |
|---------|------|
| `same_ticket` | 在同一 Ticket 範圍內（預設） |
| `same_file` | 若 file_patterns 有交集則衝突 |
| `global` | 全域不相容（無論 Ticket 是否相同） |

#### `tdd_phases` 欄位

列出此 agent 負責的 TDD Phase，用於 Phase 相序驗證。

合法值：`phase0`, `phase1`, `phase2`, `phase3a`, `phase3b`, `phase4a`, `phase4b`, `phase4c`

#### `file_patterns` 欄位

此 agent 在執行時可能寫入的所有路徑模式（glob 格式），用於 ARCH-005 衝突檢查。

**重要**：這是 `produces[*].path_pattern` 的扁平化彙整，方便衝突檢查演算法快速比對。實作時兩者必須保持同步。

### 2.4 Registry 完整性驗證規則

每個 agent entry 必須通過以下驗證：

| 驗證項目 | 規則 | 嚴重程度 |
|---------|------|---------|
| 必填欄位存在 | `name`, `version`, `accepts`, `produces`, `preconditions`, `conflict_avoidance`, `tdd_phases`, `file_patterns` | ERROR |
| agent key 唯一性 | 不允許重複 key | ERROR |
| artifact_type 格式 | kebab-case，只含 `[a-z0-9-]` | ERROR |
| path_pattern 合法性 | 有效 glob 語法 | ERROR |
| tdd_phases 值域 | 只允許預定義的 Phase 名稱 | ERROR |
| conflict_avoidance.agents 存在 | 引用的 agent 必須在 registry 中存在 | WARNING |
| file_patterns 與 produces 一致 | file_patterns 應涵蓋所有 produces.path_pattern | WARNING |
| version 格式 | Major.Minor 格式（如 `1.0`）| WARNING |

## 3. 三層架構分工規格

### 3.1 架構概述

```
decision-tree.md（決策引擎）
    → 判斷「需要什麼類型的 Agent」（行為判斷、流程路由）
    ↓  輸出：能力需求（如 tdd_phase = phase3b, file_type = dart）

registry.yaml（能力資料層 Source of Truth）
    → 查詢「哪個 Agent 有這個能力」（純資料查詢）
    ↓  輸出：候選 agent 清單 + 評分

agent-dispatch-validation-hook（驗證層）
    → 確認「選定的 Agent 確實符合需求且無衝突」（執行前驗證）
    ↓  輸出：允許派發 / WARNING / 阻止訊息
```

### 3.2 各層職責邊界

#### decision-tree.md 層

**負責**：
- 所有流程路由和條件判斷（if/else 邏輯）
- TDD Phase 推進決策（何時進入下一 Phase）
- 事件分類和派發類型決策
- 並行 vs 序列評估

**禁止**：
- 儲存 agent 能力資料
- 直接引用 agent 的技術限制（如「parsley 只能寫 Dart」）
- 成為 registry 資料的消費者（只能引用 registry 的查詢結果）

**與 Registry 的互動**：decision-tree 的「派發給誰」環節**可以**引用 registry 推薦結果（`dispatch recommend` 輸出），但核心決策邏輯不依賴 registry。

#### registry.yaml 層

**負責**：
- 儲存所有 agent 的能力宣告（accepts/produces/preconditions）
- 提供能力查詢介面（`dispatch recommend` 的資料源）
- 衝突規則宣告（conflict_avoidance）
- 成為能力資訊的 Single Source of Truth

**禁止**：
- 包含任何決策邏輯（不應有 if/else）
- 定義流程路由
- 取代 decision-tree.md 的角色

**不取代 decision-tree 的保證機制**：
- registry.yaml 只包含宣告式資料，沒有可執行邏輯
- decision-tree.md 的「第五層 TDD 階段判斷」保留為決策規則，registry 只補充機器可讀的驗證能力
- Phase 推進決策（如「Phase 2 完成後進入 Phase 3a」）永遠在 decision-tree.md 中定義，registry 只宣告「哪個 agent 負責 Phase 3a」

#### 驗證 Hook 層

**負責**：
- 在 agent 派發時讀取 registry 執行三種衝突檢查
- 輸出 WARNING 或阻止訊息（雙通道：stderr + 日誌檔）
- 提供修正建議

**禁止**：
- 修改派發決策（只能警告，不能自動重定向）
- 儲存狀態（每次派發獨立驗證）
- 包含 decision-tree 的邏輯

### 3.3 互動協定

```
1. PM（decision-tree 路由決策）
   → 執行 /ticket dispatch recommend {ticket-id}
   → 接收評分候選清單

2. PM 選定 agent
   → 觸發 Agent tool 派發（含 agent 名稱）

3. PreToolUse Hook（agent-dispatch-validation-hook）
   → 攔截 Agent tool 呼叫
   → 讀取 registry.yaml
   → 執行三種衝突檢查
   → 輸出結果（通過 / WARNING / 阻止）

4. 派發執行
   → 若 Hook 通過：agent 執行
   → 若 Hook 輸出 WARNING：PM 自行決定是否繼續（Warning 不阻止）
   → 若 Hook 輸出阻止：派發被攔截，PM 需修正
```

## 4. 三種衝突檢查規格

### 4.1 衝突類型一：Agent 同時派發衝突

**問題**：同一 Ticket 派發給語義上不相容的 agent 組合（如兩個都要負責 Phase 3b 的 agent）。

**判定規則**：

```
當派發 agent B 時，檢查：
1. 讀取 registry.yaml 中 B 的 conflict_avoidance 清單
2. 遍歷目前已對同一 Ticket 派發的所有 agent（來源：Ticket execution log 或工作上下文）
3. 若任一已派發 agent 出現在 B.conflict_avoidance[type="cannot_work_with"].agents 中：
   → 輸出 WARNING（scope=same_ticket 時）
   → 輸出阻止訊息（scope=global 時）
```

**`conflict_avoidance` 欄位使用範例**：

```yaml
conflict_avoidance:
  - type: "cannot_work_with"
    agents: ["parsley-flutter-developer"]  # 自己不可和自己同時在同一 Ticket
    reason: "同一 agent 重複派發"
    scope: "same_ticket"

  - type: "cannot_work_with"
    agents: ["cinnamon-refactor-owl"]
    reason: "Phase 3b 和 Phase 4b 不可並行（同時修改 Dart 檔案）"
    scope: "same_file"  # 只有 file_patterns 有交集時才觸發
```

**輸出格式**：

```
[CONFLICT WARNING] Agent 派發衝突偵測
衝突類型: Agent 同時派發衝突
目標 Agent: cinnamon-refactor-owl
衝突原因: Phase 3b 和 Phase 4b 不可並行（同時修改 Dart 檔案）
已派發 Agent: parsley-flutter-developer（同一 Ticket）
建議修正:
  1. 確認 parsley-flutter-developer 已完成並 commit
  2. 再派發 cinnamon-refactor-owl
```

### 4.2 衝突類型二：TDD Phase 相序衝突

**問題**：Phase 執行順序違反 TDD 流程規範（如在 Phase 1 未完成前派發 Phase 2）。

**Phase 依賴鏈定義**：

```
phase0 → phase1 → phase2 → phase3a → phase3b → phase4a → phase4b → phase4c
```

完整依賴表（允許跳過豁免規則，見 tdd-flow.md）：

| Phase | 必須先完成 | 豁免條件 |
|-------|----------|---------|
| phase1 | phase0（SA 前置審查）| 小型修改 / Bug 修復不需要 SA |
| phase2 | phase1 | 無 |
| phase3a | phase2 | 無 |
| phase3b | phase3a | 無 |
| phase4a | phase3b | 小型修改 / DOC / 單純任務可豁免跳到 phase4b |
| phase4b | phase4a（或豁免） | 見豁免條件 |
| phase4c | phase4b | 豁免時（小型/DOC/單純）直接完成，不進 phase4c |

**判定規則**：

```
當派發 agent A（負責 phase_x）時，檢查：
1. 從 Ticket 的 tdd_stage 欄位取得目前進行的 Phase
2. 查詢 phase_x 的所有前置依賴 Phase
3. 若任一前置 Phase 的 artifact 在 Ticket Execution Log 中尚未標記完成：
   → 輸出阻止訊息
4. 若前置 Phase 的 agent 尚未被派發（registry 查詢 tdd_phases）：
   → 輸出 WARNING
```

**輸出格式**：

```
[CONFLICT BLOCK] TDD Phase 相序衝突偵測
目標 Agent: sage-test-architect（phase2）
衝突原因: Phase 1 尚未完成，不可派發 Phase 2
缺少前置條件:
  - phase1-feature-spec: 未在 Execution Log 中標記完成
建議修正:
  1. 先完成 Phase 1（派發 lavender-interface-designer）
  2. Phase 1 完成後再派發 Phase 2
```

### 4.3 衝突類型三：檔案寫入衝突（ARCH-005）

**問題**：多個並行 agent 的 `file_patterns` 有交集，可能導致 git merge conflict 或資料覆蓋。

**`file_patterns` 比對演算法**：

```python
def check_file_write_conflict(agent_a: str, agent_b: str, registry: dict) -> list[str]:
    """
    比對兩個 agent 的 file_patterns 是否有潛在交集。
    返回衝突路徑模式清單（空清單表示無衝突）。
    """
    patterns_a = set(registry[agent_a]['file_patterns'])
    patterns_b = set(registry[agent_b]['file_patterns'])
    conflicts = []

    for pattern_a in patterns_a:
        for pattern_b in patterns_b:
            if patterns_overlap(pattern_a, pattern_b):
                conflicts.append((pattern_a, pattern_b))

    return conflicts

def patterns_overlap(pattern_a: str, pattern_b: str) -> bool:
    """
    判斷兩個 glob 模式是否可能匹配到同一個檔案。
    使用保守策略：若無法確定不相交，則視為有交集。

    演算法步驟：
    1. 提取兩個 pattern 的目錄前綴（最後一個 ** 或 * 之前的部分）
    2. 若目錄前綴 A 是 B 的前綴（或反之），視為有交集
    3. 若兩者的目錄前綴相同，視為有交集
    4. 其他情況視為無交集（保守）

    範例：
    - "ui/lib/**/*.dart" vs "ui/lib/core/*.dart" → 有交集（後者在前者範圍內）
    - "ui/lib/**/*.dart" vs "server/**/*.go" → 無交集（不同根目錄）
    - "docs/work-logs/**/*.md" vs "docs/work-logs/*/tickets/*.md" → 有交集
    """
    prefix_a = extract_dir_prefix(pattern_a)
    prefix_b = extract_dir_prefix(pattern_b)

    return (prefix_a.startswith(prefix_b) or
            prefix_b.startswith(prefix_a))
```

**判定規則**：

```
當同時派發 agent A 和 agent B 時（並行派發場景）：
1. 從 registry 讀取 A.file_patterns 和 B.file_patterns
2. 執行 check_file_write_conflict(A, B, registry)
3. 若衝突清單非空：
   → 輸出 WARNING（非阻止，因為 PM 可能故意序列執行）
4. 若衝突 pattern 包含核心檔案（如 constants.dart、settings.json）：
   → 輸出強烈 WARNING，建議改為序列派發
```

**ARCH-005 回溯測試案例**：

| 測試場景 | Agent A | Agent B | 預期結果 |
|---------|---------|---------|---------|
| 兩個 parsley 並行同一 ticket | parsley | parsley | WARNING（cannot_work_with + file 衝突） |
| parsley 和 cinnamon 並行 | parsley | cinnamon | WARNING（file_patterns 交集：ui/lib/**/*.dart） |
| parsley 和 fennel 並行 | parsley | fennel | 通過（ui/lib vs server/，無交集） |
| sage 和 lavender 並行 | sage | lavender | 通過（docs/tickets/\*-phase2-\* vs docs/tickets/\*-phase1-\*，無實際交集） |

**輸出格式**：

```

```

**參數說明**：

| 參數 | 說明 | 預設值 |
|------|------|--------|
| `ticket-id` | 目標 Ticket ID（必填） | - |
| `--top N` | 只返回前 N 名候選 | 5 |
| `--phase <name>` | 只考慮特定 TDD Phase 的 agent | 無（全部考慮） |
| `--dry-run` | 僅輸出評分，不執行任何驗證 | false |

### 5.2 評分演算法

**總分計算公式**：

```
total_score = type_match_score + precondition_score + file_conflict_penalty + phase_match_score
```

**各項分數定義**：

| 評分項目 | 滿分 | 計算方法 | 說明 |
|---------|------|---------|------|
| `type_match_score` | 40 | 40 × (匹配 accepts 的必要 artifact 數 / 總必要 artifact 數) | Ticket 的現有產出是否符合 agent 的必要輸入 |
| `precondition_score` | 30 | 30 × (已滿足的 precondition 數 / 總 precondition 數) | 前置條件滿足程度 |
| `phase_match_score` | 20 | 若 Ticket.tdd_stage 包含 agent.tdd_phases 中的值則 +20，否則 0 | Phase 相符程度 |
| `file_conflict_penalty` | 0（懲罰分） | 若 file_patterns 有衝突：-100（致命） | 衝突是致命的，使候選分數變為負數 |

```

    precondition_score: 0（phase3b 未完成 = 0/30）
    phase_match_score: 0（tdd_phases=[phase4b] 不符合目前 phase3b）
    file_conflict_penalty: 0
    total: 0 ← 不推薦（前置條件不足）

  sage-test-architect:
    type_match_score: 40（不需要 phase3a artifact）
    precondition_score: 30（preconditions 均有）
    phase_match_score: 0（tdd_phases=[phase2] 不符合）
    file_conflict_penalty: 0

```

### 5.4 豁免理由清單

dry-run 符合率 < 100% 的合法豁免理由：

| 豁免代碼 | 說明 | 範例場景 |
|---------|------|---------|

## 9. 已知邊界條件與限制

### 9.1 file_patterns 比對的保守策略

glob 模式的精確交集計算（需要完整 glob 展開）在 registry 靜態資料上成本過高。採用**保守策略**：目錄前綴相同即視為有潛在交集，可能產生少量誤報（false positive）。

**接受此限制的理由**：
- 誤報（輸出不必要的 WARNING）比漏報（未偵測到真實衝突）危害小
- PM 看到 WARNING 後可手動確認是否真的有衝突
- 實際使用中同一目錄下的不同 agent 並行派發極少發生

### 9.2 preconditions 驗證的靜態限制

`preconditions` 的結構化條件語法（`{subject} {verb} {object}`）依賴 Ticket Execution Log 的格式。若 Execution Log 格式不標準，動詞 `completed` 的判斷可能失敗。

**緩解措施**：
- 明確定義 Execution Log 中 Phase 完成的標記格式（Phase 2 完成 = 文件中出現 `Phase 2 完成` 或 `tdd_phase: phase2` 標記）
- 驗證失敗時輸出 WARNING 而非 ERROR，不阻止派發

### 9.3 Registry 與 .md 同步

Registry 是從 .md 手動提取的，可能隨時間出現不一致。

**緩解措施**：
- 交叉驗證工具（006.1 的驗收條件）可偵測明顯不一致
- agent .md 更新時應同步更新 registry.yaml（由 Phase 4b 重構流程的 cinnamon 負責）
