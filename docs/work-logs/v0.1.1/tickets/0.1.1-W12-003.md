## 設計分析完成

### 核心問題識別

**PC-015 錯誤根因**：當 ticket CLI 回傳非預期錯誤時，PM 直接依照錯誤提示中的建議操作（如加 --version 參數）繞過問題，未追問根因，未建立 Ticket。這導致底層配置問題（如 todolist.yaml 過期）持續存在，影響所有後續命令。

**與 PC-005 的關係**：
- PC-005（CLI 失敗假設歸因）：關注「錯誤分類」——區分是語法問題還是邏輯問題
- PC-015（錯誤提示靜默繞過）：關注「行為流程」——強制建立 Ticket 追蹤根因

### 規則建議位置

建議在 incident-response.md 中新增「ticket CLI 非預期錯誤處理」規則章節。

### 錯誤類型分類建議

| 錯誤類型 | 判斷標準 | 處理方式 |
|---------|---------|---------|
| 預期錯誤 | 使用者輸入驗證失敗（缺參數、格式錯誤） | 修正輸入後重試 |
| 指導性錯誤 | 業務邏輯驗證失敗（Ticket 狀態不符、驗收條件未滿足） | 按錯誤提示修正業務邏輯 |
| 非預期錯誤 | 系統內部錯誤（版本偵測失敗、Ticket 查詢異常） | 必須建立 Ticket 追蹤 |

### 強制流程（建議）

ticket 命令回傳非零退出碼時：
1. Step 1：區分錯誤類型
2. Step 2：禁止直接依照錯誤提示繞過（如加 --version、--force）
3. Step 3：立即執行 /ticket create 建立 pending Ticket
4. Step 4：升級給 incident-responder 分析

### 預期 vs 非預期判斷標準

**預期錯誤範例**：
- "Missing required argument: --version"
- "Invalid version format: abc123"
- "Invalid ticket ID format"

**指導性錯誤範例**：
- "Ticket 0.1.1-W9-001 is not in 'in_progress' state, cannot complete"
- "Cannot complete: 3 acceptance criteria not checked"
- "Please run 'check-acceptance' before complete"

**非預期錯誤範例**：
- "Version detection error: expected v0.1.1 but got v0.1.0"
- "Ticket 0.1.1-W9-001 not found" （無明確原因）
- "KeyError: 'current_version'"

### 禁止行為

- 收到非預期錯誤後直接加參數繞過（如 --version、--force）
- 基於錯誤提示猜測原因並自行修復
- 重複執行相同命令期望不同結果
- 忽略錯誤繼續工作，期望後續命令恢復正常

### 與 PC-005 的區別

PC-005（CLI 失敗假設歸因）：強調調查步驟（查語法→歸因），適用所有 CLI 工具
本規則：強調行為流程（非預期錯誤必須建 Ticket），特化於 ticket CLI

### Hook 建議

- 觸發條件：ticket 命令執行且 exit code != 0
- 判斷方式：識別非預期錯誤關鍵字（黑名單：version error、KeyError、unexpected）
- 排除：預期/指導性錯誤（白名單：Missing argument、Invalid format、not in、not checked）
- 動作：輸出友好提示（不阻止操作）建議建立 Ticket

### 實作時序建議

Phase 1：在 incident-response.md 新增規則章節（強制）
Phase 2：實作 PostToolUse Hook（可選，增強防護）
Phase 3：更新 ticket CLI help 和常見問題（可選）

### 適用場景

情境 1：版本偵測錯誤（PC-015 原始案例）
- 命令失敗：`ticket handoff 0.1.1-W9-002 --to 0.1.1-W9-003`
- 錯誤訊息：「找不到 Ticket，版本偵測錯誤（當前偵測版本: v0.1.0）」
- 根因：todolist.yaml current_version 過期
- 強制流程：建立 Ticket，不加 --version 繞過

情境 2：Ticket 查詢異常
- 命令失敗：`ticket track claim 0.1.1-W10-001`
- 錯誤訊息：「KeyError: 'tdd_phase'」
- 根因：Ticket 檔案格式缺陷或資料讀取邏輯問題
- 強制流程：建立 Ticket，升級 incident-responder

### 設計決策總結

1. 規則位置：納入現有 incident-response.md（不新增檔案）
2. 錯誤分類：三層分類（預期/指導性/非預期）
3. Ticket 時序：先建 Ticket，再報告上層
4. Hook 策略：友好提示（不阻止操作）
5. 受影響檔案：主要修改 incident-response.md，可選新增 Hook
