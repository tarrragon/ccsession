# Phase 2 測試設計

## 測試設計策略

### 測試架構概述

此模組為 Python 指令行工具，核心為 `create_feature_worktree()` 函式和 `main()` 入口。測試設計分為三層：

1. **單元層 (Unit)**: 測試 `create_feature_worktree()` 函式的核心邏輯
2. **輔助函式層**: 測試 `branch_exists()` 和 `worktree_exists()` 等驗證功能
3. **整合層 (Integration)**: 測試 `main()` 的命令列介面，含 dry-run 和實際執行路徑

### 層級測試決策

按照 Sociable Unit Tests 原則：

| 層級 | 被測試物件 | 隔離策略 | 目標 |
|------|-----------|--------|------|
| **單元** | `create_feature_worktree()` 函式 | Mock `run_git_command()` | 驗證前置條件檢查和 git 命令邏輯 |
| **輔助** | `branch_exists()`, `worktree_exists()` | Mock `run_git_command()` 和 `os.path.exists()` | 驗證檢查邏輯 |
| **整合** | `main()` 和 argparse | Mock `subprocess.run()` 或使用真實 git repo（測試環境） | 驗證 CLI 介面和流程 |

### Mock 策略

根據 Sociable Unit Tests 原則，只 Mock 外部世界（git 命令、檔案系統）：

| 依賴 | Mock? | 理由 |
|------|-------|------|
| `run_git_command()` | 是 | 外部系統依賴（git），測試應隔離 |
| `subprocess.run()` | 是 | 實際執行會修改版本控制狀態，測試環境難以回滾 |
| `os.path.exists()` | 是 | 檔案系統依賴，測試應隔離 |
| `os.path.abspath()` | 否 | 內層邏輯，直接使用真實函式 |
| 前置驗證邏輯 | 否 | 核心業務邏輯，直接測試 |

### 測試分層決策

- **層級 1: 單元測試（必須）** — 前置驗證、原子命令、錯誤處理
- **層級 2: 整合測試（可選）** — CLI 介面、dry-run 輸出（可在手動驗證中測試）

### A. 單元測試：`create_feature_worktree()` 函式

#### UT-01: 正常流程 — 原子命令成功

```gherkin
場景 UT-01: git worktree add -b 命令成功執行

Given:
  - branch = "feat/abc"
  - worktree_path = "../project-abc"（轉換為絕對路徑）
  - base_branch = "main"
  - worktree_exists() 回傳 False
  - branch_exists() 對 "feat/abc" 回傳 False
  - branch_exists() 對 "main" 回傳 True
  - run_git_command(["worktree", "add", "-b", "feat/abc", "{abs_path}", "main"]) 回傳 (True, "")

When:
  呼叫 create_feature_worktree("feat/abc", "../project-abc", "main")

Then:
  - 回傳值為 (True, "成功創建分支 'feat/abc' 和 worktree '{abs_path}'")
  - 確認呼叫了 run_git_command(["worktree", "add", "-b", ...]) 一次
  - 確認沒有呼叫 run_git_command(["branch", "-D", ...])（無回滾邏輯）
  - 確認沒有執行其他 git 命令
```

**測試實作**:

```python
def test_create_feature_worktree_success(mocker):
    """UT-01: 正常流程 — 原子命令成功"""
    # Setup
    mock_worktree_exists = mocker.patch(
        'create_feature_worktree.worktree_exists',
        return_value=False
    )
    mock_branch_exists = mocker.patch(
        'create_feature_worktree.branch_exists',
        side_effect=lambda b: b in ["main"]  # 只有 main 存在
    )
    mock_run_git = mocker.patch(
        'create_feature_worktree.run_git_command',
        return_value=(True, "")
    )

    # Act
    success, message = create_feature_worktree(
        branch="feat/abc",
        worktree_path="../project-abc",
        base_branch="main"
    )

    # Assert
    assert success is True
    assert "feat/abc" in message
    assert abs_path in message  # 驗證絕對路徑在回傳訊息中

    # 驗證 git 命令呼叫（核心）
    mock_run_git.assert_called_once_with(
        ["worktree", "add", "-b", "feat/abc", abs_path, "main"]
    )

    # 驗證沒有執行回滾
    assert not any(
        "branch" in str(call) and "-D" in str(call)
        for call in mock_run_git.call_args_list
    )
```

**驗收標準對應**:
- ✓ 驗證 1：使用 `git worktree add -b` 單一命令
- ✓ 驗證 2：確認無手動回滾邏輯
- ✓ 驗證 3：正常流程執行成功

**測試實作**:

```python
def test_create_feature_worktree_git_command_fails(mocker):
```

## 測試設計決策記錄

### 決策 1：Mock 策略

**決定**：只 Mock `run_git_command()`、`subprocess.run()` 和 `os.path.exists()`

**理由**：
- 根據 Sociable Unit Tests 原則，只隔離外部世界（git 命令、檔案系統）
- 前置驗證邏輯是核心業務邏輯，應直接測試
- `os.path.abspath()` 是內層工具函式，直接使用真實實作

---

### 決策 2：測試分層

**決定**：分為三層 — 單元、輔助、整合

**理由**：
- 單元層專注核心函式邏輯
- 輔助層驗證檢查函式（重要的防禦線）
- 整合層驗證 CLI 介面和流程

---

### 決策 3：dry-run 模式測試

**決定**：以 IT-01 形式驗證 dry-run 輸出改為顯示單一 git 命令

**理由**：
- Phase 1 規定 dry-run 應顯示 `git worktree add -b` 命令
- 整合測試驗證 CLI 輸出符合需求
- 測試應確認未執行任何 git 命令

---

### 決策 4：邊界條件覆蓋

**決定**：在 UT 中補充邊界條件（分支含斜線、遠端追蹤分支等）

**理由**：
- Phase 1 識別了 5 種邊界情境

- 確保實作階段無遺漏
