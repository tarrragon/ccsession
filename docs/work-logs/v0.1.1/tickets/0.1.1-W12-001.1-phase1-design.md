## 1. 功能需求分析

### 1.1 核心問題

當前 `ticket create` 命令建立 Ticket 時，`decision_tree_path` 欄位不在 frontmatter 輸出中。使用者必須在派發時才被 `agent-ticket-validation-hook` 阻擋，才補填欄位。這造成：

1. **流程中斷**：建立 → 被擋 → 補填 → 重新派發，浪費 context
2. **語意錯位**：決策路徑應在決策當下記錄，不是事後補填
3. **設計意圖違反**：`decision_tree_path` 的設計意圖是「記錄建立 Ticket 時的決策依據」，而非「派發時的補填欄位」

### 1.2 目標使用者場景

**場景 A：正常建立（提供所有參數）**

```
PM 決策完成後，執行 ticket create，同時傳入 decision_tree_path 三個子欄位。
Ticket 建立成功，frontmatter 包含完整的 decision_tree_path。
派發時 Hook 驗證通過，無需補填。
```

**場景 B：缺少 decision_tree_path（CLI 強制）**

```
PM 執行 ticket create 但未提供 --decision-tree-entry/decision/rationale。
CLI 拒絕建立，輸出清楚的錯誤訊息，說明缺少哪些參數。
PM 補充參數後重新執行，Ticket 順利建立。
```

**場景 C：直接編輯 .md 繞過 CLI（Hook 後防）**

```
使用者直接編輯 Ticket .md 檔，或透過未更新的自動化腳本建立 Ticket。
PostToolUse Hook 在檔案寫入後掃描 frontmatter。
缺少 decision_tree_path → Hook 輸出警告訊息 + 記錄日誌（不阻止建立）。
派發時 agent-ticket-validation-hook 仍為最終防線。
```

**場景 D：子任務豁免**

```
PM 建立子任務（--parent 參數），子任務繼承父任務的決策脈絡。
CLI 不強制要求子任務提供 decision_tree_path（父任務已記錄決策）。
Hook 同樣對子任務寬鬆（僅建議，不警告）。
```

**場景 E：DOC 類型任務豁免**

```
PM 建立純文件類型 Ticket（--type DOC）。
DOC 任務不涉及技術派發決策，decision_tree_path 為選填。
CLI 不強制要求，Hook 對 DOC 類型豁免警告。
```

## 2. 功能規格設計

### 2.1 decision_tree_path 欄位格式規範

欄位值為固定三子欄位的 YAML 映射結構（不接受自由文字字串）：

```yaml
decision_tree_path:
  entry_point: <非空字串>    # 進入決策樹的層級名稱
  final_decision: <非空字串> # 做出的最終決策
  rationale: <非空字串>      # 決策理由（一句話說明）
```

**entry_point 合法值範例**（來自 `.claude/rules/core/decision-tree.md`）：

| 值 | 說明 |
|----|------|
| 第負一層 並行化評估 | 並行化拆分決策 |
| 第零層 明確性檢查 | 確認訊息明確性 |
| 第一層 訊息類型判斷 | 問題或命令判斷 |
| 第二層 問題處理流程 | 查詢類處理 |
| 第三層 命令處理流程 | 開發命令處理 |
| 第三層半 執行中額外發現 | 執行中發現技術債 |
| 第四層 Ticket 執行流程 | Ticket 認領與執行 |
| 第五層 TDD 階段判斷 | TDD Phase 路由 |
| 第六層 事件回應流程 | 錯誤修復流程 |
| 第七層 完成判斷流程 | 完成與驗收 |
| 第八層 完成後路由 | Commit 後路由 |

**驗證規則**：
- 三個子欄位必須全部存在且非空字串
- entry_point 不限制於上方清單（允許自由描述，清單僅供參考）
- 不接受整個 decision_tree_path 為空字串或 null

### 2.2 CLI 介面設計（方案 A）

#### 新增 CLI 參數

在 `ticket create` 命令新增三個可選（但組合必填）的參數：

| 參數名稱 | 類型 | 必填性 | 說明 |
|---------|------|-------|------|
| `--decision-tree-entry` | 字串 | 條件必填（見豁免規則） | entry_point 值 |
| `--decision-tree-decision` | 字串 | 條件必填 | final_decision 值 |
| `--decision-tree-rationale` | 字串 | 條件必填 | rationale 值 |

**組合規則**：三個參數必須**全部提供**或**全部省略**（不接受部分提供）。

**強制條件**（以下情況必須全部提供）：
- 根任務（`--parent` 未指定）
- 類型為 IMP、TST、ADJ、ANA、INV、RES（任何非 DOC 類型）

**豁免條件**（以下情況為選填，省略時 frontmatter 不輸出此欄位）：
- 子任務（指定了 `--parent`）
- 類型為 DOC

#### 拒絕行為

缺少參數時（不符合豁免條件）：
- 輸出明確錯誤訊息（不建立 Ticket，return exit code 1）
- 錯誤格式：`[ERROR] 缺少 decision_tree_path 必填欄位`
- 附帶說明哪個欄位缺少，以及如何補充

#### CLI 用法範例

正確用法：
```bash
ticket create \
  --action "實作" --target "功能 X" \
  --decision-tree-entry "第五層 TDD 階段判斷" \
  --decision-tree-decision "派發 Phase 3b 給 parsley" \
  --decision-tree-rationale "Phase 2 測試設計已完成，進入實作階段"
```

子任務豁免（無需提供）：
```bash
ticket create \
  --parent "0.1.1-W12-001" \
  --action "設計" --target "API 介面"
```

DOC 豁免（可選提供）：
```bash
ticket create \
  --type DOC \
  --action "更新" --target "README 文件"
```

**有 decision_tree_path 時**（正常建立）：

```yaml

```

**豁免情況**（子任務或 DOC，且未提供參數）：

```yaml

...

...

```

**豁免情況但有提供**（選填時使用者主動提供）：

輸出正常結構，不省略。

### 2.4 PostToolUse Hook 設計（方案 B）

#### Hook 基本資訊

| 項目 | 值 |
|------|---|
| 檔案名稱 | `ticket-creation-validation-hook.py` |
| Hook 類型 | PostToolUse |
| 觸發工具 | Write（寫入 .md 檔案時） |
| 觸發路徑模式 | `docs/work-logs/*/tickets/*.md` |
| 行為 | 輸出警告（不阻止，exit code 0） |

#### Hook 觸發條件

1. PostToolUse 事件，工具為 Write
2. 寫入的檔案路徑符合 Ticket 路徑模式
3. 檔案內容包含有效的 YAML frontmatter（含 `---` 邊界）

#### Hook 驗證邏輯

```
讀取寫入的檔案 → 解析 frontmatter
    |
    v
是子任務？（parent_id 非空）→ 是 → 跳過（子任務豁免）
    |
    v
類型為 DOC？ → 是 → 跳過（DOC 豁免）
    |
    v
decision_tree_path 存在且三子欄位非空？ → 是 → 跳過（已完整）
    |
    v
輸出 [WARNING] 警告訊息 + 寫入日誌（exit code 0）
```

#### Hook 輸出訊息格式

```
[TICKET CREATION VALIDATION]
警告：Ticket {ticket_id} 缺少 decision_tree_path 欄位

此欄位在派發時為必填。請在派發前補充：
  decision_tree_path:
    entry_point: <進入決策樹的層級>
    final_decision: <做出的決策>
    rationale: <決策理由>

派發時由 agent-ticket-validation-hook 執行最終驗證。
```

## 3. 邊界條件分析

### 3.1 CLI 邊界條件

| 情境 | 輸入 | 預期行為 |
|------|------|---------|
| 只提供 1/3 參數 | `--decision-tree-entry "X"` | 錯誤：必須全部提供，輸出缺少的欄位名稱 |
| 只提供 2/3 參數 | `--decision-tree-entry "X" --decision-tree-decision "Y"` | 錯誤：缺少 rationale |
| 參數值為空字串 | `--decision-tree-entry ""` | 錯誤：不允許空字串值 |
| 參數值含特殊字元 | `--decision-tree-rationale "含「引號」和：冒號"` | 正常：YAML 序列化時正確轉義 |
| 子任務不提供 | `--parent "X"` 無 decision-tree-* | 正常：frontmatter 輸出 `decision_tree_path: null` |
| 子任務有提供 | `--parent "X" --decision-tree-entry "..."` | 正常：使用提供的值 |
| DOC 類型不提供 | `--type DOC` 無 decision-tree-* | 正常：frontmatter 輸出 `decision_tree_path: null` |
| 非 DOC 根任務不提供 | 標準建立，無 decision-tree-* | 錯誤：拒絕建立，輸出提示 |

### 3.2 Hook 邊界條件

| 情境 | 預期行為 |
|------|---------|
| 寫入非 Ticket 路徑的 .md 檔 | Hook 跳過（不在 Ticket 路徑模式） |
| Ticket 檔案無有效 frontmatter | Hook 跳過（無法解析，不誤報） |
| frontmatter 有 decision_tree_path 但子欄位空 | 輸出警告（視同缺少） |
| frontmatter decision_tree_path 為 null | 子任務或 DOC 豁免跳過；否則輸出警告 |
| 同一 Ticket 多次寫入 | 每次寫入都觸發，但已完整時不輸出警告 |
| Hook 執行錯誤（解析失敗） | 寫入 stderr + 日誌，exit code 0（不阻止） |

### 3.3 bulk_create 和 generate 邊界條件

`bulk_create.py` 和 `generate.py` 是批量建立命令，不直接接受 decision_tree_path 參數（批量建立的決策脈絡通常共用同一個）。

**處理方式**：
- 批量建立時 decision_tree_path 欄位輸出為 `null`
- 使用者在批量建立後手動編輯補填（由 Hook 提示）
- 這是可接受的折衷方案（批量建立不是標準工作流程）

#### execute() 新增驗證邏輯

在現有參數處理完成後、建立 TicketConfig 之前，插入以下驗證：

```python
# 處理 decision_tree_path
decision_tree_path = _build_decision_tree_path(
    entry=args.decision_tree_entry,
    decision=args.decision_tree_decision,
    rationale=args.decision_tree_rationale,
    is_child=bool(args.parent),
    ticket_type=args.type or "IMP",
)
if decision_tree_path is False:
    # 驗證失敗：缺少必填欄位
    return 1
```

#### 新增 _build_decision_tree_path() 私有函式

```python
def _build_decision_tree_path(
    entry: Optional[str],
    decision: Optional[str],
    rationale: Optional[str],
    is_child: bool,
    ticket_type: str,
) -> Optional[Dict[str, str]] | Literal[False]:
    """
    建立 decision_tree_path 字典，或在驗證失敗時返回 False。

    Returns:
        - Dict[str, str]: 完整的 decision_tree_path 值
        - None: 豁免條件（子任務或 DOC），前者無需欄位
        - False: 驗證失敗（應中止建立）
    """
```

**函式行為**：

| 情境 | 返回值 |
|------|-------|
| 豁免（is_child 或 DOC） + 無提供 | `None` |
| 豁免（is_child 或 DOC） + 有提供（完整） | `{"entry_point": ..., "final_decision": ..., "rationale": ...}` |
| 非豁免 + 全部提供（值非空） | `{"entry_point": ..., "final_decision": ..., "rationale": ...}` |
| 非豁免 + 全部未提供 | 輸出錯誤訊息，返回 `False` |
| 任何情況 + 部分提供（1 或 2 個） | 輸出錯誤訊息（說明缺少哪個），返回 `False` |
| 任何情況 + 有提供但值為空字串 | 輸出錯誤訊息（不允許空字串），返回 `False` |

## 5. 驗收標準

### 5.1 CLI 驗收條件

| 編號 | 驗收條件 | 驗證方法 |
|------|---------|---------|
| A-1 | 根任務（非 DOC）呼叫 `ticket create` 未提供 decision-tree-* 參數時，CLI 拒絕建立並輸出 DECISION_TREE_MISSING_ALL 訊息 | 執行指令，確認 exit code 1 且訊息含「缺少 decision_tree_path」 |
| A-2 | 只提供部分參數（1 或 2 個）時，CLI 拒絕建立並輸出 DECISION_TREE_MISSING_PARTIAL 訊息，說明缺少的欄位 | 執行含部分參數的指令，確認錯誤訊息列出缺少欄位 |
| A-3 | 提供值為空字串的參數時（`--decision-tree-entry ""`），CLI 拒絕並輸出 DECISION_TREE_EMPTY_VALUE | 執行含空字串的指令，確認錯誤訊息 |
| A-4 | 提供完整三個參數且值非空時，Ticket 正常建立，frontmatter 包含 decision_tree_path 三子欄位 | 建立後讀取 .md 檔，確認 YAML 結構正確 |
| A-5 | 子任務（--parent）不提供 decision-tree-* 時，Ticket 正常建立，frontmatter 的 decision_tree_path 為 null | 執行子任務建立，讀取 frontmatter 確認 |
| A-6 | DOC 類型不提供 decision-tree-* 時，Ticket 正常建立，frontmatter 的 decision_tree_path 為 null | 執行 DOC 建立，讀取 frontmatter 確認 |
| A-7 | 子任務主動提供 decision-tree-* 時，frontmatter 正確輸出（選填有效） | 執行含參數的子任務建立，確認輸出 |

### 5.2 Hook 驗收條件

| 編號 | 驗收條件 | 驗證方法 |
|------|---------|---------|
| H-1 | 寫入缺少 decision_tree_path 的非豁免 Ticket 時，Hook 輸出警告訊息到 stderr | 模擬 PostToolUse 事件，確認 stderr 含警告 |
| H-2 | 警告訊息包含 Ticket ID 和補填指引 | 確認訊息格式正確 |
| H-3 | Hook 始終返回 exit code 0（不阻止寫入） | 確認所有情境下 exit code 均為 0 |
| H-4 | 子任務（parent_id 非空）的 .md 寫入，Hook 不輸出警告 | 寫入子任務檔，確認無警告 |
| H-5 | DOC 類型 Ticket 寫入，Hook 不輸出警告 | 寫入 DOC Ticket，確認無警告 |
| H-6 | 非 Ticket 路徑的 .md 寫入，Hook 不觸發驗證 | 寫入其他 .md，確認無警告 |
| H-7 | 已有完整 decision_tree_path 的 Ticket，Hook 不輸出警告 | 寫入完整 Ticket，確認無警告 |

## 7. 實作注意事項

### 7.1 YAML 序列化考量

`decision_tree_path` 欄位值可能包含中文冒號（：）、引號、換行等特殊字元。YAML 序列化時需確保：
- 使用 `yaml.dump()` 的標準行為（自動加引號轉義）
- 不使用 `default_flow_style=False` 以外的非標準設定

### 7.2 frontmatter 欄位排列

依現有慣例，`decision_tree_path` 應放在 `dispatch_reason` 之後、`who` 之前（保持決策相關欄位集中）。

### 7.3 Hook 路徑解析

PostToolUse Hook 的觸發條件需精確比對 Ticket 路徑模式（`docs/work-logs/*/tickets/*.md`），避免誤觸發其他目錄的 .md 寫入。使用 `Path.match()` 或 `fnmatch` 進行模式比對。

### 7.4 backward compatibility

現有 Ticket 檔案（v0.1.1 之前建立）的 frontmatter 不含 `decision_tree_path` 欄位。Hook 掃描時遇到無此欄位的 Ticket，應視為缺少（輸出警告），但不阻止任何現有操作。

**影響評估**：現有完成的 Ticket（completed）不會被 Hook 觸發（只在寫入時觸發），僅影響仍在活躍操作的 Ticket。
