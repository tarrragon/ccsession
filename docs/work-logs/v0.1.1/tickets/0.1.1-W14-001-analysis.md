# 0.1.1-W14-001: 正規化 Ticket 系統為 Agent Communication Protocol - 深度分析報告

## 執行摘要

經深入分析，現有 Ticket 系統已具備異步消息傳遞協定（async message-passing protocol with persistent state）的完整骨架，但缺乏 7 個關鍵協定元素，導致：

1. **Phase 銜接錯誤**（如 IMP-011）：消費端無法可靠確認生產端的格式規範
2. **派發分散**：Agent 能力宣告散在自然語言中，PM 無法機器可讀的方式查詢
3. **進度不透明**：execution log 是 freeform markdown，缺乏結構化進度回報
4. **協議演進無版本控制**：schema 改變時無法區分新舊 ticket

本報告提出 3 個 P0 缺口的詳細設計方案和實作成本評估，為下一版本 (v0.2.0) 的正規化奠定基礎。

---

## 第一部分：Protocol 現狀分析

### 1.1 已具備的 Protocol 骨架

| 元素 | 實作形式 | 評估 |
|------|---------|------|
| **Message Schema** | YAML frontmatter 40+ 欄位 + 5W1H 框架 | 完整 |
| **State Machine** | pending → in_progress → completed/blocked/superseded | 完整 |
| **Routing** | handoff (to-sibling/to-parent/to-child/context-refresh) + direction field | 完整 |
| **Context Persistence** | .md 檔案 + handoff JSON + execution log | 完整 |
| **Identity** | ticket ID (version-wave-seq) + agent name | 完整 |
| **Dependency Graph** | blockedBy / relatedTo / parent-children | 完整 |
| **Audit Trail** | execution log + handoff archive | 完整 |
| **Error Recovery** | incident-responder + re-dispatch 機制 | 完整 |

### 1.2 識別的 7 個 Protocol 缺口及優先級

| 優先級 | 缺口 | 簡述 | 影響 | 成本 |
|--------|------|------|------|------|
| **P0** | Protocol Version | frontmatter 無版本號 | schema 演進時無法區分新舊 ticket | 中 |
| **P0** | Agent Capability Declaration | 能力宣告散在自然語言中 | PM 派發依賴記憶和規則文件 | 高 |
| **P0** | Input/Output Contract | Phase 間產出格式無正式 contract | Phase 銜接錯誤根源（IMP-011 類） | 高 |
| **P1** | Message Types / Verbs | 只有「執行」一種訊息動詞 | 限制 agent 自治和協商能力 | 中 |
| **P1** | Structured Progress | execution log 無結構化格式 | 進度不透明，自動化分析困難 | 中 |
| **P2** | Completion Proof | acceptance criteria 無機器可驗證證據 | acceptance-auditor 事後審查，不是協議層驗證 | 低 |
| **P3** | Negotiation Protocol | agent 無結構化協商通道 | PM 中轉是可行替代，限制 agent 自治 | 低 |

## 第二部分：3 個 P0 缺口深度分析

### 缺口 1：Protocol Version（協定版本）

#### 問題描述

**現狀**：frontmatter 中無版本號，當欄位語義改變時，舊 ticket 和新 ticket 混在一起無法區分。

**具體案例**：
- `direction` 欄位格式演進：`"to-sibling"` → `"to-sibling:target_id"`
- 新增 `tdd_phase` 欄位以支援 TDD Phase 追蹤
- 新增 `creation_accepted` 欄位以支援 Ticket 建立後審核流程

這些改變導致：
1. 舊程式碼無法正確解析新 ticket（如 IMP-011 — 假設 direction 是簡單字串）
2. 新程式碼無法正確讀取舊 ticket
3. 無法自動遷移和版本相容性驗證

#### 設計方案

**方案 A：三層版本化（推薦）**

```yaml
# 新增欄位到 frontmatter
protocol_version: "2.0"           # Protocol schema 版本
schema_version: "2.0"             # 向後相容（同義詞）
backend_version: "0.1.1"          # 該 protocol 被首次使用的系統版本
```

**版本化規則**：
- Major: 破壞性改變（欄位刪除、語義重定義）
- Minor: 向後相容的新增（新欄位、新指令值）
- Patch: 修復（無新欄位）

**遷移策略**：
```python
# ticket_loader.py
def load_ticket(file_path: str) -> dict:
    """載入 ticket，自動處理版本差異"""
    raw = parse_yaml_frontmatter(file_path)
    protocol_version = raw.get("protocol_version", "1.0")  # 預設舊版本
    
    if protocol_version.startswith("1."):
        raw = migrate_v1_to_v2(raw)
    elif protocol_version.startswith("2."):
        raw = migrate_v2_to_v3(raw)
    
    return raw
```

**相容性驗證**：
```python
# hooks/protocol-version-check-hook.py
def validate_protocol_version(file_path: str):
    """檢查 protocol 版本是否受支持"""
    version = extract_protocol_version(file_path)
    supported_versions = ["1.0", "2.0", "2.1"]
    
    if version not in supported_versions:
        raise VersionMismatchError(
            f"Protocol {version} not supported. "
            f"Expected one of {supported_versions}"
        )
```

**成本評估**：
- 設計：2 days（版本化策略、遷移流程）
- 實作：5 days（遷移腳本、Hook 實作、測試）
- 部署：2 days（向後相容驗證、舊 ticket 測試）
- **總計：9 days（中等成本）**

#### 與現有系統的影響

- **向後相容**：yes（預設版本 1.0，自動遷移）
- **需要遷移**：所有現存 ticket（自動執行一次）
- **Hook 變動**：新增 protocol-version-check-hook

### 缺口 2：Agent Capability Declaration（能力宣告）

#### 問題描述

**現狀**：Agent 的能力（accepts、requires、produces、preconditions）寫在 `.claude/agents/*.md` 的自然語言裡。

**具體案例**：
```markdown
# parsley-flutter-developer

你是 Flutter 開發執行專家...
[自然語言描述]
接收內容：虛擬碼、流程圖、架構決策...
轉換為 Flutter 程式碼...
```

派發流程中的決策分散：
- `.claude/rules/core/decision-tree.md` 第五層：TDD 階段派發表
- `.claude/rules/flows/incident-response.md` 第 27 行：錯誤派發對應表
- `.claude/rules/guides/query-vs-research.md`：查詢 vs 研究派發表

**問題**：
1. PM 派發時必須記住多個表格規則
2. 無法機器可讀的方式驗證派發決策的正確性
3. agent 能力衝突無法自動偵測（如 ARCH-005）
4. 新增 agent 時無法自動驗證能力宣告的完整性

#### 設計方案

**方案：Agent Capability Registry（YAML 機器可讀）**


**派發驗證 Hook**：
```python
# hooks/agent-dispatch-validation-hook.py

def validate_dispatch_decision(agent_name: str, ticket: dict):
    """驗證派發決策的正確性"""
    registry = load_agent_registry()
    agent = registry.get(agent_name)
    
    # 驗證 1: Agent 存在且版本兼容
    if not agent:
        raise AgentNotFoundError(f"Agent {agent_name} not found in registry")
    
    # 驗證 2: 前置條件滿足
    for precond in agent.preconditions:
        if not check_precondition(precond, ticket):
            raise PreconditionNotMetError(f"Precondition failed: {precond}")
    
    # 驗證 3: 衝突檢查
    for conflict in agent.conflict_avoidance:
        if check_conflict(conflict, ticket):
            raise ConflictDetectedError(f"Conflict: {conflict}")
    
    # 驗證 4: 產出物可達性
    for artifact in agent.produces:
        if not is_path_accessible(artifact.path_pattern):
            raise PermissionError(f"Cannot write to {artifact.path_pattern}")
```

**PM 派發輔助**：
```python
# skills/ticket/commands/recommend_dispatch.py

def recommend_dispatch(ticket: dict) -> List[str]:
    """根據 ticket 內容推薦合適的 agent"""
    registry = load_agent_registry()
    candidates = []
    
    for agent_name, agent in registry.items():
        score = 0
        
        # 檢查能否處理該 ticket 類型
        if matches_ticket_type(ticket, agent):
            score += 10
        
        # 檢查前置條件
        if all(check_precondition(p, ticket) for p in agent.preconditions):
            score += 5
        
        # 檢查衝突
        if any(check_conflict(c, ticket) for c in agent.conflict_avoidance):
            score -= 100  # 衝突是致命的
        
        if score > 0:
            candidates.append((agent_name, score))
    
    return sorted(candidates, key=lambda x: x[1], reverse=True)
```

- 遷移：3 days（提取現有 agent 能力，轉換為 YAML）
- 部署：2 days（向後相容驗證）
- **總計：16 days（高成本，但重要）**

### 缺口 3：Input/Output Contract（階段契約）

#### 問題描述

**現狀**：每個 TDD Phase 的產出物格式散在多個文件裡，沒有正式 contract。

**具體散落位置**：
1. `.claude/rules/flows/tdd-flow.md` → Phase 代理人表
2. `.claude/agents/lavender-interface-designer.md` → "Phase 1 產出"自然語言描述
3. `.claude/rules/core/ticket-id-conventions.md` → "-phase1-design" 後綴約定
4. `.claude/agents/sage-test-architect.md` → Phase 2 輸出格式（自然語言）
5. `.claude/references/tdd-flow-details.md` → Phase 詳細描述（參考檔案）

**導致的問題**：

IMP-011 根本原因分析：
```
Phase 3a 產出 "strategy-document"
  ↓ (消費方假設格式)
Phase 3b 讀取 direction 欄位
  ↓
假設：direction 是簡單字串 "to-sibling"
實際：direction 實際格式是 "to-sibling:0.31.1-W3-002"
  ↓
GC 修復時精確匹配失敗，導致修復無效
```

**根本原因**：沒有正式的「Phase 3a 輸出格式規範」，Phase 3b 無法可靠地確認期望格式。

**Contract 驗證 Hook**：
```python
# hooks/phase-contract-validator-hook.py

def validate_phase_output(ticket: dict, phase: str) -> ValidationResult:
    """驗證 Phase 的產出是否符合 contract"""
    contracts = load_phase_contracts()
    contract = contracts[f"phase{phase}_output"]
    
    result = ValidationResult()
    
    for artifact in contract.artifacts:
        if artifact.required:
            if not artifact_exists(ticket, artifact.path):
                result.add_error(f"Missing required artifact: {artifact.name}")
        
        if artifact_exists(ticket, artifact.path):
            # 驗證格式
            if not validate_format(ticket, artifact):
                result.add_error(f"Format validation failed: {artifact.name}")
            
            # 驗證內容
            if not validate_content(ticket, artifact):
                result.add_error(f"Content validation failed: {artifact.name}")
    
    return result
```

**Phase 轉移時的自動檢查**：
```python
# skills/tdd/commands/phase_complete.py

def complete_phase(ticket_id: str, phase: str) -> bool:
    """標記 Phase 完成，自動驗證產出物"""
    ticket = load_ticket(ticket_id)
    
    # 強制驗證該 Phase 的 contract
    validator = PhaseContractValidator()
    result = validator.validate(ticket, phase)
    
    if result.has_errors():
        print(f"[ERROR] Phase {phase} contract validation failed:")
        for error in result.errors:
            print(f"  - {error}")
        return False
    
    if result.has_warnings():
        print(f"[WARNING] Phase {phase} has warnings:")
        for warning in result.warnings:
            print(f"  - {warning}")
        # 警告不阻止完成，但會記錄
    
    return True
```

## 第三部分：P1-P3 缺口簡要分析

### 缺口 4：Message Types / Verbs（訊息動詞）

**現狀**：Ticket 只有一種「訊息類型」（task）。不同訊息意圖（request/propose/reject/inform）無法區分。

**影響**：
- Agent 無法結構化地提出替代方案（目前只能「執行」或「升級 PM」）
- PM 無法自動分析「哪些任務在協商中」

**建議方案**：
```yaml
# 新增欄位
message_type: "task"  # or "proposal", "request-clarification", "info", "decision-needed"
message_intent: "assignment"  # "needs-approval", "needs-feedback", "for-info"
```

**成本**：中等（7-10 days）
**優先級**：P1（改進 agent 自治，但 PM 中轉仍可替代）

---

### 缺口 5：Structured Progress（結構化進度）

**現狀**：execution log 是 freeform markdown，無法自動分析進度。

**影響**：
- PM 無法自動檢測進度停滯（需手動查看日誌）
- 無法自動計算 ETA
- 無法統計「各 agent 平均執行時間」

**建議方案**：
```yaml
progress_updates:
  - timestamp: "2026-03-18T10:30:00"
    status: "executing"           # pending/executing/blocked/completed
    completion_pct: 60
    artifacts_produced: ["lib/foo.dart"]
    artifacts_pending: ["lib/bar.dart"]
    decisions_needed: []
    next_milestone: "測試執行"
```

**成本**：中等（8-12 days）
**優先級**：P1（改進可觀測性，但目前人工監控仍可行）

---

### 缺口 6 & 7：Completion Proof + Negotiation Protocol

**Completion Proof**：acceptance criteria 加上機器可驗證的證據（command output、test log hash）
- **成本**：低（5-8 days）
- **優先級**：P2（acceptance-auditor 已部分補償）

**Negotiation Protocol**：Agent-to-agent 協商通道
- **成本**：高（12-15 days）
- **優先級**：P3（PM 中轉仍可替代，但限制 agent 自治）

## 附錄：已確認設計決策（2026-03-23 用戶確認）

以下設計決策經多視角審查後由用戶確認，所有後續 Ticket 實作必須遵循。

### 決策 1：Agent Registry 定位 — Source of Truth（能力資料層）

Registry 是 Agent 能力宣告的**權威來源**（誰能做什麼、接受什麼、產出什麼），但**不是決策引擎**。

**架構分工**：

```
decision-tree.md（決策引擎）  →  判斷「需要什麼能力的 Agent」
                                  ↓
registry.yaml（能力資料層）   →  查詢「哪個 Agent 有這個能力」
                                  ↓
驗證 Hook（驗證層）          →  確認「選定的 Agent 確實符合」
```

**關鍵原則**：
- decision-tree.md 是 PM 的核心決策邏輯（行為判斷、流程路由、任務分類），**不被 Registry 取代**
- Registry 只負責「能力查詢」和「派發驗證」，不涉及決策邏輯
- decision-tree 中現有的派發對應表（第五層 TDD 代理人、第六層錯誤派發）保留為決策規則，Registry 作為資料層提供機器可讀的驗證能力
- 長期目標：decision-tree 的「派發給誰」環節可引用 Registry 資料，但決策邏輯仍在 decision-tree 中

### 決策 2：Protocol Version 格式 — Semantic Versioning

採用 Major.Minor 格式（如 `1.0`、`2.0`）。

- 符合業界標準
- 支援向後相容的細粒度控制
- Major 版本變更表示不相容改動，Minor 表示向後相容擴充

### 決策 3：衝突檢查範圍 — 全部三種

Registry 的衝突檢查必須覆蓋以下三種衝突：

| 衝突類型 | 說明 | 範例 |
|---------|------|------|
| Agent 同時派發衝突 | 同一 Ticket 派發給不相容的 Agent | parsley + cinnamon 同時寫同一模組 |
| TDD Phase 相序衝突 | Phase 執行順序違反 | Phase 3b 在 Phase 2 之前 |
| 檔案寫入衝突（ARCH-005） | 多個 Agent 同時寫入同一檔案 | 兩個並行任務都改 constants.dart |

### 多視角審查結論

所有 4 個 Ticket（W1-001~004）的改善需求：

1. **拆分子任務**：認知負擔全部超閾值 10，需拆分
2. **修正依賴**：W1-002 blockedBy W1-001；W1-004 blockedBy W1-002+003
3. **補充驗收條件**：量化標準、產出物格式定義
4. **補充 Problem Analysis**：讓代理人能獨立執行
5. **正確執行順序**：Wave 1 並行 W1-001+003 → Wave 2 W1-002 → Wave 3 W1-004
