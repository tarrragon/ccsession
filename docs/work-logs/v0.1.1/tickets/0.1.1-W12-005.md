## 修正分析方向（用戶回饋）

### 核心問題重新定義：代理人缺乏職責等級辨識能力

問題不是「規則要區分身份」，而是「代理人應有職責邊界意識」。

### 正確的行為模型

代理人收到任務時應執行兩層判斷：

1. **任務屬於我的職責嗎？**
   - 是 → 執行（即使看到 PM 規則也不受影響，因為那不是我的規則）
   - 否 → 拒絕 + 回報 PM 任務派發錯誤

2. **規則適用於我嗎？**
   - skip-gate 限制 PM 不能寫程式碼 → basil 是開發者，此規則不適用
   - basil 的任務是寫程式碼 → 這正是 PM 派它來做的事

### basil 的實際錯誤

basil 讀了 PM 的規則後，把自己的「程式碼編輯」工作誤判為「PM 的程式碼編輯（被禁止的）」。
正確判斷：「我是被 PM 派來寫程式碼的開發者，skip-gate 限制的是 PM 本人不能寫，不是限制我。」

### 改善方向（修正）

1. agent 定義檔加入「職責等級聲明」和「接受/拒絕任務的判斷標準」
2. 當代理人發現任務不屬於自己職責等級時 → 明確拒絕 + 回報 PM 重新檢視
3. skip-gate 規則寫法需更精確：「PM（主線程）禁止...」而非隱含全局
4. agent prompt 模板加入：「你是 {agent_type}，你的職責是 {responsibilities}，PM 規則不適用於你」
## 根因深度分析（PM 現場觀察）

### 核心問題：規則系統缺乏角色區分機制

basil-hook-architect 並非「搞錯身份」，而是在 subagent 環境中**合理地遵守了不該適用於它的規則**。

### 技術機制

1. Agent tool spawn 的 subagent 繼承主線程的 session context
2. .claude/rules/ 下所有規則對所有 agent 一視同仁載入
3. skip-gate.md 寫「主線程禁止編輯程式碼」，但沒有 applies_to 欄位
4. basil 讀到規則 → 無法判斷是否適用於自己 → 保守遵守 → 拒絕編輯

### 影響範圍

任何包含「主線程禁止 X」的規則，都可能被 subagent 誤讀為適用於自己：
- skip-gate.md Level 3（主線程編輯限制）
- skip-gate.md Level 1（主線程禁止直接修復）
- decision-tree.md（主線程允許親自處理的範圍）

### 改善方向

1. 規則加入 applies_to 標註（如 applies_to: [rosemary-project-manager]）
2. Agent 定義檔加入明確的權限聲明
3. 規則寫法改為「角色限定」而非「全局禁止」
4. 或在 agent prompt 模板中加入身份確認段落

### 暫時解法

使用 mode: bypassPermissions 派發可繞過 Hook 限制，但這是治標不治本。

## Solution - basil 特定案例的誤判機制分析

### 1. basil 讀取 skip-gate 規則時的判斷路徑

basil 在接到 W9-002.3 派發（編輯 Hook Python 檔案）時，按如下順序進行判斷：

**Step 1: 派發任務識別**
- 派發內容：「編輯 3 個 Python Hook 檔案（.claude/hooks/*.py）」
- decision_tree_path：「Phase 3b 實作，派發 basil-hook-architect 執行」
- basil 應理解：「我被派來編輯 Hook 檔案」

**Step 2: 規則載入與衝突偵測**
- basil 在 session context 中載入 skip-gate.md（第 163-186 行）
- 讀到：「主線程（rosemary-project-manager）只能編輯以下檔案範圍」
- 讀到允許列表中有：.claude/hooks/*（在 PM 的允許範圍內）
- **關鍵問題**：規則未標註 applies_to，basil 無法判斷「誰被限制」

**Step 3: 身份判斷失敗的核心環節**
- basil 的推論：「我讀到 PM 禁止編輯 → 我在編輯 → 這規則是否適用於我？」
- 缺乏判斷機制：basil 定義檔中無「職責等級聲明」
- 保守策略：「不確定規則適用範圍 → 假設全局禁止 → 拒絕編輯」
- 誤判輸出：「根據 skip-gate 規則，我不能編輯程式碼」

### 2. basil 定義檔中的職責邊界聲明缺失

basil-hook-architect.md 目前的問題：

**缺失 1：職責等級聲明**
- 第 42-51 行有「核心職責」表，但未聲明「我是執行者（非 PM）」
- 應補充：「我的角色是執行者，PM 派發給我的任務優先級高於 PM 的禁止規則」

**缺失 2：規則適用性判斷標準**
- 第 146-156 行有「禁止行為」，但無「如何判斷 PM 規則是否適用」的指導
- 應補充：「PM 規則寫『主線程禁止 X』是限制 PM 自己，當 PM 派我做 X 時，代表 PM 已同意豁免此限制」

**缺失 3：與 PM 規則的關係說明**
- 第 159-168 行有「與其他代理人的邊界」，但無「與 PM 的邊界」
- 應補充：「PM 禁止自己編輯代碼 ≠ 禁止我編輯；當我被派來編輯時，編輯正是我的職責」

### 3. skip-gate 規則的角色標註缺失

skip-gate.md 規則寫法的問題：

**缺失 applies_to 標註**
- 第 163 行：「主線程編輯限制」無 applies_to: [rosemary-project-manager]
- 第 176 行：「禁止編輯」清單未明確指定「誰被禁止」

**寫法歧義**
- 「主線程（rosemary-project-manager）只能編輯以下檔案範圍」未明確限定主語
- subagent 讀到時，無法區分「全局禁止」vs「PM 特定禁止」

### 4. 事件根本原因層次分析

| 層級 | 問題 | 導致 basil 的誤判 |
|------|------|----------------|
| **規則層** | skip-gate.md 缺 applies_to 標註 | basil 無法判斷規則適用於誰 |
| **Agent 層** | basil 定義檔缺職責等級聲明 | basil 無法判斷「派發 vs 規則」的優先級 |
| **System 層** | 無自動過濾或判斷機制 | basil 採取保守策略（假設規則全局適用） |

### 5. 為什麼 decision_tree_path 未能阻止誤判

W9-002.3 的 decision_tree_path 已明確告知：
- entry_point: Phase 3b（實作階段）
- final_decision: 派發 basil-hook-architect 實作
- rationale: 無檔案衝突可並行

但 basil 仍誤判，原因是：
1. **無判斷標準**：basil 不知道「派發決策」vs「skip-gate 規則」誰優先
2. **無身份確認**：basil 無法從 decision_tree_path 推導出「我是執行者，規則不限我」
3. **採取保守策略**：遇到衝突時，basil 傾向相信規則而非派發
