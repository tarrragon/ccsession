## Solution

### 背景回顧

W12-007 分析發現三層防護機制失效，導致 basil-hook-architect 無法判斷「skip-gate.md 規則是否適用於我」。本任務評估三種 Hook 系統改進方案的可行性。

---

## 方案評估框架

### 方案 A：規則 metadata 標註（W12-007.1 已進行）

**實作方式**：在 Markdown 規則檔案中添加 YAML frontmatter metadata

```yaml
---
id: rule-skip-gate-level-3
title: 主線程編輯限制
applies_to:
  - rosemary-project-manager
  - name: skip-gate-level-3-exception
    description: 主線程編輯允許列表中的檔案時例外
scope: ["PM 限定"]
---
```

**優點**：
- 最簡單直接，不需要修改 Hook 系統
- 可被手工閱讀，易於維護
- 實施成本低（只需編輯規則檔案）
- 無需修改 Claude Code 的規則載入機制

**缺點**：
- 需要手動為所有規則添加 metadata（數量多）
- metadata 不會自動應用於代理人 context（需要 Hook 或其他機制支援）
- 無法自動過濾代理人看到的規則（仍需依靠人工或其他層級）

**實施成本**：低（只是文件編輯）

**何時生效**：立即（規則編輯後生效）

**潛在問題**：
- metadata 與實際規則內容容易不同步（例如規則改變但 metadata 未更新）
- 無品質保證機制確保 metadata 完整性

---

### 方案 B：SessionStart Hook 進行規則過濾

**實作方式**：建立新 Hook 在 SessionStart 時運行

```python
# .claude/hooks/rule-applicability-filter-hook.py

def filter_rules_for_agent(agent_name: str, all_rules: List[Path]) -> List[Path]:
    """
    根據代理人角色過濾適用的規則。

    流程：
    1. 偵測當前 context 中的代理人身份（從 Ticket 的 decision_tree_path）
    2. 掃描所有規則檔案，解析 applies_to 欄位
    3. 只返回「applies_to 包含該代理人」的規則
    4. 將結果作為「推薦閱讀規則」傳入代理人 context
    """
    pass
```

**工作流程**：

```
SessionStart
    |
    v
Hook 偵測當前代理人身份
    |
    v
掃描 .claude/rules/ 所有檔案
    |
    v
提取 applies_to metadata
    |
    v
過濾適用規則 → 建立「推薦規則清單」
    |
    v
將清單注入代理人 context prompt
    |
    v
代理人優先讀取適用的規則
```

**優點**：
- 自動化，無需手動干預
- 可提供個性化的「推薦規則清單」給每個代理人
- 易於發現規則 metadata 缺陷（哪些規則未標註）
- 可記錄「規則適用性決策」供審計

**缺點**：
- 需要實作 Hook（中等複雜度）
- 依賴 applies_to metadata 的完整性（需 W12-007.1 完成）
- 代理人仍可讀取全部規則，只是自動推薦適用規則（無強制過濾）
- SessionStart Hook 的執行時機和可靠性需驗證

**實施成本**：中等（需實作 Hook + metadata 協同）

**何時生效**：Hook 實作完成後

**潛在問題**：
- SessionStart Hook 的時機是否正確（何時執行？何時停止執行？）
- 如何在 Claude Code 的 Hook 系統中注入「推薦規則清單」到代理人 prompt
- 如何驗證過濾結果的正確性（特別是複雜的 applies_to 邏輯）

### 方案 C：Agent 定義檔中增加規則過濾指引

**實作方式**：在每個 Agent 定義檔中添加「角色適用規則」章節

```markdown
# 職責界線

## 適用於 basil-hook-architect 的規則

### 必讀
- .claude/rules/core/implementation-quality.md - Python 實作品質基線
- .claude/rules/core/quality-python.md - Python 專項規則
- .claude/rules/core/decision-tree.md - **第二層（問題處理）、第三層（命令處理）、第五層（TDD 階段）**
  - **不適用於你**：第四層（Ticket 執行）中「PM 親自處理」的部分

### 不適用於 basil-hook-architect
- skip-gate.md 「主線程編輯限制」（你是執行者，這針對 PM）
- decision-tree.md 「主線程決策」部分

### 判斷標準
如果規則包含以下關鍵詞，需確認是否適用於你：
- 「主線程禁止」→ 如果你被派來做，則**不適用**
- 「PM 必須」→ 檢查 decision_tree_path，確認你是執行者
- 「強制派發」→ 判斷你是被派來執行的代理人，還是被派來決策的 PM
```

**優點**：
- 低成本：只需編輯 Agent 定義檔
- 直接針對問題：讓代理人明確知道什麼規則適用於自己
- 易於擴展：每個 Agent 獨立定義，可根據角色調整

**缺點**：
- 需要手動維護 N 個 Agent 定義檔（scalability 問題）
- 無自動化驗證，容易不同步
- 未來新增規則或 Agent 需要同步更新
- 無法自動過濾代理人看到的規則（仍是被動指導）

**實施成本**：低到中等（需編輯所有 Agent 定義檔）

**何時生效**：編輯完成後立即生效

**潛在問題**：
- 當規則頻繁變更時，Agent 定義檔的「適用規則清單」容易過時
- 無版本控制，不易追蹤「規則適用性」的演變

## 推薦方案：組合策略（A + B + C）

基於上述分析，推薦採用**三層遞進式方案**：

### 短期（優先實施）：方案 A + C

**Step 1：方案 A - 規則 metadata 標註（W12-007.1）**
- 為所有包含「角色限定」的規則添加 `applies_to` metadata
- 工作量：中等（需逐一檢查和標註，但都是編輯工作）
- 時程：與 W12-007.1 同步進行
- 產出：metadata-ready 的規則集

**Step 2：方案 C - Agent 定義檔指引（W12-007.2 的擴充）**
- 在每個 Agent 定義檔的「職責界線」章節添加「適用規則清單」
- 包含判斷標準（如何區分「這條規則是否適用於我」）
- 工作量：低（在既有章節基礎上擴充）
- 時程：與 W12-007.2 同步進行
- 產出：Agent 有明確的「適用規則指南」

**預期效果**：
- basil 讀到 Agent 定義檔會看到「skip-gate.md 主線程限制不適用於你」
- basil 讀到 skip-gate.md 的 metadata 標註「applies_to: rosemary-project-manager」會確認自己不是目標
- 雙重保險機制，降低誤判概率

---

### 中期（後續計劃）：方案 B - SessionStart Hook

**條件**：W12-007.1 完成（metadata 標註齊全）

**工作內容**：
1. 建立 `rule-applicability-filter-hook.py`
2. SessionStart 時自動檢測代理人身份
3. 過濾適用規則，建立「推薦清單」
4. 將推薦清單注入代理人 context prompt

**實施時程**：作為 W12-007.3.1 或 W12-007.3.2 子任務

**預期效果**：
- 自動化過濾，無需代理人手動判斷
- 減少「看到不適用規則導致誤判」的情況
- 為未來的 Agent 自動提供個性化規則清單

## 風險與防護

- **風險**：metadata 與實際規則內容不同步
- **防護**：在規則編輯 Hook 中檢查 applies_to 更新

### 方案 B 的風險

- **防護**：先試點測試，確認 Hook 執行時機和 context 注入可行性
- **風險**：代理人仍可讀取全部規則（推薦不是強制）
- **防護**：配合方案 C 提供明確的「不適用規則」列表

### 方案 C 的風險
- **風險**：當規則頻繁變更時，Agent 定義檔容易過時
- **防護**：建立「規則變更通知機制」，提醒更新 Agent 定義檔

## 長期架構思考

目前三層防護的設計有個基本假設：**規則適用性的判斷權交給代理人**。

這導致：
- 如果規則寫得不清楚，代理人會誤判
- 如果 metadata 不完整，Hook 無法過濾
- 如果 Agent 定義檔過時，代理人收到錯誤指導

**更好的架構方向**（未來升級）：
1. **版本化規則**：規則附加版本號，區分「PM 版本」和「Agent 版本」
2. **自動化路由**：由 Hook 直接將規則分發到不同 context（PM context vs Agent context）
3. **規則品質閘門**：Hook 在規則寫入時檢查 applies_to 和內容一致性
