# 0.1.1-W14-001: 正規化 Ticket 系統為 Agent Communication Protocol

## 背景

在研究外部 agent protocol 專案後，發現本專案的 Ticket 系統本質上就是一個 agent 間溝通交接的 protocol，差異在於加上了文件持久化。這個認知促使我們審視現有模型的完整性。

## 現有 Protocol 元素（已具備）

| Protocol 元素 | 現有實作 |
|---|---|
| Message Schema | YAML frontmatter 40+ 欄位，5W1H 框架 |
| State Machine | pending -> in_progress -> completed/blocked/superseded |
| Routing | handoff direction（to-sibling/to-parent/to-child/context-refresh） |
| Context Persistence | .md 檔案 + handoff JSON + execution log |
| Identity | ticket ID（version-wave-seq）+ agent name |
| Dependency Graph | blockedBy / relatedTo / parent-children |
| Audit Trail | execution log + handoff archive |

## 識別的 7 個 Protocol 缺口

### 1. Protocol Version（協定版本）-- P0

frontmatter schema 沒有版本號。欄位語義改變時（如 direction 從純字串變成 direction:target_id 複合格式），舊 ticket 和新 ticket 混在一起無法區分。

```yaml
# 需要新增
protocol_version: "2.0"
```

沒有版本號，protocol 就無法安全演進。

### 2. Agent Capability Declaration（能力宣告）-- P0

agent 能做什麼寫在 .claude/agents/*.md 的自然語言裡，沒有機器可讀的 schema。PM 靠記憶和規則文件做派發。

```yaml
# 需要的概念
agent: parsley-flutter-developer
capability:
  accepts: ["phase3b-task"]
  requires: ["phase3a-strategy-doc"]
  produces: ["code-change", "execution-report"]
  preconditions: ["phase3a completed", "test design exists"]
```

影響：decision-tree 和 incident-response 的派發對應表是手動維護的 registry，分散在多個規則檔裡。

### 3. Input/Output Contract（階段契約）-- P0

每個 TDD Phase 的產出物格式散在 tdd-flow.md、agent 定義、ticket-id-conventions.md 裡，沒有正式 contract。

```yaml
# 需要的概念
phase3a:
  input:
    required: ["phase2-test-design-doc", "ticket-with-acceptance-criteria"]
  output:
    required:
      - artifact: "strategy-document"
        path: "{ticket-id}-phase3a-strategy.md"
  validation:
    - "strategy document exists"
    - "all test cases from phase2 are addressed"
```

影響：Phase 間銜接錯誤（IMP-011 欄位格式溯源）根源在此——消費端不知道生產端的精確格式。

### 4. Message Types / Verbs（訊息動詞）-- P1

ticket 只有一種「訊息類型」。正規 protocol 會區分通訊意圖：

| 缺少的動詞 | 目前替代 | 語義缺口 |
|---|---|---|
| REQUEST | ticket create + claim | 合併了「請求」和「接受」 |
| PROPOSE | 不存在 | agent 無法結構化提出替代方案 |
| REJECT | blocked 狀態 | blocked 可能是依賴問題也可能是拒絕 |
| INFORM | execution log append | freeform markdown，非結構化 |
| CONFIRM | claim | claim 只表示「我拿了」，不表示「我理解了」 |

### 5. Structured Progress（結構化進度）-- P1

execution log 是 freeform markdown，沒有結構化進度回報格式：

```yaml
# 需要的概念
progress:
  timestamp: "2026-03-18T10:30:00"
  agent: "parsley-flutter-developer"
  status: "executing"
  completion_pct: 60
  artifacts_produced: ["lib/foo.dart"]
  artifacts_pending: ["lib/bar.dart"]
  decisions_needed: []
```

### 6. Completion Proof（完成證明）-- P2

acceptance criteria 是 checkbox，缺少機器可驗證的完成證據：

```yaml
# 目前
acceptance:
  - "[x] 測試通過"

# 需要的概念
acceptance:
  - criterion: "測試通過"
    verified_by: "parsley-flutter-developer"
    verified_at: "2026-03-18T10:30:00"
    evidence_type: "command_output"
    evidence: "42 passed, 0 failed"
```

acceptance-auditor 部分補償了這個缺口，但它是事後審查，不是 protocol 層面的結構化證據。

### 7. Negotiation Protocol（協商機制）-- P3

agent 只能「執行」或「升級 PM」，沒有結構化的協商通道。PM 中轉 + AskUserQuestion 是可用替代方案，但不是 agent-to-agent 的。

## 實作優先級建議

| 優先級 | 缺口 | 理由 |
|---|---|---|
| P0 | Protocol Version | 最小改動，沒有版本就無法安全演進 |
| P0 | Input/Output Contract | Phase 銜接錯誤（IMP-011 類）根源 |
| P0 | Agent Capability Declaration | 派發從「查規則」變「查 registry」 |
| P1 | Message Types / Verbs | PM 中轉模式下影響較小，但限制 agent 自治 |
| P1 | Structured Progress | 取代 freeform execution log |
| P2 | Completion Proof | acceptance-auditor 已部分補償 |
| P3 | Negotiation | PM 中轉是可行替代 |

## 定位總結

現有 Ticket 系統是一個「有持久化的非同步訊息傳遞協定」，核心骨架完整。缺口在三個方向：

1. **Schema 自描述能力**：protocol version + agent capability -- 讓 protocol 可靠演進
2. **Contract 嚴格性**：input/output contract -- 讓 Phase 銜接從隱式約定變顯式驗證
3. **訊息語義豐富度**：message types -- 讓 agent 從「被動執行者」升級為「主動協作者」

## 後續規劃

待認領執行時，建議：
1. 先深入分析每個缺口的具體設計方案（本 ticket 的 ANA 階段）
2. 依分析結果拆分為多個子 ticket，P0 缺口先行
3. 每個缺口可能需要獨立的 TDD 流程
