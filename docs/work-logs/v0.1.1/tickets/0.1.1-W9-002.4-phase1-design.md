# Phase 1 功能規格設計：/worktree SKILL MVP

## 1. 功能需求分析

### 1.1 核心問題

開發者在多 Ticket 並行開發時，面臨以下 UX 痛點：

| 問題 | 影響 |
|------|------|
| 手動輸入分支名稱和 worktree 路徑（容易打錯） | 建立 worktree 速度慢且出錯率高 |
| 無法快速確認哪個 worktree 對應哪個 Ticket | 切換工作環境時需要記憶對應關係 |
| 每次 Session 都看到分支狀態提醒（含非異常情況） | 正常工作流程被無意義訊息打斷 |
| main 分支上修改 `.claude/` 文件被 Hook 阻止 | 規則/文件更新無法在 main 上進行 |

### 1.2 使用者角色與場景

**角色**：使用 Claude Code 的開發者（同時進行多個 Ticket 開發）

**核心場景**：

場景 1：開始新 Ticket 開發
```
Given: 開發者拿到 Ticket 0.1.1-W9-002.1
When: 執行 /worktree create 0.1.1-W9-002.1
Then: 自動建立 feat/0.1.1-W9-002.1 分支和 ../ccsession-0.1.1-W9-002.1 worktree
      輸出 cd 指令讓開發者可立即切換
```

場景 2：查看全局 worktree 狀態
```
Given: 開發者正在執行多個並行 Ticket
When: 執行 /worktree status
Then: 顯示所有 worktree 的 Ticket 對應、分支狀態、變更摘要
```

場景 3：查看特定 Ticket 狀態
```
Given: 開發者想確認某個 Ticket 的進度
When: 執行 /worktree status 0.1.1-W9-002.1
Then: 只顯示該 Ticket 對應 worktree 的詳細狀態
```

場景 4：Session 啟動（正常 worktree 環境）
```
Given: 開發者在正確的 feat/xxx worktree 中啟動 Session
When: SessionStart Hook 執行
Then: 靜默（不輸出任何提醒）
```

場景 5：Session 啟動（異常情況）
```
Given: 開發者在 main 分支啟動 Session
When: SessionStart Hook 執行
Then: 顯示警告和建議操作
```

場景 6：在 main 分支修改 .claude/ 文件
```
Given: 開發者在 main 分支嘗試修改 .claude/rules/some-rule.md
When: Edit Hook 執行
Then: 允許操作（.claude/ 和 docs/ 路徑豁免保護分支限制）
```

## 2. 命名約定規格

### 2.1 自動命名規則

`/worktree create` 從 ticket-id 自動推導命名，遵循以下規則：

| 組件 | 規則 | 範例 |
|------|------|------|
| 分支名稱 | `feat/{ticket-id}` | `feat/0.1.1-W9-002.1` |
| Worktree 路徑 | `{parent-dir}/{project-name}-{ticket-id}` | `../ccsession-0.1.1-W9-002.1` |

**`{parent-dir}`**：主倉庫的上一層目錄（由 `get_project_root()` 推導）

**`{project-name}`**：主倉庫目錄名稱（e.g. `ccsession`）

**推導邏輯**：
```
ticket-id: 0.1.1-W9-002.1
branch: feat/0.1.1-W9-002.1
project-root: /Users/mac-eric/project/ccsession
project-name: ccsession
parent-dir: /Users/mac-eric/project
worktree-path: /Users/mac-eric/project/ccsession-0.1.1-W9-002.1
```

### 2.2 反推邏輯（status 使用）

`/worktree status` 從 worktree 的分支名稱反推 Ticket ID：

| 分支模式 | 反推結果 |
|---------|---------|
| `feat/{ticket-id}` | ticket-id = `{ticket-id}` |
| `feat/0.1.1-W9-002.1` | Ticket: `0.1.1-W9-002.1` |
| `feat/0.1.1-W9-002` | Ticket: `0.1.1-W9-002` |
| `main`、`develop` 等保護分支 | 顯示為「主倉庫」，無 Ticket |
| 其他 `feat/xxx`（非 ticket-id 格式） | 顯示分支名，Ticket: 「無法辨識」 |

**Ticket ID 格式識別**（正規表達式）：
```
pattern = r"^\d+\.\d+\.\d+-W\d+-\d+(\.\d+)*$"
```
例如：`0.1.1-W9-002`、`0.1.1-W9-002.1`、`0.31.0-W3-001.2.3` 均符合。

## 3. CLI 介面定義

### 3.1 SKILL 入口

```
/worktree <subcommand> [args]
```

觸發方式（SKILL.md 描述關鍵字）：
- 明確指令 `/worktree`
- 關鍵字：「建立 worktree」、「新增 worktree」、「查看 worktree 狀態」

### 3.2 `create` 子命令

#### 語法

```
/worktree create <ticket-id> [--base <branch>] [--dry-run]
```

#### 參數規格

| 參數 | 類型 | 必填 | 說明 | 範例 |
|------|------|------|------|------|
| `ticket-id` | positional | 必填 | Ticket ID | `0.1.1-W9-002.1` |
| `--base` | option | 選填 | 基礎分支（預設 `main`） | `--base develop` |
| `--dry-run` | flag | 選填 | 只顯示將要執行的操作，不實際執行 | `--dry-run` |

#### 輸出格式（成功）

```
正在建立 worktree...
  Ticket: 0.1.1-W9-002.1
  分支:   feat/0.1.1-W9-002.1
  基礎:   main
  路徑:   /Users/mac-eric/project/ccsession-0.1.1-W9-002.1

建立成功。

下一步：
  cd /Users/mac-eric/project/ccsession-0.1.1-W9-002.1
```

#### 輸出格式（dry-run）

```
[Dry Run] 將要執行的操作：
  git worktree add -b feat/0.1.1-W9-002.1 \
    /Users/mac-eric/project/ccsession-0.1.1-W9-002.1 \
    main

實際執行請移除 --dry-run 參數。
```

#### 輸出格式（錯誤）

```
[錯誤] {錯誤訊息}

{建議操作}
```

#### 錯誤情境清單

| 情境 | 錯誤訊息 | 建議操作 |
|------|---------|---------|
| ticket-id 格式無效 | `無效的 Ticket ID 格式："{ticket-id}"` | `Ticket ID 格式應為 X.X.X-WN-NNN（如：0.1.1-W9-002.1）` |
| 分支已存在 | `分支已存在：feat/{ticket-id}` | `如需重新建立，請先刪除分支：git branch -d feat/{ticket-id}` |
| Worktree 路徑已存在 | `目錄已存在：{worktree-path}` | `如需重新建立，請先移除目錄或使用其他 ticket-id` |
| 基礎分支不存在 | `基礎分支不存在：{base}` | `請確認分支名稱，或省略 --base 參數使用預設的 main` |
| 非 git 倉庫 | `當前目錄不在 git 倉庫中` | `請在 git 倉庫根目錄執行此命令` |
| git 命令失敗 | `建立 worktree 失敗：{git 錯誤訊息}` | （顯示 git 原始錯誤） |

### 3.3 `status` 子命令

#### 語法

```
/worktree status [<ticket-id>]
```

#### 參數規格

| 參數 | 類型 | 必填 | 說明 | 範例 |
|------|------|------|------|------|
| `ticket-id` | positional | 選填 | 指定查詢特定 Ticket | `0.1.1-W9-002.1` |

#### 輸出格式（無參數，顯示全部）

```
Worktree 狀態（共 3 個）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[主倉庫]
  路徑：   /Users/mac-eric/project/ccsession
  分支：   main
  變更：   0 個未 commit

[0.1.1-W9-002.1]
  路徑：   /Users/mac-eric/project/ccsession-0.1.1-W9-002.1
  分支：   feat/0.1.1-W9-002.1
  領先：   +3 commits ahead of main
  落後：   -0 commits behind main
  變更：   2 個未 commit

[0.1.1-W9-002.2]
  路徑：   /Users/mac-eric/project/ccsession-0.1.1-W9-002.2
  分支：   feat/0.1.1-W9-002.2
  領先：   +1 commits ahead of main
  落後：   -1 commits behind main
  變更：   0 個未 commit
```

#### 輸出格式（指定 ticket-id）

```
[0.1.1-W9-002.1]
  路徑：   /Users/mac-eric/project/ccsession-0.1.1-W9-002.1
  分支：   feat/0.1.1-W9-002.1
  領先：   +3 commits ahead of main
  落後：   -0 commits behind main
  變更：   2 個未 commit
```

#### 輸出格式（無 worktree 時）

```
目前沒有任何 worktree（除主倉庫外）。

建立新的 worktree：
  /worktree create <ticket-id>
```

#### 輸出格式（指定 ticket-id 但找不到）

```
[錯誤] 找不到 Ticket 0.1.1-W9-002.1 對應的 worktree。

目前存在的 worktree：
  - 0.1.1-W9-002.2 (feat/0.1.1-W9-002.2)

建立此 Ticket 的 worktree：
  /worktree create 0.1.1-W9-002.1
```

#### 狀態欄位定義

| 欄位 | 來源 | 計算方式 |
|------|------|---------|
| 路徑 | `git worktree list --porcelain` | `path` 欄位 |
| 分支 | `git worktree list --porcelain` | `branch` 欄位（去除 refs/heads/ 前綴） |
| 領先 | `git rev-list --count {branch}..{base}` | 反向（main 比 branch 多幾個） |
| 落後 | `git rev-list --count {base}..{branch}` | 正向（branch 比 main 少幾個） |
| 變更 | `git -C {worktree-path} status --porcelain` | 行數統計 |

**注意**：`領先/落後` 的計算需要在主倉庫執行 git 命令（因 worktree 共用 object store），但 `變更` 需要在對應 worktree 目錄執行。

## 4. SKILL 模組結構定義

### 4.1 目錄結構

```
.claude/skills/worktree/
├── SKILL.md                    # SKILL 入口（Claude 讀取）
└── scripts/
    └── worktree_manager.py     # 主邏輯（create + status）
```

### 4.2 SKILL.md 規格

SKILL.md 需包含：
- `name: worktree`
- `description`：含觸發關鍵字（建立 worktree、查看 worktree 狀態）
- `argument-hint: "<subcommand> [args]"`
- 子命令使用說明（create / status）
- 執行方式說明

### 4.3 `worktree_manager.py` 函式介面

#### `parse_ticket_id(ticket_id: str) -> bool`
```
目的：驗證 ticket-id 格式是否符合命名規範
輸入：ticket_id: str
輸出：True（合法）/ False（不合法）
規則：符合 ^\d+\.\d+\.\d+-W\d+-\d+(\.\d+)*$ 模式
```

#### `derive_branch_name(ticket_id: str) -> str`
```
目的：從 ticket-id 推導分支名稱
輸入：ticket_id: str（合法格式）
輸出：f"feat/{ticket_id}"
範例：derive_branch_name("0.1.1-W9-002.1") -> "feat/0.1.1-W9-002.1"
```

#### `derive_worktree_path(ticket_id: str) -> str`
```
目的：從 ticket-id 推導 worktree 目錄路徑（絕對路徑）
輸入：ticket_id: str（合法格式）
輸出：絕對路徑字串
邏輯：
  root = get_project_root()
  project_name = os.path.basename(root)
  parent_dir = os.path.dirname(root)
  return os.path.join(parent_dir, f"{project_name}-{ticket_id}")
範例："0.1.1-W9-002.1" -> "/Users/mac-eric/project/ccsession-0.1.1-W9-002.1"
```

#### `cmd_create(ticket_id: str, base: str = "main", dry_run: bool = False) -> int`
```
目的：執行 create 子命令
輸入：ticket_id, base, dry_run
輸出：exit code（0 成功，1 失敗）
副作用：
  - 成功時建立 git branch 和 worktree
  - 輸出操作結果到 stdout
  - 錯誤時輸出錯誤訊息到 stdout（非 stderr）
```

#### `extract_ticket_id_from_branch(branch: str) -> str | None`
```
目的：從分支名稱反推 Ticket ID
輸入：branch: str（如 "feat/0.1.1-W9-002.1"）
輸出：ticket_id 字串，或 None（無法辨識）
邏輯：
  1. 確認以 "feat/" 開頭
  2. 提取後半部分
  3. 用 parse_ticket_id() 驗證格式
  4. 合法則返回，否則返回 None
```

#### `get_worktree_ahead_behind(branch: str, base: str = "main") -> tuple[int, int]`
```
目的：計算分支相對 base 的領先/落後 commit 數
輸入：branch（短名稱，如 "feat/0.1.1-W9-002.1"），base（如 "main"）
輸出：(ahead, behind)  其中:
  ahead = branch 比 base 多幾個 commit（branch 超前）
  behind = base 比 branch 多幾個 commit（branch 落後）
命令：
  ahead: git rev-list --count {base}..{branch}
  behind: git rev-list --count {branch}..{base}
```

#### `get_worktree_uncommitted_count(worktree_path: str) -> int`
```
目的：計算指定 worktree 路徑的未 commit 變更數
輸入：worktree_path（絕對路徑）
輸出：未 commit 的變更行數（git status --porcelain 的行數）
命令：git -C {worktree_path} status --porcelain
```

#### `cmd_status(ticket_id: str | None = None) -> int`
```
目的：執行 status 子命令
輸入：ticket_id（None 表示查詢全部）
輸出：exit code（0 成功，1 失敗）
副作用：輸出狀態報表到 stdout
```

## 5. Hook 行為規格

### 5.1 `is_in_worktree()` 函式（新增至 git_utils.py）

#### 函式介面
```python
def is_in_worktree() -> bool:
    """
    檢查當前工作目錄是否在 git worktree（非主倉庫）中

    Returns:
        True: 當前在 worktree 中（非主倉庫）
        False: 當前在主倉庫或非 git 環境
    """
```

#### 實作邏輯
```
策略：比較 git worktree 的 common directory 和 git directory
  - git rev-parse --git-common-dir  -> 主 .git 目錄路徑
  - git rev-parse --git-dir         -> 當前 .git 目錄路徑
  - 如果兩者不同 -> 在 worktree 中（worktree 的 .git 是一個指向主倉庫的文件）
  - 如果兩者相同 -> 在主倉庫中
```

**注意**：worktree 中的 `--git-dir` 輸出類似 `/path/to/.git/worktrees/name`，而 `--git-common-dir` 輸出 `/path/to/.git`，兩者不同即可判定為 worktree。

### 5.2 branch-verify-hook 改造規格

#### 現有行為
- 在保護分支（main/master 等）上執行 Edit/Write 時：`deny`

#### 新增行為：路徑豁免

在保護分支上，以下路徑允許編輯（`allow`）：

| 允許路徑模式 | 說明 | 範例 |
|------------|------|------|
| `.claude/` 開頭的路徑 | 規則、方法論、Hook 配置等 | `.claude/rules/xxx.md` |
| `docs/` 開頭的路徑 | 工作日誌、Ticket 文件 | `docs/work-logs/xxx.md` |
| `CLAUDE.md` | 專案設定入口 | `CLAUDE.md` |
| `README.md` | 專案說明 | `README.md` |

**判斷優先序**：
```
1. 是 Edit/Write 工具？否 -> allow
2. 取得當前分支 -> 失敗 -> allow（保守）
3. 在 worktree 中？是 -> 使用 is_allowed_branch() 判斷
4. 在 worktree 中且 is_allowed_branch？是 -> allow
5. 是保護分支？否 -> allow（其他分支）
6. 是保護分支 + 是豁免路徑？是 -> allow
7. 是保護分支 + 不是豁免路徑？-> deny（現有行為）
```

#### 豁免路徑判定函式

```python
def is_exempt_path_on_protected_branch(file_path: str) -> bool:
    """
    判斷此路徑是否在保護分支上被豁免（允許編輯）

    適用場景：需要在 main 分支上更新規則、文件、Ticket 時
    """
    exempt_prefixes = [
        ".claude/",
        "docs/",
    ]
    exempt_exact = [
        "CLAUDE.md",
        "README.md",
    ]

    normalized = file_path.lstrip("/")  # 移除開頭斜線
    for prefix in exempt_prefixes:
        if normalized.startswith(prefix):
            return True
    return normalized in exempt_exact
```

#### deny 訊息更新

`deny` 訊息中的建議操作需更新，加入 `/worktree` SKILL 提示：

```
保護分支編輯被阻止

當前在保護分支 '{branch}' 上，無法直接編輯檔案：
{file_path}

建議操作：
1. 建立 feature worktree（推薦）：
   /worktree create <ticket-id>

2. 或手動建立分支：
   git checkout -b feat/your-feature

注意：.claude/ 和 docs/ 路徑在保護分支上允許直接編輯。
```

### 5.3 branch-status-reminder 改造規格

#### 現有行為
- Session 啟動時：永遠輸出分支狀態資訊（含 worktree 列表、保護分支警告）

#### 新行為：異常才輸出

**靜默條件**（所有條件同時滿足時，不輸出任何內容）：

| 條件 | 說明 |
|------|------|
| 在 worktree 中（`is_in_worktree()` 返回 True） | 表示在獨立的開發環境 |
| 當前分支符合 `is_allowed_branch()` | 表示在正確的 feature/fix/... 分支 |

**輸出條件**（任一滿足時，輸出提醒）：

| 情況 | 輸出內容 | 嚴重程度 |
|------|---------|---------|
| 在主倉庫且在保護分支 | 警告：建議建立 worktree，推薦使用 `/worktree create` | WARNING |
| 在主倉庫且在 allowed 分支（feat/ 等） | 提示：建議使用 worktree 保持環境隔離 | INFO |
| 在 worktree 但分支不是 allowed | 警告：worktree 分支異常（可能是 detached HEAD） | WARNING |
| 無法獲取分支資訊 | 警告：無法獲取分支資訊 | WARNING |

#### 輸出格式（異常：主倉庫保護分支）

```
[branch-status-reminder] 警告：當前在主倉庫的保護分支 'main' 上

建議操作：
  建立 feature worktree 進行開發：
  /worktree create <ticket-id>

  或手動建立分支：
  git checkout -b feat/your-feature
```

#### 輸出格式（提示：主倉庫 allowed 分支）

```
[branch-status-reminder] 提示：當前在主倉庫的開發分支 'feat/xxx'

建議使用 worktree 保持環境隔離：
  /worktree create <ticket-id>
```

#### 靜默時的行為
- 完全不輸出任何內容（exit 0 但無 stdout）
- 日誌（logger.debug）仍記錄（不輸出到 stdout/stderr）

## 6. 行為場景提取（Given-When-Then）

### 6.1 create 子命令

場景 1：正常建立 worktree
```
Given: ticket-id 為合法格式，分支和路徑均不存在，main 分支存在
When: /worktree create 0.1.1-W9-002.1
Then: 建立 feat/0.1.1-W9-002.1 分支
      建立 ../ccsession-0.1.1-W9-002.1 worktree
      輸出成功訊息和 cd 指令
      exit code 0
```

場景 2：指定 base 分支
```
Given: ticket-id 合法，base 分支 develop 存在
When: /worktree create 0.1.1-W9-002.1 --base develop
Then: 從 develop 建立 feat/0.1.1-W9-002.1 分支和 worktree
```

場景 3：dry-run 模式
```
Given: 任何 ticket-id（合法格式即可）
When: /worktree create 0.1.1-W9-002.1 --dry-run
Then: 只輸出將要執行的 git 命令，不實際執行
      exit code 0
```

場景 4：ticket-id 格式無效
```
Given: ticket-id 為 "my-feature"（不符合格式）
When: /worktree create my-feature
Then: 輸出「無效的 Ticket ID 格式」錯誤訊息
      exit code 1
```

場景 5：分支已存在
```
Given: feat/0.1.1-W9-002.1 分支已存在
```

## 7. 邊界條件分析

### 7.1 create 子命令邊界條件

| 邊界條件 | 預期行為 |
|---------|---------|
| ticket-id 有很多層（如 `0.1.1-W9-002.1.2.3`） | 合法，分支名 `feat/0.1.1-W9-002.1.2.3`，路徑 `ccsession-0.1.1-W9-002.1.2.3` |
| ticket-id 只有父任務（如 `0.1.1-W9-002`） | 合法，依命名規則處理 |
| 主倉庫目錄名稱含特殊字元 | 使用 `os.path.basename()` 取得目錄名稱，不加工 |
| base 為保護分支（如 main） | 合法，create 不限制 base 分支類型 |
| git worktree add 失敗（磁碟空間不足等） | 捕獲錯誤，輸出 git 原始錯誤訊息，exit 1 |

### 7.2 status 子命令邊界條件

| 邊界條件 | 預期行為 |
|---------|---------|
| worktree 路徑被手動刪除但 git 還記錄 | `git rev-list` 可能失敗，以 N/A 顯示 |
| 分支名不是 feat/ 開頭（如 `hotfix/xxx`） | 顯示分支名，Ticket ID 顯示「無法辨識」 |
| detached HEAD 狀態的 worktree | 分支顯示「(detached)」，Ticket ID 顯示「無法辨識」 |
| 主倉庫在清單中 | 始終顯示為「主倉庫」項目 |
| ahead/behind 計算中 base（main）不存在 | 顯示 N/A |
| 大量 worktree（如 10 個以上） | 正常顯示，無數量限制 |

### 7.3 Hook 邊界條件

| 邊界條件 | 預期行為 |
|---------|---------|
| `is_in_worktree()` 在非 git 目錄執行 | 返回 False（保守預設） |
| git 命令超時（10s） | 返回 False（保守預設），不阻塞 Hook |
| file_path 為絕對路徑（如 `/Users/mac-eric/.claude/rules/xxx.md`） | 路徑豁免邏輯應正規化路徑，取 `{project_root}` 的相對路徑後再判斷 |
| file_path 只有檔名（無路徑前綴） | 不符合豁免條件，走原有保護分支邏輯 |

### 架構決策記錄

**決策 1：worktree_manager.py 直接重用 create_feature_worktree() 的邏輯**

理由：`create_feature_worktree.py` 是獨立腳本，不是可 import 的模組。`worktree_manager.py` 應呼叫 `run_git_command(["worktree", "add", "-b", branch, path, base])` 直接執行，或在 Phase 3a 決定是否重構 `create_feature_worktree.py` 為可 import 的函式。

**決策 2：status 的 Ticket ID 辨識以 branch name 為準**

理由：worktree 路徑命名可能因手動建立而不一致，branch name 是更可靠的反推來源。

**決策 3：ahead/behind 以 main 為基準**

理由：MVP 階段以 `main` 為唯一比較基準，簡化設計。進階版本可支援動態指定 base。

**決策 4：Hook 豁免路徑以相對路徑模式比對**

理由：file_path 在不同環境可能是絕對路徑或相對路徑，需正規化後比對。具體正規化策略由 W9-002.3 實作者決定（可基於 project_root 計算相對路徑）。
