## 1. 實作策略設計

### 1.1 核心目標

在 `ticket create` 命令中新增 `decision_tree_path` 欄位的強制驗證機制，確保：
1. CLI 層面強制驗證（一道防線）
2. Hook 層面智能警告（二道防線）
3. 派發層面最終驗證（三道防線）

### 1.2 實作邏輯流程

```
ticket create 命令執行
    |
    v
[CLI 驗證層] _build_decision_tree_path()
    |
    +-- 檢查是否豁免（子任務 || DOC 類型）
    |   |
    |   +-- 是豁免 + 無參數 → 返回 None
    |   +-- 是豁免 + 有參數 → 處理並返回字典
    |   +-- 非豁免 + 全部提供 → 返回字典
    |   +-- 非豁免 + 部分/無參數 → 返回 False（拒絕建立）
    |   +-- 任何情況 + 空字串值 → 返回 False（拒絕建立）
    |
    v
創建 TicketConfig 字典
    |
    v
[Builder 層] create_ticket_frontmatter()
    |
    +-- 將 decision_tree_path 放入 frontmatter
    |   ├── None → 輸出 "decision_tree_path: null"
    |   └── Dict → 輸出 YAML 映射結構
    |
    v
保存 Ticket .md 檔案
    |
    v
[PostToolUse Hook] ticket-creation-validation-hook.py
    |
    +-- 判斷檔案是否為 Ticket 路徑
    +-- 判斷是否豁免（子任務 || DOC）
    +-- 判斷 decision_tree_path 是否完整
    +-- 若缺少 → 輸出警告到 stderr（exit code 0）
    |
    v
派發時 agent-ticket-validation-hook 執行最終驗證
```

### 1.3 五個核心元件的修改策略

#### 1.3.1 create.py（命令入口）

**修改位置**：在 `execute()` 函式中的「建立配置」段之前

**流程**：
1. 提取三個 CLI 參數：`--decision-tree-entry`, `--decision-tree-decision`, `--decision-tree-rationale`
2. 呼叫 `_build_decision_tree_path()` 驗證和構建
3. 若驗證失敗（返回 False）→ 輸出錯誤訊息，return 1
4. 將返回值（字典或 None）放入 TicketConfig

**關鍵邏輯**（新增 `_build_decision_tree_path()` 函式）：

```pseudocode
函式 _build_decision_tree_path(entry, decision, rationale, is_child, ticket_type):
    豁免 = is_child OR (ticket_type == "DOC")

    // 判斷參數提供狀態
    參數_計數 = count([entry, decision, rationale] 中非 None 的個數)

    if 豁免:
        if 參數_計數 == 0:
            返回 None  // 豁免，無參數
        elif 參數_計數 == 3 and 所有值非空:
            返回 {"entry_point": entry, "final_decision": decision, "rationale": rationale}  // 豁免，有參數
        else:
            // 豁免但部分提供，應該拒絕（保護一致性）
            輸出錯誤("豁免條件下三個參數必須全部提供或全部省略")
            返回 False
    else:
        // 非豁免（根任務或 IMP/TST/ADJ/ANA/INV/RES 類型）
        if 參數_計數 == 0:
            輸出錯誤(CreateMessages.DECISION_TREE_MISSING_ALL)
            返回 False
        elif 參數_計數 == 3:
            if 有任何值為空字串:
                輸出錯誤(CreateMessages.DECISION_TREE_EMPTY_VALUE, field_name=空字串欄位)
                返回 False
            else:
                返回 {"entry_point": entry, "final_decision": decision, "rationale": rationale}
        else:
            缺少欄位 = ["entry_point", "final_decision", "rationale"] 中未提供的欄位
            輸出錯誤(CreateMessages.DECISION_TREE_MISSING_PARTIAL, missing_fields=缺少欄位)
            返回 False
```

#### 1.3.2 ticket_builder.py（Ticket 建構）

**修改位置**：在 TicketConfig TypedDict 類別中新增欄位

**改動**：
1. 在 TicketConfig 中新增欄位：
   ```python
   decision_tree_path: Optional[Dict[str, str]]  # {"entry_point": ..., "final_decision": ..., "rationale": ...}
   ```

2. 在 `create_ticket_frontmatter()` 函式中輸出此欄位：
   - 位置：在 `dispatch_reason` 之後、`who` 之前
   - 邏輯：
     ```python
     "decision_tree_path": config.get("decision_tree_path"),  // None 或 Dict
     ```

**預期輸出**：
- `config["decision_tree_path"] = None` → frontmatter 輸出 `decision_tree_path: null`
- `config["decision_tree_path"] = {...}` → frontmatter 輸出 YAML 映射結構（三個子欄位）

#### 1.3.3 command_lifecycle_messages.py（錯誤訊息）

**新增三個常數**（追加到 CreateMessages 類別）：

class CreateMessages:

#### 1.3.4 ticket-creation-validation-hook.py（新建 Hook）

**檔案路徑**：`.claude/hooks/ticket-creation-validation-hook.py`

**Hook 類型**：PostToolUse

**觸發條件**：
- 工具為 Write
- 檔案路徑符合 `docs/work-logs/*/tickets/*.md` 模式

**核心邏輯**：

```pseudocode
函式 check_ticket_decision_tree_path(file_path, content):
    // 判斷檔案是否符合 Ticket 路徑模式
    if NOT file_path 符合 "docs/work-logs/*/tickets/*.md":
        返回 None  // 非 Ticket 檔案，跳過

    // 解析 frontmatter
    try:
        frontmatter = 解析 YAML frontmatter(content)
    except:
        輸出異常到 stderr
        寫入日誌
        返回 None  // 無法解析，跳過（不誤報）

    // 判斷豁免條件
    parent_id = frontmatter.get("parent_id")
    ticket_type = frontmatter.get("type")

    if parent_id OR ticket_type == "DOC":
        返回 None  // 豁免，無需警告

    // 判斷欄位是否完整
    decision_tree_path = frontmatter.get("decision_tree_path")

    if decision_tree_path is None:
        輸出警告訊息到 stderr
        寫入日誌
        返回 警告訊息

    if decision_tree_path is Dict:
        entry_point = decision_tree_path.get("entry_point")
        final_decision = decision_tree_path.get("final_decision")
        rationale = decision_tree_path.get("rationale")

        if entry_point AND final_decision AND rationale (都非空):
            返回 None  // 完整，無需警告
        else:
            輸出警告訊息
            返回 警告訊息

    返回 None  // 預設：無警告
```

**Hook 進入點**：

```python
def main() -> int:
    """PostToolUse Hook 進入點（環境變數獲取 file_path 和 content）"""
    // 1. 從環境變數取得 file_path 和 content
    // 2. 呼叫 check_ticket_decision_tree_path()
    // 3. 若有警告訊息，輸出到 stderr
    // 4. 寫入日誌
    // 5. 返回 0（始終允許）
```

## 2. 資料結構選擇

### 2.1 CLI 參數設計

| 參數名稱 | 類型 | 必填性 | 說明 |
|---------|------|-------|------|
| `--decision-tree-entry` | str | 條件必填 | 進入決策樹的層級（如「第五層 TDD 階段判斷」） |
| `--decision-tree-decision` | str | 條件必填 | 最終決策描述（如「派發 Phase 3b 給 parsley」） |
| `--decision-tree-rationale` | str | 條件必填 | 決策理由（如「Phase 2 已完成」） |

**組合規則**：三個參數必須全部提供或全部省略（不接受部分提供）

**豁免條件**：
- 子任務（`--parent` 指定）
- DOC 類型（`--type DOC`）

### 2.2 TicketConfig 新增欄位

```python
decision_tree_path: Optional[Dict[str, str]]
# 結構：{"entry_point": str, "final_decision": str, "rationale": str}
# None 表示豁免（子任務或 DOC 且未提供參數）
```

### 2.3 Frontmatter 輸出結構

**有值時**（Dict）：
```yaml
decision_tree_path:
  entry_point: 第五層 TDD 階段判斷
  final_decision: 派發 Phase 3b 給 parsley
  rationale: Phase 2 測試設計已完成，進入實作階段
```

**豁免時**（None）：
```yaml
decision_tree_path: null
```

## 4. 控制流程圖（詳細）

```
START: ticket create 命令
    |
    v
[Phase 1] 參數解析
    ├─ 提取 decision-tree-entry, decision, rationale
    ├─ 檢查 is_child (args.parent is not None)
    ├─ 檢查 ticket_type (args.type or "IMP")
    |
    v
[Phase 2] 票種判定
    ├─ is_child?
    │  ├─ Yes → child_seq = get_next_child_seq(parent), ticket_id = format_child_id
    │  └─ No → seq = get_next_seq(), ticket_id = format_ticket_id
    |
    v
[Phase 3] 決策樹驗證
    ├─ CALL _build_decision_tree_path(entry, decision, rationale, is_child, ticket_type)
    |
    ├─ Decision Point 1: 豁免?
    │  ├─ Yes (is_child || type==DOC) → goto Decision Point 2
    │  └─ No → goto Decision Point 3
    |
    ├─ Decision Point 2: 參數個數?
    │  ├─ 0 個 → RETURN None ✓（豁免無參數）
    │  ├─ 3 個 (全非空) → RETURN Dict ✓（豁免有參數）
    │  └─ 1 或 2 個 → ERROR (豁免但不完整) ✗
    |
    ├─ Decision Point 3: 非豁免
    │  ├─ 0 個 → ERROR (缺全部) ✗
    │  ├─ 1 或 2 個 → ERROR (缺某些) ✗
    │  ├─ 3 個
    │  │   ├─ 有空字串 → ERROR (空值) ✗
    │  │   └─ 全非空 → RETURN Dict ✓
    │  └─ 輸出錯誤訊息到 stderr
    |
    v
[Phase 4] 檢查返回值
    ├─ False (驗證失敗)?
    │  ├─ Yes → 輸出錯誤訊息，RETURN 1 [END FAIL]
    │  └─ No → goto Phase 5
    |
    v
[Phase 5] 建立 TicketConfig
    ├─ config["decision_tree_path"] = 返回值 (None 或 Dict)
    ├─ ... 其他欄位
    |
    v
[Phase 6] 建立 frontmatter
    ├─ CALL create_ticket_frontmatter(config)
    ├─ frontmatter["decision_tree_path"] = config.get("decision_tree_path")
    │  ├─ None → YAML: "decision_tree_path: null"
    │  └─ Dict → YAML: "decision_tree_path:\n  entry_point: ...\n  ..."
    |
    v
[Phase 7] 建立 body
    ├─ CALL create_ticket_body(what, who)
    ├─ 產出標準 Execution Log 樣板
    |
    v
[Phase 8] 儲存檔案
    ├─ tickets_dir.mkdir(parents=True, exist_ok=True)
    ├─ CALL save_ticket(ticket, ticket_path)
    ├─ 寫入 docs/work-logs/v{version}/tickets/{ticket_id}.md
    |
    v
[Phase 9] PostToolUse Hook（自動觸發）
    ├─ Hook 掃描檔案
    ├─ 判斷檔案路徑 (符合 Ticket 模式?)
    ├─ 解析 frontmatter
    ├─ Decision: 豁免?
    │  ├─ Yes (parent_id || type==DOC) → SKIP [NO WARNING]
    │  └─ No → goto 檢查欄位
    ├─ Decision: decision_tree_path 完整?
    │  ├─ Yes (三子欄位非空) → SKIP [NO WARNING]
    │  └─ No → OUTPUT 警告到 stderr，寫入日誌
    |
    v
[Phase 10] 輸出成功訊息
    ├─ 列印 Ticket ID
    ├─ 列印位置
    ├─ 列印類型
    ├─ （如需要）更新 parent 的 children
    ├─ 列印建立檢查清單
    |
    v
RETURN 0 [END SUCCESS]
```

## 7. 語言特定實作注意事項

### 7.1 Python 考量

**版本相關**：Python 3.11+（使用 typing 標準特性）

**優先使用的標準庫**：
- `argparse`：已使用，CLI 參數處理
- `typing.Dict / Optional`：TypedDict 相容性
- `yaml`：YAML 序列化和解析（已有依賴）

**關鍵實作技巧**：
1. 使用 `Optional[str]` 表達可選參數，使用 `Optional[Dict[str, str]]` 表達複雜類型
2. YAML 序列化時讓 yaml.dump() 自動處理特殊字元
3. 使用 f-string 格式化錯誤訊息
4. 避免硬編碼，使用 CreateMessages 常數

**效能最佳化建議**：
- `_build_decision_tree_path()` 函式內部邏輯簡潔（無需特別最佳化）
- Hook 掃描時使用 Path.match() 而非 regex 提升效能

**可能的技術挑戰**：
1. YAML 中文字元轉義和顯示（solved by yaml.dump()）
2. 空字串 vs None 判定邏輯清晰（需仔細測試）
3. 豁免條件邏輯完整性（需確保無遺漏情形）
