## SA 建議

### 核心問題識別

當前 decision_tree_path 驗證存在「驗證時間缺口」：
- **設計意圖**：派發時驗證已填寫的決策路徑
- **實際情況**：派發時才檢查，導致「建立 → 派發被擋 → 事後補填」
- **根本原因**：Ticket 建立階段無強制要求

### 一級推薦：採用方案 A（強制 CLI 參數）

**理由**：
1. **設計一致性**：ticket create 應在建立時就要求完整資訊
2. **流程清晰**：決策與記錄同時進行，而非分開
3. **實作成本低**：只需新增參數驗證邏輯，無 UX 改變
4. **質量守護**：從源頭杜絕不完整 Ticket

**參數設計建議**：
```bash
ticket create --action "..." --target "..." \
  --decision-tree-entry "第四層 Ticket 執行" \
  --decision-tree-decision "派發給 parsley" \
  --decision-tree-rationale "修改兩個獨立檔案"
```

### 二級推薦：配套方案 B（PostToolUse Hook）

**目的**：作為「最後防線」
- 直接編輯 .md 檔案繞過 CLI 驗證時
- 提供友善的補填提示而非拒絕派發

**Hook 行為**：
- 建立後自動掃描 decision_tree_path
- 缺少 → 輸出警告 + 記錄日誌（但不阻止）
- 派發時 agent-ticket-validation-hook 才最終阻止

### 三級收穫：長期架構改善

實作此方案過程中，可同時：
1. 整理 Ticket 建立的所有必填欄位清單
2. 評估是否有其他欄位也應在建立時強制
3. 考慮將 CLI 參數進一步簡化為「預設值 + 覆蓋」模式

### 檢查清單與驗證方案

**檢查清單完善建議**：
- 現狀：提示 「是否已填寫 decision_tree_path？」（提示版）
- 改進：改為執行驗證時更新為「已自動驗證」（確認版）

**驗證方案強化**：
- 方案 A 實施後，建立階段已驗證（無需 Hook 執行）
- Hook 仍需保留作為防守線
## 方案分析

### 方案 A：CLI 參數強制要求（建立階段驗證）

**實作方式**：
- 新增 `--decision-tree-entry` 參數（必須，字串）
- 新增 `--decision-tree-decision` 參數（必須，字串）
- 新增 `--decision-tree-rationale` 參數（必須，字串）
- 在 execute() 中檢查三個參數是否都提供
- 缺少時拋出錯誤（而非警告），阻止 Ticket 建立

**優點**：
- 最強制性，完全從源頭阻止無欄位 Ticket 建立
- ticket create 呼叫端必須清楚自己的決策樹路徑
- 無事後補填的可能性

**缺點**：
- CLI 參數過多（3 個新參數）
- 命令行很長且不友善
- 使用者需要先決策再建立（可能打斷工作流）

**Code 複雜度**：低（參數檢查 + frontmatter 傳遞）

---

### 方案 B：建立後 Hook 檢查並強制提示（建立階段提醒）

**實作方式**：
- 不修改 ticket create 命令
- 新建 `PostToolUse` Hook（ticket-creation-validation-hook）
- Ticket 建立後自動掃描 frontmatter
- 缺少 decision_tree_path → Hook 提示補填

**優點**：
- 流程對使用者最友善（無強制參數）
- Ticket 建立成功後自動檢查
- 提示清晰且可操作

**缺點**：
- 仍然是「事後檢查」（非源頭）
- Hook 無法阻止 Ticket 建立，只能提示
- 使用者可能忽視提示
- 延遲驗證（兩個 Hook 階段才完整檢查）

**Code 複雜度**：中等（Hook 編寫 + 日誌記錄）

---

### 方案 C：互動式引導（建立過程中填寫）

**實作方式**：
- 修改 ticket create 命令以支援互動模式
- 若未提供 --decision-tree 參數 → 進入互動模式
- 逐步提示使用者輸入三個欄位值
- 或提供預填選項（常見的 entry_point 列表）

**優點**：
- 既友善又強制（建立時必須完成）
- 使用者立即看到選項而非盲目填寫
- entry_point 可以提供下拉選單

**缺點**：
- 改變 ticket create UX（加入互動步驟）
- Code 複雜度最高
- 需要處理中斷/逃出情境

**Code 複雜度**：高（互動邏輯 + 選單處理）

---

## 方案推薦

**建議採用 方案 A + 方案 B 混合**：

1. **立即**（優先）：實作方案 A（CLI 參數強制）
   - ticket create 在缺少 decision_tree 參數時明確拒絕
   - 強制從源頭解決流程缺口
   - 給使用者明確的錯誤訊息："缺少 --decision-tree-* 參數"

2. **配套**：保留方案 B（PostToolUse Hook 提示）
   - 作為「最後防線」（以防有人直接編輯 .md 檔）
   - Hook 檢查並記錄到日誌

**不建議方案 C**：
- 互動模式加重 Ticket 建立流程
- 與現有 CLI 設計哲學不符（前置決策不在此決策樹層級產生）
- PM 應在派發時就已決策，ticket create 只是記錄
