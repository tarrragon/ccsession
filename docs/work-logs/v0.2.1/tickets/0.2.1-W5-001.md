## JSONL Agent 事件格式分析

### 目錄結構

Subagent 有獨立的 JSONL 檔案，存放在 parent session 的子目錄中：

```
~/.claude/projects/{project-slug}/{sessionId}/
  subagents/
    agent-{agentId}.jsonl       # subagent 對話紀錄
    agent-{agentId}.meta.json   # subagent 元資料
```

Parent session 的 JSONL 仍在原位：`{project-slug}/{sessionId}.jsonl`

### Meta 檔案格式

```json
{
  "agentType": "parsley-flutter-developer",
  "description": "DRY refactor: buildHighlightableText"
}
```

欄位：agentType（代理人角色名稱）、description（任務描述）。

### Subagent JSONL 事件欄位

每行 JSONL 包含以下關鍵欄位（與 parent 格式相同，但多了 agentId）：

| 欄位 | 值範例 | 說明 |
|------|--------|------|
| sessionId | 86043eca-... (parent UUID) | 指向 parent session |
| agentId | ae508ccd7a4dabb52 | subagent 唯一識別碼 |
| isSidechain | true | 標記為旁鏈（subagent） |
| type | user / assistant | 訊息類型（與 parent 相同） |
| parentUuid | null 或 message UUID | JSONL 內部的訊息鏈結 |

重要：sessionId 欄位值等於 parent session 的 UUID，不是 subagent 自己的 ID。

### Parent JSONL 中的 Agent Tool Call

Parent session JSONL 包含 Agent tool_use 事件：

```json
{
  "name": "Agent",
  "input": {
    "subagent_type": "parsley-flutter-developer",
    "description": "DRY refactor: buildHighlightableText",
    "prompt": "..."
  }
}
```

### 實際資料規模

本專案（ccsession）中，多數有 subagent 的 session 含 2-21 個 subagent JSONL 檔案。

### 現有 Go Backend 缺口

file_watcher.go 的 scanExistingFiles() 只掃描 project 目錄下的頂層 .jsonl 檔案（第 164-168 行）。完全忽略 {sessionId}/subagents/ 子目錄。handleFsEvent() 也只處理頂層新增的 .jsonl。

## HTTP Hook 可行性評估

### 現有 Hook 事件類型

Claude Code 目前支援的 Hook 事件：PreToolUse、PostToolUse、UserPromptSubmit、SessionStart、Stop。

**不存在 SubagentStart / SubagentStop 事件。** 這是 Claude Code Hook 系統尚未提供的功能。

### 可替代方案：PreToolUse/PostToolUse on Agent matcher

專案 settings.json 已配置 PostToolUse + Agent matcher（dispatch-count-guard-hook.py、agent-commit-verification-hook.py）。這些 Hook 在 parent session 派發 Agent tool call 前後觸發。

環境變數可用資訊（推測）：
- CLAUDE_SESSION_ID — parent session ID
- tool input 中的 subagent_type、description

限制：
- Hook 只在 parent session 觸發，無法知道 subagent 的 agentId
- Hook 無法追蹤 subagent 何時完成（PostToolUse 觸發時 subagent 已結束）
- 需要 HTTP call 到 Go Backend，增加延遲和失敗風險

## 方案比較

| 維度 | 方案 A：純 JSONL 解析 | 方案 B：HTTP Hook 通知 | 方案 C：混合方案 |
|------|---------------------|---------------------|----------------|
| 資料來源 | subagents/ 目錄 + meta.json | PreToolUse/PostToolUse Agent | JSONL 為主 + Hook 補充 |
| 即時性 | fsnotify 監聽，接近即時 | Hook 觸發時通知，但僅 parent 端 | 同方案 A |
| 可靠性 | 高（檔案系統一定有） | 中（Hook 可能失敗、靜默跳過） | 高 |
| 資訊完整度 | 完整（agentId、agentType、description、全部對話） | 不完整（無 agentId、無法追蹤進度） | 完整 |
| 實作複雜度 | 中（擴展 FileWatcher + Parser） | 高（HTTP endpoint + Hook 腳本 + 失敗處理） | 高（兩套機制） |
| parent-child 關聯 | sessionId 欄位直接指向 parent | 需從 CLAUDE_SESSION_ID 推斷 | 同方案 A |
| SubagentStart/Stop | 不存在此 Hook 事件 | 不存在此 Hook 事件 | N/A |

## 推薦方案：方案 A（純 JSONL 解析）

### 理由

1. **資料已經完整存在**：subagents/ 目錄下有獨立 JSONL + meta.json，包含所有需要的資訊
2. **架構一致**：現有 Backend 已使用 fsnotify + JSONL 解析，擴展路徑自然
3. **關聯性內建**：subagent JSONL 的 sessionId 欄位直接指向 parent，agentId 標識自身
4. **Hook 方案不可行**：Claude Code 不提供 SubagentStart/SubagentStop Hook 事件；PostToolUse Agent matcher 資訊不足（無 agentId）且只在 subagent 結束後觸發
5. **零額外依賴**：不需要 HTTP endpoint、不需要 Hook 腳本、不增加失敗點

### 實作概要設計

#### 1. FileWatcher 擴展

- scanExistingFiles()：掃描 `{sessionId}/subagents/*.jsonl` 子目錄
- handleFsEvent()：監聽 subagents/ 目錄的 Create 事件
- extractSessionInfo()：從路徑識別 subagent（路徑含 /subagents/agent-{id}.jsonl）

#### 2. 資料模型擴展

SessionEvent 新增欄位：
- AgentID string — subagent 識別碼（空字串 = parent session）
- ParentSessionID string — 指向 parent（從 JSONL sessionId 欄位取得）
- AgentType string — 代理人類型（從 meta.json 讀取）
- AgentDescription string — 任務描述（從 meta.json 讀取）

SessionRegistry 需要：
- 以 agentId 為 key 的 subagent session 追蹤
- parent-child 關聯查詢（列出某 session 的所有 subagent）

#### 3. meta.json 解析

新增 AgentMeta struct + 讀取邏輯。subagent JSONL 首次被發現時，讀取同目錄的 .meta.json。

#### 4. WebSocket/Frontend 擴展

- 新增 session type 區分（parent / subagent）
- 新增 parent-child 樹狀結構 API
- Frontend 可按層級分組顯示

### 估計影響範圍

| 檔案 | 變更類型 |

| server/file_watcher.go | 擴展掃描和監聽邏輯 |
