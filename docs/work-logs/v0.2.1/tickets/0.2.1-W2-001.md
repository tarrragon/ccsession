## Task Summary

## Phase 1 功能規格設計

### 1. 需求分析

**核心問題**：當使用者同時監控多個專案時，所有專案的 session 混在同一列表，無法快速聚焦特定專案。

**解決方案**：在 Session List 頂部加入按專案分組的 TabBar，每個 Tab 過濾顯示對應專案的 sessions，Tab 內部沿用現有的 active/idle/completed 分組機制。

### 2. 資料流設計

```
SessionListNotifier.sessions (List<SessionInfo>)
    |
    v
groupSessionsByProject(sessions)  -- 新增純函式
    |   key: projectPath, value: List<SessionInfo>
    v
sortedProjectPaths  -- 字母排序，空 projectPath 排最後
    |
    v
TabBar（每個 Tab = 一個 project）
    |
    v（選中 Tab 的 sessions）
filteredGroupedSessions()（現有搜尋 + groupSessionsByStatus）
    |
    v
flattenGroups() → ListView（現有機制不變）
```

#### 3.4 修改 SessionGroupUiNotifier：改為 per-project 狀態

**風險點**：現有 SessionGroupUiState 是全域共用的，改為 per-project 後需要以 projectPath 為 key。

**方案**：使用 family provider，以 projectPath 為參數。

```dart

/// 修改後：
@riverpod
class SessionGroupUiNotifier extends _$SessionGroupUiNotifier {
  @override
  SessionGroupUiState build(String projectPath) {
    return const SessionGroupUiState();
  }
  // 方法簽名不變：setPage, toggleExpanded, resetAllPages
}
```

**影響範圍**：
- `sessionGroupUiNotifierProvider` → `sessionGroupUiNotifierProvider(projectPath)`
- `session_list_page.dart` 中所有 `ref.read(sessionGroupUiNotifierProvider.notifier)` 需傳入 projectPath
- `flattenGroups` 呼叫處需傳入對應 project 的 uiState


```
  └── asyncState.when(data:)
```

**為什麼用 ConsumerStatefulWidget**：`DefaultTabController` 需要 `TickerProviderStateMixin`。

### 5. 狀態管理方案

| 狀態 | Provider | 粒度 | 說明 |
|------|----------|------|------|
| 全部 sessions | sessionListNotifierProvider | 全域 | 現有，不變 |
| 當前 Tab 索引 | projectTabNotifierProvider | 全域 | 新增 |
| 搜尋狀態 | sessionListSearchNotifierProvider | 全域 | 現有，filteredGroupedSessions 增加 projectPath 參數 |
| 分頁/摺疊 | sessionGroupUiNotifierProvider(projectPath) | per-project | 修改為 family |

### 6. 邊界條件處理

| 場景 | 處理方式 |
|------|---------|
| 無任何 session | 不顯示 TabBar，直接顯示 "No sessions"（現有行為） |
| 僅 1 個專案 | 仍顯示 TabBar（1 個 Tab），保持一致性 |
| session 的 projectPath 為空字串 | 歸入 "Other" 分組，排序時排在最後 |
| 多個 session 有相同 projectPath | 正常歸入同一 Tab |
| 即時新增/移除 session 導致專案數變化 | TabController 需重建（length 變化），當前 Tab 索引 clamp 到有效範圍 |
| 搜尋過濾後某專案 session 數為 0 | 該 Tab 內顯示空狀態，Tab 仍保留（不因搜尋隱藏 Tab） |
| Tab 切換時搜尋狀態 | 搜尋狀態跨 Tab 共享（全域），切換 Tab 後搜尋條件仍生效 |
| projectPath 含特殊字元或很長 | Tab 標籤只顯示 extractProjectName 的結果（最後一段路徑） |

### 7. 行為場景提取

場景 1: 基本專案分組顯示
Given: 有 3 個 session 分屬 2 個不同 projectPath
When: 頁面載入完成
Then: TabBar 顯示 2 個 Tab，各 Tab 顯示對應專案的 sessions

場景 2: Tab 切換保持獨立狀態
Given: Tab A 的 completed 分組已摺疊，分頁在第 2 頁
When: 切換到 Tab B 再切回 Tab A
Then: Tab A 的 completed 仍為摺疊，分頁仍在第 2 頁

場景 3: 無專案資訊的 session
Given: 有 session 的 projectPath 為空字串
When: 頁面載入完成
Then: 該 session 歸入 "Other" Tab，且 "Other" Tab 排在最後

場景 4: 專案數動態變化
Given: 正在檢視 Tab B
When: 新 session 加入，屬於新專案 C
Then: TabBar 新增 Tab C（按字母排序插入），當前仍停留在 Tab B

場景 5: 搜尋跨 Tab 生效
Given: 搜尋列輸入 "auth"
When: 切換不同 Tab
Then: 每個 Tab 內都只顯示匹配 "auth" 的 sessions

場景 6: 可捲動 TabBar
Given: 有超過 5 個專案
When: TabBar 寬度不足以一次顯示所有 Tab
Then: TabBar 可水平捲動檢視所有 Tab

場景 7: 空列表狀態
Given: 無任何 session
When: 頁面載入完成
Then: 不顯示 TabBar，顯示 "No sessions" 提示

場景 8: Tab 排序規則
Given: 有專案 "zoo"、"alpha"、"beta" 和一個空 projectPath session
When: 頁面載入完成
Then: Tab 順序為 alpha, beta, zoo, Other
