# 0.2.1-W1-001 Phase 2 Test Case Design

## 1. 測試策略規劃

### 1.1 分層測試決策

本 Ticket 全部場景屬於**整合測試**層級，驗證跨模組呼叫鏈串接，不重複現有單元測試邏輯。

| 端 | 測試層級 | 測試目標 | 現有單元測試 |
|----|---------|---------|------------|
| Go | 整合測試 | FileWatcher → Parser → Registry → EventDispatcher → WebSocketServer 管線 | 47 個（各模組獨立） |
| Flutter | 整合測試 | WebSocketService.messageStream → Notifier 狀態更新管線 | 29 個（各模組獨立） |

### 1.2 Mock 策略（Sociable Unit Tests 原則）

**Go 端**：不 Mock 任何內部模組。使用真實的 Registry、EventDispatcher、WebSocketServer，僅隔離外部世界（檔案系統用 tmpDir、HTTP 用 httptest.Server）。

| 依賴 | 策略 | 理由 |
|------|------|------|
| 檔案系統 | tmpDir 隔離 | 外部世界 |
| HTTP Server | httptest.Server | 外部世界 |
| WebSocket 連線 | gorilla/websocket Dialer 連到 httptest | 外部世界 |
| SessionRegistry | 真實物件 | 內部模組，驗證串接 |
| EventDispatcher | 真實物件 | 內部模組，驗證串接 |
| FileWatcher | 真實物件 | 內部模組，驗證串接 |
| time.Now | 注入 timeProvider | 控制 status scan |

**Flutter 端**：Mock WebSocketService（外部邊界），使用真實 Notifier 和 ProviderContainer。

| 依賴 | 策略 | 理由 |
|------|------|------|
| WebSocketService | FakeWebSocketService（StreamController 注入） | 外部邊界，控制輸入 |
| SessionListNotifier | 真實物件 | 內部模組，驗證串接 |
| ConversationNotifier | 真實物件 | 內部模組，驗證串接 |
| ProviderContainer | 真實 Riverpod container | 驗證 provider 連動 |

### 1.3 測試隔離策略

| 端 | 隔離方式 |
|----|---------|
| Go | 每個測試函式建立獨立 integrationHarness（含獨立 tmpDir、channels、goroutines），測試結束 teardown |
| Flutter | 每個測試建立獨立 ProviderContainer + FakeWebSocketService，測試結束 dispose |

#### TC-GO-01: JSONL 寫入觸發 session_list 推送

**測試策略層級**：整合測試
**串接點覆蓋**：fileWatcher→parser、parser→eventDispatcher、eventDispatcher→hub、hub→client

```
場景：JSONL 檔案寫入後，WebSocket client 收到 session_list 更新

Given: integrationHarness 已啟動（所有 goroutine 運行中）
Then（前置驗證）: httpServer 已啟動且可存取

Given: WebSocket client 已連線到 httpServer
Then（前置驗證）: client 收到初始 session_list 訊息（sessions 為空陣列或現有清單）

When: 呼叫 h.writeJSONL("session-A", "/project/path", userMessageJSON)
      （在 tmpDir/projects/{encodedPath}/session-A.jsonl 寫入一行 user message）

Then: client 在 5 秒 timeout 內收到 ServerMessage
Then: message.Type == "session_list"
Then: message.Data.Sessions 陣列包含 sessionID == "session-A" 的項目
Then: 該 session 的 Status 為 active
```

**邊界條件**：

```
場景：JSONL 格式錯誤不中斷監控

Given: integrationHarness 已啟動，WebSocket client 已連線
When: 在 JSONL 檔案中寫入非 JSON 字串（如 "this is not json"）
Then: client 不收到任何 session_event（無 crash）
When: 隨後寫入一行正確的 user message JSON
Then: client 收到 session_list 更新（管線仍然正常運作）
```

#### TC-GO-05: session_status_change 在狀態變更時廣播

**測試策略層級**：整合測試
**串接點覆蓋**：watcher→dispatcher→hub（status scan）

```
場景：session 超時變為 idle 時廣播狀態變更

Given: integrationHarness 已啟動（timeProvider 可控）
Given: WebSocket client 已連線
Given: 已透過 writeJSONL 建立 "session-1"，狀態為 active
Then（前置驗證）: client 收到 session_list，"session-1" status 為 active

When: EventDispatcher 的 status scan 在下一個 tick 偵測到 "session-1"
      超過 idle 閾值（透過 timeProvider 推進時間）

Then: client 收到 ServerMessage，type == "session_status_change"
Then: message.Data.SessionID == "session-1"
Then: message.Data.Status == "idle"
```

**設計備註**：此場景需要研究 EventDispatcher 的 status scan 機制是否由 timeProvider 控制或由獨立 goroutine 定期觸發。Phase 3a/3b 實作時需確認具體觸發方式。

#### TC-GO-07: EventDispatcher 輸出通道滿時 non-blocking drop

**邊界條件**：

```
場景：dispatchCh 緩衝區滿時不阻塞 FileWatcher

Given: integrationHarness 已啟動，但 WebSocketServer.Run 未啟動
      （dispatchCh 無消費者，會填滿）
Then（前置驗證）: dispatchCh 緩衝區大小為 DispatchChBufferSize

When: 透過 writeJSONL 快速寫入超過 DispatchChBufferSize 行事件

Then: FileWatcher 和 EventDispatcher 不阻塞（不 deadlock）
Then: 寫入操作在合理時間內完成（5 秒 timeout）
```

**設計備註**：此場景驗證 non-blocking send 的實作正確性。Phase 3b 實作時需確認 EventDispatcher 的 dispatchAfterUpdate 是否使用 select-default 模式。

## 3. 測試環境設置規劃

### 3.1 Go 端 integrationHarness

| 元件 | 設置 | 清理 |
|------|------|------|
| tmpDir | os.MkdirTemp | os.RemoveAll |
| channels | 建立 sessionEvCh、hookEvCh、dispatchCh | cancel context（goroutine 自行退出） |
| SessionRegistry | NewSessionRegistry(timeProvider) | 無需清理 |
| FileWatcher | NewFileWatcher(tmpDir, eventCh, registry) | context cancel |
| EventDispatcher | NewEventDispatcher(registry, sessionEvCh, hookEvCh, outCh, timeProvider) | context cancel |
| WebSocketServer | NewWebSocketServer(registry, dispatchCh, timeProvider) | context cancel |
| httptest.Server | httptest.NewServer(http.HandlerFunc(wsServer.HandleWS)) | httpServer.Close() |
| WebSocket client | websocket.DefaultDialer.Dial(httpServer.URL) | conn.Close() |

**teardown 順序**：cancel context → httpServer.Close() → conn.Close() → os.RemoveAll(tmpDir)

## 4. 行為鏈式推演總結

### 4.1 Go 端行為鏈

```
JSONL 檔案寫入
  → FileWatcher.readNewLinesForReader 偵測
    → ParseLine 解析為 SessionEvent
      → eventCh 送出
        → EventDispatcher.processSessionEvent 讀取
          → registry.UpsertFromSessionEvent（更新 session 狀態）
          → registry.AppendEvent（儲存歷史）
            → dispatchAfterUpdate 送入 outCh
              → WebSocketServer.processDispatchedEvent 讀取
                → broadcastSessionList（所有 client）
                → pushToSubscribers（已訂閱 client）
```

每個箭頭（→）代表一個串接點，TC-GO-01 到 TC-GO-05 覆蓋全部串接點。

### 4.2 Flutter 端行為鏈

```
WebSocketService.messageStream 推入 ServerMessage
  → SessionListNotifier._handleMessage（type routing）
    → _handleSessionList（session_list）
    → _handleStatusChange（session_status_change）
  → ConversationNotifier._handleMessage（type routing）
    → _handleSessionHistory（session_history）
    → _handleSessionEvent（session_event）
    → _handleError（error）

connectionStateProvider 變更
  → ConversationNotifier listener
    → _resubscribeCurrentSession
      → subscribeSession + requestSessionHistory

ConversationNotifier.loadSession
  → unsubscribeSession（舊 session）
  → requestSessionHistory + subscribeSession（新 session）
```

TC-FL-01 到 TC-FL-06 覆蓋全部串接點。

### 4.3 四維度行為分支覆蓋

| 維度 | Go 端覆蓋 | Flutter 端覆蓋 |
|------|----------|---------------|
| 正常流程 | TC-GO-01, 02, 03, 05 | TC-FL-01, 02, 03, 04, 05 |
| 異常流程 | TC-GO-03（session_not_found）, TC-GO-06（invalid action） | TC-FL-06（error 訊息） |
| 邊界條件 | TC-GO-01（格式錯誤不中斷）, TC-GO-04（未訂閱不推送）, TC-GO-07（通道滿） | TC-FL-01（空列表）, TC-FL-02（不同 sessionId 忽略）, TC-FL-03（未知 sessionId）, TC-FL-04（無 session 時重連）, TC-FL-05（切換取消舊訂閱） |
| 中斷操作 | TC-GO-07（消費者停止） | TC-FL-04（重連場景） |

### 4.4 完成標準確認

- 所有 11 個串接點皆有測試覆蓋
- 四個維度的場景皆有至少一個測試案例
- 無法再提出新的「如果...那麼...」組合（已窮舉 JSONL 錯誤、未訂閱、不存在 session、無效 action、通道滿、空列表、sessionId 不匹配、重連、切換 session 等場景）
- 所有 Then 都是可直接觀察的狀態（WebSocket 收到的訊息、provider state 的欄位值、sentMessages 記錄）
