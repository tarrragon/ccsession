## Problem Analysis

## 根因

## 多視角分析結論

### Tier 分類（code-explorer）

- Tier 2（特定場景，1734 行）：parallel-dispatch, tdd-flow, task-splitting 等 10 個
- Tier 3（參考性質，173 行）：skill-index, methodology-index

### 架構方案評估（linux）
- 方案 A 全部移入 rules/：否決（+3005 行 context 膨脹 280%）

- 方案 C SessionStart hook 提醒：否決（hook 不能強制 Read）

- 核心規則（封閉）嵌入 SKILL.md，觸發即載入

- 不改動 rules/ 目錄結構，不增加自動載入負擔

## 最終方案：Manager Skill 作為角色辨識器

### 核心設計
SKILL.md 不嵌入規則，不搬家，只做角色辨識和路由：
1. 寬鬆觸發詞 — 涵蓋開發相關操作，容易被觸發
2. SKILL.md 很短（30-50 行）— 只做角色辨識
3. 主線程 → 讀 pm-rules/decision-tree.md，依照引導做事
4. 代理人 → 忽略，繼續執行 ticket

### 角色辨識邏輯
- 主線程：正在做任務拆分、派發、驗收、決策（不寫程式碼）
- 代理人：已認領 ticket，正在執行開發/測試/分析任務

### 為什麼不嵌入規則（linux 審查結論）
- pm-rules/ 不動、不搬、不精簡
- 精簡版必然丟失邊界條件，維護兩套版本是技術債務工廠
- SKILL.md 是路由器不是容器
- Read decision-tree.md 一次的 token 成本遠低於維護精簡版的認知成本

### 觸發詞策略（explorer 分析結論）
- 寬鬆但不與 ticket/tdd skill 衝突
- 因為 SKILL.md 很短，多次觸發的 context 成本可控
- 角色辨識讓非主線程快速跳過，不浪費 context
