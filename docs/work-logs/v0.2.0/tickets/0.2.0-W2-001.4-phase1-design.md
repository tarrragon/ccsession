## 1. 模組概述

### 1.1 職責定義

WebSocket Server 是 Go Backend 對 Flutter Frontend 的**唯一即時通訊管道**。負責：

1. 管理多個 Client 的 WebSocket 連線生命週期
2. 處理 Client 請求（訂閱/取消訂閱/查詢）
3. 消費 EventDispatcher 的 `DispatchedEvent` 並推送給已訂閱的 Client
4. 維持心跳機制（30 秒 ping/pong）

### 1.2 在整體架構中的位置

```
+----------------------------+
|  Event Dispatcher (§3.7)   |
|  chan DispatchedEvent       |
+------------+---------------+
             |
             v
+----------------------------+     +----------------------------+
|  WebSocket Server (§3.3)   |     |  Session Registry (§3.4)   |
|  - 消費 DispatchedEvent    |---->|  - List() 查詢 session     |
|  - 管理 Client 連線        |     |  - Get() 查詢單一 session  |
|  - 推送訊息給 Client       |     |  - GetHistory() 查詢歷史   |
+----------------------------+     +----------------------------+
             |
             | WebSocket (ws://localhost:{port}/ws)
             v
+----------------------------+
|  Flutter Frontend          |
+----------------------------+
```

### 1.3 職責不涵蓋

- 本模組**不**負責事件融合或去重（由 EventDispatcher 處理）
- 本模組**不**負責 session 狀態管理（由 SessionRegistry 處理）
- 本模組**不**負責 JSONL 解析或 HTTP Hooks 接收
- 本模組**不**負責 session 歷史事件的儲存（由 SessionRegistry 管理）

## 2. 公開 API 定義

### 2.1 核心 Struct

#### WebSocketServer

```go
// WebSocketServer 管理所有 WebSocket Client 連線，
// 消費 EventDispatcher 的輸出並推送給已訂閱的 Client。
//
// 並發安全：使用 sync.RWMutex 保護 clients map。
// 每個 Client 連線由獨立的 readPump/writePump goroutine 處理。
type WebSocketServer struct {
    registry   *SessionRegistry
    dispatchCh <-chan DispatchedEvent  // 來自 EventDispatcher 的事件輸入
    clients    map[*Client]struct{}    // 已連線 Client 集合
    mu         sync.RWMutex           // 保護 clients map
    upgrader   websocket.Upgrader     // gorilla/websocket upgrader
}
```

#### Client

```go
// Client 代表單一 WebSocket 連線，追蹤其訂閱狀態。
//
// 每個 Client 有獨立的 send channel，writePump goroutine 從此 channel 讀取並寫入 WebSocket。
// 若 send channel 滿，writePump 會關閉連線（Client 消費太慢）。
type Client struct {
    conn          *websocket.Conn
    send          chan []byte           // 已序列化的 JSON 訊息
    subscriptions map[string]struct{}   // 訂閱的 sessionID 集合
    mu            sync.RWMutex         // 保護 subscriptions map
}
```

### 2.2 WebSocket 訊息結構

#### Client 請求訊息（Client -> Server）

```go
// ClientMessage 是 Client 發送給 Server 的請求格式。
type ClientMessage struct {
    Action    string `json:"action"`              // subscribe_session | unsubscribe_session | get_session_list | get_session_history
    SessionID string `json:"sessionId,omitempty"` // 目標 session UUID
    Limit     int    `json:"limit,omitempty"`     // get_session_history 的回傳筆數上限
    Before    string `json:"before,omitempty"`    // ISO 8601 時間戳，分頁 cursor
}
```

#### Server 推送訊息（Server -> Client）

```go
// ServerMessage 是 Server 推送給 Client 的訊息格式。
type ServerMessage struct {
    Type string      `json:"type"` // session_list | session_event | session_history | session_status_change | error
    Data interface{} `json:"data"`
}
```

#### 各 Type 對應的 Data 結構

```go
// SessionListData 對應 type="session_list" 的 data。
type SessionListData struct {
    Sessions []*SessionInfo `json:"sessions"`
}

// SessionEventData 對應 type="session_event" 的 data。
// 推送單一 SessionEvent 給已訂閱的 Client。
type SessionEventData struct {
    SessionID    string       `json:"sessionId"`
    Type         string       `json:"type"`
    Timestamp    string       `json:"timestamp"`    // ISO 8601 UTC
    MessageID    string       `json:"messageId"`
    ContentIndex int          `json:"contentIndex"`
    IsLastContent bool        `json:"isLastContent"`
    Content      EventContent `json:"content"`
    ToolName     string       `json:"toolName,omitempty"`
    AgentID      string       `json:"agentId,omitempty"` // [v0.3 預留] 從 SessionInfo 帶入
}

// SessionHistoryData 對應 type="session_history" 的 data。
type SessionHistoryData struct {
    SessionID string          `json:"sessionId"`
    Events    []*SessionEvent `json:"events"`    // 依 timestamp 升序
    HasMore   bool            `json:"hasMore"`   // 是否還有更早的事件
}

// SessionStatusChangeData 對應 type="session_status_change" 的 data。
type SessionStatusChangeData struct {
    SessionID string        `json:"sessionId"`
    Status    SessionStatus `json:"status"`
    Timestamp string        `json:"timestamp"` // ISO 8601 UTC
}

// ErrorData 對應 type="error" 的 data。
type ErrorData struct {
    Code    string `json:"code"`
    Message string `json:"message"`
}
```

## 3. 函式簽名

### 3.1 WebSocketServer 建構與生命週期

```go
// NewWebSocketServer 建立 WebSocket Server 實例。
// registry 用於查詢 session 資料。
// dispatchCh 為 EventDispatcher 的輸出通道。
func NewWebSocketServer(registry *SessionRegistry, dispatchCh <-chan DispatchedEvent) *WebSocketServer

// HandleWS 處理 WebSocket 升級請求（http.HandlerFunc）。
// 此方法作為 HTTP handler 註冊到路由 /ws。
// 每個成功升級的連線會啟動 readPump 和 writePump goroutine。
func (s *WebSocketServer) HandleWS(w http.ResponseWriter, r *http.Request)

// Run 啟動 EventDispatcher 事件消費迴圈。
// 此方法阻塞，應在獨立 goroutine 中執行。
// 收到 ctx.Done() 時停止消費，關閉所有 Client 連線。
func (s *WebSocketServer) Run(ctx context.Context)
```

### 3.2 Client 管理

```go
// registerClient 將新 Client 加入 clients map。
func (s *WebSocketServer) registerClient(client *Client)

// unregisterClient 移除 Client 並關閉連線。
func (s *WebSocketServer) unregisterClient(client *Client)

// clientCount 回傳目前連線的 Client 數量。
func (s *WebSocketServer) clientCount() int
```

### 3.3 Client 讀寫 Pump

```go
// readPump 持續從 WebSocket 讀取 Client 訊息，
// 解析 ClientMessage 並路由到對應處理函式。
// 若讀取失敗或連線關閉，呼叫 unregisterClient。
func (s *WebSocketServer) readPump(client *Client)

// writePump 持續從 client.send channel 讀取訊息並寫入 WebSocket。
// 同時負責定期發送 ping 心跳。
// 若寫入失敗，關閉連線。
func (s *WebSocketServer) writePump(client *Client)
```

### 3.4 Client 請求處理

```go
// handleSubscribeSession 將 Client 加入指定 session 的訂閱清單。
// 若 sessionID 為空或在 Registry 中不存在，回傳 error 訊息。
func (s *WebSocketServer) handleSubscribeSession(client *Client, msg ClientMessage)

// handleUnsubscribeSession 將 Client 從指定 session 的訂閱清單移除。
func (s *WebSocketServer) handleUnsubscribeSession(client *Client, msg ClientMessage)

// handleGetSessionList 查詢 SessionRegistry.List() 並推送 session_list 訊息。
func (s *WebSocketServer) handleGetSessionList(client *Client)

// handleGetSessionHistory 查詢指定 session 的歷史事件並推送 session_history 訊息。
// 支援 limit + before 參數的 timestamp-based cursor 分頁。
// limit 預設 DefaultHistoryLimit，上限 MaxHistoryLimit。
// before 為 null 時回傳最新的 limit 筆事件。
func (s *WebSocketServer) handleGetSessionHistory(client *Client, msg ClientMessage)
```

### 3.5 事件推送

```go
// broadcastSessionList 向所有已連線 Client 推送 session_list 訊息。
func (s *WebSocketServer) broadcastSessionList()

// pushToSubscribers 將 session_event 推送給訂閱了指定 sessionID 的 Client。
func (s *WebSocketServer) pushToSubscribers(sessionID string, msg ServerMessage)

// broadcastStatusChange 向所有已連線 Client 推送 session_status_change 訊息。
func (s *WebSocketServer) broadcastStatusChange(sessionID string, status SessionStatus, timestamp time.Time)

// sendToClient 將訊息序列化後送入 client.send channel。
// 若 channel 已滿，關閉 Client 連線（Client 消費太慢）。
func (s *WebSocketServer) sendToClient(client *Client, msg ServerMessage)
```

### 3.6 SessionRegistry 歷史查詢介面（需由 SessionRegistry 擴充）

WebSocket Server 的 `get_session_history` 功能需要 SessionRegistry 提供歷史事件查詢：

```go
// GetHistory 查詢指定 session 的歷史事件。
// limit 為回傳最大筆數。
// before 為 cursor 時間戳，回傳此時間之前的事件；零值表示從最新事件開始。
// 回傳事件依 timestamp 升序排列。
// hasMore 表示是否還有更早的事件。
//
// 此方法需由 SessionRegistry 新增（目前尚未實作），
// 是 .4 子任務的前置需求。
func (r *SessionRegistry) GetHistory(sessionID string, limit int, before time.Time) (events []*SessionEvent, hasMore bool, err error)

// AppendEvent 將 SessionEvent 加入指定 session 的歷史記錄（記憶體中）。
// 單一 session 最多保留 MaxHistoryLimit 筆事件（超過時移除最舊的）。
//
// 此方法由 EventDispatcher 呼叫（在 processSessionEvent 中），
// 是 .4 子任務的前置需求。
func (r *SessionRegistry) AppendEvent(sessionID string, event SessionEvent)
```

**注意**：SessionRegistry 目前不儲存歷史事件。`.4` 子任務實作時需擴充 SessionRegistry，新增 `events map[string][]*SessionEvent` 欄位和上述兩個方法。

## 4. 資料流圖

### 4.1 Client 連線建立流程

```
[Flutter Frontend]
       |
       | HTTP GET /ws (Upgrade: websocket)
       v
[WebSocketServer.HandleWS()]
       |
       | websocket.Upgrade()
       v
[建立 Client{conn, send: make(chan, 256), subscriptions: {}}]
       |
       +-- registerClient(client) → 加入 clients map
       |
       +-- go readPump(client)    → 讀取 Client 訊息
       |
       +-- go writePump(client)   → 寫入訊息 + 心跳
       |
       v
[推送 session_list 給新 Client]
       |
       v
[Client 收到完整 session 列表快照]
```

### 4.2 事件推送流程（EventDispatcher -> Client）

```
[EventDispatcher.outCh] → DispatchedEvent
       |
       v
[WebSocketServer.Run() select loop]
       |
       | 判斷 ChangeType
       v
+-- ChangeTypeNew / ChangeTypeUpdated:
|     |
|     +-- broadcastSessionList()           → 所有 Client 收到更新的 session_list
|     |
|     +-- pushToSubscribers(sessionID, session_event)
|           → 只推送給訂閱了此 sessionID 的 Client
|
+-- ChangeTypeStatusChanged:
      |
      +-- broadcastStatusChange(sessionID, newStatus)
            → 所有 Client 收到 session_status_change
```

### 4.3 Client 請求處理流程

```
[Client WebSocket 訊息]
       |
       v
[readPump() 讀取]
       |
       | json.Unmarshal → ClientMessage
       v
[依 Action 路由]
       |
       +-- subscribe_session    → handleSubscribeSession()
       |                           → 加入 subscriptions
       |                           → 回傳確認（無額外訊息）
       |
       +-- unsubscribe_session  → handleUnsubscribeSession()
       |                           → 從 subscriptions 移除
       |
       +-- get_session_list     → handleGetSessionList()
       |                           → registry.List()
       |                           → sendToClient(session_list)
       |
       +-- get_session_history  → handleGetSessionHistory()
       |                           → registry.GetHistory(sessionID, limit, before)
       |                           → sendToClient(session_history)
       |
       +-- 未知 action          → sendToClient(error: INVALID_ACTION)
       |                           → WARN log
       |
       +-- JSON 解析失敗        → sendToClient(error: INVALID_JSON)
                                   → WARN log
```

### 4.4 心跳機制

```
[writePump goroutine]
       |
       | 每 30 秒
       v
[發送 ping frame]
       |
       v
[Client 回傳 pong]
       |
       | readPump 設定 pong handler → 重置讀取 deadline
       v
[若 35 秒內無 pong → 連線逾時 → unregisterClient()]
```

## 5. 錯誤處理策略

### 5.1 錯誤分類表

| 錯誤情境 | 偵測時機 | 處理方式 | 日誌級別 |
|---------|---------|---------|---------|
| WebSocket 升級失敗 | HandleWS | 回傳 HTTP 400，不建立 Client | ERROR |
| Client 訊息 JSON 解析失敗 | readPump | 回傳 error 訊息（INVALID_JSON），不關閉連線 | WARN |
| 未知 action | readPump 路由 | 回傳 error 訊息（INVALID_ACTION），不關閉連線 | WARN |
| subscribe 的 sessionID 為空 | handleSubscribeSession | 回傳 error 訊息（INVALID_PARAMS） | WARN |
| subscribe 的 session 不存在 | handleSubscribeSession | 回傳 error 訊息（SESSION_NOT_FOUND） | WARN |
| get_session_history 的 session 不存在 | handleGetSessionHistory | 回傳 error 訊息（SESSION_NOT_FOUND） | WARN |
| get_session_history 的 before 格式錯誤 | handleGetSessionHistory | 忽略 before，回傳最新事件 | WARN |
| client.send channel 已滿 | sendToClient | 關閉 Client 連線（消費太慢） | WARN |
| pong 逾時 | readPump deadline | 關閉 Client 連線 | INFO |
| WebSocket 寫入錯誤 | writePump | 關閉 Client 連線 | ERROR |
| WebSocket 讀取錯誤（正常關閉） | readPump | unregisterClient，正常流程 | INFO |
| WebSocket 讀取錯誤（異常關閉） | readPump | unregisterClient | ERROR |
| dispatchCh 關閉 | Run() select | 停止消費，等待 ctx 取消 | INFO |

### 5.2 Error 訊息回傳格式

```go
// 錯誤回傳範例

    Type: "error",
    Data: ErrorData{
        Code:    "SESSION_NOT_FOUND",
        Message: "session abc-123 not found",
    },

```

## 6. 邊界條件

### 6.1 連線管理邊界

| 邊界條件 | 預期行為 |
|---------|---------|
| 零個 Client 連線時收到 DispatchedEvent | 正常消費事件，不推送（無目標） |
| 多個 Client 同時連線 | 各自獨立，broadcastSessionList 向全部推送 |
| Client 連線後立即斷開 | unregisterClient 清理，不影響其他 Client |
| 同一 Client 重複訂閱同一 session | 冪等，subscriptions 為 map，不重複 |
| 同一 Client 取消未訂閱的 session | 冪等，不報錯 |
| Client 訂閱後 session 被刪除 | 推送 session_status_change(completed)，Client 可自行清理 |

### 6.2 訊息大小邊界

| 邊界條件 | 預期行為 |
|---------|---------|
| Client 發送超過 MaxMessageSize 的訊息 | readPump 讀取失敗，關閉連線 |
| Server 推送超大 session_history | 正常推送（由 limit 控制大小） |
| session_event 的 Content.Output 超大（1MB tool 輸出） | 正常推送，不截斷 |

### 6.3 分頁邊界

| 邊界條件 | 預期行為 |
|---------|---------|
| limit=0 | 使用 DefaultHistoryLimit (100) |
| limit 超過 MaxHistoryLimit | 截斷為 MaxHistoryLimit (1000) |
| limit 為負數 | 使用 DefaultHistoryLimit (100) |
| before 指向不存在的時間點（太早） | 回傳空 events，hasMore=false |
| before 為 null / 空字串 | 回傳最新的 limit 筆事件 |
| session 歷史事件為空 | 回傳空 events，hasMore=false |
| session 歷史事件少於 limit | 回傳全部，hasMore=false |

### 6.4 並發邊界

| 邊界條件 | 處理方式 |
|---------|---------|
| 多個 Client 同時發送訊息 | 每個 Client 有獨立 readPump goroutine |
| broadcastSessionList 和 registerClient 並發 | clients map 以 sync.RWMutex 保護 |
| sendToClient 和 writePump 並發 | client.send 為 buffered channel，天然線程安全 |
| subscribe 和 pushToSubscribers 並發 | client.subscriptions 以 sync.RWMutex 保護 |
| Run() 消費和 HandleWS 同時執行 | 各自操作不同資源，無競態 |

## 7. 與其他模組的介面

### 7.1 與 EventDispatcher 的介面（輸入）

WebSocket Server 消費 EventDispatcher 的 `outCh`：

```go
// 消費介面
dispatchCh <-chan DispatchedEvent

// 消費方式（在 Run() 中）
for {
    select {
    case event, ok := <-s.dispatchCh:
        if !ok {
            return // channel 關閉
        }
        s.processDispatchedEvent(event)
    case <-ctx.Done():
        return
    }
}
```

**DispatchedEvent 路由規則**：

| ChangeType | 推送行為 |
|-----------|---------|
| `new` | broadcastSessionList() + pushToSubscribers(session_event) |
| `updated` | pushToSubscribers(session_event) |
| `status_changed` | broadcastStatusChange() |

### 7.2 與 SessionRegistry 的介面（查詢）

| 方法 | 用途 | 呼叫時機 |
|------|------|---------|
| `registry.List()` | 取得所有 session 列表 | handleGetSessionList、新 Client 連線時 |
| `registry.Get(sessionID)` | 驗證 session 存在 | handleSubscribeSession |
| `registry.GetHistory(sessionID, limit, before)` | 分頁查詢歷史事件 | handleGetSessionHistory |

### 7.3 與 main.go 的整合

```go
// main.go 中的初始化和啟動
dispatchCh := make(chan DispatchedEvent, DispatcherOutChanSize)

registry := NewSessionRegistry(nil)
dispatcher := NewEventDispatcher(registry, sessionEvCh, hookEvCh, dispatchCh, nil)
wsServer := NewWebSocketServer(registry, dispatchCh)

// 註冊路由
http.HandleFunc("/ws", wsServer.HandleWS)
http.Handle("/hooks/agent-event", NewHooksHandler(hookEvCh))

// 啟動
go dispatcher.Run(ctx)
go wsServer.Run(ctx)

// HTTP Server 啟動
server := &http.Server{Addr: fmt.Sprintf(":%d", port)}
go server.ListenAndServe()
```

## 8. v0.3 預留設計

### 8.1 session_event.data 的 AgentID 欄位

`SessionEventData` 結構已包含 `AgentID` 欄位（`json:"agentId,omitempty"`）。

**v0.2 行為**：
- 推送 session_event 時，從 `SessionRegistry.Get(sessionID)` 取得 `SessionInfo.AgentID`
- 若 SessionInfo.AgentID 為空（尚未收到 Hook 事件），AgentID 欄位為空字串（omitempty 不輸出）
- Client 端不依賴此欄位

**v0.3 行為**：
- AgentID 由 HTTP Hook 事件即時更新到 SessionInfo
- 推送 session_event 時帶入最新的 AgentID
- Client 端用於 AgentNode 拓撲視圖中的節點識別

### 8.2 未來擴充點

| 擴充 | 說明 |
|------|------|
| agent_status_change 訊息類型 | v0.3 新增，用於 agent 層級的狀態變更 |
| agent_message 訊息類型 | v0.3 新增，用於 agent 間通訊事件 |
| 認證機制 | 未來可在 HandleWS 中加入 token 驗證 |

## 9. 行為場景（Given-When-Then）

### 場景 1：新 Client 連線後收到 session 列表快照

```
Given: WebSocket Server 已啟動，SessionRegistry 中有 3 個 session
When:  Flutter Frontend 建立 WebSocket 連線到 ws://localhost:8765/ws
Then:  連線成功（HTTP 101 Switching Protocols）
       Client 立即收到 ServerMessage{Type:"session_list", Data: {sessions: [3 個 SessionInfo]}}
       Server 記錄 INFO log（layer=websocket_server, clientAddr=..., totalClients=1）
```

### 場景 2：Client 訂閱 session 後收到即時事件

```
Given: Client 已連線，SessionRegistry 中有 session "abc-123"
When:  Client 發送 {"action":"subscribe_session","sessionId":"abc-123"}
       隨後 EventDispatcher 推送 DispatchedEvent（sessionID="abc-123", ChangeType="updated"）
Then:  Client 收到 ServerMessage{Type:"session_event", Data: SessionEventData{...}}
       Data 包含該 session 的最新事件內容
```

### 場景 3：Client 取消訂閱後不再收到事件

```
Given: Client 已訂閱 session "abc-123"
When:  Client 發送 {"action":"unsubscribe_session","sessionId":"abc-123"}
       隨後 EventDispatcher 推送 session "abc-123" 的事件
Then:  Client 不收到任何 session_event
```

### 場景 4：get_session_history 首次載入（無 before）

```
Given: Session "abc-123" 有 200 筆歷史事件
When:  Client 發送 {"action":"get_session_history","sessionId":"abc-123"}
Then:  Client 收到 ServerMessage{
         Type: "session_history",
         Data: {sessionId:"abc-123", events: [最新100筆], hasMore: true}
       }
       events 依 timestamp 升序排列
```

### 場景 5：get_session_history 分頁載入

```
Given: Session "abc-123" 有 200 筆歷史事件
       Client 已載入最新 100 筆，最早事件 timestamp 為 "2026-03-25T10:00:00.000Z"
When:  Client 發送 {"action":"get_session_history","sessionId":"abc-123","before":"2026-03-25T10:00:00.000Z"}
Then:  Client 收到 100 筆更早的事件，hasMore=false
```

### 場景 6：心跳機制正常運作

```
Given: Client 已連線
When:  30 秒內無任何 Client/Server 訊息交換
Then:  Server 發送 ping frame
       Client 回傳 pong frame
       連線持續，讀取 deadline 重置
```

### 場景 7：心跳逾時斷線

```
Given: Client 已連線
When:  Server 發送 ping frame 後 35 秒內未收到 pong
Then:  readPump 讀取 deadline 超時
       unregisterClient(client) 清理
       Server 記錄 INFO log（layer=websocket_server, reason=pong_timeout）
```

### 場景 8：訂閱不存在的 session

```
Given: Client 已連線，SessionRegistry 中無 session "nonexistent"
When:  Client 發送 {"action":"subscribe_session","sessionId":"nonexistent"}
Then:  Client 收到 ServerMessage{Type:"error", Data: {code:"SESSION_NOT_FOUND", message:"..."}}
       subscriptions 不變
```

### 場景 9：session_status_change 廣播

```
Given: 3 個 Client 已連線
When:  EventDispatcher 推送 DispatchedEvent{ChangeType:"status_changed", Session:{ID:"abc",Status:"idle"}}
Then:  所有 3 個 Client 收到 ServerMessage{
         Type: "session_status_change",
         Data: {sessionId:"abc", status:"idle", timestamp:"..."}
       }
```

### 場景 10：Client send buffer 滿時強制斷線

```
Given: Client 已連線但消費極慢（不從 WebSocket 讀取）
When:  Server 累計推送超過 ClientSendBufferSize (256) 筆訊息
Then:  sendToClient 偵測到 channel 滿
       關閉 Client 連線
       記錄 WARN log（layer=websocket_server, reason=send_buffer_full）
```

### 場景 11：多 Client 同時連線

```
Given: WebSocket Server 已啟動
When:  Client A 和 Client B 幾乎同時建立連線
Then:  兩個 Client 各自獨立：
       - 各自收到 session_list 快照
       - 各自維護獨立的 subscriptions
       - Client A 訂閱 session X，Client B 不訂閱
       - session X 的事件只推送給 Client A
```

## 11. 技術決策紀錄

### TDR-001：使用 gorilla/websocket 而非標準庫

**決策**：使用 `github.com/gorilla/websocket` 而非 Go 標準庫的 `net/http` + `golang.org/x/net/websocket`。

**理由**：
- gorilla/websocket 是 Go 生態中最成熟的 WebSocket 庫
- 支援 ping/pong frame 控制、讀取 deadline、寫入 deadline
- API 設計更適合 server-side 使用
- 標準庫的 websocket 已被標記為不推薦使用

### TDR-002：Client send channel 而非直接寫入

**決策**：每個 Client 有獨立的 `send chan []byte`，由 writePump goroutine 序列化寫入。

**理由**：
- 避免多個 goroutine 同時寫入同一個 WebSocket 連線（websocket.Conn 不是並發安全的）
- send channel 滿時可快速判定 Client 消費太慢並斷線
- 與 gorilla/websocket 官方 chat example 的設計模式一致

### TDR-003：broadcastSessionList 而非差異更新

**決策**：session_list 推送完整列表快照而非差異。

**理由**：
- 簡化 Client 端邏輯（不需要維護差異合併狀態機）
- session 數量通常 < 50，完整列表序列化開銷可忽略
- v0.2 優先確保正確性，v0.3 可最佳化為差異更新

### TDR-004：DispatchedEvent 路由規則

**決策**：`ChangeTypeNew` 和 `ChangeTypeUpdated` 觸發 session_event 推送，`ChangeTypeStatusChanged` 觸發 session_status_change 推送。

**理由**：
- session_event 對應「有新的對話內容」
- session_status_change 對應「狀態變更」（active/idle/completed）
- 分開推送讓 Client 可以獨立處理內容更新和狀態變更
