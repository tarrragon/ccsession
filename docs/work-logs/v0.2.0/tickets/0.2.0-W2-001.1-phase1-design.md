## 1. 模組概述

### 1.1 職責邊界

本 Ticket 實作 Go Backend 的**內容事件源**，由兩個模組組成：

| 模組 | 職責 | 對應 spec |
|------|------|-----------|
| `FileWatcher` | 監控 `~/.claude/projects/` 下所有 `.jsonl` 檔案變更；offset-based 增量讀取；動態偵測新 session | §3.1 |
| `JSONLParser` | 逐行解析 JSONL；展開 assistant content array 為多個 `SessionEvent`；設定 ContentIndex 和 IsLastContent Boundary 信號 | §3.2 |

### 1.2 在整體架構中的位置

```
~/.claude/projects/*.jsonl
         |
         | [fsnotify 事件]
         v
+-------------------+
|   FileWatcher     |  監控層（§3.1）
|  SessionFileReader|  per-file goroutine + offset tracking
+--------+----------+
         |
         | raw JSONL line（string）
         v
+-------------------+
|   JSONLParser     |  解析層（§3.2）
+--------+----------+
         |
         | []SessionEvent（展開後的子事件）
         v
+-------------------+
|  eventCh channel  |  chan SessionEvent（輸出至 Event Dispatcher §3.7）
+-------------------+
```

### 1.3 職責不涵蓋

- 本模組**不**負責 HTTP Hooks 事件（由 §3.6 HookHandler 處理）
- 本模組**不**負責 Session Registry 狀態管理（由 §3.4 處理）
- 本模組**不**負責 WebSocket 推送（由 §3.3 處理）
- 本模組**不**解析 `sessions-index.json`（由 Session Registry 讀取）

## 2. 公開 API 定義

### 2.1 核心 Struct

#### FileWatcher

```go
// FileWatcher 監控 Claude Code 的 JSONL 對話檔案目錄，
// 偵測到新增行時將解析後的事件送入 eventCh。
// 每個被監控的 session 檔案對應一個獨立的 SessionFileReader goroutine。
type FileWatcher struct {
    claudeHome string                          // ~/.claude 根目錄
    watchers   map[string]*SessionFileReader   // 檔案路徑 -> reader
    parser     *JSONLParser                    // 解析器
    eventCh    chan SessionEvent               // 輸出到 Event Dispatcher
    watcher    *fsnotify.Watcher               // fsnotify 實例
    mu         sync.RWMutex                    // 保護 watchers map
}
```

#### SessionFileReader

```go
// SessionFileReader 追蹤單一 JSONL 檔案的讀取位置，
// 支援 offset-based 增量讀取（只讀取新 append 的行）。
type SessionFileReader struct {
    filePath  string    // 絕對路徑
    offset    int64     // 已讀取到的位元組位置（初始 0）
    sessionID string    // 從目錄路徑或 JSONL 欄位提取
}
```

#### JSONLParser

```go
// JSONLParser 將一行 JSONL 文字解析為零個或多個 SessionEvent。
// assistant 類型的 content array 會展開為多個子事件，
// 其餘類型產生一個事件。
type JSONLParser struct{}
```

#### SessionEvent（來自 spec §3.2，完整定義）

```go
// SessionEvent 是 Backend 內部統一的事件格式，
// 表示對話中的單一最小可見單元。
type SessionEvent struct {
    SessionID     string       `json:"sessionId"`
    ProjectPath   string       `json:"projectPath"`
    Type          string       `json:"type"`          // user, assistant, tool_use, tool_result, thinking
    Timestamp     time.Time    `json:"timestamp"`
    MessageID     string       `json:"messageId"`     // JSONL 行的 uuid，用於去重和排序
    ContentIndex  int          `json:"contentIndex"`  // 在 content array 中的索引；非 assistant 類型為 -1
    IsLastContent bool         `json:"isLastContent"` // 是否為該 messageId 下的最後一個子事件
    Content       EventContent `json:"content"`
    ToolName      string       `json:"toolName,omitempty"`
}
```

#### EventContent（依 Type 而異）

```go
// EventContent 依 SessionEvent.Type 不同而有不同的有效欄位。
// 實作時使用 json.RawMessage 或 interface{}，由 caller 依 Type 轉型。
type EventContent struct {
    // Type == "user" 或 "assistant"：
    Text string `json:"text,omitempty"`

    // Type == "tool_use"：
    ToolName  string          `json:"toolName,omitempty"`
    ToolInput json.RawMessage `json:"toolInput,omitempty"`
    ToolUseID string          `json:"toolUseId,omitempty"`

    // Type == "tool_result"：
    // ToolUseID 同上
    Output  string `json:"output,omitempty"`
    IsError bool   `json:"isError,omitempty"`

    // Type == "thinking"：
    // Text 同上
}
```

### 2.2 函式簽名

#### FileWatcher 建構與生命週期

```go
// NewFileWatcher 建立並初始化一個 FileWatcher。
// claudeHome 為 ~/.claude 的絕對路徑（已展開 ~）。
// bufferSize 為 eventCh 的緩衝大小，建議 100。
//
// 回傳 error 時表示 fsnotify 初始化失敗（例如 OS 不支援 inotify）。
func NewFileWatcher(claudeHome string, bufferSize int) (*FileWatcher, error)

// Start 開始監控 claudeHome/projects/ 目錄。
// 此方法為阻塞呼叫，需在獨立 goroutine 中執行。
// 收到 ctx.Done() 時停止監控並清理資源。
func (fw *FileWatcher) Start(ctx context.Context) error

// Events 回傳只讀事件通道，供 Event Dispatcher 消費。
func (fw *FileWatcher) Events() <-chan SessionEvent
```

#### FileWatcher 內部方法（package 層級可見，供測試）

```go
// scanExistingFiles 掃描 claudeHome/projects/ 下所有現有 .jsonl 檔案，
// 為每個檔案建立 SessionFileReader。
// 此方法在 Start() 初始化時呼叫一次。
func (fw *FileWatcher) scanExistingFiles() error

// handleFsEvent 處理 fsnotify 事件：
// - Write/Create 事件：呼叫對應 SessionFileReader.ReadNewLines()
// - Remove 事件：移除 watcher，觸發 session completed 事件
// - 非 .jsonl 檔案：忽略
func (fw *FileWatcher) handleFsEvent(event fsnotify.Event)

// addFile 為指定路徑建立 SessionFileReader 並加入監控。
// 若路徑非 .jsonl 或已存在，直接回傳（冪等）。
func (fw *FileWatcher) addFile(filePath string) error
```

#### SessionFileReader

```go
// ReadNewLines 從 offset 位置開始讀取新行，
// 將每行送入 parser 解析後轉發到 eventCh。
// 讀取完成後更新 offset。
// 若遇到不完整行（檔案末端無換行），不更新 offset，等待下次呼叫。
func (r *SessionFileReader) ReadNewLines(parser *JSONLParser, eventCh chan<- SessionEvent) error
```

#### JSONLParser

```go
// ParseLine 解析單行 JSONL 文字，回傳零個或多個 SessionEvent。
// - 忽略 progress/queue-operation/file-history-snapshot 等輔助類型
// - assistant 類型的 content array 展開為多個子事件
// - user/tool_result 類型各產生一個事件（ContentIndex = -1）
// - JSON 格式錯誤時回傳 nil, error（由 caller 記錄並忽略）
//
// filePath 用於從路徑提取 ProjectPath（目錄名反轉義 `-` -> `/`）。
func (p *JSONLParser) ParseLine(line string, filePath string) ([]SessionEvent, error)

// expandAssistantContent 將 assistant message 的 content array 展開為多個 SessionEvent。
// 設定正確的 ContentIndex（0-based）和 IsLastContent（末元素為 true）。
// 每個 SessionEvent 共享相同的 MessageID（JSONL 行的 uuid）。
func (p *JSONLParser) expandAssistantContent(
    raw jsonlRow,
    sessionID string,
    projectPath string,
) []SessionEvent
```

## 3. 資料流圖

### 3.1 正常流程（JSONL 新行寫入）

```
[Claude Code 寫入新行到 session.jsonl]
           |
           | [OS inotify/kqueue Write event]
           v
[fsnotify.Watcher] -- 事件 --> [FileWatcher.handleFsEvent()]
           |
           | event.Name == "*.jsonl" && event.Op == Write
           v
[SessionFileReader.ReadNewLines()]
           |
           | 從 offset 讀取到 EOF（逐行）
           v
           [對每一行]
           |
           v
[JSONLParser.ParseLine(line, filePath)]
           |
           +-- type == "user"       --> 1 個 SessionEvent（ContentIndex=-1）
           |
           +-- type == "assistant"  --> expandAssistantContent()
           |                              --> N 個 SessionEvent
           |                              ContentIndex: 0, 1, ..., N-1
           |                              IsLastContent: false, false, ..., true
           |
           +-- type == "tool_result"--> 1 個 SessionEvent（ContentIndex=-1）
           |
           +-- type == "progress"   --> nil（忽略）
           |   "queue-operation"
           |   "file-history-snapshot"
           |
           +-- JSON 格式錯誤         --> nil, error（記錄 WARN，跳過）
           |
           v
[eventCh <- SessionEvent]  (chan SessionEvent，buffered)
           |
           v
[Event Dispatcher (§3.7) 消費]
```

### 3.2 新 Session 偵測流程

```
[Claude Code 建立新 session.jsonl]
           |
           | [OS Create event]
           v
[FileWatcher.handleFsEvent()]
           |
           | event.Op == Create && 副檔名 == ".jsonl"
           v
[FileWatcher.addFile(filePath)]
           |
           +-- 建立 SessionFileReader（offset=0）
           +-- 加入 watchers map
           +-- fsnotify.Add(filePath)（監控此檔案）
           |
           v
[後續 Write 事件按正常流程處理]
```

### 3.3 檔案刪除流程

```
[session.jsonl 被刪除]
           |
           | [OS Remove event]
           v
[FileWatcher.handleFsEvent()]
           |
           v
[從 watchers map 移除該路徑]
           |
           v
[發送一個 SessionEvent{Type: "session_completed", SessionID: ...}]
           |
           v
[Event Dispatcher 據此更新 Session Registry 狀態為 completed]
```

## 4. 錯誤處理策略

### 4.1 錯誤分類與處理方式

| 錯誤情境 | 偵測時機 | 處理方式 | 日誌級別 |
|---------|---------|---------|---------|
| JSONL 行格式不完整（EOF 在換行前） | ReadNewLines | 不更新 offset，等待下次讀取 | 無 |
| JSONL 行 JSON 格式錯誤 | ParseLine | 忽略此行，繼續處理下一行 | WARN |
| session 檔案被刪除 | handleFsEvent(Remove) | 移除 watcher，發送 session_completed 事件 | INFO |
| 讀取時權限不足（os.Open 失敗） | ReadNewLines | 記錄 WARN，跳過此檔案（不移除 reader） | WARN |
| fsnotify 初始化失敗 | NewFileWatcher | 回傳 error，程式無法啟動 | ERROR |
| fsnotify 監控目錄不存在 | Start | 回傳 error，程式無法啟動 | ERROR |
| 未知 JSONL type（非 progress 等） | ParseLine | 忽略此行 | DEBUG |
| eventCh 滿（消費者太慢） | ReadNewLines | 阻塞等待（背壓機制） | 無 |

### 4.2 不完整行的處理細節

JSONL 是 append-only 格式，Claude Code 寫入時可能在換行前觸發 fsnotify 事件。

```
狀態：offset 指向最後一個完整換行符之後的位置

讀取邏輯：
  1. 讀取從 offset 到 EOF 的全部內容
  2. 按 "\n" 分割
  3. 最後一個片段若沒有 "\n" 結尾 → 不處理，不更新 offset
  4. 其餘完整行逐行送入 ParseLine
  5. offset 更新到最後一個完整行結尾（含換行符）之後
```

### 4.3 Go 1.21+ 錯誤包裝慣例

```go
// 正確：保留上下文
return fmt.Errorf("read file %s at offset %d: %w", r.filePath, r.offset, err)

// 禁止：丟棄上下文
return errors.New("read failed")
```

## 5. 邊界條件

### 5.1 輸入邊界

| 邊界條件 | 預期行為 |
|---------|---------|
| 空的 JSONL 行（只有換行） | ParseLine 回傳 nil（不是錯誤） |
| 只包含空白的行 | ParseLine 嘗試解析後失敗，回傳 nil, error（WARN 記錄，忽略） |
| 超長行（例如 tool 輸出 1MB） | 正常解析；EventContent.Output 保留完整字串 |
| content array 為空（[]） | expandAssistantContent 回傳空切片，不送出事件 |
| content array 只有 1 個元素 | IsLastContent=true, ContentIndex=0 |
| content array 有 N 個元素 | ContentIndex 0..N-1，IsLastContent 只有最後一個為 true |
| message.content 為字串而非 array（user 類型） | 直接建立一個 text SessionEvent |
| Timestamp 格式異常（無法解析 ISO 8601） | 使用 time.Time{} 零值，記錄 WARN |

### 5.2 並發邊界

| 邊界條件 | 處理方式 |
|---------|---------|
| 多個 .jsonl 同時被寫入 | 每個檔案有獨立的 SessionFileReader goroutine，互不影響 |
| 同一檔案短時間收到多個 Write 事件 | handleFsEvent 為序列處理（單一 goroutine 處理 fsnotify 事件），不會並發讀同一檔案 |
| 新增檔案和讀取檔案並發 | watchers map 以 sync.RWMutex 保護，addFile 和 handleFsEvent 使用寫鎖 |
| Start() 和 Events() 並發呼叫 | eventCh 在建構時建立，Events() 只讀取不修改，無競態 |

### 5.3 檔案系統邊界

| 邊界條件 | 處理方式 |
|---------|---------|
| ~/.claude/projects/ 目錄不存在 | Start() 回傳 error（fatal），記錄 ERROR |
| projects/ 下有非 .jsonl 檔案 | addFile 和 handleFsEvent 只處理 .jsonl，其他忽略 |
| 符號連結（symlink） | 不特別處理；os.Open 行為依 OS 而定 |
| 目錄深度（projects/{encoded-path}/*.jsonl） | 使用 filepath.Walk 或 fsnotify recursive，確保遞迴監控一層子目錄 |
| offset 超過檔案大小（truncate 情境） | 檢測 offset > fileSize，重置 offset=0 並全量重讀 |

### 5.4 Race Condition 防護

```
FileWatcher.watchers 的並發存取：
  - 讀取（handleFsEvent 查詢）：使用 RLock
  - 寫入（addFile/removeFile）：使用 Lock
  - 禁止在持鎖期間呼叫 ReadNewLines（避免死鎖）

SessionFileReader.offset 的並發存取：
  - 設計保證同一時間只有一個 goroutine 呼叫 ReadNewLines
  - 不需要額外的鎖
```

## 6. 與其他模組的介面

### 6.1 輸出介面：SessionEvent Channel

```go
// FileWatcher 對外暴露的唯一輸出介面
func (fw *FileWatcher) Events() <-chan SessionEvent

// 使用範例（在 Event Dispatcher 中）：
for event := range fileWatcher.Events() {
    dispatcher.Dispatch(event)
}
```

**Channel 屬性**：

| 屬性 | 值 | 說明 |
|------|----|----|
| 方向 | 只讀（`<-chan`） | 外部只能消費，不能發送 |
| 緩衝大小 | 100（可配置） | 防止短暫的消費者慢速導致阻塞 |
| 關閉時機 | `Start()` 的 context 被取消時 | caller 應用 `for range` 或選擇性消費 |

### 6.2 輸入依賴

| 依賴 | 類型 | 說明 |
|------|------|------|
| `claudeHome` | string | 從配置 `config.yaml` 的 `claude_home` 讀取，由 main.go 傳入 |
| `fsnotify.Watcher` | 外部套件 | `github.com/fsnotify/fsnotify`（需加入 go.mod） |

### 6.3 Event Dispatcher 消費契約

Event Dispatcher (§3.7) 消費 `fileWatcher.Events()` 時需遵守以下契約：

| 項目 | 規範 |
|------|------|
| 消費速度 | 需能跟上 eventCh 的生產速度，避免 channel 滿而阻塞 FileWatcher |
| 錯誤處理 | SessionEvent 本身不攜帶錯誤狀態；channel 關閉表示 FileWatcher 已停止 |
| Type 識別 | 消費者依 `SessionEvent.Type` 路由到不同處理器 |
| Boundary 信號 | `IsLastContent == true` 表示一個 MessageID 下的最後一個子事件，可觸發「訊息完整」通知 |

### 6.4 session_completed 特殊事件

當 JSONL 檔案被刪除時，FileWatcher 發送以下特殊事件（非正常 JSONL 內容）：

```go
SessionEvent{
    SessionID: "<從路徑提取的 session ID>",
    Type:      "session_completed",
    Timestamp: time.Now(),
    // 其餘欄位為零值
}
```

Event Dispatcher 收到此事件後應通知 Session Registry 將對應 session 標記為 completed。

## 7. 行為場景（Given-When-Then）

### 場景 1：FileWatcher 正常偵測新行（核心路徑）

```
Given: FileWatcher 已啟動，正在監控 ~/.claude/projects/
       session-abc.jsonl 已存在且 offset=100
When:  Claude Code 向 session-abc.jsonl append 一行 JSONL（user 訊息）
Then:  FileWatcher 在 100ms 內偵測到 Write 事件
       ReadNewLines 從 offset=100 讀取新行
       ParseLine 產生 1 個 SessionEvent（Type="user", ContentIndex=-1）
       事件送入 eventCh
       offset 更新為 100 + 新行位元組數
```

### 場景 2：Assistant Content Array 展開

```
Given: 一行 JSONL 的 type="assistant"，content 包含 [text, tool_use, text] 三個元素
When:  JSONLParser.ParseLine 解析此行
Then:  回傳 3 個 SessionEvent：
         event[0]: Type="assistant", ContentIndex=0, IsLastContent=false, Content.Text=...
         event[1]: Type="tool_use",  ContentIndex=1, IsLastContent=false, Content.ToolName=...
         event[2]: Type="assistant", ContentIndex=2, IsLastContent=true,  Content.Text=...
       三個事件共享相同的 MessageID（JSONL 行的 uuid）
```

### 場景 3：不完整 JSON 行的容錯

```
Given: session.jsonl 末端有一行沒有結尾換行（寫入中斷）
When:  FileWatcher 讀取到此行
Then:  此行不送入 ParseLine
       offset 不更新（仍指向此行開始之前）
       下次 Write 事件時重新嘗試讀取
```

### 場景 4：動態偵測新 Session 檔案

```
Given: FileWatcher 正在運行，projects/ 下有 2 個 .jsonl 檔案
When:  Claude Code 建立新的 session-xyz.jsonl
Then:  FileWatcher 在 100ms 內偵測到 Create 事件
       addFile 建立 SessionFileReader（offset=0）
       後續 Write 事件按正常流程處理
```

### 場景 5：Session 檔案刪除

```
Given: FileWatcher 監控中的 session-abc.jsonl 被刪除
When:  OS 觸發 Remove 事件
Then:  從 watchers map 移除 session-abc.jsonl 的 SessionFileReader
       發送一個 SessionEvent{Type: "session_completed", SessionID: "abc"}
       Event Dispatcher 收到後更新 Session Registry
```

### 場景 6：檔案讀取權限不足

```
Given: projects/ 下有一個 session-secure.jsonl，但目前使用者無讀取權限
When:  FileWatcher 嘗試呼叫 ReadNewLines
Then:  ReadNewLines 返回 os.ErrPermission 類型的 error
       FileWatcher 記錄 WARN log（包含 filePath）
       跳過此檔案，不移除 reader（下次仍會嘗試）
       其他 session 繼續正常運作
```

### 場景 7：多個 Session 同時寫入

```
Given: FileWatcher 同時監控 session-A.jsonl 和 session-B.jsonl
When:  兩個檔案幾乎同時收到 Write 事件
Then:  兩個 SessionFileReader 的讀取不相互干擾
       eventCh 按事件到達順序接收兩個 session 的事件（交錯順序為可接受行為）
       兩個 session 的 ContentIndex 各自正確計算（互不影響）
```

## 9. 技術決策紀錄

### TDR-001：使用 fsnotify 而非輪詢

**決策**：使用 `github.com/fsnotify/fsnotify` 而非定時輪詢（polling）。

**理由**：
- fsnotify 基於 OS 原生機制（inotify/kqueue/FSEvents），延遲最低可達 < 10ms
- 輪詢在大量 session 時 CPU 開銷顯著
- spec §3.1 明確要求使用 fsnotify

**代價**：需要處理平台差異（Linux inotify 限制 watches 數量），但監控 session 數量通常 < 50，不構成問題。

### TDR-002：每個檔案用獨立 goroutine vs 共用 goroutine

**決策**：使用**共用的單一 fsnotify 事件循環 goroutine**，而非每個檔案獨立 goroutine。

**理由**：
- fsnotify 本身是基於 channel 的，一個 watcher 即可監控多個路徑
- 每個 SessionFileReader 的 ReadNewLines 呼叫是快速的 I/O 操作，不需要並發
- 避免過多 goroutine 的調度開銷

**實作方式**：`handleFsEvent` 在 FileWatcher 的事件循環中序列處理，Read 操作同步執行。若 Read 變成瓶頸，可改為 goroutine pool（Phase 4 重構項目）。

### TDR-003：EventContent 設計

**決策**：使用單一 `EventContent` struct 而非 interface 或多個 struct（union type 模式）。

**理由**：
- Go 不支援 sum type，interface 需要型別斷言增加 caller 複雜度
- 單一 struct 搭配 `omitempty` 可序列化到 JSON，欄位語義由 `SessionEvent.Type` 決定
- 與 spec §3.2 的 EventContent 定義一致

**代價**：caller 需要依 Type 判斷使用哪些欄位（implicit contract），由 godoc 文件補充說明。

### TDR-004：session_completed 特殊事件

**決策**：檔案刪除時透過 eventCh 發送特殊的 `session_completed` SessionEvent，而非提供獨立的回呼。

**理由**：
- 維持 EventDispatcher 的消費介面統一（只需監聽一個 channel）
- 避免引入額外的 callback 機制，保持模組邊界清晰
- Event Dispatcher 可依 Type 路由，統一處理所有事件來源
