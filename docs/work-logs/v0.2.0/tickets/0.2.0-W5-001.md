# 0.2.0-W5-001: [ANA] 評估 v0.3 Agent Graph 元件對 v0.2 的前置需求

## 背景

v0.3 規劃實作 `AgentGraphWidget`（見 spec.md 第 8 節），需要以下資料驅動動畫：

| 資料結構 | 型別 | 欄位 |
|---------|------|------|
| AgentNode | `List<AgentNode>` | id, label, status |
| AgentMessage | `Stream<AgentMessage>` | fromId, toId, type, timestamp |

v0.2 的後端（Go）和前端（Flutter）資料層是否已具備對接能力，需要提前評估。

## 評估維度

### 1. Agent 識別資訊完整性

**問題**：v0.3 的 `AgentNode` 需要 `id`（唯一識別符）、`label`（顯示名稱）、`status`（idle/thinking/active/error）。

**現況對照**：
- `SessionInfo.AgentID` — HTTP Hooks 提供（SubagentStart 的 `agent_id`）
- `SessionInfo.AgentType` — HTTP Hooks 提供（`agent_type`）
- `SessionInfo.Status` — 已有（active/idle/completed），但語義略有差異（v0.3 需要 thinking/error）

**評估要點**：
- `AgentID` 在純 JSONL 模式（無 HTTP Hooks）下是否有替代來源？
- `agent_type` 能否作為 `label`？或需要額外的 `agent_name` 欄位？
- v0.2 的 `active/idle/completed` 能否對應到 v0.3 的 `thinking/active/error`？

### 2. Agent Parent-Child 關係

**問題**：v0.3 的 graph 需要呈現 agent 間的上下層關係（主 agent → subagent → sub-subagent）。

**現況對照**：
- JSONL `parentUuid` — 追蹤訊息父子關係（非 agent 層級）
- HTTP Hooks `SubagentStart` — 有 `agent_id` 和 `session_id`，但**未明確包含 parent agent ID**

**評估要點**：
- HTTP Hooks 是否提供 parent agent ID？或需要透過 session 相關性推導？
- `SessionEvent` 是否需要新增 `parentAgentId` 欄位？
- Worktree-based agent（WorktreeCreate 事件）如何歸屬至父 agent？

### 3. WebSocket 推送事件格式擴充性

**問題**：v0.3 需要前端即時接收 agent 狀態變化（thinking/active/error），現有 `session_status_change` 是否足夠？

**現況對照**：
```json
{ "type": "session_status_change", "data": { "sessionId": "...", "status": "active" } }
```

**評估要點**：
- `session_status_change` 的 `status` 值集合（active/idle/completed）能否擴充為包含 `thinking/error`？
- 或需要新增獨立的 `agent_status_change` 事件類型以保持向後相容？
- WebSocket 協議是否需要在 v0.2 預留 `agentId` 欄位（即使目前無值）？

### 4. 訊息傳遞方向識別

**問題**：v0.3 的 `AgentMessage` 需要 `fromId` 和 `toId`，代表訊息在哪兩個 agent 之間傳遞。

**現況對照**：
- JSONL `SessionEvent` — 有 `SessionID`，但無「由哪個 agent 發給哪個 agent」的欄位
- HTTP Hooks `SubagentStop.agent_transcript_path` — 可推導出 subagent 完成，但非即時方向資訊
- JSONL `tool_use` + `tool_result` — 有 `toolUseId` 配對，但這是 tool 層級非 agent 層級

**評估要點**：
- 目前 JSONL 格式是否包含 agent 間訊息方向資訊？
- 需要 HTTP Hooks 的哪個欄位才能識別「A agent 向 B agent 發送訊息」？
- v0.2 是否需要在 `SessionEvent` 中預留 `sourceAgentId` / `targetAgentId` 欄位？

### 5. Flutter 前端 Stream 介面設計

**問題**：`AgentGraphWidget` 接受 `Stream<AgentMessage>`，v0.2 的前端資料層是否已設計為 Stream 架構以便 v0.3 接入？

**現況對照**：
- v0.2 前端（spec.md 第 4-5 節）目前規格尚待確認是否採用 StreamController 或 Riverpod AsyncNotifier
- WebSocket 事件接收端若已設計為 Stream，v0.3 接入成本極低

**評估要點**：
- v0.2 的 WebSocket 事件層是否計畫以 `Stream<SessionEvent>` 形式暴露？
- `AgentMessage` 可以視為 `SessionEvent` 的過濾子集，v0.2 的 Provider 架構是否支援此模式？
- 是否需要在 v0.2 預先定義 `AgentEventRepository` 介面（即使 v0.3 才實作）？

## 預期產出

分析完成後應衍生以下兩類 Ticket（視分析結論而定）：

1. **補強 Ticket**（若發現 v0.2 明確缺少必要欄位）：
   - 範例：在 `HookEvent` 新增 `parentAgentId` 欄位
   - 範例：WebSocket `session_status_change` 新增 `agentId` 欄位

2. **設計預留 Ticket**（若發現 v0.3 有介面依賴，但 v0.2 尚未設計）：
   - 範例：定義 `AgentEventRepository` 介面草稿
   - 範例：為 `Stream<SessionEvent>` 確立暴露方式

### 跨維度關鍵發現

**1. `parent_agent_id` 是最關鍵的單點依賴**

維度 2、3、4 的缺口都歸因於同一個問題：Claude Code 的 `SubagentStart` HTTP Hook 是否傳送 `parent_agent_id`。spec.md 未記錄此欄位，需實測 Claude Code v2.1.69+ 的 Hook payload 確認。

- 若 Claude Code 原生提供：v0.2 只需在 `HookEvent` 新增 `ParentAgentID string` 欄位，成本極低
- 若不提供：v0.3 需設計啟發式時間戳關聯算法（從 `tool_use(Task)` + `SubagentStart` 時間戳配對推導）

**2. Session 1:1 vs Agent 1:N 架構落差**

v0.2 的 `SessionRegistry` 以 `sessionId` 為 key（1:1），但 v0.3 Agent Graph 需要多個 agent 共存（1:N）。這是最大的架構缺口，需在 v0.3 新增 `AgentRegistry` 或擴充 `SessionRegistry`。

**3. 狀態語義分歧**

v0.2 狀態（session 生命週期）和 v0.3 狀態（agent 節點視覺）是不同維度：

| v0.2 SessionStatus | v0.3 AgentNode.status | 關係 |
|---|---|---|
| `active` | `active` | 直接對應 |
| `idle` | `idle` | 直接對應 |
| `completed` | 無對應（或 dimmed idle） | 語義分歧 |
| 無 | `thinking` | 需新增觸發源（JSONL thinking type） |
| 無 | `error` | 需新增觸發源（tool_result isError） |

建議不擴充 `SessionStatus`，另建 `AgentStatus` 類型，避免語義污染。
