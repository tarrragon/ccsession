# 0.2.0-W5-010 分析報告：pre-fix-evaluation-hook 測試失敗攔截失效原因

## 1. 現有機制分析

### pre-fix-evaluation-hook.py 覆蓋範圍

**觸發條件**：PostToolUse Hook，matcher 為 `Bash` 和 `mcp__dart__run_tests`。

**攔截邏輯**：
1. 從 stdin 讀取 `tool_response`
2. 檢查成功標誌（`all tests passed` / `no issues found`），有則跳過
3. 用正則表達式分類錯誤：SYNTAX > COMPILATION > TEST_FAILURE > ANALYZER_WARNING
4. SYNTAX_ERROR：exitCode=0（允許，簡化流程）
5. 其他錯誤：exitCode=2（阻塞），輸出「必須開 Ticket」提示

**TEST_FAILURE 正則模式**：
- `Expected:\s*(.+?)\s*Actual:` — 斷言失敗
- `(\d+)\s+tests?\s+failed` — 失敗計數
- `FAILED` — 通用失敗標記
- `AssertionError` — 斷言錯誤（注意：拼寫錯誤，應為 `AssertionError` 或 `AssertionError`，但 Dart 使用的是不同格式）

**關鍵發現**：Hook 在正則匹配到錯誤時確實會 exitCode=2 阻塞，機制本身是完整的。

## 2. PC-026 場景還原與失效原因

### PC-026 描述的場景

測試失敗被發現後，以「pre-existing」「不是我造成的」「與當前任務無關」為由未建立 Ticket。問題持續存在多個 session。

### 失效原因分析

Hook **技術上可能正常觸發了**，但 PC-026 的根因不是 Hook 未觸發，而是以下三個層面的問題：

**原因 1：Hook 輸出是「建議」而非「強制阻塞」**

Hook exitCode=2 會阻塞當前工具的後續操作，但：
- 它只阻塞「修復動作」，不阻塞「忽略並繼續其他工作」
- 代理人/PM 看到 Hook 警告後，可以選擇不修復也不建 Ticket，直接繼續其他任務
- Hook 沒有驗證「Ticket 是否已建立」的閉環機制

**原因 2：Subagent 中的測試失敗不受 PM 監控**

- Phase 3b 代理人執行 `flutter test`，Hook 觸發並輸出警告
- 但 subagent 禁止使用 AskUserQuestion，無法向 PM 升級
- Subagent 可能看到警告後自行判斷為 pre-existing 而繼續
- PM 只收到最終回報（成功/失敗），不知道中間有測試失敗被忽略

**原因 3：輸出被截斷或未被正則匹配**

- `flutter test` 輸出超過 2KB 時，會被截斷為 `Output too large... Full output saved to: /path/xxx.txt`
- Hook 收到的 `tool_response` 是截斷後的摘要，不包含完整測試結果
- 正則表達式無法匹配到截斷摘要中的錯誤模式，Hook 靜默通過

## 3. 識別的覆蓋盲區

### 盲區 1：大量輸出截斷導致 Hook 無法解析

當 `flutter test` 輸出超過 Claude Code 的工具輸出限制時，`tool_response` 被替換為截斷訊息（如 `Output too large (279.4KB). Full output saved to: .../tool-results/xxx.txt`）。此時 Hook 收到的字串不包含 `FAILED`、`tests failed` 等關鍵字，所有正則模式均不匹配，Hook 回傳 exitCode=0，測試失敗完全被忽略。

**影響**：全量測試（`flutter test`）幾乎必定超過輸出限制，這是最常見的測試執行方式，也是最大的覆蓋盲區。

### 盲區 2：Hook 無閉環驗證（警告後未追蹤 Ticket 建立）

Hook 輸出 exitCode=2 後，只提示「必須開 Ticket」，但沒有後續機制驗證 Ticket 是否實際被建立。代理人可以：
1. 看到警告
2. 判斷為 pre-existing
3. 繼續其他工作

整個過程中沒有任何閘門阻止「看到警告但不建 Ticket」的行為。

### 盲區 3：非 Bash/MCP 的測試執行方式

Hook matcher 僅匹配 `Bash` 和 `mcp__dart__run_tests`。如果測試透過其他方式執行（例如未來新增的測試工具），Hook 不會觸發。目前此盲區影響較小，但隨工具擴展會擴大。

### 盲區 4：Subagent 環境中的行為差異

Subagent（Phase 3b parsley）中 Hook 正常觸發，但 subagent 對 Hook 警告的處理缺乏規範：
- 沒有明確規則要求 subagent 必須在回報中包含 Hook 警告
- Subagent 的「最小回報原則」可能導致 Hook 警告被過濾

## 4. 補強方案設計

### 方案 A：擴展 pre-fix-evaluation-hook.py 處理截斷輸出（優先）

**目標**：解決盲區 1（最大覆蓋缺口）

**具體修改**：

在 `main()` 函式中，`tool_response` 解析之前新增截斷偵測邏輯：

```python
# 新增：偵測截斷輸出
TRUNCATION_PATTERN = r"Output too large.*?Full output saved to:\s*(\S+)"
truncation_match = re.search(TRUNCATION_PATTERN, output_str)
if truncation_match:
    saved_path = truncation_match.group(1)
    # 嘗試讀取完整輸出
    try:
        full_output = Path(saved_path).read_text(encoding="utf-8")
        output_str = full_output  # 用完整輸出替換截斷版本
        logger.info(f"Loaded full output from {saved_path}")
    except (OSError, IOError) as e:
        # 無法讀取時，保守處理：視為可能有錯誤
        logger.warning(f"Cannot read truncated output file: {e}")
        # 檢查截斷摘要中是否有失敗指標
        if any(kw in output_str.lower() for kw in ["fail", "error", "exception"]):
            # 生成警告輸出
            output = generate_truncated_warning_output(saved_path)
            print(json.dumps(output, ensure_ascii=False, indent=2))
            return 2
```

新增函式 `generate_truncated_warning_output()`：提示使用者完整輸出已儲存在指定路徑，需人工檢查。

### 方案 B：新增 flutter test 退出碼偵測

**目標**：補強方案 A 的替代路徑

`flutter test` 失敗時退出碼非 0。Hook 可額外檢查 input_data 中的退出碼資訊（如果 Claude Code PostToolUse 提供）：

```python
# 新增：檢查工具退出碼
tool_exit_code = input_data.get("tool_exit_code", 0)
if tool_exit_code != 0 and not errors:
    # 工具失敗但正則未匹配到錯誤（可能是截斷）
    logger.warning(f"Tool exited with code {tool_exit_code} but no errors detected")
    output = generate_exit_code_warning_output(tool_exit_code)
    print(json.dumps(output, ensure_ascii=False, indent=2))
    return 2
```

注意：需確認 Claude Code PostToolUse Hook 的 input schema 是否包含 `tool_exit_code` 欄位。若不包含，此方案不可行。

### 方案 C：Subagent 回報規範補充（流程層面）

**目標**：解決盲區 4

在 parsley-flutter-developer 代理人定義中新增規則：

> 執行 `flutter test` 後，若 Hook 輸出包含 `[WARNING]` 或 exitCode=2 的阻塞訊息，**必須**在回報主線程時包含此警告。禁止過濾 Hook 警告。

此為流程補強，不需要修改 Hook 程式碼。
