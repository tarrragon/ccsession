## 1. 模組概述

### 1.1 在雙源架構中的定位

本 Ticket 實作 Go Backend 的**事件融合層**，是整個雙源架構的核心聚合點：

```
+----------------------------+     +----------------------------+
|  File Watcher + JSONL      |     |  HTTP Hooks Handler        |
|  Parser (.1)               |     |  (.2)                      |
|  chan SessionEvent         |     |  chan HookEvent            |
+------------+---------------+     +-------------+--------------+
             |                                   |
             +----------+     +------------------+
                        |     |
                        v     v
             +----------+-----+----------+
             |  Event Dispatcher (§3.7)  |  <- 本模組核心（event_dispatcher.go）
             |  - 消費雙源事件            |
             |  - 去重（5 秒窗口）        |
             |  - HTTP 事件優先          |
             |  - 呼叫 Session Registry  |
             +----------+----------------+
                        |
                        v
             +----------+----------------+
             |  Session Registry (§3.4)  |  <- 本模組核心（session_registry.go）
             |  - SessionInfo CRUD       |
             |  - 狀態機轉換             |
             |  - Source of Truth        |
             +----------+----------------+
                        |
                        v
             +----------+----------------+
             |  WebSocket Hub (§3.3)     |  <- .4 子任務（本模組不實作）
             +----------------------------+
```

### 1.2 職責邊界

| 模組 | 職責 | 不負責 |
|------|------|--------|
| `SessionRegistry` | 管理所有 session 的 `SessionInfo`；執行狀態機轉換；提供查詢介面 | 消費事件 channel；WebSocket 推送；事件去重 |
| `EventDispatcher` | 消費 `SessionEvent` 和 `HookEvent` 兩個 channel；執行去重；呼叫 Registry 更新；向 WebSocket 推送（透過 outCh） | 直接管理 session 狀態；HTTP 處理；JSONL 解析 |

### 1.3 職責不涵蓋

- 本模組**不**實作 WebSocket Hub（由 §3.3 / .4 子任務處理）
- 本模組**不**實作 JSONL 解析（由 .1 子任務的 FileWatcher + JSONLParser 處理）
- 本模組**不**實作 HTTP Hooks 接收（由 .2 子任務的 HooksHandler 處理）
- 本模組**不**實作 `sessions-index.json` 讀取（此功能在 v0.2 範圍外）

## 2. 資料結構定義

### 2.1 SessionStatus 狀態類型

```go
// SessionStatus 表示 session 的生命週期狀態。
// 狀態機轉換規則詳見 §3.2。
type SessionStatus string

const (
    // SessionStatusActive 表示 session 正在活躍運作。
    // 觸發條件：JSONL 有新事件 OR 收到 SubagentStart Hook 事件。
    SessionStatusActive SessionStatus = "active"

    // SessionStatusIdle 表示 session 暫時閒置。
    // 觸發條件：2-30 分鐘無新事件 OR 收到 TeammateIdle Hook 事件。
    SessionStatusIdle SessionStatus = "idle"

    // SessionStatusCompleted 表示 session 已結束。
    // 觸發條件：30 分鐘以上無事件 OR 收到 SubagentStop Hook 事件（即時）。
    SessionStatusCompleted SessionStatus = "completed"
)
```

### 2.2 SessionInfo 結構體

```go
// SessionInfo 保存單一 session 的完整狀態資訊。
// 此結構體是 Session Registry 的核心資料單元，
// 由 JSONL 事件和 HTTP Hook 事件共同填充。
//
// 欄位填充來源：
//   - JSONL 事件填充：ID, ProjectPath, Summary, GitBranch, EventCount, LastEventAt
//   - HTTP Hook 事件填充：AgentID, AgentType, LastMessage
//   - [v0.3 預留] 欄位：ParentAgentID, AgentName
type SessionInfo struct {
    // 基礎識別（JSONL 事件填充）
    ID          string        `json:"id"`
    ProjectPath string        `json:"projectPath"`
    Summary     string        `json:"summary,omitempty"`
    GitBranch   string        `json:"gitBranch,omitempty"`

    // 生命週期狀態
    Status      SessionStatus `json:"status"`
    LastEventAt time.Time     `json:"lastEventAt"`
    EventCount  int           `json:"eventCount"`

    // HTTP Hooks 提供的欄位（SubagentStart/Stop 填充）
    AgentID     string `json:"agentId,omitempty"`
    AgentType   string `json:"agentType,omitempty"`
    LastMessage string `json:"lastMessage,omitempty"`  // SubagentStop 的最後回應摘要

    // [v0.3 預留] agent 父子關係追蹤
    // v0.2 中此欄位會被填充（若 Claude Code 提供），但不用於任何業務邏輯。
    // v0.3 實作 AgentNode 拓撲視圖時啟用。
    ParentAgentID string `json:"parentAgentId,omitempty"`

    // [v0.3 預留] agent 顯示名稱
    // v0.2 中永遠為空字串。v0.3 從 sessions-index.json 或 Hook 事件填充。
    AgentName string `json:"agentName,omitempty"`
}
```

**欄位說明**：

| 欄位 | 來源 | 必填 | v0.2 行為 |
|------|------|------|-----------|
| `ID` | JSONL SessionID | 是 | Registry 的 map key |
| `ProjectPath` | JSONL ProjectPath | 是 | 從檔案路徑解碼 |
| `Summary` | JSONL 首行 user 訊息（截斷） | 否 | 最多 100 字元 |
| `GitBranch` | 保留欄位 | 否 | v0.2 永遠為空 |
| `Status` | 狀態機計算 | 是 | 初始為 active |
| `LastEventAt` | 每次事件更新 | 是 | time.Now() |
| `EventCount` | 累計計數 | 是 | 初始為 0，每次事件 +1 |
| `AgentID` | HTTP SubagentStart | 否 | 僅 Hook 事件更新 |
| `AgentType` | HTTP SubagentStart | 否 | 僅 Hook 事件更新 |
| `LastMessage` | HTTP SubagentStop | 否 | 每次 Stop 覆蓋 |
| `ParentAgentID` | [v0.3 預留] | 否 | 填充但不使用 |
| `AgentName` | [v0.3 預留] | 否 | 永遠為空 |

### 2.3 UnifiedEvent 統一事件格式

```go
// UnifiedEvent 是 Event Dispatcher 內部的統一事件表示，
// 用於去重和路由處理。caller 不應直接使用此型別。
//
// Source 欄位標識事件來源，用於 HTTP 優先級排序。
type UnifiedEvent struct {
    Source    EventSource   // 事件來源（JSONL 或 HTTP）
    SessionID string        // 關聯的 session ID
    EventType string        // 事件類型（SessionEvent.Type 或 HookEvent.Type）
    Timestamp time.Time     // 事件時間（用於去重窗口計算）
    AgentID   string        // agent 識別符（用於去重 key 組合）

    // 原始事件（只有一個非 nil）
    SessionEvt *SessionEvent // JSONL 來源事件
    HookEvt    *HookEvent    // HTTP 來源事件
}

// EventSource 標識事件來源，用於優先級排序。
type EventSource string

const (
    EventSourceJSONL EventSource = "jsonl"  // 來自 JSONL file watching
    EventSourceHTTP  EventSource = "http"   // 來自 HTTP Hooks
)
```

### 2.4 DeduplicationKey 去重鍵

```go
// deduplicationKey 是事件去重的組合鍵。
// 在 EventDispatcher 內部使用，不對外暴露。
//
// 去重規則：agent_id + event_type + timestamp（5 秒窗口內視為重複）
// HTTP 事件優先：若 HTTP 事件已處理，相同 dedup key 的 JSONL 事件被忽略。
type deduplicationKey struct {
    AgentID   string
    EventType string
    // Timestamp 被捨去秒以下精度，並截斷至 5 秒窗口
    // 實作：timestamp.Truncate(DedupWindowDuration)
    WindowKey time.Time
}
```

## 4. Session Registry API 定義

### 4.1 SessionRegistry 結構體

```go
// SessionRegistry 是所有 session 狀態的 Source of Truth。
// 所有對 session 狀態的讀取和修改都透過此結構體進行。
//
// 並發安全：使用 sync.RWMutex 保護所有欄位存取。
// - 讀取操作（Get, List）使用 RLock
// - 寫入操作（Upsert, UpdateStatus）使用 Lock
type SessionRegistry struct {
    sessions map[string]*SessionInfo  // session ID -> SessionInfo
    mu       sync.RWMutex
}
```

### 4.2 SessionRegistry 建構函式

```go
// NewSessionRegistry 建立並初始化一個空的 SessionRegistry。
// sessions map 在建構時初始化，避免 nil map 的寫入 panic。
func NewSessionRegistry() *SessionRegistry
```

### 4.3 SessionRegistry 公開方法

#### UpsertFromSessionEvent

```go
// UpsertFromSessionEvent 依據 JSONL 事件更新或建立 SessionInfo。
//
// 行為規則：
//   - 若 sessionID 不存在 → 建立新的 SessionInfo，Status 設為 active
//   - 若 sessionID 已存在 → 更新 LastEventAt、EventCount（+1）
//   - 若 type == "session_completed" → 強制設定 Status 為 completed
//   - 其他類型 → 重新計算 Status（呼叫 computeStatus，傳入當前時間）
//   - 若為首個 user 訊息（EventCount == 0 且 Type == "user"）→ 填入 Summary
//
// 此方法不更新 AgentID/AgentType/LastMessage（由 UpsertFromHookEvent 負責）。
func (r *SessionRegistry) UpsertFromSessionEvent(event SessionEvent)
```

#### UpsertFromHookEvent

```go
// UpsertFromHookEvent 依據 HTTP Hook 事件更新 SessionInfo。
//
// 行為規則（依 event.Type）：
//   SubagentStart:
//     - 若 sessionID 不存在 → 建立 SessionInfo（最小化填充，等待 JSONL 補充）
//     - 更新 AgentID、AgentType
//     - 若 ParentAgentID 非空 → 填入 SessionInfo.ParentAgentID（v0.3 預留）
//     - 強制設定 Status 為 active
//   SubagentStop:
//     - 若 sessionID 存在 → 更新 LastMessage、LastEventAt
//     - 強制設定 Status 為 completed（即時，不等候超時）
//   TaskCompleted:
//     - 更新 LastEventAt
//     - 重新計算 Status（不強制 completed）
//   TeammateIdle:
//     - 更新 LastEventAt
//     - 強制設定 Status 為 idle
//
// session_id 不存在且事件類型不是 SubagentStart 時：
//   僅記錄 WARN log，不建立 SessionInfo（避免孤立記錄）。
func (r *SessionRegistry) UpsertFromHookEvent(event HookEvent)
```

#### ScanAndUpdateStatus

```go
// ScanAndUpdateStatus 掃描所有 session，依照超時閾值更新狀態。
// 此方法由 EventDispatcher 定期呼叫（每 StatusScanInterval 一次）。
//
// 掃描規則：
//   - completed 狀態的 session：跳過（終態，不再變更）
//   - 其他狀態：呼叫 computeStatus(session.LastEventAt) 重新計算
//
// 回傳值：狀態發生改變的 SessionInfo 清單（用於 WebSocket 推送通知）。
func (r *SessionRegistry) ScanAndUpdateStatus() []*SessionInfo
```

#### Get

```go
// Get 依 sessionID 取得 SessionInfo。
// 若不存在，回傳 nil, false（Go 慣用模式）。
// 回傳的是 SessionInfo 的副本，修改不影響 Registry 內部狀態。
func (r *SessionRegistry) Get(sessionID string) (*SessionInfo, bool)
```

#### List

```go
// List 回傳所有 SessionInfo 的快照（副本切片）。
// 適合用於初始 WebSocket 連線時的全量推送。
// 排序：依 LastEventAt 降序（最近活躍的排前面）。
func (r *SessionRegistry) List() []*SessionInfo
```

#### Count

```go
// Count 回傳目前 Registry 中的 session 總數。
// 輕量操作，使用 RLock。
func (r *SessionRegistry) Count() int
```

### 4.4 SessionRegistry 內部方法

```go
// computeStatus 依照 lastEventAt 計算當前應有的狀態。
// 此方法在持鎖期間呼叫，不執行額外的鎖定。
//
// 規則：
//   - now - lastEventAt < ActiveThreshold → active
//   - ActiveThreshold <= now - lastEventAt < IdleThreshold → idle
//   - now - lastEventAt >= IdleThreshold → completed
//
// 注意：此方法不處理「強制」狀態轉換（如 SubagentStop → completed）；
//       強制轉換由 UpsertFromHookEvent 直接設定。
func (r *SessionRegistry) computeStatus(lastEventAt time.Time) SessionStatus

// updateSummary 從第一個 user 事件的文字截取摘要。
// 最多 MaxSummaryLength 個字元，超出時加上 "..."。
func (r *SessionRegistry) updateSummary(info *SessionInfo, event SessionEvent)
```

## 5. Event Dispatcher API 定義

### 5.1 EventDispatcher 結構體

```go
// EventDispatcher 消費來自 JSONL 和 HTTP 的雙源事件，
// 執行去重後更新 Session Registry，並輸出統一事件供 WebSocket 推送。
//
// 生命週期：透過 Run() 啟動，ctx 取消時停止。
// 並發安全：dedup map 以 sync.Mutex 保護。
type EventDispatcher struct {
    registry    *SessionRegistry       // 注入的 Session Registry
    sessionEvCh <-chan SessionEvent    // JSONL 事件輸入
    hookEvCh    <-chan HookEvent       // HTTP Hook 事件輸入
    outCh       chan<- DispatchedEvent // 輸出給 WebSocket Hub

    // 去重表（key -> 最後一次處理的時間戳）
    dedupTable  map[deduplicationKey]time.Time
    dedupMu     sync.Mutex
}
```

### 5.2 DispatchedEvent 輸出事件格式

```go
// DispatchedEvent 是 EventDispatcher 的輸出，
// 供 WebSocket Hub 廣播給所有連線的 UI clients。
//
// ChangeType 描述此次推送的類型，讓 UI client 決定如何更新視圖。
type DispatchedEvent struct {
    ChangeType ChangeType    `json:"changeType"`
    Session    *SessionInfo  `json:"session"`
    Timestamp  time.Time     `json:"timestamp"`
}

// ChangeType 描述 SessionInfo 的變更類型。
type ChangeType string

const (
    // ChangeTypeNew 表示新 session 被偵測到（首次出現在 Registry）。
    ChangeTypeNew ChangeType = "new"

    // ChangeTypeUpdated 表示 session 狀態或內容有更新。
    ChangeTypeUpdated ChangeType = "updated"

    // ChangeTypeStatusChanged 表示 session 生命週期狀態發生轉換。
    ChangeTypeStatusChanged ChangeType = "status_changed"
)
```

### 5.3 EventDispatcher 建構函式

```go
// NewEventDispatcher 建立並初始化 EventDispatcher。
//
// 參數：
//   - registry：已初始化的 SessionRegistry（依賴注入）
//   - sessionEvCh：來自 FileWatcher 的 JSONL 事件 channel（唯讀）
//   - hookEvCh：來自 HTTP Hooks Handler 的事件 channel（唯讀）
//   - outCh：輸出給 WebSocket Hub 的 channel（只寫）
//
// outCh 由 caller（main.go）建立，建議緩衝大小 DispatcherOutChanSize。
func NewEventDispatcher(
    registry    *SessionRegistry,
    sessionEvCh <-chan SessionEvent,
    hookEvCh    <-chan HookEvent,
    outCh       chan<- DispatchedEvent,
) *EventDispatcher
```

### 5.4 EventDispatcher 主要方法

#### Run

```go
// Run 啟動 EventDispatcher 的主事件循環。
// 此方法為阻塞呼叫，應在獨立 goroutine 中執行。
// 收到 ctx.Done() 時停止所有消費，並關閉 outCh。
//
// 內部啟動：
//   - 一個 goroutine 消費 sessionEvCh（JSONL 事件）
//   - 一個 goroutine 消費 hookEvCh（HTTP 事件）
//   - 一個定時器每 StatusScanInterval 執行一次 ScanAndUpdateStatus
//   - 一個定時器每 DedupCleanupInterval 清理過期去重記錄
func (d *EventDispatcher) Run(ctx context.Context)
```

#### processSessionEvent

```go
// processSessionEvent 處理單一 JSONL 事件。
//
// 執行步驟：
//   1. 建立 deduplicationKey（AgentID 在 JSONL 事件中可能為空，使用 MessageID 替代）
//   2. 查詢去重表：若 5 秒窗口內已有 HTTP 事件處理同一 key → 忽略，記錄 DEBUG
//   3. 更新去重表（JSONL 事件記錄）
//   4. 呼叫 registry.UpsertFromSessionEvent(event)
//   5. 建立 DispatchedEvent，送入 outCh
//
// 注意：JSONL 事件的 AgentID 可能為空（非 agent 產生的對話），
//       此時去重 key 以 MessageID 作為 AgentID 的替代，確保唯一性。
func (d *EventDispatcher) processSessionEvent(event SessionEvent)

// processHookEvent 處理單一 HTTP Hook 事件。
//
// 執行步驟：
//   1. 解析 HookEvent.Timestamp 為 time.Time（RFC 3339 格式）
//   2. 建立 deduplicationKey（以 AgentID + Type + windowKey）
//   3. 查詢去重表：若 5 秒窗口內已有相同 key → 忽略，記錄 DEBUG
//   4. 更新去重表（HTTP 事件記錄，標記為「HTTP 已處理」）
//   5. 呼叫 registry.UpsertFromHookEvent(event)
//   6. 建立 DispatchedEvent，送入 outCh
//
// HTTP 優先：HTTP 事件先記錄到去重表，後續相同 key 的 JSONL 事件在步驟 2 被攔截。
func (d *EventDispatcher) processHookEvent(event HookEvent)
```

#### sendToOutCh

```go
// sendToOutCh 以 non-blocking 方式發送 DispatchedEvent 到輸出 channel。
// 若 outCh 已滿，記錄 WARN log 並丟棄事件（UI 可從下次全量推送恢復）。
func (d *EventDispatcher) sendToOutCh(event DispatchedEvent)
```

#### cleanupDedupTable

```go
// cleanupDedupTable 移除去重表中所有超過 DedupWindowDuration 的舊記錄。
// 由定時器每 DedupCleanupInterval 呼叫一次，防止記憶體無限增長。
func (d *EventDispatcher) cleanupDedupTable()
```

## 6. 去重機制設計

### 6.1 去重鍵組合規則

```
去重鍵 = AgentID + EventType + WindowKey

其中：
  - AgentID：HookEvent.AgentID 或 SessionEvent.MessageID（JSONL 無 AgentID 時）
  - EventType：事件類型字串
  - WindowKey：Timestamp.Truncate(5 * time.Second)
              （將時間截斷至 5 秒精度，同一 5 秒窗口視為同一批次）
```

### 6.2 HTTP 事件優先實作

```
時序圖：

HTTP Hooks Handler          Event Dispatcher            去重表
     |                           |                        |
     | -- HookEvent{SubStart} -> |                        |
     |                           | -- check key A -> |    |
     |                           |                   |    |
     |                           | <-- not found --- |    |
     |                           | -- set key A (HTTP) -> |
     |                           |                        |
     |                           | -- UpsertFromHookEvent |
     |                           |                        |
     | (稍後 JSONL 偵測到同一事件) |                        |
FileWatcher                      |                        |
     | -- SessionEvent{...} ---> |                        |
     |                           | -- check key A -> |    |
     |                           |                   |    |
     |                           | <-- found (HTTP) -|    |
     |                           | -- IGNORE (DEBUG log)  |
     |                           |                        |
```

### 6.3 JSONL 事件的特殊去重邏輯

JSONL 事件（SessionEvent）不含 `AgentID`，因此去重 key 使用 `MessageID` 作為替代：

- `MessageID` 是 JSONL 行的 `uuid` 欄位，對每個訊息唯一
- HTTP 事件使用 `AgentID`，JSONL 事件使用 `MessageID`
- 兩者的 key 空間不重疊，不會誤判為重複

**例外**：當 JSONL 事件的 `MessageID` 為空時，去重 key 退化為 `"" + EventType + WindowKey`，可能誤判為重複。此邊界條件應在測試中驗證。

## 7. 狀態機設計

### 7.1 狀態轉換矩陣

| 當前狀態 | 觸發條件 | 新狀態 | 來源 |
|---------|---------|--------|------|
| 任意 | 收到 JSONL 任意非 session_completed 事件 | active | computeStatus（若時間 < 2min） |
| 任意 | 收到 JSONL session_completed 事件 | completed | UpsertFromSessionEvent 強制 |
| 任意 | 收到 HTTP SubagentStart | active | UpsertFromHookEvent 強制 |
| 任意 | 收到 HTTP SubagentStop | completed | UpsertFromHookEvent 強制（即時） |
| 任意 | 收到 HTTP TeammateIdle | idle | UpsertFromHookEvent 強制 |
| active | 2 分鐘無新事件（定時掃描） | idle | ScanAndUpdateStatus |
| idle | 30 分鐘無新事件（定時掃描） | completed | ScanAndUpdateStatus |
| completed | 任何新事件（復活情境） | active | UpsertFromSessionEvent / UpsertFromHookEvent |

**注意**：`completed` 是終態，僅在新事件到來時可「復活」（重新激活同一 session ID）。

### 7.2 定時掃描與即時觸發的優先級

```
優先級（高 → 低）：
1. HTTP SubagentStop → 立即 completed（最高優先）
2. HTTP SubagentStart → 立即 active
3. HTTP TeammateIdle → 立即 idle
4. JSONL 任意事件 → 更新 LastEventAt，重新計算狀態
5. 定時掃描（每 30 秒）→ 依超時閾值更新過期 session
```

## 8. 資料流設計

### 8.1 正常流程：JSONL 對話事件

```
[JSONL 新行寫入]
       |
       v
[FileWatcher → SessionEvent channel]
       |
       v
[EventDispatcher.processSessionEvent]
       |
       +-- 去重檢查 → 非重複
       |
       v
[SessionRegistry.UpsertFromSessionEvent]
       |
       +-- 新 session → 建立 SessionInfo（Status=active）
       +-- 已有 session → 更新 LastEventAt、EventCount
       |
       v
[DispatchedEvent → outCh → WebSocket Hub（.4 子任務）]
```

### 8.2 即時狀態觸發：HTTP SubagentStop

```
[Claude Code 發送 SubagentStop Hook]
       |
       v
[HTTP Hooks Handler → HookEvent channel]
       |
       v
[EventDispatcher.processHookEvent]
       |
       +-- 去重檢查 → 標記為 HTTP 已處理
       |
       v
[SessionRegistry.UpsertFromHookEvent(SubagentStop)]
       |
       +-- 強制 Status = completed
       +-- 更新 LastMessage、LastEventAt
       |
       v
[DispatchedEvent{ChangeType: "status_changed"} → outCh]
```

### 8.3 定時狀態掃描

```
[定時器觸發（每 30 秒）]
       |
       v
[EventDispatcher 呼叫 registry.ScanAndUpdateStatus]
       |
       v
[SessionRegistry 掃描所有 session]
       |
       +-- active session > 2 min 無事件 → idle
       +-- idle session > 30 min 無事件 → completed
       +-- 其他 → 不變
       |
       v
[回傳 changed sessions]
       |
       v
[對每個 changed session → DispatchedEvent{status_changed} → outCh]
```

### 8.4 WebSocket 全量推送（初始連線）

```
[新 WebSocket client 連線]
       |（由 WebSocket Hub 處理，非 Dispatcher 職責）
       v
[WebSocket Hub 呼叫 registry.List()]
       |
       v
[回傳所有 SessionInfo 快照]
       |
       v
[全量推送給新連線的 client]
```

## 9. 錯誤處理策略

### 9.1 錯誤分類表

| 錯誤情境 | 偵測位置 | 處理方式 | Log 層級 |
|---------|---------|---------|---------|
| HookEvent.Timestamp 格式無法解析 | processHookEvent | 使用 time.Now() 替代，繼續處理 | WARN |
| HookEvent 的 SessionID 為空 | processHookEvent | 忽略此事件，不更新 Registry | WARN |

// 正確：使用 fmt.Errorf + %w 保留上下文

## 11. 邊界條件

### 11.1 輸入邊界

| 邊界條件 | 預期行為 |
|---------|---------|
| 相同 sessionID 的 JSONL 事件早於 HTTP SubagentStart 到達 | UpsertFromSessionEvent 建立 SessionInfo，HTTP 到達後補充 AgentID/AgentType |
| HTTP SubagentStop 到達，但 sessionID 不在 Registry 中 | 記錄 WARN，不建立孤立 SessionInfo |
| HTTP SubagentStop 後又收到相同 sessionID 的 JSONL 事件（復活） | UpsertFromSessionEvent 重設狀態為 active |
| JSONL 事件的 MessageID 為空字串 | 去重 key 退化，可能誤判，記錄 WARN |
| HookEvent.Timestamp 為非 RFC 3339 格式 | 使用 time.Now() 替代，記錄 WARN |
| HookEvent.SessionID 為空 | 忽略此事件 |
| 同一 sessionID 在 5 秒內大量事件（burst） | 第一個事件正常處理，去重窗口內的 HTTP 重複事件被忽略 |

### 11.2 並發邊界

| 邊界條件 | 處理方式 |
|---------|---------|
| sessionEvCh 和 hookEvCh 同時有事件 | 兩個獨立 goroutine 各自消費，透過 Registry mutex 序列化寫入 |
| ScanAndUpdateStatus 與 UpsertFromSessionEvent 並發 | Registry RWMutex 保證安全：Scan 使用 Lock，Upsert 使用 Lock |
| cleanupDedupTable 與 processSessionEvent 並發 | dedupMu 保護去重表，確保一致性 |
| outCh 消費者（WebSocket Hub）尚未啟動 | sendToOutCh 使用 non-blocking send，channel 滿時丟棄並 WARN |

### 11.3 v0.3 預留欄位邊界

| 欄位 | v0.2 邊界行為 |
|------|--------------|
| `SessionInfo.ParentAgentID` | SubagentStart 事件若含 `parent_agent_id`，自動填充；不用於業務邏輯 |
| `SessionInfo.AgentName` | 永遠為空字串；不觸發任何邏輯 |

## 12. 行為場景（Given-When-Then）

### 場景 1：新 Session 建立（JSONL 首個事件）

```
Given: SessionRegistry 為空，FileWatcher 啟動並監控 ~/.claude/projects/
When:  Claude Code 寫入第一行 JSONL（user 訊息）到新的 session.jsonl
Then:  EventDispatcher 收到 SessionEvent{Type:"user", SessionID:"abc"}
       Registry 建立新的 SessionInfo{ID:"abc", Status:"active", EventCount:1}
       SessionInfo.Summary 填入首個 user 訊息的前 100 字元
       DispatchedEvent{ChangeType:"new"} 送入 outCh
```

### 場景 2：HTTP SubagentStop 即時觸發 completed（核心路徑）

```
Given: Session "abc" 已存在，Status 為 active
       距上次事件僅 1 分鐘（未超出 2 分鐘 active 閾值）
When:  Claude Code 發送 SubagentStop Hook 事件（SessionID="abc"）
Then:  EventDispatcher 收到 HookEvent{Type:"SubagentStop", SessionID:"abc"}
       Registry 立即設定 SessionInfo.Status = "completed"
       Registry 更新 LastMessage 為 SubagentStop.LastMessage
       DispatchedEvent{ChangeType:"status_changed", Session.Status:"completed"} 送入 outCh
       此轉換無需等待 30 分鐘超時
```

### 場景 3：去重機制（HTTP 優先）

```
Given: Session "abc" 已存在
       EventDispatcher 去重表中有 key{AgentID:"x", Type:"SubagentStart", Window:T}（HTTP 已處理）
When:  JSONL 偵測到同一事件，SessionEvent{Type:"assistant", MessageID:"same-uuid"} 到達
       但此事件的 dedup key 與已有的 HTTP 記錄匹配（同 5 秒窗口）
Then:  EventDispatcher 識別為 HTTP 已處理的重複事件
       記錄 DEBUG log
       不再次呼叫 Registry.UpsertFromSessionEvent
       outCh 不發送重複的 DispatchedEvent
```

### 場景 4：定時掃描觸發 idle 轉換

```
Given: Session "abc" Status 為 active，LastEventAt 為 3 分鐘前
When:  EventDispatcher 定時掃描觸發（每 30 秒一次）
Then:  registry.ScanAndUpdateStatus 計算 delta = 3 min > ActiveThreshold(2 min)
       SessionInfo.Status 更新為 "idle"
       回傳 changed sessions = [SessionInfo{ID:"abc", Status:"idle"}]
       DispatchedEvent{ChangeType:"status_changed", Status:"idle"} 送入 outCh
```

### 場景 5：SubagentStart 補充 AgentID（JSONL 事件先於 Hook）

```
Given: Session "abc" 由 JSONL 事件建立，SessionInfo.AgentID 為空
When:  稍後 Claude Code 發送 SubagentStart Hook（SessionID="abc", AgentID="xyz"）
Then:  Registry.UpsertFromHookEvent 更新 SessionInfo.AgentID = "xyz"
       SessionInfo.AgentType 被填入
       SessionInfo.Status 強制設定為 active
       DispatchedEvent{ChangeType:"updated"} 送入 outCh
```

### 場景 6：TeammateIdle 觸發 idle 轉換

```
Given: Session "abc" Status 為 active，距上次事件 30 秒（未超時）
When:  Claude Code 發送 TeammateIdle Hook（SessionID="abc"）
Then:  Registry.UpsertFromHookEvent 強制設定 Status = "idle"
       不等待 2 分鐘超時
       DispatchedEvent{ChangeType:"status_changed", Status:"idle"} 送入 outCh
```

### 場景 7：outCh 已滿的容錯

```
Given: EventDispatcher 正在運行，outCh 緩衝區已全滿（WebSocket Hub 尚未啟動）
When:  新的 JSONL SessionEvent 到達
Then:  Registry 正常更新（狀態更新不受影響）
       sendToOutCh 偵測到 channel 已滿
       記錄 WARN log（event dropped, outCh full）
       DispatchedEvent 被丟棄（UI 下次連線時從 registry.List() 恢復全量狀態）
```

### 場景 8：孤立 SubagentStop（Session 不存在）

```
Given: SessionRegistry 中沒有 SessionID="ghost" 的記錄
When:  收到 HookEvent{Type:"SubagentStop", SessionID:"ghost"}
Then:  Registry.UpsertFromHookEvent 偵測到 sessionID 不存在
       記錄 WARN log（orphan SubagentStop for session ghost）
       不建立新的 SessionInfo
       outCh 不發送任何事件
```

### 場景 9：v0.3 預留欄位 ParentAgentID 填充

```
Given: EventDispatcher 接收到含 parent_agent_id 的 SubagentStart Hook
When:  HookEvent{Type:"SubagentStart", AgentID:"child", ParentAgentID:"parent"} 到達
Then:  Registry.UpsertFromHookEvent 填入 SessionInfo.ParentAgentID = "parent"
       v0.2 業務邏輯不使用此欄位（無 DispatchedEvent 特殊處理）
       欄位值保留於 SessionInfo 供 v0.3 使用
```

## 14. 技術決策紀錄

### TDR-001：SessionStatus 使用 string 而非 iota int

**決策**：使用 `type SessionStatus string` 而非 `type SessionStatus int`（iota）。

**理由**：
- SessionInfo 需要 JSON 序列化後直接傳給 UI client，string 可讀性更高（"active" vs "0"）
- WebSocket 推送的 DispatchedEvent 包含 SessionInfo，保持一致性
- 避免 UI 端需要映射表

**代價**：比較效能略低於 int，但 session 數量通常 < 50，無效能問題。

### TDR-002：ScanAndUpdateStatus 使用定時掃描而非 time.AfterFunc

**決策**：使用固定週期（每 30 秒）的定時掃描，而非為每個 session 設定個別的 `time.AfterFunc`。

**理由**：
- session 數量動態，`time.AfterFunc` 需要管理大量 timer 的清理
- 30 秒精度的狀態轉換對 UI 顯示已足夠（用戶感知不到 30 秒誤差）
- 實作更簡單，不存在 timer leak 風險

**代價**：狀態轉換最多延遲 30 秒（例如 session 在 2 分 01 秒後才被掃描到）。在 spec 的要求精度內可接受。

### TDR-003：DispatchedEvent 使用 ChangeType 而非 diff

**決策**：輸出 `DispatchedEvent` 包含完整的 `SessionInfo` 快照和 `ChangeType` 標籤，而非只傳送變更的欄位（diff）。

**理由**：
- UI client 通常需要完整的 session 狀態來更新視圖
- diff 格式增加 client 端的複雜度（需要合併 patch）
- session 數量少（< 50），全量推送每個 session 的 KB 級資料無效能問題

**代價**：每次狀態更新傳輸的資料量較大，但對 WebSocket 而言影響可忽略。

### TDR-004：去重表使用 map + mutex 而非 channel 序列化

**決策**：去重表使用 `map[deduplicationKey]time.Time` + `sync.Mutex`，而非透過單一 goroutine + channel 序列化所有操作。

**理由**：
- JSONL 和 HTTP 事件由兩個獨立 goroutine 消費（雙源並發）
- 若用 channel 序列化，會引入額外的 goroutine 和 channel 管理
- map + mutex 的實作更直觀，去重邏輯本身是輕量操作（讀取+寫入），鎖競爭低

**代價**：高頻事件時 dedupMu 可能有輕微競爭，但 DedupWindowDuration=5s 已有效降低事件頻率。

### TDR-005：EventDispatcher 與 SessionRegistry 的職責切割

**決策**：Session 狀態的計算邏輯放在 SessionRegistry（`computeStatus`），而非 EventDispatcher。

**理由**：
- 狀態計算屬於 domain 邏輯，應與 Registry 封裝在一起
- EventDispatcher 是協調層，不應承擔業務規則
- 測試時可獨立測試 Registry 的狀態機，不依賴 Dispatcher
