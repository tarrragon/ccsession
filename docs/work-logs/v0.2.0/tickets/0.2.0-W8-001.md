## Problem Analysis

## Hook vs PM 決策主權交叉分析

### 分析範圍
- Hook 檔案：67 個（含 archived）
- PM 規則：19 個（.claude/pm-rules/）
- 已註冊事件：PreToolUse(4 組)、SessionStart(1 組)、PostToolUse(4 組)、UserPromptSubmit(1 組)、Stop(1 組)

### 衝突類型分類

#### 類型 A：Hook 搶先阻塞了 PM 應有的決策權（5 個）

1. **command-entrance-gate-hook.py**（BLOCK, UserPromptSubmit）
   - 行為：開發/測試/調整命令在無 Ticket 時直接 exit(2) 阻塞
   - 衝突：PM 可能有正當理由在無 Ticket 時執行探索性開發（如緊急 hotfix），但 Hook 搶先阻塞，PM 無法判斷
   - 嚴重度：中。Hook 已有「探索類不阻攔」白名單，但邊界模糊

2. **creation-acceptance-gate-hook.py**（BLOCK, UserPromptSubmit）
   - 行為：claim 時若 creation_accepted != true，直接 exit(2)
   - 衝突：PM 可能已口頭確認品質但忘記設置欄位，Hook 搶先阻塞讓 PM 無法解釋
   - 嚴重度：低。設計合理，但缺乏 PM override 機制

3. **branch-verify-hook.py**（BLOCK, PreToolUse）
   - 行為：在保護分支上 Edit/Write 時直接 deny
   - 衝突：已有路徑豁免（.claude/, docs/），衝突較小
   - 嚴重度：低

4. **ticket-file-access-guard-hook.py**（BLOCK, PreToolUse）
   - 行為：阻止直接 Read ticket 檔案，強制使用 /ticket CLI
   - 衝突：PM 有時需要直接閱讀 ticket 原始內容進行除錯
   - 嚴重度：低

5. **mcp-run-tests-validator.py**（BLOCK, PreToolUse）
   - 行為：無 paths 參數時阻止全量測試
   - 衝突：PM 可能需要執行全量測試驗收版本
   - 嚴重度：低

#### 類型 B：Hook 自動做了 PM 可能想控制的決定（4 個）

1. **pre-fix-evaluation-hook.py**（AUTO-CLASSIFY, PostToolUse）
   - 行為：自動偵測錯誤類型並分類（SYNTAX_ERROR 直接修、其他強制開 Ticket）
   - 衝突：錯誤分類應由 incident-responder 執行（pm-rules/incident-response.md），但 Hook 搶先分類
   - 嚴重度：高。與 skip-gate.md 規則 1「強制派發 incident-responder」直接衝突

2. **handoff-prompt-reminder-hook.py**（AUTO-RESUME, UserPromptSubmit）
   - 行為：自動寫入 resumed_at 並注入 Ticket 內容，代替 PM 決定是否恢復任務
   - 衝突：PM 可能想先評估 context 再決定是否恢復
   - 嚴重度：中

3. **ticket-reinstall-hook.py**（AUTO-INSTALL, SessionStart）
   - 行為：自動重新安裝 ticket CLI
   - 衝突：無。純技術維護，不涉及決策
   - 嚴重度：無

4. **post-commit-fetch-hook.py**（AUTO, PostToolUse）
   - 行為：commit 後自動 git fetch
   - 衝突：無。純技術維護
   - 嚴重度：無

#### 類型 C：Hook 和 PM 規則重疊但方向一致（6 個）

1. **process-skip-guard-hook.py** + pm-rules/skip-gate.md — 流程省略防護（一致）
2. **acceptance-gate-hook.py** + pm-rules/ticket-lifecycle.md — 驗收流程（一致）
3. **parallel-suggestion-hook.py** + pm-rules/parallel-dispatch.md — 並行建議（一致）
4. **session-context-guard-hook.py** + handoff 規則 — context 累積提醒（一致）
5. **agent-dispatch-validation-hook.py** + agent registry — 派發衝突檢查（一致）
6. **main-thread-edit-restriction-hook.py** + pm-rules/skip-gate.md Level 3 — 編輯限制（一致）

### 根本問題

Hook 系統缺乏「分級機制」，所有阻塞型 Hook 都用 exit(2) 強制拒絕，沒有「建議但不阻塞」和「阻塞但可 override」的中間層級。PM 在被 Hook 阻塞時只能繞道，無法行使決策主權。

## 產出一：PM 決策主權清單

以下決策點 **Hook 禁止搶先處理**，必須由 PM 判斷後執行：

| # | 決策點 | 目前搶先的 Hook | PM 應有的判斷 |
|---|--------|----------------|-------------|
| 1 | 錯誤分類與修復策略 | pre-fix-evaluation-hook（自動分類 SYNTAX_ERROR vs 其他） | PM 決定是否派發 incident-responder 或直接修復（skip-gate 規則 1） |
| 2 | 任務恢復時機 | handoff-prompt-reminder-hook（自動寫入 resumed_at） | PM 評估 context 狀態後決定恢復哪個任務 |
| 3 | 流程省略的正當性 | process-skip-guard-hook（偵測省略意圖） | PM 可能有正當理由調整流程（如小型修改跳過 SA） |
| 4 | 緊急修復的 Ticket 豁免 | command-entrance-gate-hook（無 Ticket 阻塞） | PM 判斷是否為需要立即處理的 P0 緊急情況 |
| 5 | 全量測試執行時機 | mcp-run-tests-validator（阻塞無 paths 的全量測試） | PM 在版本驗收時可能需要全量測試 |
| 6 | Wave 收尾的彈性 | acceptance-gate-hook（子任務未完成阻塞 complete） | PM 可能判斷某子任務可延後但主任務可先完成 |
| 7 | 代理人派發的檔案衝突處理 | file-ownership-guard-hook（警告檔案衝突） | PM 決定是否接受風險並行或改為序列 |

## 產出三：決策空白區域（7 個）

以下 7 個決策點目前 **既無 Hook 也無 PM 規則** 明確覆蓋：

| # | 決策空白 | 風險 | 建議補充方案 |
|---|---------|------|------------|
| 1 | **跨版本 Ticket 遷移決策** | 版本升級時 pending Ticket 是否遷移、關閉或重新評估，無明確規則 | 建議在 pm-rules/version-progression.md 補充遷移決策流程 |
| 2 | **代理人 context 耗盡的重試策略** | 代理人因 prompt too long 失敗時，PM 是否重試、拆分、或 handoff，無標準流程 | 建議在 pm-rules/incident-response.md 補充「代理人環境」子類的重試決策樹 |
| 3 | **多 Wave 並行的優先級衝突** | 同時有多個 Wave 的 Ticket 可執行時，PM 如何決定優先順序，無規則 | 建議在 pm-rules/parallel-dispatch.md 補充跨 Wave 優先級規則 |
| 4 | **Hook 自身的修改審核** | 修改 Hook 程式碼時無特殊審核流程，可能引入 Hook 行為退化 | 建議建立 Hook 修改的 PR 審查規則或 Hook 測試門檻 |
| 5 | **SA 審查不通過的升級路徑** | SA 認為不建議實作時，PM 和用戶之間的溝通協議不明確 | 建議在 pm-rules/tdd-flow.md 補充 SA 否決後的 AskUserQuestion 場景 |
| 6 | **代理人產出品質不達標的重做決策** | 代理人完成任務但品質不合格時，PM 是否重做、補 Ticket、或接受，無標準 | 建議在 pm-rules/verification-framework.md 補充品質不達標的決策分支 |
| 7 | **SessionStart Hook 過多導致啟動延遲** | 目前有 12 個 SessionStart Hook，無效能監控或裁減機制 | 建議在 hook-health-monitor 中加入啟動時間閾值警告（如 > 10 秒） |
