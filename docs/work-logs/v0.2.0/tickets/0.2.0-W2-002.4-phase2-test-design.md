# 0.2.0-W2-002.4 Phase 2: Dashboard 主畫面組裝測試設計

---

## 1. 概述

### 1.1 測試目標

基於 Phase 1 功能規格（0.2.0-W2-002.4-phase1-design.md），設計完整的測試案例覆蓋：

- **DashboardPage Widget 佈局結構**：雙欄佈局、sidebar/main area 組配、ProviderScope 正確包裝
- **ConnectionStatusBar 狀態指示**：各連線狀態的顏色和文字正確映射
- **selectedSessionId 橋接機制**：sidebar 選取 → ConversationNotifier.loadSession 觸發 → main area 更新的完整流程
- **空白初始狀態**：未選中時 main area 顯示提示文字
- **邊界和異常情況**：連線中斷、重複選擇、session 不存在等

### 1.2 測試分層

測試分為三個獨立的群組（Test Group），便於 Phase 3b 並行實作：

| Test Group | 模組 | 測試量 | 焦點 |
|-----------|------|-------|------|
| **TG-30** | DashboardPage Widget 佈局 | 6 個測試案例 | Widget 樹結構、佈局尺寸、ProviderScope |
| **TG-31** | ConnectionStatusBar Widget | 4 個測試案例 | 連線狀態 → 顏色/文字映射、edge cases |
| **TG-32** | DashboardPage 狀態橋接 | 8 個測試案例 | ref.listen 機制、selectedSessionId 變更觸發 loadSession |

**測試群組設計原則**（SRP）：
- TG-30：純 Widget 佈局測試，無 selectedSessionId 狀態變更
- TG-31：ConnectionStatusBar 隔離測試，mock connectionStateProvider
- TG-32：selectedSessionId 橋接機制測試，涉及 ref.listen 和 ConversationNotifier 互動

## 4. TG-32: DashboardPage selectedSessionId 橋接機制測試

### 測試群組描述

驗證 DashboardPage 的 `ref.listen(selectedSessionIdProvider)` 機制正確觸發 `ConversationNotifier.loadSession()`，以及 selectedSessionId 變更時 main area 正確更新。

### 4.1 測試環境設置

**Mock 策略**：
- Fake ConversationNotifier（追蹤 loadSession 呼叫）
- Fake SessionListNotifier（可控制 selectedSessionId）
- Mock WebSocketService

**Fake Implementation**：
```dart
class _FakeConversationNotifier extends ConversationNotifier {
  _FakeConversationNotifier(this._initialState);

  final ConversationState _initialState;
  final List<String> loadSessionCalls = []; // 追蹤呼叫

  @override
  Future<ConversationState> build() async => _initialState;

  @override
  Future<void> loadSession(String sessionId) async {
    loadSessionCalls.add(sessionId);
    // 模擬載入行為
    state = AsyncData(_initialState.copyWith(sessionId: sessionId));
  }
}

class _FakeSessionListNotifier extends SessionListNotifier {
  _FakeSessionListNotifier(this._state);

  SessionListState _state;

  @override
  Future<SessionListState> build() async => _state;

  // 供測試控制 selectedSessionId
  void setSelectedSessionId(String? id) {
    _state = _state.copyWith(selectedSessionId: id);
    state = AsyncData(_state);
  }
}
```

### 4.2 測試案例設計

#### TC-32-01: selectedSessionId 從 null 變為「s1」時觸發 loadSession

**Given**: DashboardPage 已渲染，selectedSessionId 初始為 null

**When**: 呼叫 setSelectedSessionId('s1')（模擬使用者點擊）

**Then**:
- ConversationNotifier.loadSession('s1') 被呼叫 1 次
- 參數為 's1'

**實作指南**：
```dart
testWidgets('calls loadSession when selectedSessionId changes from null to s1',
    (tester) async {
  final fakeConversationNotifier = _FakeConversationNotifier(
    const ConversationState(),
  );

  final fakeSessionListNotifier = _FakeSessionListNotifier(
    const SessionListState(selectedSessionId: null), // 初始 null
  );

  await tester.pumpWidget(
    ProviderScope(
      overrides: [
        conversationNotifierProvider.overrideWith(
          () => fakeConversationNotifier,
        ),
        sessionListNotifierProvider.overrideWith(
          () => fakeSessionListNotifier,
        ),
        selectedSessionIdProvider.overrideWith((ref) {
          return ref.watch(sessionListNotifierProvider).valueOrNull
              ?.selectedSessionId;
        }),
      ],
      child: MaterialApp(home: DashboardPage()),
    ),
  );

  // 模擬使用者點擊 session
  fakeSessionListNotifier.setSelectedSessionId('s1');
  await tester.pumpAndSettle();

  // 驗證 loadSession 被呼叫
  expect(fakeConversationNotifier.loadSessionCalls, contains('s1'));
});
```

## 12. 測試設計決策記錄

### 決策 1：測試群組以 SRP 功能職責拆分

**背景**：三個測試目標有不同的依賴和複雜度

**決策**：
- TG-30 — Widget 佈局（無業務邏輯）
- TG-31 — ConnectionStatusBar 隔離（純映射）
- TG-32 — selectedSessionId 橋接（涉及 ref.listen）

**優勢**：
- Phase 3b 可按功能群組並行實作
- 各群組測試目標單一，易於除錯
- 無跨群組依賴，可獨立通過

### 決策 2：使用 Fake Notifier 而非 Mock

**背景**：ConversationNotifier 和 SessionListNotifier 需要完整狀態管理

**決策**：自行實作 Fake Notifier 類別，繼承原 Notifier，覆寫 build 和方法

**優勢**：
- 比 Mock 更接近實際行為
- 能追蹤方法呼叫（loadSessionCalls）
- 型別檢查完全相容

**權衡**：
- 需要更多測試程式碼
- 但收益是測試可靠性大幅提升

### 決策 3：TC-32-03 驗證「不重複觸發」而非「呼叫次數」

**背景**：ref.listen 的去重邏輯由 Riverpod 保證，測試不應重複驗證

**決策**：檢查呼叫清單長度不變，而非檢查具體的呼叫次數計數

**理由**：
- Riverpod 的去重已充分測試
- 我們只需驗證邏輯正確性（前後值相同時 listener 不觸發）
- 避免過度耦合實作細節
