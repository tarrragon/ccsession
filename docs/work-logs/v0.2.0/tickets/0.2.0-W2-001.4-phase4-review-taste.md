# Phase 4a Taste Review: 0.2.0-W2-001.4 WebSocket Server

## Taste Score: Acceptable (leaning Good)

This is competent WebSocket server code. The structure is clear, the separation of concerns is reasonable, and most functions are short. But there are a few places where the design could be tighter.

---

## 值得稱讚的設計

1. **SessionQuerier interface** (`session_querier.go`): Clean, minimal read-only interface. Three methods, each with a clear contract. This is exactly the right abstraction boundary -- WebSocketServer doesn't need to know about SessionRegistry internals. Good taste.

2. **sendToClient with backpressure** (line 310-329): The non-blocking select with buffer-full eviction is the correct pattern. You don't block the server on a slow consumer. The client gets dropped, which is the right thing to do.

3. **Constants discipline**: Every magic number, every log message, every error code is a named constant in its own file. Zero hardcoded strings in the server logic. This is how it should be done.

4. **readPump/writePump separation**: Classic gorilla/websocket pattern, correctly implemented. Each goroutine has clear ownership of read vs write, clean defer chains for cleanup.

---

## 問題（按重要性排序）

### P1: sendToClient vs sendToClientUnsafe -- 兩套 marshal+send 邏輯（設計債務）

`sendToClient` (line 310) 和 `sendToClientUnsafe` (line 410) 做同一件事：marshal JSON + 送入 channel。但行為不同：

- `sendToClient`: buffer full 時主動踢掉 client（取鎖、刪除、close channel）
- `sendToClientUnsafe`: buffer full 時只 log 警告，不踢

這兩個函式有相同的 marshal 邏輯但不同的 backpressure 策略。問題是：

1. **JSON marshal 重複了兩次**。如果你改 ServerMessage 的序列化方式，要改兩處。
2. **行為差異是隱性的**。`sendToClientUnsafe` 的名字暗示「不安全是因為沒持鎖」，但真正的差異是「buffer full 時不踢 client」。名字沒有表達這個語義差異。
3. **broadcastSessionList 呼叫 sendToClientUnsafe 時，slow consumer 不會被踢掉**。broadcast 場景是最容易觸發 buffer full 的場景，卻恰好用了不踢的版本。

**建議**：統一 marshal 到一處。讓 broadcast 路徑也能正確處理 slow consumer。可以把 marshal 提出來變成 `marshalMessage`，然後 `sendToClient` 和 broadcast 路徑共用一個 `enqueue(client, data []byte)` 函式。

### P2: handleGetSessionList 和 sendInitialSessionList 完全重複

Line 236-245 和 line 299-308 是逐字相同的程式碼。

```go
func (s *WebSocketServer) handleGetSessionList(client *Client) {
    sessions := s.querier.List()
    if sessions == nil { sessions = []*SessionInfo{} }
    s.sendToClient(client, ServerMessage{...})
}

func (s *WebSocketServer) sendInitialSessionList(client *Client) {
    sessions := s.querier.List()
    if sessions == nil { sessions = []*SessionInfo{} }
    s.sendToClient(client, ServerMessage{...})
}
```

`sendInitialSessionList` 完全可以刪掉，`HandleWS` 直接呼叫 `handleGetSessionList`。或者反過來，讓 `handleGetSessionList` 委託給一個 `sendSessionListTo(client)` 私有函式。

### P3: nil-to-empty-slice 防禦散落三處

Line 238、284、301-302、365-366 都在做同一件事：`if x == nil { x = []*T{} }`。

這個防禦邏輯應該在 `querier.List()` 和 `querier.GetHistory()` 的契約中保證「永遠回傳非 nil slice」，而不是讓每個消費者自己防禦。SessionRegistry 的 `List()` 和 `GetHistory()` 已經用 `make` 初始化了，但你不信任介面契約，在消費端重複防禦。

如果你要防禦，至少集中到一處（比如 `sendSessionListTo` 內部做一次就好）。現在是四處重複。

### P4: processDispatchedEvent 中 ChangeTypeUpdated 沒帶 Event 資料

Line 340-361: `ChangeTypeNew` 和 `ChangeTypeUpdated` 都送 `SessionEventData`，但 `Event` 欄位始終是 nil。結構體定義了 `Event *SessionEvent`（models line 31），但從沒填入。

如果 client 收到 `session_event` 訊息但 `event` 永遠是 null，這個欄位存在的意義是什麼？要麼填入實際 event，要麼從結構體移除。空欄位是暗示「未來會用」的典型過度設計。

## 小型觀察

1. **line 313**: `"failed to marshal server message"` 是唯一一個硬編碼的 log 字串，其他全部用了常數。應該提取到 `websocket_messages.go`。

2. **ServerMessage.Data 用 `interface{}`**：Go 1.21+ 應該用 `any`（語義相同，但 `any` 是慣用寫法）。不影響功能，純風格。

3. **GetHistory 的 sort**（session_registry.go line 313）：每次查詢都排序。如果 AppendEvent 保證時間順序插入（目前看起來是），這個 sort 是多餘的。要麼在 AppendEvent 時維持有序，要麼在這裡排序，不需要兩者都做或都不保證。

4. **unregisterClient 的鎖粒度**（line 108-119）：先取鎖刪除 client，再解鎖後呼叫 `clientCount()`（又取一次鎖）。可以在持鎖時直接讀 `len(s.clients)`，避免二次取鎖。微小的效能點，但更重要的是它暗示了一個不必要的 TOCTOU 窗口（刪除和計數之間可能有新 client 註冊）。

---

## 結論

整體設計是務實的。readPump/writePump 分離、SessionQuerier 介面抽象、常數紀律都做得好。主要問題集中在 DRY 違反（P2 重複函式、P3 nil 防禦散落）和 sendToClient/sendToClientUnsafe 的行為差異不夠明確（P1）。P4 的空 Event 欄位是過度設計的信號。

這些不是架構問題，是打磨問題。花半天清理 P1-P3 就能從 Acceptable 升到 Good taste。
