## Problem Analysis

## 問題發現過程

在 0.2.0-W3-002 Phase 3b 拆分評估中，PM 使用了以下錯誤的評估邏輯：

### 錯誤的評估方式（現狀）
1. **以 context 預算為主要判斷標準** — 估算代理人 context 消耗量，若在可管理範圍內就不拆分
2. **以技術依賴為不拆分理由** — 測試群組間有函式呼叫依賴，就判定不適合拆分
3. **以「代理人做得到」為合併依據** — 只要單一代理人能處理就合併派發

### 正確的評估方式（應改為）
1. **SRP 功能職責導向** — 每個子任務應聚焦單一功能面（版本解析、版本比較、偵測決策、降級整合是不同功能）
2. **序列派發解決依賴** — 測試群組有依賴不代表不能拆分，可透過序列執行解決
3. **Phase 2 測試設計時就要考慮可拆分性** — 測試群組應設計為可獨立執行，減少 Sociable Test 帶來的隱含依賴

### 影響範圍
- tdd-flow.md（3b 拆分評估標準）
- task-splitting.md（策略 7 測試群組拆分）
- sage-test-architect 代理人定義（測試設計應考慮拆分友善性）
- parallel-dispatch.md（拆分判斷邏輯）

### 結論
SRP 不只是程式碼設計原則，也是代理人派發原則。代理人做得到不代表應該合併，讓代理人專注在單一功能面才能發揮最大效能。
