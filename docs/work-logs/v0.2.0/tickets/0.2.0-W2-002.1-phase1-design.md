## 1. 功能需求分析

### 1.1 核心問題

Flutter Frontend 需要與 Go Backend（`ws://localhost:8765/ws`）建立 WebSocket 連線，接收即時 session 事件，並將 JSON 訊息解析為強型別 Dart 資料模型。這是所有 Frontend 功能的基礎層。

### 1.2 使用者場景

| 場景 | 描述 |
|------|------|
| 啟動連線 | App 啟動後自動連線到 Backend |
| 接收 session 列表 | 連線成功後收到完整 session 快照 |
| 即時事件更新 | 訂閱的 session 有新事件時即時收到 |
| 斷線重連 | 網路中斷後自動以指數退避策略重連 |
| 心跳保活 | 30 秒 ping/pong 維持連線存活 |

### 1.3 設計目標

1. WebSocket 連線管理封裝為獨立 service，與 UI 層完全解耦
2. Dart 資料模型精確對應 Go Backend JSON 結構（零手動解析）
3. 連線狀態透過 Riverpod 暴露為響應式 stream
4. 重連邏輯透明，上層不需要關心重連細節

## 5. WebSocketService API 介面

### 5.1 公開介面

```dart
abstract class WebSocketService {
  /// 當前連線狀態
  WsConnectionState get connectionState;

  /// 連線狀態 stream（UI 訂閱用）
  Stream<WsConnectionState> get connectionStateStream;

  /// Server → Client 訊息 stream（已解析為強型別）
  Stream<ServerMessage> get messageStream;

  /// 連線到 WebSocket server
  /// [uri] 預設為 ws://localhost:8765/ws
  Future<void> connect({Uri? uri});

  /// 手動斷線（不觸發重連）
  Future<void> disconnect();

  /// 送出 Client → Server 訊息
  void send(ClientMessage message);

  /// 便捷方法：請求 session 列表
  void requestSessionList();

  /// 便捷方法：請求指定 session 歷史事件
  void requestSessionHistory(
    String sessionId, {
    int? limit,
    String? before,
  });

  /// 便捷方法：訂閱 session 即時事件
  void subscribeSession(String sessionId);

  /// 便捷方法：取消訂閱
  void unsubscribeSession(String sessionId);

  /// 釋放資源
  void dispose();
}
```

### 5.2 實作類別 `WebSocketServiceImpl`

**內部狀態**：

| 欄位 | 類型 | 說明 |
|------|------|------|
| `_channel` | `WebSocketChannel?` | 底層 WebSocket 通道 |
| `_connectionStateController` | `StreamController<WsConnectionState>` | 狀態廣播 |
| `_messageController` | `StreamController<ServerMessage>` | 訊息廣播 |
| `_reconnectStrategy` | `ReconnectStrategy` | 重連策略實例 |
| `_heartbeatTimer` | `Timer?` | 心跳計時器 |
| `_pongTimer` | `Timer?` | Pong 超時計時器 |
| `_isManualDisconnect` | `bool` | 手動斷線旗標（阻止重連） |
| `_currentUri` | `Uri?` | 當前連線 URI（重連用） |

**connect() 流程**：

```
connect(uri)
    |
    v
設定 _currentUri, _isManualDisconnect = false
    |
    v
更新狀態 → connecting
    |
    v
WebSocketChannel.connect(uri)
    |
    +-- 成功 → 更新狀態 → connected
    |          → _reconnectStrategy.reset()
    |          → 啟動心跳計時器
    |          → 監聽 _channel.stream
    |          → requestSessionList()（自動取得初始快照）
    |
    +-- 失敗 → 更新狀態 → reconnecting
              → _scheduleReconnect()
```

**訊息接收流程**：

```
_channel.stream.listen(rawMessage)
    |
    v
jsonDecode(rawMessage) → Map<String, dynamic>
    |
    v
ServerMessage.fromJson(map)
    |
    v
_messageController.add(serverMessage)
```

**disconnect() 流程**：

```
disconnect()
    |
    v
_isManualDisconnect = true
    |
    v
取消心跳計時器、Pong 計時器
    |
    v
_channel?.sink.close()
    |
    v
更新狀態 → disconnected
```

## 6. 重連策略 — `ReconnectStrategy`

### 6.1 介面

```dart
class ReconnectStrategy {
  /// 當前延遲時間
  Duration get currentDelay;

  /// 計算下一次重連延遲（呼叫後內部遞增）
  Duration nextDelay();

  /// 重置延遲到初始值（連線成功後呼叫）
  void reset();
}
```

### 6.2 指數退避算法

```
初始延遲 = 1s
乘數 = 2
最大延遲 = 30s

nextDelay() 序列：1s → 2s → 4s → 8s → 16s → 30s → 30s → ...
```

**行為規格**：

| 呼叫次數 | 回傳延遲 | 計算 |
|---------|---------|------|
| 第 1 次 | 1s | min(1 * 2^0, 30) = 1 |
| 第 2 次 | 2s | min(1 * 2^1, 30) = 2 |
| 第 3 次 | 4s | min(1 * 2^2, 30) = 4 |
| 第 4 次 | 8s | min(1 * 2^3, 30) = 8 |
| 第 5 次 | 16s | min(1 * 2^4, 30) = 16 |
| 第 6 次 | 30s | min(1 * 2^5, 30) = 30（觸頂） |
| 第 7+ 次 | 30s | 持續觸頂 |

### 6.3 重連排程 `_scheduleReconnect()`

```
_scheduleReconnect()
    |
    v
如果 _isManualDisconnect → 不重連，return
    |
    v
更新狀態 → reconnecting
    |
    v
delay = _reconnectStrategy.nextDelay()
    |
    v
Future.delayed(delay) → connect(_currentUri)
```

## 7. 心跳機制

### 7.1 行為規格

| 項目 | 值 | 來源 |
|------|-----|------|
| Ping 間隔 | 30 秒 | Go HeartbeatInterval |
| Pong 超時 | 35 秒 | Go PongWaitTimeout |

**注意**：`web_socket_channel` 套件在 Web 平台上不支援應用層 ping/pong frame。因此心跳機制設計為**應用層 ping**（發送 JSON `{"action":"ping"}`），而非 WebSocket protocol-level ping。

但 Go Backend 目前使用 protocol-level ping。因此有兩個方案：

**方案 A（建議）**：Flutter 端不主動發 ping，僅依賴 Go Backend 的 protocol-level ping/pong。`web_socket_channel` 底層會自動回應 protocol-level pong。Flutter 端設定一個 35 秒的 inactivity timer：如果 35 秒內沒收到任何訊息，判定連線已斷開，觸發重連。

**方案 B**：在 Go Backend 增加應用層 ping 支援（`{"type":"ping"}`），Flutter 端回應 `{"action":"pong"}`。此方案需修改 Backend，不在本 Ticket 範圍。

**本 Ticket 採用方案 A**：

```
連線成功 → 啟動 inactivity timer（35s）
    |
收到任何訊息 → 重置 inactivity timer
    |
inactivity timer 到期 → 判定連線斷開 → 觸發重連
    |
手動斷線 → 取消 inactivity timer
```

/// WebSocketService 單例
@riverpod
WebSocketService webSocketService(Ref ref) {
  final service = WebSocketServiceImpl();

## 9. 錯誤處理

### 9.1 連線錯誤

| 錯誤情境 | 處理方式 |
|---------|---------|
| 連線失敗（server 未啟動） | 狀態 → reconnecting，觸發指數退避重連 |
| 連線中途斷開 | 狀態 → reconnecting，觸發指數退避重連 |
| 手動斷線 | 狀態 → disconnected，不觸發重連 |

### 9.2 訊息解析錯誤

| 錯誤情境 | 處理方式 |
|---------|---------|
| JSON 解析失敗 | log ERROR，丟棄該訊息，不中斷連線 |
| 未知 message type | log WARN，丟棄該訊息，不中斷連線 |
| payload 欄位缺失 | freezed 的 `@Default` 填入預設值，不拋例外 |

### 9.3 Server 錯誤回應

| Server error code | 處理方式 |
|------------------|---------|
| SESSION_NOT_FOUND | 透過 messageStream 傳遞，由上層處理 |
| INVALID_ACTION | log WARN（Client 端 bug 指示器） |
| INTERNAL_ERROR | log ERROR，透過 messageStream 傳遞 |

## 10. 邊界條件

| 條件 | 預期行為 |
|------|---------|
| App 啟動時 Backend 未運行 | 狀態 connecting → reconnecting，持續重連 |
| 重連過程中手動 disconnect | 停止重連，狀態 → disconnected |
| 重連過程中再次呼叫 connect | 取消舊的重連排程，以新 URI 重新連線 |
| 連續收到多個 session_list | 後者覆蓋前者（由下游 provider 處理） |
| 收到空 session 列表 | 正常處理，sessions = [] |
| 極大 payload（> 1MB） | `web_socket_channel` 無限制，正常接收 |
| dispose() 後呼叫 send/connect | 忽略操作，不拋例外 |

## 12. 驗收標準（Given-When-Then）

### 場景 1: 成功連線（正常流程）

```
Given: Go Backend 在 ws://localhost:8765/ws 運行中
When: WebSocketService.connect() 被呼叫
Then: connectionState 轉為 connected
      且 messageStream 收到 session_list 訊息
```

### 場景 2: 連線失敗自動重連（異常流程）

```
Given: Go Backend 未運行
When: WebSocketService.connect() 被呼叫
Then: connectionState 轉為 connecting → reconnecting
      且第一次重連延遲 1 秒
      且第二次重連延遲 2 秒（指數退避）
```

### 場景 3: 指數退避觸頂（邊界條件）

```
Given: 已連續失敗 6 次以上
When: 下一次重連排程
Then: 延遲固定為 30 秒（不超過最大值）
```

### 場景 4: 手動斷線不重連

```
Given: WebSocket 已連線
When: WebSocketService.disconnect() 被呼叫
Then: connectionState 轉為 disconnected
      且不觸發任何重連排程
```

### 場景 5: 重連成功重置退避

```
Given: 已經歷 3 次重連失敗（當前延遲 4s）
When: 第 4 次重連成功
Then: connectionState 轉為 connected
      且退避延遲重置為 1s
      且自動請求 session_list
```

### 場景 6: 訊息解析（正常流程）

```
Given: WebSocket 已連線
When: 收到 {"type":"session_list","data":{"sessions":[...]}} JSON
Then: messageStream 產出 ServerMessage(type: "session_list", data: ...)
```

### 場景 7: JSON 解析失敗（異常流程）

```
Given: WebSocket 已連線
When: 收到無效 JSON 字串
Then: log ERROR
      且 messageStream 不產出任何訊息
      且連線不中斷
```

### 場景 8: 心跳超時偵測（邊界條件）

```
Given: WebSocket 已連線且 inactivity timer 設為 35 秒
When: 35 秒內未收到任何訊息
Then: 判定連線斷開
      且 connectionState 轉為 reconnecting
      且觸發重連排程
```

### 場景 9: 連線狀態 enum 完整轉換

```
Given: 初始狀態為 disconnected
When: 依序執行 connect() → 成功 → 斷線 → 重連中 → disconnect()
Then: 狀態轉換序列為:
      disconnected → connecting → connected → reconnecting → disconnected
```

### 場景 10: Client 訊息發送

```
Given: WebSocket 已連線
When: 呼叫 subscribeSession('session-123')
Then: WebSocket 送出 {"action":"subscribe_session","sessionId":"session-123"}
```

### 場景 11: dispose 後操作安全

```
Given: WebSocketService 已 dispose
When: 呼叫 send() 或 connect()
Then: 操作被忽略，不拋出例外
```
