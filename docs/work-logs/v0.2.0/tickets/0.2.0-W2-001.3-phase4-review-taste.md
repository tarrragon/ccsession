# 程式碼品味審查：session_registry.go + event_dispatcher.go

**審查者**：linux（Linus Torvalds 精神）
**審查範圍**：`server/session_registry.go`、`server/event_dispatcher.go`
**Ticket**：0.2.0-W2-001.3

---

## Taste Score：Acceptable（接近 Good taste，有一個值得修正的設計問題）

整體品質令人滿意。資料結構設計合理，mutex 使用克制，狀態機邏輯清晰。但有一個設計問題讓我不得不扣分。

---

## 值得稱讚的設計

在指出問題之前，先承認做得好的地方。

**`computeStatus` 函式**——這是整個審查最好的程式碼：

```go
switch {
case elapsed < ActiveThreshold:
    return SessionStatusActive
case elapsed < IdleThreshold:
    return SessionStatusIdle
default:
    return SessionStatusCompleted
}
```

三個狀態，三個分支，沒有特例，沒有巢狀。這就是 good taste。

**RWMutex 分層**——`SessionRegistry` 用 `RWMutex` 區分讀寫，`EventDispatcher` 的 `dedupMu` 是獨立的 `sync.Mutex`，鎖的粒度正確。兩把鎖做兩件事，不混用。

**深度複製一致性**——`Get()` 和 `List()` 都回傳深度複製。這是正確的設計：Registry 是 Source of Truth，外部不應該透過指標竄改內部狀態。

## 問題一：`UpsertFromHookEvent` 末尾的條件寫入（設計問題，需修正）

這是我唯一真正在意的問題。

```go
// UpsertFromHookEvent 末尾
if exists {
    r.sessions[event.SessionID] = session
}
```

這行程式碼是錯的。更精確說：它是一個謊言。

看 `SubagentStart` 分支的邏輯：

```go
case HookEventSubagentStart:
    if !exists {
        session = &SessionInfo{...}
        r.sessions[event.SessionID] = session  // <-- 已經寫入了！
    }
    session.AgentID = event.AgentID
    // ...修改 session 欄位
    session.Status = SessionStatusActive
```

`SubagentStart` 在 `!exists` 時就已經把指標寫入 `r.sessions`。後面再次修改 `session.AgentID` 等欄位，是直接操作那個已存在於 map 中的指標。函式末尾的 `if exists { r.sessions[...] = session }` 對 `SubagentStart` 的新 session 完全是死程式碼，因為 `exists == false`。

但這不只是死程式碼的問題。**它暗示了一個錯誤的心智模型**：「只有 exists 時才需要回寫」。

真正發生的事情是：`SubagentStart` 的新 session 透過指標就地修改，`UpsertFromSessionEvent` 也是這樣（直接修改 `session.AgentID` 後，函式末尾的 `r.sessions[event.SessionID] = session` 也是冗餘的，因為 session 是 `*SessionInfo`，對指標的修改直接反映在 map 中）。

這整個「寫入 map」的邏輯分散在三個地方：

1. `SubagentStart` 分支內（`!exists` 時）
2. 函式末尾（`exists` 時）
3. `session_registry.go` 第 87 行（`UpsertFromSessionEvent` 末尾無條件寫入）

**根本問題是：這段程式碼混用了值語義（value semantics）和指標語義（pointer semantics）**。`SessionInfo` 放在 map 裡是指標，對指標的修改不需要回寫 map。但程式碼寫得好像是在用值語義一樣，在末尾多做了一次「確保一致」的冗餘寫入。

**正確的設計應該統一語義**：要嘛讓 map 存值（`map[string]SessionInfo`）、所有修改後都回寫，要嘛讓 map 存指標並接受「修改指標就是修改 map」的直觀——不要混著用。

## 問題二：`processSessionEvent` 和 `processHookEvent` 有 40+ 行的重複邏輯

```go
// 兩個函式都有完全相同的這個模式：

// 記錄舊狀態
oldSession, _ := d.registry.Get(event.SessionID)
oldStatus := ""
if oldSession != nil {
    oldStatus = string(oldSession.Status)
}

// [更新 registry]

// 取得新狀態
newSession, _ := d.registry.Get(event.SessionID)

// 決定 ChangeType
var changeType ChangeType
if oldStatus == "" {
    changeType = ChangeTypeNew
} else if string(newSession.Status) != oldStatus {
    changeType = ChangeTypeStatusChanged
} else {
    changeType = ChangeTypeUpdated
}

// 推送事件
d.sendToOutCh(...)
```

這段邏輯在兩個函式中各出現一次，共 30+ 行。唯一的差異是中間那行「更新 registry」呼叫的是 `UpsertFromSessionEvent` 還是 `UpsertFromHookEvent`。

可以提取為：

```go
func (d *EventDispatcher) dispatchAfterUpdate(sessionID string, update func()) {
    oldSession, _ := d.registry.Get(sessionID)
    oldStatus := ""
    if oldSession != nil {
        oldStatus = string(oldSession.Status)
    }

    update()

    newSession, _ := d.registry.Get(sessionID)
    if newSession == nil {
        return
    }

    changeType := d.determineChangeType(oldStatus, string(newSession.Status))
    d.sendToOutCh(DispatchedEvent{
        ChangeType: changeType,
        Session:    newSession,
        Timestamp:  d.now(),
    })
}
```

這樣每個 `processXxxEvent` 函式就只需要做自己獨特的部分：解析 timestamp、構建 dedup key、呼叫 `dispatchAfterUpdate`。

## 問題三：`processHookEvent` 的 timestamp 解析邏輯放錯地方

```go
func (d *EventDispatcher) processHookEvent(event HookEvent) {
    // 解析 Timestamp
    var timestamp time.Time
    if event.Timestamp != "" {
        if t, err := time.Parse(time.RFC3339, event.Timestamp); err == nil {
            timestamp = t
        } else {
            logger.Warn(...)
            timestamp = d.now()
        }
    } else {
        timestamp = d.now()
    }
    // ...
```

這段邏輯（8 行、兩層 if）可以用 guard clause 壓縮：

```go
timestamp := d.now()
if event.Timestamp != "" {
    if t, err := time.Parse(time.RFC3339, event.Timestamp); err == nil {
        timestamp = t
    } else {
        logger.Warn(LogTimestampParseFailed, ...)
    }
}
```

更進一步，可以提取為 `parseEventTimestamp(ts string) time.Time`。timestamp 解析是一個獨立的關注點，不應該污染 processHookEvent 的主要邏輯。

## 小型觀察（不影響 taste score，但值得記錄）

**`deduplicationKey` 的 `WindowKey` 欄位名稱**：`WindowKey time.Time` 這個命名有點奇怪——它是一個截斷後的時間點，叫 `Window` 不如叫 `Bucket` 或 `TruncatedAt`。這是 bucket-based dedup 的標準用語，`Bucket time.Time` 更能表達「時間分桶」的語義。

**`truncateString` 的雙重長度檢查**：

```go
func truncateString(s string, maxLen int) string {
    if len(s) <= maxLen {  // 第一次：byte 長度
        return s
    }
    runes := []rune(s)
    if len(runes) <= maxLen {  // 第二次：rune 長度
        return s
    }
    return string(runes[:maxLen])
}
```

第一個 `if len(s) <= maxLen` 是 byte 長度的快速路徑，可以。但注釋說「簡單截斷（不考慮 UTF-8 字符邊界）」然後立刻用 `[]rune` 做了 UTF-8 安全截斷，這個注釋是錯的——程式碼確實考慮了 UTF-8 邊界。要嘛修正注釋，要嘛真的決定不考慮 UTF-8（但那就不應該用 rune）。

## 結論

**唯一真正需要修正的問題是問題一**（混用值語義與指標語義導致的冗餘寫入與錯誤心智模型）。這是設計上的不一致，不只是效能問題。

**問題二和問題三**是重構機會，可以大幅降低兩個主要函式的認知負擔，建議在 Phase 4b 處理。

**不要忽視問題一**。一個 map 裡存的是指標，但程式碼的寫法暗示「修改後需要回寫才算數」——這種不一致會讓維護者在未來做出錯誤假設。
