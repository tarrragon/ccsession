## 1. 實作策略設計

### 1.1 實作順序（依賴關係分析）

實作分為三個層次，嚴格由底層向上：

```
Layer A: 純資料定義（無依賴）
  ├── 常數定義
```

## 2. 資料結構選擇

### 2.1 資料模型

| 元件 | 結構選擇 | 理由 |
|------|---------|------|
| SessionInfo, SessionEvent 等 | 不可變值物件（freezed） | 與 Go Backend JSON 結構一一對應，自動生成 fromJson/toJson/equality/copyWith |
| WsConnectionState | 列舉 | 四個固定狀態值，不需額外資料 |
| ServerMessage | 信封模式（type + raw data map） | data 欄位為 dynamic，由消費端依 type 選擇對應 payload 類別解析 |
| ClientMessage | 值物件（freezed） | toJson 直接送出 WebSocket |

### 2.2 服務內部狀態

| 欄位 | 結構選擇 | 理由 |
|------|---------|------|
| 連線狀態廣播 | 廣播型 stream controller | 多個 listener 可同時訂閱 |
| 訊息廣播 | 廣播型 stream controller | 多個下游 provider 消費 |
| 重連策略 | 獨立物件（組合，非繼承） | 可單獨測試、可替換 |
| 手動斷線旗標 | 布林值 | 阻止自動重連的最簡方式 |
| 已 dispose 旗標 | 布林值 | dispose 後靜默忽略操作 |

## 3. 資料流程圖

### 3.1 Server → Client 訊息流

```
WebSocket raw string
    |
    v
JSON 解碼 → Map
    |
    +-- 解碼失敗 → log ERROR, 丟棄, 繼續監聽
    |
    v
ServerMessage.fromJson(map)
    |
    v
廣播到 messageStream
    |
    v
（後續 Ticket）下游 provider 依 type 分流處理
```

### 3.2 Client → Server 訊息流

```
便捷方法呼叫（subscribeSession / requestSessionList / ...）
    |
    v
建構 ClientMessage 物件
    |
    v
clientMessage.toJson() → Map → JSON 編碼 → String
    |
    v
channel.sink.add(jsonString)
    |
    +-- channel 為 null 或已 dispose → 靜默忽略
```

### 3.3 連線生命週期

```
connect(uri)
    |
    v
設定 uri, 清除手動斷線旗標
    |
    v
狀態 → connecting
    |
    v
建立 WebSocket 通道
    |
    +-- 成功:
    |   狀態 → connected
    |   重連策略.reset()
    |   啟動 inactivity timer (35s)
    |   監聽 channel.stream
    |   自動 requestSessionList()
    |
    +-- 失敗:
        狀態 → reconnecting
        排程重連（delay = 重連策略.nextDelay()）
```

### 3.4 斷線與重連

```
channel.stream done/error 事件
    |
    v
手動斷線旗標為 true? ─是→ 不重連, return
    |
    v（否）
已 dispose? ─是→ 不重連, return
    |
    v（否）
狀態 → reconnecting
    |
    v
排程重連:
    delay = 重連策略.nextDelay()
    等待 delay 後 → connect(已儲存的 uri)
```

### 3.5 心跳（Inactivity Timer）

```
連線成功 → 啟動 timer (35s)
    |
收到任何訊息 → 取消舊 timer, 啟動新 timer (35s)
    |
timer 到期 → 關閉 channel → 觸發斷線流程（→ 重連）
    |
手動斷線 / dispose → 取消 timer
```

## 4. 控制流程圖

### 4.1 connect() 虛擬碼

```
FUNCTION connect(uri):
    IF _isDisposed THEN RETURN

    取消現有重連排程（如有）
    _currentUri = uri ?? 預設 URI
    _isManualDisconnect = false
    設定狀態 → connecting

    TRY:
        _channel = 建立 WebSocket 通道(_currentUri)
        設定狀態 → connected
        _reconnectStrategy.reset()
        啟動 inactivity timer
        開始監聽 _channel.stream:
            ON data(raw):
                重置 inactivity timer
                TRY:
                    map = JSON 解碼(raw)
                    message = ServerMessage.fromJson(map)
                    _messageController.add(message)
                CATCH:
                    log ERROR（解析失敗）
            ON done:
                _handleDisconnection()
            ON error:
                _handleDisconnection()
        自動 requestSessionList()
    CATCH:
        設定狀態 → reconnecting
        _scheduleReconnect()
```

### 4.2 disconnect() 虛擬碼

```
FUNCTION disconnect():
    _isManualDisconnect = true
    取消重連排程（如有）
    取消 inactivity timer
    關閉 _channel（如有）
    設定狀態 → disconnected
```

### 4.3 _scheduleReconnect() 虛擬碼

```
FUNCTION _scheduleReconnect():
    IF _isManualDisconnect OR _isDisposed THEN RETURN
    設定狀態 → reconnecting
    delay = _reconnectStrategy.nextDelay()
    _reconnectTimer = 排程延遲(delay):
        connect(_currentUri)
```

### 4.4 send() 虛擬碼

```
FUNCTION send(clientMessage):
    IF _isDisposed THEN RETURN
    IF _channel 為 null THEN RETURN
    jsonString = JSON 編碼(clientMessage.toJson())
    _channel.sink.add(jsonString)
```

### 4.5 dispose() 虛擬碼

```
FUNCTION dispose():
    _isDisposed = true
    _isManualDisconnect = true
    取消重連排程
    取消 inactivity timer
    關閉 _channel
    關閉 _connectionStateController
    關閉 _messageController
```

### 4.6 ReconnectStrategy 虛擬碼

```
CLASS ReconnectStrategy:
    _attempt = 0
    _initialDelay = 常數(1s)
    _maxDelay = 常數(30s)
    _multiplier = 常數(2)

    FUNCTION nextDelay():
        delay = _initialDelay * (_multiplier ^ _attempt)
        delay = min(delay, _maxDelay)
        _attempt = _attempt + 1
        RETURN delay

    PROPERTY currentDelay:
        RETURN min(_initialDelay * (_multiplier ^ _attempt), _maxDelay)

    FUNCTION reset():
        _attempt = 0
```

## 5. 關鍵實作指引

### 5.1 第一階段目標（Layer A + B — 資料定義 + 純邏輯）

**目標測試**: TG-01 ~ TG-06（24 個測試案例）

**優先順序**: 常數 → enum → freezed 模型 → code gen → ReconnectStrategy

**關鍵注意事項**:
- freezed 模型的 JSON key 必須與 Go Backend 的 json tag 完全一致（camelCase）
- Go 的 `omitempty` 表示該欄位在 JSON 中可能不存在，Dart 側用 `@Default` 處理
- `EventContent.toolInput` 在 Go 側為 `any`，Dart 側對應 `Object?`
- `SessionInfo.firstUserMessageAt` 在 Go 側為 `time.Time`（omitempty），零值時不輸出，Dart 側為 `DateTime?`
- Go 時間格式為 RFC 3339（`time.Time` 的 JSON 預設序列化），freezed/json_serializable 預設也支援 ISO 8601

### 5.2 第二階段目標（Layer C — WebSocketService）

**目標測試**: TG-07（29 個測試案例）

**整合策略**:
- WebSocketService 依賴 Layer A 的資料模型和 Layer B 的 ReconnectStrategy
- 測試使用 Mock WebSocketChannel + FakeAsync 控制時間
- connect() 的 WebSocket 通道建立需可注入（測試替換）

**實作切入點**:
1. 先實作 WebSocketService 介面（抽象定義）
2. 實作 WebSocketServiceImpl 的 connect/disconnect 基本流程
3. 加入訊息接收和解析
4. 加入重連排程
5. 加入 inactivity timer（心跳偵測）
6. 加入 send 和便捷方法
7. 加入 dispose 和安全防護
8. 最後加入 Riverpod provider

## 6. 權宜方案與技術債務

### 6.1 最小可行實作

- ServerMessage 採信封模式（type + raw data map），不做 sealed class / union type 分流。下游 provider 自行依 type 解析 data。這是刻意的簡化，避免過早抽象。
- Riverpod provider 只定義基礎三個（service、connectionState、serverMessage），不實作下游消費 provider。
- 心跳採方案 A（inactivity timer），不修改 Go Backend。

### 6.2 已知限制

| 限制 | 說明 | 影響 |
|------|------|------|
| ServerMessage.data 為 raw Map | 消費端需手動呼叫對應 payload 的 fromJson | 後續 Ticket 可能封裝為 helper |
| 無應用層 ping | 依賴 Go Backend protocol-level ping + inactivity timer | 如 Backend 停止 ping 則 35 秒後才偵測到斷線 |
| WebSocket URI 硬編碼預設值 | 後續需從設定檔或環境變數讀取 | 開發階段足夠 |

### 6.3 技術債務標記

| 項目 | Phase 4 建議 |
|------|-------------|
| WebSocketChannel 建立方式封裝 | 考慮提取 factory 方法，提升可測試性 |
| ServerMessage 分流邏輯 | 後續可評估 sealed class union type |
| 錯誤處理 log 機制 | 目前用 print/debugPrint，後續統一為 AppLogger |

## 7. 語言特定實作注意事項

### Dart/Flutter 考量

- **freezed code gen 順序**：所有 freezed 模型檔案寫完後統一執行 `build_runner build`，避免中間狀態的編譯錯誤
- **json_serializable 的 DateTime 處理**：預設支援 ISO 8601 字串，與 Go 的 `time.Time` JSON 輸出相容
- **StreamController broadcast**：connectionStateStream 和 messageStream 必須用 `StreamController.broadcast()` 建立，允許多個 listener
- **Timer 和 Future.delayed**：測試中需用 `fakeAsync` 控制，實作中不可使用全域 Timer，必須持有引用以便取消
- **web_socket_channel 套件**：跨平台（io + html），connect 方法為 `WebSocketChannel.connect(uri)`
- **pubspec.yaml 套件新增**：需新增 web_socket_channel, freezed, freezed_annotation, json_serializable, json_annotation, build_runner, mocktail, fake_async, stream_channel

## 8. Phase 3b 拆分評估

### 8.1 測試群組依賴分析

```
TG-01 SessionInfo         ─┐
TG-02 SessionEvent        ─┤
TG-03 ServerMessage       ─┼── Layer A（無交叉依賴）
TG-04 ClientMessage       ─┤
TG-05 WsConnectionState   ─┘
                             |
TG-06 ReconnectStrategy   ── Layer B（僅依賴常數）
                             |
TG-07 WebSocketService    ── Layer C（依賴 TG-01~06 所有產出）
```

### 8.2 並行可行性評估

| 群組 | 可獨立實作？ | 修改檔案 | 與其他群組檔案交集 |
|------|------------|---------|------------------|
| TG-01~05（合併為一組） | 是 | models/*.dart + constants/*.dart | 無（TG-07 只讀取不修改） |
| TG-06 | 是 | websocket/reconnect_strategy.dart | 無 |
| TG-07 | 否（依賴 TG-01~06 產出） | websocket/websocket_service.dart + websocket_provider.dart | 讀取 models/ 和 reconnect_strategy.dart |

### 8.3 Context 消耗預估

| 群組 | 設計文件讀取 | 實作量 | 測試量 | 緩衝(30%) | 總計 |
|------|-----------|-------|-------|----------|------|
| TG-01~05（資料模型） | ~3K | ~2K（freezed 模板化） | ~3K | ~2.5K | ~10.5K |
| TG-06（重連策略） | ~1K | ~0.5K | ~1K | ~0.8K | ~3.3K |
| TG-07（WebSocket Service） | ~4K | ~4K | ~6K | ~4K | ~18K |
| **合計** | | | | | **~31.8K** |

### 8.4 拆分建議

**建議拆分為 2 個子任務**：

| 子任務 | 測試群組 | 測試案例數 | 預估 context | 修改檔案 |
|--------|---------|-----------|-------------|---------|
| 3b-A: 資料模型 + 重連策略 | TG-01~06 | 29 | ~14K | constants/*.dart, models/*.dart, reconnect_strategy.dart, pubspec.yaml |
| 3b-B: WebSocketService + Provider | TG-07 | 29 | ~18K | websocket_service.dart, websocket_provider.dart |

**拆分理由**：
1. 總 context ~32K 超過 20K 閾值，必須拆分
2. TG-01~06 全部是無外部依賴的純資料/邏輯，可合併為一組（合計 ~14K，在閾值內）
3. TG-07 單獨一組（~18K，在閾值內但偏高，可接受）
4. 3b-A 和 3b-B 有嚴格順序依賴（B 依賴 A 的產出），**不可並行**

**執行順序**：3b-A（資料模型 + code gen + 重連策略）→ 3b-B（WebSocketService + Provider）

**注意**：3b-A 完成後必須執行 `build_runner build` 產生 freezed/json_serializable code gen 檔案，3b-B 才能正常編譯。
