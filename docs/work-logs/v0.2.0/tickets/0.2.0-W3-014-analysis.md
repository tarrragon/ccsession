# 0.2.0-W3-014 分析報告：多視角審查聯集 vs 交集決策機制缺失

## 問題摘要

多視角審查（三人組/parallel-evaluation）預設採聯集策略合併所有建議，缺乏交集處理機制，導致「減法」建議被「加法」建議系統性稀釋。

---

## 根因分析

### 直接原因：衝突處理策略制度化為聯集

`multi-perspective-analysis-methodology.md` 第 276-284 行明確定義：

| 衝突類型 | 現行策略 | 問題 |
|---------|---------|------|
| 根因不一致 | 列出所有可能根因，逐一排查 | 聯集（加法） |
| 建議衝突 | 選擇最穩健方案 | 模糊，實務上傾向保留 |
| 優先級分歧 | 採用最高優先級 | 加法（取 max） |
| **範圍分歧** | **取範圍聯集** | **明確的加法偏見制度化** |

第 283 行「範圍分歧 → 取範圍聯集，確保不遺漏修復點」是加法偏見的制度化根源。

### 結構性原因：三種發現的不對稱處理

彙整報告格式區分三類發現，但處理權重不對稱：

| 類別 | 處理方式 | 實際效果 |
|------|---------|---------|
| 共識發現（交集） | 自動採納 | 正確 |
| 視角特有發現 | 自動納入追蹤 | **加法**：每個視角的獨特發現都保留 |
| 衝突發現 | 列出供 PM 決策 | **模糊**：PM 傾向保留雙方（和稀泥） |

「視角特有發現」自動納入，意味著每增加一個審查視角，產出物只會膨脹不會收縮。

### 深層原因：缺乏「減法權威」角色

linux 被定義為「Good Taste 品味把關」常駐委員，但：
- linux 的意見和其他審查者的權重相同（1/3 投票權）
- 當 linux 說「刪除」而其他人說「保留」時，聯集策略讓「保留」自動勝出
- 品味審查的價值在於**否決權**（veto），不是投票權

### W3-003 實際案例

| linux 建議 | code-reviewer 回應 | 實際結果 |
|-----------|-------------------|---------|
| 刪除遞迴展開器抽象 | 同意 | 保留（後來 W3-011 才刪） |
| 維度 7→3 | 保留 4（並發） | 保留 7→3+4 提示（折衷） |
| 刪迭代機制 | 反對，保留上限 | 保留上限+停止條件+超限流程（大部分保留） |

每次「刪除 vs 保留」衝突，結果都是保留或折衷（部分刪除），從未完全採納刪除建議。

## 改善方案

### 方案：衝突分類處理 + 品味否決權

#### 1. 衝突處理策略改為分類處理（取代一律聯集）

| 衝突類型 | 新策略 | 理由 |
|---------|--------|------|
| 加法 vs 加法（都想加東西） | 聯集（現行） | 不遺漏 |
| **加法 vs 減法（一方想加、一方想刪）** | **預設減法，加法需舉證** | 加法偏見矯正 |
| 減法 vs 減法（都想刪東西） | 交集（刪最少的） | 保守刪除 |
| 範圍分歧 | **依衝突類型分類處理**，不再一律聯集 | 取代第 283 行 |

**核心規則**：「加法 vs 減法」衝突中，舉證責任在加法方（要保留的人需說明保留理由），不在減法方。

#### 2. linux 品味否決權（Taste Veto）

| 現行 | 改善 |
|------|------|
| linux 是 1/3 投票權 | linux 對「複雜度增加」有否決權 |
| linux 的「刪除」建議和其他人的「保留」平權 | linux 的「刪除」需要其他兩人**同時**反對才能被否決 |

**否決條件**：linux 標記為 Garbage/Acceptable 的項目，至少需要其他 2 位審查者**同時**提出保留理由才能保留。單一審查者的反對不足以推翻品味否決。

#### 3. 彙整報告新增「衝突決策記錄」

在彙整報告的「衝突發現」表格後，新增：

```markdown
### 衝突決策記錄

| 衝突 | 決策 | 決策依據 | 舉證方 |
|------|------|---------|--------|
| {衝突} | 保留/刪除 | {理由} | {誰舉證} |
```

PM 必須對每個衝突做出明確的二元決策（保留或刪除），禁止折衷合併。
