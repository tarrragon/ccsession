## Problem Analysis

### 問題根因（兩層）

**表層**：Phase 1 設計文件 14K+ tokens 過大，Phase 3b context 耗盡。

**深層**：所有初始需求假設都不完整。直覺性開發（「看起來簡單就直接做」「PM 寫什麼就做什麼」）導致需求邊界不清，後期大量來回審查消耗遠超初期投入。AI 擅長從龐大參考資料中推演和分析，應在需求初期就善用此能力做更完善的評估和補充——這不是 /tdd 的流程編排能解決的，需要獨立的「需求完善度品質閘門」。

### 影響範圍

- .claude/skills/spec/ — 新建獨立 Skill
- .claude/agents/lavender-interface-designer.md — 更新為使用 /spec 模板
- /tdd 與 /spec 的分工邊界定義
- 所有後續 Phase 1 產出的設計文件

### 相關 Error Pattern

待查詢（context 耗盡相關）

### 設計決策記錄

**多視角評估結果**（2026-03-25）：

| 審查者 | 結論 | 核心論點 |
|--------|------|---------|
| code-reviewer | 擴展 /tdd | 獨立 /spec 造成雙入口邏輯衝突 |
| linux | 最小化擴展 | 加約束不加工具 |
| code-explorer | 獨立 /spec | /tdd 已超載，Spec 是不同關注點 |

**用戶決策**：採用獨立 /spec 方案。理由：
1. Spec 的價值不是格式管理，而是「需求完善度閘門」——強制用 AI 做深度需求評估
2. /tdd 管「已確定需求的開發流程」，/spec 管「需求是否足夠完善可以進入開發」，是不同關注點
3. 以 AI 成長速度，1 個月內就需要更完整的 Spec 管理能力
4. code-explorer 擔心的 /tdd 超載和長期拆分債風險是正確的
5. code-reviewer 擔心的「雙入口」問題，透過明確分工消除：/spec 是產出工具，不是 Phase 1 入口

**第二輪多視角發想**（2026-03-25）：

| 角色 | 關鍵貢獻 |
|------|---------|
| 需求品質守護者 | 7 個需求完善度檢查維度；與 SA 分工定義（SA 問「該不該做」、/spec 問「描述得夠不夠清楚」）；具體 Lite/Full 模板範例 |
| 架構設計師 | 完整目錄結構和資料流；Spec 文件 = Phase 1 設計文件；4 個防雙入口技術手段；V1/V2 邊界精確定義 |
| 品味審查官 | 核心抽象「recursive requirement expander」；validate 應做語義驗證非格式檢查；必填只要 Purpose + Scenarios；最大風險是變成額外流程閘門 |

**三方綜合結論**：
- 核心抽象：遞迴需求展開器——把模糊需求展開成無歧義的行為契約
- validate 兩層：結構檢查（自動）+ AI 語義推演（沿 7 維度找未展開需求）
- /spec 是 lavender 在 Phase 1 內部使用的工具，不是流程入口
- /spec 和 /tdd 完全解耦，不互相呼叫
- Spec 文件即 Phase 1 設計文件（同一檔案）
- V1 取 GWT + Lite/Full + 區段獨立性；Delta/Archive/RFC 2119 歸 V2

### 外部參考：OpenSpec/Spectra SDD 方法論

研究來源：https://github.com/kaochenlong（高見龍），基於 https://github.com/Fission-AI/OpenSpec

**可參考的設計要點**：

1. **Spec = 行為契約**：用 Requirement + GWT Scenario 格式，描述「系統應做什麼」而非「怎麼做」。使用 RFC 2119 關鍵字（SHALL/MUST/SHOULD/MAY）
2. **每個 Requirement 獨立區段**：含 Purpose、Requirements、Scenarios，天然支援按區段提取（正是本 Ticket 要解決的問題）
3. **Delta Specs 差異化管理**：ADDED/MODIFIED/REMOVED 格式，不重寫整份 spec，適合增量開發
4. **Lite/Full 兩級嚴謹度**：簡單功能用 Lite spec（行為需求 + 驗收條件），跨團隊/API 變更用 Full spec
5. **四層 Artifact DAG**：proposal → specs/design → tasks，依賴是啟用器而非閘門

**融合建議**：
- Phase 1 模板可借鑑 Requirement + Scenario 的區段結構
- 每個函式/模組的規格應包含：Purpose、API 簽名、GWT Scenarios、錯誤處理、依賴
- 考慮引入 Lite/Full 模式對應簡單修改 vs 完整功能開發
