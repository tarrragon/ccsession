## Problem Analysis

### 問題根因

Phase 1 lavender-interface-designer 產出的設計文件缺乏標準化結構，導致：
- 文件整體 14K+ tokens，Phase 3b 代理人需全量讀取
- 無法按函式/模組獨立提取區段
- PM 派發 Phase 3b 時缺乏精確引用機制

### 影響範圍

- .claude/skills/tdd/ — 需新增 Phase 1 產出模板
- .claude/agents/lavender-interface-designer.md — 需更新產出格式要求
- 所有後續 Phase 1 產出的設計文件

### 相關 Error Pattern

待查詢（context 耗盡相關）

### 外部參考：OpenSpec/Spectra SDD 方法論

研究來源：https://github.com/kaochenlong（高見龍），基於 https://github.com/Fission-AI/OpenSpec

**可參考的設計要點**：

1. **Spec = 行為契約**：用 Requirement + GWT Scenario 格式，描述「系統應做什麼」而非「怎麼做」。使用 RFC 2119 關鍵字（SHALL/MUST/SHOULD/MAY）
2. **每個 Requirement 獨立區段**：含 Purpose、Requirements、Scenarios，天然支援按區段提取（正是本 Ticket 要解決的問題）
3. **Delta Specs 差異化管理**：ADDED/MODIFIED/REMOVED 格式，不重寫整份 spec，適合增量開發
4. **Lite/Full 兩級嚴謹度**：簡單功能用 Lite spec（行為需求 + 驗收條件），跨團隊/API 變更用 Full spec
5. **四層 Artifact DAG**：proposal → specs/design → tasks，依賴是啟用器而非閘門

**融合建議**：
- Phase 1 模板可借鑑 Requirement + Scenario 的區段結構
- 每個函式/模組的規格應包含：Purpose、API 簽名、GWT Scenarios、錯誤處理、依賴
- 考慮引入 Lite/Full 模式對應簡單修改 vs 完整功能開發
