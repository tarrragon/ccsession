## Problem Analysis

### 問題根因

PM 派發 Phase 4b 代理人（cinnamon-refactor-owl）時，透過 Agent tool 的 prompt 參數傳遞完整的 Phase 4a 分析報告和修復指令。當 4a 報告較大（多份分析、多個修復項目），prompt 本身就佔據大量 context，加上 rules/ 自動載入的 context（已由 W5-012 處理），代理人在「理解任務」階段就耗盡 context，無法完成任何修改。

**直接原因**：Phase 4b 的交接是「prompt-based」——所有資訊都塞在派發 prompt 裡。
**根本原因**：TDD 流程中缺乏「Ticket-based 交接」機制——Phase 4a 的產出物沒有標準化的落地位置，PM 只能透過 prompt 傳遞。

### 影響範圍

- .claude/agents/cinnamon-refactor-owl.md — Phase 4b 代理人定義
- .claude/pm-rules/tdd-flow.md — TDD 流程中 Phase 4a→4b 轉換規則
- .claude/skills/tdd/references/phase4-refactor.md — Phase 4 指引
- .claude/pm-rules/parallel-dispatch.md — 多視角分析派發

## 現況分析：各 Phase 交接方式對比

| Phase 轉換 | 交接方式 | 資訊載體 | 問題 |
|-----------|---------|---------|------|
| 1→2 (lavender→sage) | prompt-based | PM prompt 含功能規格摘要 | 規格小，通常無問題 |
| 2→3a (sage→pepper) | prompt-based | PM prompt 含測試案例摘要 | 測試案例小，通常無問題 |
| 3a→3b (pepper→parsley) | prompt-based + 檔案 | PM prompt 指向策略文件路徑 | 代理人自行 Read 檔案 |
| 4a→4b (parallel-eval→cinnamon) | prompt-based | PM 在 prompt 嵌入完整 4a 報告 | **context 爆炸** |

**關鍵差異**：Phase 4a→4b 的交接物（多視角分析報告）遠大於其他 Phase 的交接物。

## Ticket-based 交接方案設計

### 方案概述

將 Phase 4a 的產出物標準化寫入 Ticket 執行日誌，Phase 4b 代理人從 Ticket 檔案讀取，而非從 PM prompt 接收。

### 具體設計

**Step 1：Phase 4a 產出物落地**

Phase 4a（/parallel-evaluation B）完成後，PM 將分析結論寫入 Ticket：

```bash
ticket track append-log <ticket-id> --section "Solution" "Phase 4a 分析結論：..."
```

或建立獨立的 Phase 4a 分析報告檔案：

```
docs/work-logs/v{version}/tickets/{ticket-id}-phase4a-report.md
```

**Step 2：PM 整理精簡修復清單**

根據 IMP-039 教訓，PM 不只轉存報告，還需整理為「可執行」格式：

```markdown
## Phase 4b 修復清單

### P0（必修）
1. file.go:238-252 — 提取常數 STATUS_ACTIVE
   現狀：hardcoded "active"
   改為：使用 StatusActive 常數

### P1（建議）
2. file.go:300-310 — Guard Clause 簡化
   現狀：3 層巢狀 if
   改為：early return 模式
```

**Step 3：Phase 4b 派發 prompt 精簡化**

PM 派發 cinnamon 時，prompt 只需包含：

```
Ticket: {ticket-id}
Phase 4b 修復清單位置：docs/work-logs/v{version}/tickets/{ticket-id}-phase4b-fixlist.md
請 Read 修復清單後逐項執行，每項改完後跑測試驗證。
```

### 對其他 Phase 代理人的影響評估

| Phase | 現有交接 | 需要改為 Ticket-based？ | 理由 |
|-------|---------|----------------------|------|
| 1→2 | prompt | 否 | 交接物小（功能規格路徑） |
| 2→3a | prompt | 否 | 交接物小（測試案例路徑） |
| 3a→3b | prompt + 檔案路徑 | 已是（指向檔案） | 代理人自行 Read 策略文件 |
| **4a→4b** | **prompt 嵌入全文** | **是（本方案）** | 交接物大，需落地到檔案 |
| 4b→4c | prompt | 可選 | 4b 產出物如果大，也應落地 |

**結論**：只有 Phase 4a→4b 需要改為 Ticket-based，其他 Phase 的交接物足夠小，prompt-based 可行。4b→4c 可作為後續改善。

## 實作建議

需修改的檔案：

1. **cinnamon-refactor-owl.md** — 新增「從 Ticket 讀取修復清單」的工作流程
2. **tdd-flow.md** — Phase 4a→4b 轉換步驟加入「PM 整理修復清單並寫入檔案」
3. **phase4-refactor.md** — Phase 4b 章節加入修復清單標準格式和讀取指引

預期效果：Phase 4b 派發 prompt 從數 KB（含完整報告）降至 ~200 bytes（僅含 Ticket ID 和檔案路徑）。
